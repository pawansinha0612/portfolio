Locust getting started: load tests in plain Python

Your team's test code is all Python, and the load test needs the same signing helper, the same fixtures and the same data generator. With Locust, a load test is a Python file, so it can import any of it.

Install

python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install locust
locust --version

Use a virtual environment and pin the version in requirements.txt. Current releases need Python 3.11 or newer. This guide was checked against Locust 2.47.

The first locustfile

Save this as locustfile.py:

import random

from locust import HttpUser, task, between


class ShopUser(HttpUser):
    # Each simulated user waits 1-3 s between tasks (think time)
    wait_time = between(1, 3)

    @task(5)  # weight: browsing is 5x as common as viewing one item
    def browse(self):
        self.client.get("/products")

    @task(1)
    def view_item(self):
        item_id = random.randint(1, 10)
        # name= groups every /products/<id> under one row in the stats
        self.client.get(f"/products/{item_id}", name="/products/[id]")
  • HttpUser is one simulated user with its own HTTP session (self.client, a requests-style client that keeps cookies).
  • @task(5) sets a weight. Each time the user picks a task, browse is five times as likely as view_item.
  • name= groups dynamic URLs into one row of statistics. Without it, every id gets its own row and the report is unreadable.
  • Any status of 400 or above is a failure by default. A 200 with an error in the body is a success unless you check it with catch_response (see data and auth).

Web UI or headless

# Web UI on http://localhost:8089: set users and spawn rate, start, watch live charts
locust -f locustfile.py -H https://staging.example.com

# Headless: 100 users, starting 10 per second, for 15 minutes, summary at the end
locust -f locustfile.py -H https://staging.example.com \
  --headless -u 100 -r 10 -t 15m --only-summary

The web UI is the best way to develop a test: you can change the user count while it runs and watch the effect. Headless is for repeatable runs and CI. -u is the peak number of users, -r how many start per second, -t the run time. Without -t, a headless run goes until you stop it.

wait_time: the setting that decides your load

Locust users loop: pick a task, run it, wait, repeat. So Locust is a closed model, and the request rate depends on response times. wait_time is how you shape it:

wait_timeBehaviourUse for
between(1, 3)Random 1-3 s after each taskHuman think time
constant(2)Exactly 2 s after each taskSimple, predictable pauses
constant_pacing(5)Each task cycle takes at least 5 s, including the taskPacing: steady rate per user
constant_throughput(2)At most 2 task runs per second per userA target request rate: users × throughput

For a throughput target, constant_throughput or constant_pacing gets you close to an open model, as long as each task finishes inside its time slot.

from locust import FastHttpUser, task, constant_throughput


class ApiUser(FastHttpUser):
    # Each user aims for 2 task runs per second, whatever the response time
    # (as long as a task takes less than 0.5 s). 100 users = about 200 tasks/s.
    wait_time = constant_throughput(2)

    @task
    def products(self):
        with self.client.get("/products", catch_response=True) as res:
            if res.status_code != 200 or not res.json().get("items"):
                res.failure("empty or failed product list")

Here 100 users give about 200 tasks a second. But if the server slows down so a task takes longer than 0.5 s, the rate drops: users can only wait less, not run faster. Give yourself headroom with more users at a lower per-user rate, and compare the achieved RPS with the target after every run. See open vs closed workload model and coordinated omission.

FastHttpUser uses a faster HTTP client than HttpUser, so one process can generate several times more requests. Its API is close to HttpUser but not identical. Use it when the load generator's CPU is the limit.

A config file

Put settings in locust.conf (read automatically from the current folder) so runs are repeatable and reviewable:

# locust.conf: picked up automatically from the current directory
locustfile = locustfile.py
host = https://staging.example.com
headless = true
users = 50
spawn-rate = 5
run-time = 15m
csv = results/run
html = results/report.html

Command-line flags override the file. Environment variables work too: any option as LOCUST_ plus the name in capitals, for example LOCUST_HOST.

Know the limits

  • One Locust process uses one CPU core (Python's GIL). If it reaches 100% CPU, Locust warns you and the response times include its own delay. Use --processes or master and workers.
  • Percentiles in the console and the report are good enough to compare runs, but they're calculated from rounded buckets. For precise tail analysis, export the data or use an APM's numbers. See why averages lie.
