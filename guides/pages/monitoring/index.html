What to monitor during a load test

The test failed at 2:14 pm. The load tool shows exactly when. The infrastructure dashboard has 1-minute averages, the APM keeps traces for an hour, the database metrics live with another team, and nobody wrote down which pods were running. Monitoring for a load test has to be set up before the run, or the run tells you only that something broke.

The five layers to watch

LayerWatchWhy
Load generatorCPU, memory, network, VUs or threads, dropped iterationsA saturated generator produces fake latency. Check this first, every run.
Client view (the test results)Request rate, error rate, p50/p95/p99 per transaction, over timeThe user-facing truth, and the SLIs you report against
System under test: hosts and containersCPU per core, run queue, memory available, disk await, network, CPU throttling, pod restartsThe USE method per resource
Runtimes and middlewareGC pauses, heap after GC, thread pools, connection pools, queues, cache hit ratiosSoftware resources are where most bottlenecks live
Data stores and dependenciesQuery latency and top SQL, locks, replication lag, downstream latency and errors, rate limitsThe bottleneck is often one hop away from where it shows up

Add the platform's own events to the timeline: autoscaling, deployments, failovers, cron jobs and backups. A latency spike that lines up with a scale-out event is a very different problem from one that doesn't.

Resolution and retention

  • Scrape or push at 5 to 15 seconds during tests. Production defaults of 60 seconds hide anything shorter than a few minutes. 1-second tools like vmstat 1 are worth running on key hosts as well.
  • Keep raw data until the report is signed off. Many platforms downsample after a few days, and APM trace retention can be hours. Export or screenshot what you need while it is still detailed.
  • Percentiles need the right source. Averaging per-host p95s gives a number that means nothing. Use histograms that can be merged, or compute percentiles from the raw results. The percentiles explainer shows why.

Make every graph line up

  • One clock. Use NTP everywhere and show all dashboards in the same time zone. A 3-minute clock skew between the load generator and the servers makes correlation guesswork.
  • One test ID. Tag every metric from the load tool with a run ID (k6 --tag testid=..., a JMeter application or test title) and record the start and end time in the test log.
  • Annotations. Mark ramp stages, configuration changes and incidents on the dashboards. Grafana annotations or a simple shared log both work.
  • Same dashboard for every run. Comparable runs need comparable views. Save the dashboard as code alongside the test scripts.

Pre-test checklist

  1. The load generator's own CPU, memory and network are visible.
  2. Every host and container in the request path reports at 15 seconds or better, including the database and the load balancer.
  3. GC logging is on for JVM services. Pool and queue metrics are exposed.
  4. APM sampling is high enough to catch slow requests, and trace retention covers the report-writing window.
  5. Database statistics are reset or snapshotted at the start (for example pg_stat_statements_reset()).
  6. Clocks are in sync and everyone knows the test ID and time window.
  7. Someone owns each dashboard during the run and knows the abort criteria.
