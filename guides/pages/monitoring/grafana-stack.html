A Grafana stack for watching load tests

The k6 summary at the end of a run gives you one p95 for the whole test. The spike at minute 9, the slow climb in error rate and the moment the server's CPU hit 100% are all averaged away. This kit gives you live, per-interval graphs for k6 and JMeter next to the server metrics, in one docker compose up.

Start the stack

You need Docker with the Compose plugin (Docker Desktop on Mac and Windows includes it).

unzip kit.zip && cd loadtest-monitoring-kit
docker compose up -d
docker compose ps

Open http://localhost:3000, log in with admin / admin and set a new password. The "k6 load test + system under test" dashboard is the home page, and both dashboards are in the "Load testing" folder. Prometheus is on http://localhost:9090 if you want to try queries directly.

k6 to Prometheus

k6 ships a Prometheus remote write output. k6 pushes metrics to Prometheus every 5 seconds, so there is nothing for Prometheus to scrape and no port to open on the load generator. Prometheus only accepts pushes when started with --web.enable-remote-write-receiver, which the compose file does.

K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true \
k6 run -o experimental-prometheus-rw --tag testid=$(date +%Y%m%d-%H%M) k6/smoke.js

Or run the sample from inside the stack against your own target:

TARGET_URL=https://test-env.example.com docker compose --profile k6 run --rm k6

Why native histograms matter

By default, k6 converts each trend metric (like http_req_duration) into gauges such as k6_http_req_duration_p99. Those values are computed over everything since the test started, not over the last interval. At minute 25 of a 30-minute test, a 2-minute slowdown barely moves them. And because they are percentiles, you can't combine them across tags or load generators.

With native histograms switched on (K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM set to true), each trend becomes a Prometheus native histogram, k6_http_req_duration_seconds. Grafana can then compute real windowed percentiles that merge correctly across request names and generators:

histogram_quantile(0.95, sum by (name) (rate(k6_http_req_duration_seconds{testid=~"$testid"}[$__rate_interval])))

The pinned Prometheus (v3.15) ingests native histograms over remote write without extra flags. On Prometheus 2.x and early 3.x releases, also start it with --enable-feature=native-histograms. The dashboard in the kit expects native histograms. If you can't use them, set K6_PROMETHEUS_RW_TREND_STATS=p(95),p(99),max and query the gauges instead, knowing they are cumulative.

Tag every run

--tag testid=... adds a testid label to every series. The dashboard's Test ID dropdown filters on it, so you can look at one run or overlay two. Give requests a stable name tag (http.get(url, { tags: { name: 'product' } })) for URLs with IDs in them, or each unique URL becomes its own time series.

JMeter to InfluxDB

JMeter's built-in Backend Listener has an InfluxDB client that writes the InfluxDB 1.x line protocol every 5 seconds. That is why the kit uses InfluxDB 1.8: it accepts those writes with no tokens or extra setup. The sample plan is already configured:

jmeter -n -t jmeter/sample-test.jmx -q jmeter/user.properties -Jhost=test-env.example.com

To add it to your own plan: Add > Listener > Backend Listener, choose this implementation, and set the parameters below:

org.apache.jmeter.visualizers.backend.influxdb.InfluxdbBackendListenerClient
ParameterValue
influxdbUrlhttp://localhost:8086/write?db=jmeter
applicationA name for the system under test (a dashboard dropdown)
measurementjmeter
percentiles50;95;99 (stored as fields pct50.0, pct95.0, pct99.0)
summaryOnlyfalse, to get per-transaction series

The percentile window catch

By default, the percentiles the Backend Listener sends are computed over a sliding window of the last 100 samples (backend_metrics_window), not over the 5-second interval. At 500 requests per second, that window is a fifth of a second of data. The kit's user.properties sets backend_metrics_window_mode=timed, which makes the percentiles for successful and failed samples cover each send interval. The "all samples" percentiles stay on the 100-sample window even in timed mode, so the dashboard plots p95 from the successful (statut=ok) rows. The tag really is spelled statut (French for status).

Each point the listener writes holds the counts for one interval, so throughput is sum("count") / 5 grouped by 5 seconds. Active threads come from rows with transaction = 'internal'.

node-exporter on the system under test

Load test results without server metrics only tell you that something got slow. node-exporter exposes CPU, memory, disk, network and TCP statistics from a Linux host on port 9100. It belongs on the servers you are testing, not on your laptop.

  • On a Linux test server with Docker: copy the kit there and run docker compose --profile linux-host up -d node-exporter. It uses host networking and reads the host's /proc and /sys.
  • Without Docker: download the binary from the node_exporter releases and run it as a service.
  • Point Prometheus at it: edit the node job in prometheus/prometheus.yml with each server's address, then docker compose restart prometheus.
  - job_name: node
    static_configs:
      - targets: ["app-1.test.internal:9100", "app-2.test.internal:9100", "db-1.test.internal:9100"]
        labels:
          role: sut

On Docker Desktop for Mac or Windows, the linux-host profile shows Docker's own Linux VM. That is fine for checking the dashboard works and useless for real analysis. For Kubernetes, the kube-prometheus-stack Helm chart installs node-exporter as a DaemonSet along with cAdvisor-based container metrics (which you need for CPU throttling).

The Prometheus datasource is provisioned with a 5-second timeInterval, which keeps $__rate_interval short enough to show spikes but long enough to always contain two k6 pushes.

JMeter load test (InfluxDB)

Active threads, throughput, error rate and total requests at the top, then p95 and throughput per transaction, failures per transaction and errors by response code. Pick the application in the dropdown. Every panel is plain InfluxQL, so you can copy queries into your own dashboards.

The compose file

# Load test monitoring stack: k6 -> Prometheus, JMeter -> InfluxDB 1.8, node-exporter, Grafana.
# Guide: https://pawansinha.com.au/guides/monitoring/grafana-stack/
#
#   docker compose up -d                        # Prometheus, InfluxDB, Grafana
#   docker compose --profile linux-host up -d   # also node-exporter (Linux hosts only, see README)
#   docker compose --profile k6 run --rm k6     # run the sample k6 test inside the stack
#   docker compose down -v                      # stop and delete the data
#
# Grafana: http://localhost:3000 (admin / admin, change it on first login)

name: loadtest-monitoring

services:
  prometheus:
    image: prom/prometheus:v3.15.1
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.path=/prometheus
      - --storage.tsdb.retention.time=15d
      # Accept k6's remote write pushes on /api/v1/write
      - --web.enable-remote-write-receiver
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prometheus-data:/prometheus
    ports:
      - "9090:9090"
    extra_hosts:
      # lets Prometheus reach node-exporter on the Docker host (needed on Linux)
      - "host.docker.internal:host-gateway"
    restart: unless-stopped

  influxdb:
    # InfluxDB 1.x: JMeter's built-in Backend Listener writes the 1.x line protocol to /write?db=jmeter
    image: influxdb:1.8
    environment:
      - INFLUXDB_DB=jmeter
      - INFLUXDB_HTTP_AUTH_ENABLED=false
    volumes:
      - influxdb-data:/var/lib/influxdb
    ports:
      - "8086:8086"
    restart: unless-stopped

  grafana:
    image: grafana/grafana:13.2.5
    environment:
      - GF_SECURITY_ADMIN_USER=admin
      - GF_SECURITY_ADMIN_PASSWORD=admin
      - GF_USERS_ALLOW_SIGN_UP=false
      - GF_DASHBOARDS_DEFAULT_HOME_DASHBOARD_PATH=/var/lib/grafana/dashboards/k6-prometheus.json
    volumes:
      - ./grafana/provisioning:/etc/grafana/provisioning:ro
      - ./grafana/dashboards:/var/lib/grafana/dashboards:ro
      - grafana-data:/var/lib/grafana
    ports:
      - "3000:3000"
    depends_on:
      - prometheus
      - influxdb
    restart: unless-stopped

  node-exporter:
    # Host metrics (CPU, memory, disk, network). Run it on the machine you are testing.
    # On Docker Desktop (Mac/Windows) it only sees Docker's Linux VM, so it sits behind a profile.
    image: prom/node-exporter:v1.12.1
    profiles: ["linux-host"]
    command:
      - --path.rootfs=/host
    pid: host
    network_mode: host
    volumes:
      - /:/host:ro,rslave
    restart: unless-stopped

  k6:
    # Optional: run the sample test from inside the stack.
    image: grafana/k6:1.8.2
    profiles: ["k6"]
    environment:
      - K6_PROMETHEUS_RW_SERVER_URL=http://prometheus:9090/api/v1/write
      - K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true
      - TARGET_URL=${TARGET_URL:-https://quickpizza.grafana.com}
    volumes:
      - ./k6:/scripts:ro
    command: run -o experimental-prometheus-rw --tag testid=compose-run /scripts/smoke.js
    depends_on:
      - prometheus

volumes:
  prometheus-data:
  influxdb-data:
  grafana-data:

Grafana is provisioned from files: the datasources get fixed uids (prometheus and influxdb-jmeter), which the dashboard JSON refers to, so the dashboards work on first start without any clicking.

apiVersion: 1

datasources:
  - name: Prometheus
    uid: prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      # Matches the scrape interval and k6's 5 s push interval, so $__rate_interval stays sensible.
      timeInterval: 5s

  - name: InfluxDB-JMeter
    uid: influxdb-jmeter
    type: influxdb
    access: proxy
    url: http://influxdb:8086
    jsonData:
      dbName: jmeter
      httpMode: GET
      timeInterval: 5s

Troubleshooting

  • k6 logs "remote write endpoint ... 404" or "connection refused": check the URL ends with /api/v1/write, Prometheus is up (docker compose ps), and from inside the compose network the host is prometheus, not localhost.
  • Panels say "No data" for k6: the time picker may not cover the run, or the Test ID dropdown needs a refresh after the first run. In Prometheus, run {__name__=~"k6_.*"} to confirm data arrived. If you see k6_http_req_duration_p99 but no k6_http_req_duration_seconds, native histograms were not enabled for that run.
  • JMeter panels empty: check jmeter.log for Backend Listener errors, and query InfluxDB directly: curl -G 'http://localhost:8086/query?db=jmeter' --data-urlencode 'q=SHOW TAG VALUES FROM "jmeter" WITH KEY = "application"'.
  • node-exporter target is down: open http://localhost:9090/targets. On Linux, the compose file maps host.docker.internal to the host gateway. Firewalls on the test servers must allow port 9100 from the Prometheus host.
  • Grafana says the dashboard was changed: provisioned dashboards can be edited (allowUiUpdates: true), but changes are overwritten from the JSON files on restart. Export your changes back into grafana/dashboards/ to keep them.

Beyond a laptop

  • Run the stack and the load generator on separate machines from the system under test. They compete for CPU and memory, and that shows up in your results.
  • Several k6 instances can push to the same Prometheus. Add K6_PROMETHEUS_RW_LABELS=generator=gen-1 so their series don't collide, and let sum() combine them. Native histograms make the combined percentiles correct.
  • Already have Prometheus or Grafana Cloud? Point K6_PROMETHEUS_RW_SERVER_URL at its remote write endpoint (with K6_PROMETHEUS_RW_USERNAME and K6_PROMETHEUS_RW_PASSWORD or a bearer token) and import the dashboard JSON.
  • Prefer InfluxDB for k6 too? k6 can write to InfluxDB 1.x with -o influxdb=http://localhost:8086/k6. InfluxDB 2.x needs the xk6-output-influxdb extension. The kit's dashboards are built for the Prometheus path.
  • Change the default password and don't expose port 3000 to the internet.
