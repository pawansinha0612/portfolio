Exercise 9: compare two runs

The release candidate's p95 is 8% worse than last week's. Is that a regression, or just the difference between two runs of the same code? If you don't know how much your results wobble on their own, you can't answer, and you will either block a good release or wave through a bad one.

  • 25 minutes
  • 3 runs of 1 minute at 10 iterations/s
  • Run locally only

Goal

Run the same test twice on the same build to measure noise (an A/A comparison), then change the build and run it again (A/B). Use k6's --summary-export files and the compare runs tool to decide whether the difference is real.

Setup

docker run --rm --name quickpizza -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

The script

Save as 09-compare.js. It uses a fixed arrival rate, so both runs get exactly the same load whatever the latency does:

// Exercise 9: a steady, repeatable run to compare before and after a change. Run locally only.
//   k6 run --summary-export=baseline.json 09-compare.js
import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';
const AUTH = { 'Content-Type': 'application/json', Authorization: 'token abcdef0123456789' };

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: 10,
      timeUnit: '1s',
      duration: '1m',
      preAllocatedVUs: 10,
      maxVUs: 50,
    },
  },
  summaryTrendStats: ['avg', 'min', 'med', 'max', 'p(90)', 'p(95)', 'p(99)'],
  // One threshold per name, so the summary (and the compare tool) gets one row per request
  thresholds: {
    'http_req_duration{name:pizza}': ['p(95)<2000'],
    'http_req_duration{name:doughs}': ['p(95)<2000'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const pizza = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), {
    headers: AUTH,
    tags: { name: 'pizza' },
  });
  check(pizza, { 'pizza status is 200': (r) => r.status === 200 });

  const doughs = http.get(`${BASE_URL}/api/doughs`, { headers: AUTH, tags: { name: 'doughs' } });
  check(doughs, { 'doughs status is 200': (r) => r.status === 200 });
}

Run it

# Run A and run A again: same build, nothing changed
k6 run --summary-export=baseline.json 09-compare.js
k6 run --summary-export=rerun.json 09-compare.js

Now "ship a release" that adds 50 ms to one internal call. Stop the container and start it with:

docker run --rm --name quickpizza -p 3333:3333 \
  -e QUICKPIZZA_DELAY_COPY_API_NAMES=50ms \
  ghcr.io/grafana/quickpizza-local:latest
# Run B: the candidate
k6 run --summary-export=candidate.json 09-compare.js

Open the compare runs tool. Load baseline.json as the baseline and rerun.json as the candidate, and read the verdict. Then do it again with candidate.json. The files stay in your browser.

Prefer the terminal? This prints the p95 of each request name from all three files:

for f in baseline rerun candidate; do
  jq -r --arg f "$f" '[$f,
    (.metrics["http_req_duration{name:pizza}"]["p(95)"] | floor),
    (.metrics["http_req_duration{name:doughs}"]["p(95)"] | floor)] | @tsv' "$f.json"
done

What you should see

Illustrative numbers, p95 in milliseconds:

Runpizza p95doughs p95
baseline1124
rerun (A/A)1184
candidate1654

The A/A pair differs a little even though nothing changed. The candidate moves pizza by about 50 ms and leaves doughs alone.

Questions

  1. How big was the difference between your two A runs, in percent? What does that mean for the smallest regression you can detect with this test?
  2. Why did doughs not change? Why is it useful to have a request that shouldn't change in the comparison?
  3. The regression added 50 ms to one internal call. How much did pizza's p95 move? Is it exactly 50 ms, and why might it not be?
  4. How would you make the comparison more trustworthy before using it as a release gate in CI?
Answer / what to look for
  1. Typically a few percent on a quiet laptop, sometimes more. That spread is your noise floor. If two runs of the same build differ by 6%, a 5% "regression" is not evidence of anything. Either the change has to be clearly bigger than the noise, or you need more runs (or longer ones) so the noise shrinks.
  2. Its path doesn't touch the copy service, so the change can't affect it. A control like that separates "the change made X slower" from "the machine was busier during run B". If the control moves as much as the target, suspect the environment, not the code.
  3. Close to 50 ms, because each pizza calls the names endpoint once, in sequence, on the critical path. It won't be exact: QuickPizza adds its own random pause to every pizza, and p95 of a sum isn't the sum of the p95s. Had the delay been on a call made several times per request, or made in parallel, the effect would be bigger or smaller.
  4. Run each side more than once and compare distributions, not single numbers. Use the same environment, data and warm-up for both. Pin the load with an arrival-rate executor (as here). Keep tags stable so transactions match by name. Set the regression rule from your measured noise, for example "p95 worse by more than 10% and more than 20 ms".
