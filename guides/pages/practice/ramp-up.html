Exercise 3: ramp up and read the summary

The report says "average response time 95 ms". The product owner hears "fast". One request in twenty took nearly twice that, and the slowest waited over three times as long. The summary k6 prints has everything you need to tell the real story, if you know which lines to read and how to check they add up.

  • 20 minutes
  • Up to 10 virtual users, about 2 minutes
  • Run locally only

Goal

Shape load over time with stages, read percentiles instead of the average, and sanity-check the throughput k6 reports with Little's Law. If your numbers don't agree with Little's Law, either the test or your reading of it is wrong.

Setup

docker run --rm --name quickpizza -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

The script

Save as 03-ramp.js:

// Exercise 3: ramp up, hold, ramp down, then read the summary. Run locally only.
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';

export const options = {
  stages: [
    { duration: '30s', target: 10 }, // ramp up to 10 VUs
    { duration: '1m', target: 10 },  // hold
    { duration: '15s', target: 0 },  // ramp down
  ],
  summaryTrendStats: ['avg', 'min', 'med', 'p(90)', 'p(95)', 'p(99)', 'max'],
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<1000'],
  },
};

const params = {
  headers: { 'Content-Type': 'application/json', Authorization: 'token abcdef0123456789' },
  tags: { name: 'pizza' },
};

export default function () {
  const res = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), params);
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1); // think time
}

summaryTrendStats adds p99 to the summary. k6 shows avg, min, med, max, p(90) and p(95) by default.

Run it

k6 run 03-ramp.js

Watch the progress line while it runs. The VU count climbs to 10 over 30 seconds, holds for a minute, then drains.

A summary shaped like this. These numbers are illustrative, yours will differ:

Questions

  1. Little's Law says concurrency = throughput × time in the system. During the one-minute hold you have 10 VUs, and each iteration takes about iteration_duration. What request rate should you see during the hold? Why is the overall http_reqs rate in the summary lower than that?
  2. Roughly how many requests should the whole run make? Work it out from the stages before you look, then compare with http_reqs.
  3. Compare avg, med, p95 and max. Which one would you put in a report as "the response time", and what does the gap between p95 and max tell you?
  4. Double the VUs (change both targets of 10 to 20) and run again. Did p95 change much? What does that say about where QuickPizza is on its queueing curve?
Answer / what to look for
  1. Throughput = concurrency ÷ time per iteration. With 10 VUs and about 1.1 s per iteration (1 s think time plus the request), that is about 10 ÷ 1.1 ≈ 9 iterations per second during the hold. The summary rate is lower because it averages over the whole run, including the ramps where fewer VUs were active.
  2. Ramp up: 30 s at an average of 5 VUs ≈ 5 × 30 ÷ 1.1 ≈ 136. Hold: 60 s at 10 VUs ≈ 545. Ramp down: 15 s at an average of 5 VUs ≈ 68. Total ≈ 750. If you are within a few percent, the test did what you designed. If you are far off, something is wrong (errors that end iterations early, VUs stuck on long timeouts, a mistaken stage) and the latency numbers can't be trusted yet.
  3. Report percentiles: p95 (and p99 for anything user-facing), with the median for context. The average mixes fast and slow requests into a number no user experienced. A big gap between p95 and max means a long tail: a few requests are much slower than the rest. With only a few hundred samples, max is a single request, so treat it as a clue, not a result. See why averages lie.
  4. Probably not much. At 20 VUs with 1 s of think time the server receives fewer than 20 requests per second, which is far below what it can handle, so there is almost no queueing. Latency only climbs once utilisation gets high. Finding that point is Exercise 6.
