Exercise 8: watch it live in Grafana

The end-of-test summary says p95 was 400 ms. It doesn't say whether that was 400 ms all along, or 100 ms for 25 minutes and two seconds for the last five. Averages over a whole run hide when things went wrong, and the client's view alone can't tell you why. A dashboard with the load generator and the server on the same time axis can.

  • 40 minutes
  • 3 virtual users, 3 minutes
  • Run locally only, needs Docker Compose

Goal

Run Prometheus and Grafana locally with the free monitoring kit, stream k6 results into it while a test runs, add QuickPizza's own metrics as a scrape target, and read client-side and server-side latency side by side.

Setup

1. Download and start the kit (Prometheus on port 9090, Grafana on port 3000):

curl -sSfLO https://pawansinha.com.au/guides/monitoring/kit.zip
unzip kit.zip && cd loadtest-monitoring-kit
docker compose up -d

2. Tell Prometheus to scrape QuickPizza too. Add this job at the end of prometheus/prometheus.yml in the kit, keeping the indentation of the other jobs:

  - job_name: quickpizza
    static_configs:
      - targets: ["host.docker.internal:3333"]
docker compose restart prometheus

The kit already maps host.docker.internal to your machine, on Linux as well as Docker Desktop.

3. Start QuickPizza with the hidden fault from Exercise 7 (or a known one, such as -e QUICKPIZZA_DELAY_COPY_API_NAMES=300ms).

4. Open localhost:9090/targets and check the quickpizza target is up. Then log in to Grafana at localhost:3000 (admin / admin, then change the password).

The script

No new script. Reuse 07-slow-dependency.js from Exercise 7, run for three minutes so there is something to watch.

Run it

K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true \
k6 run -o experimental-prometheus-rw --tag testid=practice-08 \
  -e DURATION=3m 07-slow-dependency.js

Open the k6 load test + system under test dashboard and pick practice-08 in the Test ID dropdown. Then go to Explore, choose the Prometheus data source and run this query for QuickPizza's own view:

histogram_quantile(0.95,
  sum by (le, path) (rate(quickpizza_server_http_request_duration_seconds_bucket[1m])))

What you should see

  • Load: VUs and request rate flat at 3 VUs and a steady request rate.
  • p95 by request name: one line per k6 name tag. pizza and the slow dependency sit well above the rest, flat for the whole run.
  • The Explore query: one line per server route, with the same route standing out.
  • The System under test row is empty unless you run node-exporter. On a Mac or Windows it would only show Docker's Linux VM anyway, so skip it here.

Questions

  1. Halfway through a run, stop the container and start it again without the delay (it takes a few seconds). What does the dashboard show that the end-of-test summary can't?
  2. Client-side p95 for names (from k6) and server-side p95 for /api/names (from QuickPizza) are close but not equal. Which is bigger, and what is in the difference?
  3. Why does the kit send k6 trends as native histograms instead of k6's default p95/p99 gauges?
  4. On a real project, what would you add to this dashboard before trusting it during a go-live test?
Answer / what to look for
  1. A step: p95 for the slow names drops to the baseline at the moment of the restart, with a short burst of errors while the container was down. The summary would only show one blended p95 and an error count, with no hint that there were two different systems in one run. Time series are how you see warm-up, degradation over time, a deploy in the middle of a test, or the minute a cache filled up.
  2. Client-side is bigger. It includes everything outside the server's timer: the network, Docker's port forwarding, reading and parsing the request before the metrics middleware starts its clock, and writing the response. On a real network, the gap is where you find load balancers, TLS termination, proxies and queueing in front of the app. A big gap means "look between the client and the code", not in the code.
  3. k6's default Prometheus output sends percentiles as gauges computed over the whole test so far, so a spike late in a long test barely moves them. Native histograms let Prometheus compute a real percentile over any window with histogram_quantile(). Read the monitoring kit guide for the details.
  4. Server metrics from every tier (CPU, memory, GC, connection pools, database), the load generator's own CPU, annotations for deploys and test start, and the business transactions your targets are written in. Then check the dashboard against the summary of one known run before anyone makes a decision from it.

When you are done: docker compose down -v in the kit folder stops the stack and deletes its data.
