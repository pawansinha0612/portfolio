Exercise 2: thresholds that fail the run

Your nightly load test has been green for three months. Someone finally opens the report and finds p95 went from 200 ms to 1.4 seconds in week six. Nothing failed because nothing was allowed to. A test without thresholds is a measurement. A test with thresholds is a decision.

  • 20 minutes
  • 2 virtual users, 30 seconds per run
  • Run locally only

Goal

Write pass/fail criteria as k6 thresholds, see the exit code change when one is crossed, stop a broken run early with abortOnFail, and use QuickPizza's fault injection to fail the error-rate threshold for real.

Setup

Start QuickPizza locally (setup). The error injection in step 3 sends special headers to the server, which is one more reason this belongs on your own machine.

docker run --rm --name quickpizza -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

The script

Save as 02-thresholds.js:

// Exercise 2: thresholds that pass or fail the run (exit code 99 on failure).
// Run locally only. Try: -e P95_MS=50   or   -e FAIL_PCT=10
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';
const P95_MS = __ENV.P95_MS || 800;
const FAIL_PCT = __ENV.FAIL_PCT || '';

export const options = {
  vus: 2,
  duration: '30s',
  thresholds: {
    // Fewer than 1% of requests may fail
    http_req_failed: ['rate<0.01'],
    // 95% of pizza requests must finish within P95_MS milliseconds
    'http_req_duration{name:pizza}': [`p(95)<${P95_MS}`],
    // Stop early if checks are clearly broken (evaluated after the first 10s)
    checks: [{ threshold: 'rate>0.95', abortOnFail: true, delayAbortEval: '10s' }],
  },
};

const headers = {
  'Content-Type': 'application/json',
  Authorization: 'token abcdef0123456789',
};
if (FAIL_PCT) {
  // QuickPizza fault injection: make the ingredients lookup fail FAIL_PCT% of the time
  headers['x-error-get-ingredients'] = 'practice-fault';
  headers['x-error-get-ingredients-percentage'] = String(FAIL_PCT);
}

export default function () {
  const res = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), {
    headers,
    tags: { name: 'pizza' },
  });
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}

The name tag matters. http_req_duration{name:pizza} is a sub-metric: the threshold applies only to requests tagged name: pizza. In a real script, each request gets its own threshold, because a fast health check averaged in with a slow checkout hides the checkout.

Run it three ways

# 1. Healthy: should pass
k6 run 02-thresholds.js; echo "exit code: $?"

# 2. An impossible latency target: should fail
k6 run -e P95_MS=50 02-thresholds.js; echo "exit code: $?"

# 3. Inject errors into 10% of ingredient lookups: should fail and stop early
k6 run -e FAIL_PCT=10 02-thresholds.js; echo "exit code: $?"

What you should see

Run 1 ends with a green THRESHOLDS block and exit code: 0. Run 2 marks the p95 threshold with a cross, prints thresholds on metrics 'http_req_duration{name:pizza}' have been crossed and exits with 99. Run 3 looks something like this (illustrative):

  █ THRESHOLDS

    checks
    ✗ 'rate>0.95' rate=70.00%

    http_req_duration{name:pizza}
    ✓ 'p(95)<800' p(95)=50.74ms

    http_req_failed
    ✗ 'rate<0.01' rate=30.00%

ERRO[0010] thresholds on metrics 'checks, http_req_failed' were crossed; at least one has
           abortOnFail enabled, stopping test prematurely
exit code: 99

Run 3 stops after about 10 seconds instead of 30. That is delayAbortEval: '10s' at work.

Questions

  1. In run 3 you asked for 10% of ingredient lookups to fail. Why did roughly a third of pizza requests fail instead of 10%?
  2. Why does the abort wait 10 seconds (delayAbortEval) instead of stopping on the first failed check?
  3. Run 2 failed on latency. Should a latency threshold use abortOnFail? When would you use it and when not?
  4. In run 3, p95 still passed. Is that good news?
Answer / what to look for
  1. Fan-out. To build one pizza, QuickPizza's recommendations service looks up four kinds of ingredient (olive oil, tomato, mozzarella, toppings), and the fault applies to each lookup. A pizza succeeds only if all four succeed: 0.94 ≈ 0.66, so about 34% of pizzas fail. One flaky dependency called several times per request multiplies its failure rate. The same maths applies to latency, which is why tail latency gets worse as fan-out grows.
  2. A rate needs enough samples to mean anything. One failure in the first two requests is a 50% failure rate. The delay stops a single unlucky request from killing a two-hour soak test.
  3. Usually not. A latency breach still produces useful data about how the system behaves when slow. Abort when carrying on is pointless or harmful: errors that show the script or environment is broken, or a test against a shared environment that is hurting other people.
  4. No. Failed requests are often fast (an error is cheap to return), so they can pull percentiles down. Always read latency together with the error rate. Thresholds on http_req_duration{expected_response:true} measure successful requests only, if that is what your target means.
