Load testing database-heavy systems

The search page held 300 ms at 1,000 users in the test environment. In production it took 7 seconds on day one. The test database had 40,000 orders. Production had 90 million, and the biggest customer alone had 2 million. Same code, same queries, different plans, different cache behaviour. For database-heavy systems, the data is part of the test.

Data volume changes everything

A query plan is chosen from table statistics. On a small table, a sequential scan is the right plan and nobody notices a missing index. At production size, the same query reads gigabytes. Volume also decides whether the working set fits in memory, how long index maintenance takes on writes, and how big sorts and hash joins get.

  • Test at production volume, or at the volume you expect after the growth period you care about (for example 18 months from now). Size data from the business forecast, not from what was convenient to load.
  • Grow the volume in the test. Write-heavy soak tests add rows as they run. A table that grows by 5 million rows over a 12-hour soak test can change plans mid-test. That is a finding, not noise.
  • Match the infrastructure too: instance class, storage type and provisioned IOPS, and database parameters such as memory settings. A test database on a different storage tier tells you about that storage tier. See volume testing.

Realistic data: distribution and skew

Row counts are not enough. Real data is skewed: a few customers have most of the orders, a few products get most of the views, recent rows are read far more than old ones. Uniform random test data hides the hot rows (lock contention) and the heavy parameters (bad plans).

  • Masked production copies keep real distributions. Mask or tokenise personal data properly before it leaves production, consistently across tables so joins still work, and agree it with whoever owns privacy.
  • Synthetic data is safer and needs more care. Generate it with realistic distributions (Zipf-like for popularity, time-weighted for recency) rather than uniform. In PostgreSQL, generate_series with skewed random values goes a long way:
-- 50 million orders across 1 million customers, heavily skewed towards low customer IDs
INSERT INTO orders (customer_id, created_at, total_cents)
SELECT 1 + floor(1000000 * power(random(), 3))::int,       -- power() skews towards small IDs
       now() - (random() * interval '730 days'),
       (500 + random() * 50000)::int
FROM generate_series(1, 50000000);
ANALYZE orders;
  • Test parameters must follow the same skew. If the load script picks customer IDs uniformly, it will almost never ask for the heavy customer. Feed it a parameter file sampled from real access patterns, including the known heavy cases. See parameterisation.
  • Reset between runs. Tests that write data change the next run's starting point. Restore from a snapshot, or at least run ANALYZE and record row counts before each run.

Cache state: cold, warm and too warm

The database buffer pool, the OS page cache and storage caches all make repeated reads cheap. A test that hits the same 1,000 rows for an hour measures memory, not your database. A test that starts right after a restart measures disk.

  • Decide which state matches the risk: steady-state peak (warm) or the morning after a failover (cold). Test both if failover is a real event for you.
  • Use a warm-up period and leave it out of the results.
  • Check the buffer cache hit ratio during the test. In PostgreSQL, blks_hit / (blks_hit + blks_read) from pg_stat_database. A test at 99.9% when production runs at 95% is too warm.

App-level test or database benchmark?

QuestionUse
Will our system handle peak with our queries and our data?Application-level load test (k6, JMeter, Gatling) against the real stack
Is the new instance class or storage faster than the old one?Standard benchmark (pgbench, sysbench, HammerDB) on both, same settings
Did the database version upgrade or parameter change regress?Benchmark with a custom script of your top queries, before and after
How does one specific query behave under concurrency?pgbench custom script, or sysbench with a Lua script

Standard benchmark workloads are synthetic. They are excellent for comparing infrastructure and configuration, and say little about your application. Don't quote a TPC-C-like number as your system's capacity.

pgbench (PostgreSQL)

pgbench ships with PostgreSQL. It has a built-in TPC-B-like workload and, more usefully, runs your own SQL scripts with random parameters.

# create test tables at scale factor 100 (10 million rows in pgbench_accounts)
pgbench -i -s 100 benchdb

# 50 clients, 8 worker threads, 10 minutes, progress every 10 s, per-statement latencies
pgbench -c 50 -j 8 -T 600 -P 10 -r benchdb

# open model: target 2,000 transactions/s, count transactions slower than 50 ms as late
pgbench -c 50 -j 8 -T 600 -R 2000 -L 50 -P 10 benchdb

A custom script with your own query and skewed parameters (random_zipfian needs PostgreSQL 11 or later):

-- top_orders.sql
\set cid random_zipfian(1, 1000000, 1.1)
SELECT id, total_cents FROM orders WHERE customer_id = :cid ORDER BY created_at DESC LIMIT 20;
pgbench -n -f top_orders.sql -c 32 -j 8 -T 300 -P 10 benchdb

-n skips vacuuming the built-in tables, which don't exist for a custom-only run. Without -R, pgbench is a closed model: each client waits for its transaction before sending the next, so it reports how fast the database can go, not how it behaves at your arrival rate. With -R, the latency it reports includes schedule lag, the open-model view (see open vs closed models).

sysbench (MySQL and PostgreSQL)

sysbench is the common choice for MySQL and MariaDB, and also has a PostgreSQL driver. Its OLTP workloads are Lua scripts you can copy and adapt.

COMMON="--db-driver=mysql --mysql-host=db.test.internal --mysql-user=sbtest \
  --mysql-password=$SBPASS --mysql-db=sbtest --tables=16 --table-size=5000000"

sysbench oltp_read_write $COMMON --threads=16 prepare
sysbench oltp_read_write $COMMON --threads=64 --time=600 --report-interval=10 --percentile=99 run
sysbench oltp_read_write $COMMON cleanup

Other built-in workloads include oltp_read_only, oltp_write_only, oltp_point_select and oltp_update_index. --rate switches to a fixed arrival rate. Run a series at increasing --threads values (8, 16, 32, 64, 128) and plot throughput and p99: the knee is the database's concurrency sweet spot, and a useful input for sizing the application's connection pools.

HammerDB

HammerDB is an open-source database benchmarking tool hosted by the TPC. It runs workloads derived from TPC-C (called TPROC-C, an OLTP order-processing workload) and TPC-H (TPROC-H, analytic queries) against Oracle, SQL Server, Db2, MySQL, MariaDB and PostgreSQL. That makes it the usual choice for comparing database engines or platforms on the same workload, for example SQL Server on-premises vs a managed cloud offering.

  • It has a GUI and a command-line interface (hammerdbcli) that runs Tcl or Python scripts, so runs can be automated.
  • TPROC-C reports NOPM (new orders per minute) and TPM (database transactions per minute). NOPM is comparable across databases. TPM depends on how each engine counts transactions.
  • Size the schema with the warehouse count. More warehouses means more data and less contention. Follow the HammerDB documentation's guidance for warehouses per virtual user.
  • Results from HammerDB are not official TPC results and shouldn't be described as such.

What to measure

  • Throughput and latency percentiles from the test tool, over time.
  • Top queries by total time during the run (pg_stat_statements, performance_schema, Query Store). See the database bottlenecks guide.
  • Waits and locks, sampled during the run.
  • Host metrics: CPU, memory, disk latency and IOPS against the volume's limit, especially for the WAL or redo log volume.
  • Replication lag on replicas. Read replicas that fall behind under write load serve stale data.
  • Background work: autovacuum in PostgreSQL, purge lag in InnoDB, checkpoints. These often explain periodic latency spikes.
