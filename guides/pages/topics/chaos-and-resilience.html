Chaos and resilience testing under load

The architecture diagram has retries, a circuit breaker, a fallback cache and two availability zones. Nobody has seen any of them work. Then the payment provider slows from 200 ms to 4 seconds at 8 pm on a Friday. Retries triple the traffic to it, every request thread waits on it, and the whole site goes down because one optional dependency got slow. Resilience you haven't tested is a hope, not a feature.

Chaos engineering in five rules

Chaos engineering grew out of Netflix's practice of deliberately breaking parts of its production system (Chaos Monkey). The published principles boil down to this:

  1. Define steady state as a measurable output: orders per minute, p95 latency, error rate. Not CPU.
  2. Write a hypothesis: "If one of three payment pods is killed, checkout success stays above 99.5% and p95 stays under 1 second."
  3. Inject real-world events: instance loss, latency, errors from dependencies, network partitions, full disks, clock skew.
  4. Minimise the blast radius: start small (one pod, a small share of traffic, a test environment) and have a way to stop at once.
  5. Automate and repeat: resilience decays as the system changes. An experiment that passed in March proves little in November.

An experiment that disproves the hypothesis is a success: you found a weakness before your users did.

Toxiproxy: faults between services

Toxiproxy, open-sourced by Shopify, is a TCP proxy you put between a service and its dependency. You then add "toxics" through its API or CLI: latency, bandwidth limits, timeouts, connection resets, slow closes. It works with any TCP protocol (HTTP, database, Redis, Kafka), runs anywhere, and is ideal for test environments and CI.

# start the server (API on port 8474)
toxiproxy-server &

# proxy local port 26379 to the real Redis, then point the app at localhost:26379
toxiproxy-cli create --listen localhost:26379 --upstream redis.test.internal:6379 redis

# add 1 second of latency with 200 ms of jitter to responses
toxiproxy-cli toxic add --type latency --attribute latency=1000 --attribute jitter=200 redis

# simulate an outage: disable the proxy, then enable it again
toxiproxy-cli toggle redis
toxiproxy-cli toggle redis

# remove the toxic (default name is <type>_<stream>)
toxiproxy-cli toxic remove --toxicName latency_downstream redis

Other toxics include bandwidth, timeout (stop all data and close after a delay), reset_peer, slow_close, slicer and limit_data. Toxics can apply to a percentage of connections with --toxicity. Check the project's README for the exact CLI flags in your version, and client libraries exist for most languages if you want to drive it from tests.

AWS Fault Injection Service

AWS FIS runs fault experiments against real AWS resources. You define an experiment template with:

  • Targets: resources selected by ID, tag or filter, for example EC2 instances tagged env=perf, a share of ECS tasks or EKS pods.
  • Actions: for example stopping or terminating EC2 instances, stopping ECS tasks, failing over an RDS or Aurora cluster, disrupting network connectivity in a subnet, injecting API throttling or errors, or running CPU and memory stress and network latency on instances through Systems Manager documents.
  • Stop conditions: CloudWatch alarms that end the experiment automatically, for example when the error rate passes 5%.
  • An IAM role that limits what the experiment can touch.

FIS is useful because it exercises the platform itself (load balancer health checks, Auto Scaling replacement, Aurora failover, cross-zone behaviour), which a proxy between two services can't. The list of supported actions grows regularly, so check the current FIS action reference. FIS is charged per action-minute.

Kubernetes: Chaos Mesh and LitmusChaos

Both are open-source CNCF projects that define experiments as Kubernetes custom resources.

Chaos Mesh

Covers pod kills and failures (PodChaos), network delay, loss, partition and bandwidth (NetworkChaos), CPU and memory stress, I/O faults, clock skew, HTTP faults and DNS errors, plus workflows to chain them. A latency experiment against one service:

apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: payments-latency
  namespace: shop
spec:
  action: delay
  mode: all
  selector:
    namespaces: [shop]
    labelSelectors:
      app: payments
  delay:
    latency: '800ms'
    jitter: '100ms'
  duration: '10m'

LitmusChaos

Provides a hub of ready-made faults (pod delete, pod network latency, CPU hog, node drain and many more), a web UI called ChaosCenter for scheduling and history, and probes that check steady state automatically during the experiment: an HTTP probe against a health endpoint, a Prometheus probe on a query such as error rate, or a command probe. Probes turn an experiment into a pass or fail result you can put in a pipeline.

Pick Chaos Mesh for a broad set of fault types and simple YAML. Pick Litmus if built-in steady-state probes and a shared experiment hub matter more. For faults injected from inside a k6 test, Grafana's xk6-disruptor extension can add latency and errors to Kubernetes pods and services during a load test.

Combine faults with load

A fault in an idle system rarely shows anything. A pod restart at 5 requests per second is invisible. At peak, the same restart moves its traffic to pods that were already at 70% CPU, and their latency climbs. Pool exhaustion, retry amplification and slow failover only happen under concurrency. So the most useful resilience test is a load test with a fault in the middle:

  1. Run steady load at expected peak with an open workload model (arrival rate), so the load doesn't drop when the system slows. A closed model quietly reduces pressure during the fault and hides the problem. See open vs closed.
  2. Hold steady state for 10 to 15 minutes to get a baseline.
  3. Inject the fault for a fixed period, for example 5 minutes.
  4. Remove it and keep the load running for another 10 to 15 minutes.
  5. Measure: error rate and latency during the fault, time to detect (did alerts fire?), time to recover after removal, and whether it recovered at all. Metastable failures are the dangerous kind: the system stays degraded after the trigger is gone, usually because retries or a cold cache keep it overloaded.

Mark the fault window with an annotation in your dashboards (see the Grafana stack), and agree pass criteria in advance. For example: during the fault, error rate under 1% and p95 under 2 seconds. After it, back to baseline within 2 minutes.

Running experiments safely

  • Start in a test environment that mirrors production topology. Move to production only with small blast radius, stop conditions and the team watching.
  • Tell the people who will be paged. A surprise chaos experiment teaches the wrong lessons.
  • Always have an abort: FIS stop conditions, deleting the Chaos Mesh resource, removing the toxic. Test the abort first.
  • Record each experiment: hypothesis, fault, result, follow-up actions. That record becomes your error budget and reliability evidence for go-live.
