Mobile app performance testing

The marketing team sends a push notification to 800,000 users at 7 pm. Within 90 seconds, 120,000 people open the app. Each launch makes 14 API calls, a few thousand retry on patchy 4G, and the backend that handled the load test's smooth ramp falls over. The ones who get in wait 6 seconds for the home screen on a three-year-old Android phone. Mobile performance has two halves, and most teams only test one.

The two meet on the network: a slow API response is worse on a 300 ms round trip, and an app that makes 14 sequential calls at launch multiplies every millisecond of backend latency.

Startup time

Startup is the first thing users feel and the metric app stores report. Both platforms distinguish cold starts (process not running, the slowest and the one to test), warm starts and hot starts.

  • Android: Time to Initial Display (TTID) is the first frame. Time to Full Display (TTFD) is when the app calls reportFullyDrawn() after loading its real content, which is the number that matters to users. Android vitals in the Play Console flags cold starts of 5 seconds or more as excessive.
  • iOS: Apple's guidance is for the first frame to appear within about 400 ms of launch. Measure with the App Launch template in Instruments, or in an XCTest with XCTApplicationLaunchMetric.
# Android: quick cold-start check from the command line
adb shell am force-stop com.example.app
adb shell am start -W -n com.example.app/.MainActivity
# TotalTime: 1243   <- ms to the first frame of the launched activity
// iOS: launch time in an XCTest UI test target
func testLaunchPerformance() throws {
    measure(metrics: [XCTApplicationLaunchMetric()]) {
        XCUIApplication().launch()
    }
}

For repeatable Android measurements in CI, use the Jetpack Macrobenchmark library, which runs cold, warm and hot starts many times on a real device and reports percentiles. Typical causes of slow starts: heavy work in Application.onCreate or the app delegate, SDKs initialised eagerly, synchronous disk or network calls before the first frame, and on Android, code that hasn't been ahead-of-time compiled (Baseline Profiles help).

Frame rate and jank

At 60 Hz the app has 16.7 ms to produce each frame. At 120 Hz, 8.3 ms. A frame that misses its deadline is a dropped frame, and the user sees stutter while scrolling or animating. That is jank on Android and a hitch on iOS.

# Android: frame statistics since the last reset, for one app
adb shell dumpsys gfxinfo com.example.app reset
# ... scroll the feed for 30 seconds ...
adb shell dumpsys gfxinfo com.example.app
# Total frames rendered: 1820
# Janky frames: 146 (8.02%)
# 50th percentile: 9ms   90th: 17ms   95th: 23ms   99th: 61ms

Android vitals also counts slow frames and frozen frames (frames taking over 700 ms). On iOS, the Animation Hitches instrument in Xcode shows hitch time ratio and which frames missed. Test on a low-end device: frame budgets that a flagship meets with room to spare are often missed on the mid-range phones that many users actually own.

Profile release-like builds on real devices. Debug builds on Android run without many optimisations and can be several times slower, and the emulator and simulator use your computer's CPU, not the phone's.

Network conditioning

Office Wi-Fi hides the problems users have on trains and in lifts. Test under realistic latency, bandwidth and packet loss:

  • iOS: Network Link Conditioner, in the Developer settings on a device, and as a macOS tool in Apple's Additional Tools for Xcode. It has presets such as 3G, LTE and Very Bad Network.
  • Android emulator: network speed and latency settings in the emulator's extended controls.
  • Any device through a proxy: Charles Proxy and similar tools can throttle traffic.
  • Linux gateway or test host: tc netem adds latency, jitter and loss to an interface.
# add 150 ms ± 30 ms latency and 1% loss on eth0 (Linux, as root)
tc qdisc add dev eth0 root netem delay 150ms 30ms loss 1%
# remove it
tc qdisc del dev eth0 root

Watch what the app does under these conditions: how many requests it makes before showing content, whether they run in parallel, timeouts and retries, and whether it shows cached content while waiting.

Backend load from mobile traffic patterns

Mobile traffic has a shape web traffic often doesn't. Build it into the workload model:

  • Push-notification bursts. A campaign sent to everyone at once produces a spike in minutes, not a ramp over an hour. Model it from real open-rate curves after past pushes, and test a thundering herd explicitly.
  • Launch fan-out. One app open can mean 10 to 20 API calls (config, feature flags, profile, feed, notifications count). Load = launches per second × calls per launch. Script the real launch sequence, not one endpoint at a time.
  • Retries on bad networks. Mobile clients retry. Under backend stress, aggressive client retries multiply traffic exactly when it hurts most. Check the app's retry policy and include it in the model. See retry storms.
  • Scheduled background work. Background refresh and sync jobs set to fixed times (midnight, top of the hour) line up across millions of devices. Jitter in the app avoids it. Test that it is there.
  • Old app versions. Users update slowly, so old versions keep calling old endpoints with old payloads. Include their share in the mix.
  • Slow clients hold connections longer. Requests from slow networks keep server connections and threads busy longer than requests from the data centre. Some load tools can limit bandwidth per virtual user. Otherwise allow for it in connection and thread sizing.

Capture the real sequence from a device with a proxy, or from your API gateway logs, then convert it into a script. The workload model builder helps turn launch rates into request rates, and the capacity calculator sizes the backend.

Field data from real devices

Lab tests on a few devices can't cover the range your users have. Field data fills that gap: Android vitals in the Google Play Console and Firebase Performance Monitoring on Android, and Xcode Organizer and MetricKit on iOS, report launch times, hangs and frame metrics from real users' devices. Use field data to choose which devices and network profiles to test in the lab, and to confirm that a fix worked.
