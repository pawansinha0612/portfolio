How to use it

  • One plan per release. If you have a test strategy, this plan only covers what is specific to this release.
  • Make every test able to fail. The "Passes when" column in section 4 should be a number someone can check, not "acceptable performance".
  • Write the environment gaps down. A smaller database or a stubbed dependency changes what your results mean. Reviewers need to see it before the test, not after.
  • Build the workload first. Section 3 comes from the workload model sheet.

One plan per release or test cycle. If a section doesn't apply, write "Not applicable" and why, so reviewers can see it was considered.

1. Objective and scope

  • Objective: For example: confirm the new search service meets its NFRs at 1.5 × last year's peak.
  • In scope: Journeys and APIs tested.
  • Out of scope: What is not tested, and why.
  • What changed since the last test: Code, infrastructure, configuration, data volumes.

5. Environment

  • Environment: Name and size compared with production.
  • Gaps from production and their effect: For example: one database replica instead of three, so read capacity is lower.
  • Load generators: Where they run, and that their CPU will be watched.

6. Test data

  • Accounts, products and other data needed, how many, and how they're created.
  • How data is reset between runs.

7. Monitoring

  • Dashboards and APM views used, with links.
  • Server metrics captured: CPU, memory, GC, pools, database, queues.

8. Entry and exit criteria

  • Entry: Build deployed and stable, smoke test passed, monitoring working, data loaded.
  • Exit: All planned tests run, results analysed, report issued.
