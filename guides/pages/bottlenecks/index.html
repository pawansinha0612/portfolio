Finding the bottleneck: a step-by-step playbook

The load test failed. p95 went from 300 ms to 4 seconds at 600 users, and five people have five theories: the database, the garbage collector, the load balancer, "the network", and "just add pods". This playbook replaces the guessing with a fixed order of steps that ends with one proven cause and one change.

1. Confirm the symptom with percentiles

Before hunting for a cause, make sure the problem is real and describe it precisely. "It got slow" is not a symptom. "p95 for POST /checkout crossed 800 ms at 450 requests per second, while GET /products stayed under 120 ms" is.

  • Look at p50, p95 and p99 per transaction, never only the average. A rising p99 with a flat p50 means a minority of requests is waiting for something (a lock, a pool, a GC pause, a cold cache). Everything rising together means a shared resource is saturated. See why averages lie.
  • Plot latency over time, not one number for the whole run. A test that averages fine can hide a 90-second stall at minute 12.
  • Check the error rate alongside latency. Fast errors (a 503 in 5 ms) pull percentiles down and make a broken system look quick.
  • Rule out the load generator. Check the generator's CPU (keep it under about 70 to 80%), network and, for k6, the http_req_blocked and dropped_iterations metrics. If the injector is saturated, every number after that point is about the injector.
  • Check you ran an open model when the question is about arrival rates. A closed-loop tool slows down with the system and under-reports the tail. That is coordinated omission.

The k6 results analyser and JTL analyser turn raw results into these per-transaction percentiles quickly. Compare runs shows what moved between a good and a bad run.

2. Find the saturation point

Plot throughput and latency against load from a stepped or ramping test. The shape tells you a lot before you open a single server metric.

  • Throughput rises linearly, latency flat: healthy, below capacity.
  • Throughput flattens, latency climbs: you have reached the knee. Some resource is at or near 100% busy and requests are queueing in front of it. By Little's Law (concurrency = throughput × response time), once throughput is capped any extra concurrency turns directly into waiting time.
  • Throughput falls as load rises: retrograde scaling. Something is getting worse with concurrency: lock contention, cache thrashing, connection storms or retries. Gunther's Universal Scalability Law calls this the coherency penalty.
  • Latency jumps in steps or spikes at regular intervals: look for periodic work: GC, cron jobs, log rotation, cache expiry (cache stampede), autoscaling events.

Write down the load level of the knee. Every metric in the next steps should be read at that moment, not averaged over the whole test. The queueing explainer shows why latency goes vertical as utilisation approaches 100%.

3. USE method, per resource

Brendan Gregg's USE method checks every resource for three things: Utilisation (how busy), Saturation (how much work is queued) and Errors. It works because it is exhaustive. You go through the list and cannot skip the resource you don't suspect.

Software resources (pools, locks, queues, rate limits) are where most bottlenecks in modern services live. A database connection pool of 20 serving 200 threads will cap throughput long before CPU reaches 50%. 4. RED method, per service

USE looks at resources. The RED method looks at each service from the outside: Rate (requests per second), Errors and Duration (latency percentiles). In a system of ten services, RED tells you which one to apply USE to.

  • Compare each service's own latency with the latency it reports for its downstream calls. If service A takes 900 ms and 850 ms of it is waiting on service B, A is a victim, not the cause.
  • Watch for fan-out: one user request that makes 30 downstream calls inherits the tail of all 30.
  • Rising errors in a downstream service often show up upstream as latency (timeouts and retries), not as errors. Read about retry storms.

5. Follow the slow trace

Aggregates tell you where to look. A single slow trace tells you what happened. Filter traces in your APM to the slow transaction at the knee (for example duration above your p99) and open several, not one.

  • Find the longest span on the critical path, then check whether it was working or waiting. A 2-second database span with a 5 ms query inside it usually means waiting for a connection or a lock.
  • Gaps between spans are time nobody instrumented: queueing in a thread pool, GC pauses, serialisation, or a missing span.
  • Compare a slow trace with a fast trace of the same endpoint. The difference is the bottleneck.

How to read a waterfall properly is covered in APM and tracing.

6. Write a hypothesis you can disprove

Write it down in one sentence with a prediction: "Checkout saturates because the order service's connection pool (max 20) is exhausted at 450 req/s. If that is right, pool wait time rises from zero at the knee, the database is under 40% CPU, and raising the pool to 40 moves the knee to about 800 req/s unless the database saturates first."

A good hypothesis names the resource, the metric that proves it, and what should happen when you change it. If you can't name the metric, you don't have a hypothesis yet. Go back to step 3.

Common false leads: high CPU on a box that is not on the critical path, a slow query that runs once per test, and GC logs that look busy but add up to 1% of wall time. Size every suspect against the latency you are trying to explain.

7. Change one thing, then retest

  • One change per run. Two changes in one run means you can't tell which one helped, or whether one helped and the other hurt.
  • Same test, same data, same environment. Rerun the baseline first if the environment may have drifted.
  • Expect the bottleneck to move. Fixing the pool will push load onto the database. That is progress, and the next round of the playbook starts there.
  • Keep a log of hypothesis, change, result. It becomes the most valuable part of the test report (see the results report template).
