Reading a Linux server under load

Your dashboard says CPU is at 45% and the app is still timing out. Averages across 16 cores and 60-second scrapes hide exactly the thing you need: one core pinned at 100%, a disk queue that spikes for two seconds, a listen queue that overflows. These are the commands to run on the box while the test is at its knee, and what to look for in each.

The first 60 seconds

Brendan Gregg published a well-known checklist for the first minute on a struggling Linux host. A version of it, tuned for load testing, is below. Run it on each server in the path while the test is at the load level where things go wrong. Most of these come from the procps and sysstat packages (apt install sysstat or dnf install sysstat).

uptime                 # load averages: 1, 5, 15 minutes
dmesg -T | tail -20    # OOM kills, TCP drops, disk errors
vmstat 1 10            # run queue, memory, swap, CPU split
mpstat -P ALL 1 5      # per-core CPU: look for one hot core
pidstat 1 5            # which processes use the CPU
iostat -xz 1 5         # per-disk latency and utilisation
free -m                # memory, look at "available"
sar -n DEV 1 5         # network throughput per interface
sar -n TCP,ETCP 1 5    # new connections, retransmits
ss -s                  # socket summary
top                    # overall check, press 1 for per-core

Use 1-second intervals. A problem that lasts 3 seconds disappears inside a 60-second average, and that is the granularity most monitoring tools give you.

CPU: top, mpstat, vmstat

vmstat 1

procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
14  0      0 812340  20112 4021388    0    0     0    48 9120 15230 82 12  5  1  0
ColumnMeaningWorry when
rRunnable tasks: running or waiting for a CPUConsistently above the number of cores. That is CPU saturation, work is queueing.
bTasks blocked in uninterruptible sleep, usually disk I/OPersistently above 0 under load
si / soSwap in / out per secondAny sustained non-zero value on a latency-sensitive server
csContext switches per secondA big jump compared with baseline at the same throughput: lock contention or too many threads
us / syUser / kernel CPU %sy above about 20 to 30%: syscall-heavy work, small network writes, lock spinning
waIdle while waiting for I/OHigh wa means CPUs are idle because of I/O. Check iostat.
stSteal: time the hypervisor gave to another guestAbove a few percent on a VM: noisy neighbour or burst credits exhausted

The first vmstat line is an average since boot. Ignore it.

mpstat -P ALL 1

Shows each core separately. The pattern to catch is one core at 100% %usr while the others are idle. That is a single-threaded bottleneck (a Node.js event loop, a Redis instance, a single consumer thread, a lock everything funnels through). Average CPU says 7% on a 16-core box. A core at 100% %soft points at network interrupt handling stuck on one CPU. Check that receive-side scaling spreads the NIC queues across cores.

top and load average

In top, press 1 for per-core lines, H for threads and P to sort by CPU. Load average on Linux counts runnable tasks and tasks in uninterruptible sleep, so a high load with idle CPUs usually means disk or NFS waits, not CPU. Compare load with the core count: a 1-minute load of 32 on 8 cores is saturation.

Memory: free, vmstat, dmesg

free -m
               total        used        free      shared  buff/cache   available
Mem:           15921        9811         412          88        5697        5712

Read available, not free. Linux uses spare memory as page cache, so low "free" is normal. Low "available" (under about 10% of total) plus swap activity or OOM kills is the real signal. For the JVM, remember the heap is only part of the process: metaspace, thread stacks, direct buffers and the code cache sit outside it. A container limit sized to -Xmx will get OOM-killed.

dmesg -T | grep -i -E 'killed process|out of memory'

Disk: iostat -x

iostat -xz 1
Device   r/s    w/s   rkB/s   wkB/s  r_await w_await aqu-sz %util
nvme0n1  820.0 1450.0 13120.0 92800.0   0.21    4.80   7.12  98.4
ColumnMeaningWorry when
r_await / w_awaitAverage ms per read / write, including queue timeWell above the device's normal: SSD reads over a few ms, cloud volumes over about 10 ms, or rising with load
aqu-szAverage queue length (older sysstat: avgqu-sz)Growing steadily with load: saturation
%utilPercentage of time the device had at least one I/O in flightNear 100% on a single spinning disk. On SSD, NVMe and cloud volumes it can show 100% with headroom left, so judge by await and IOPS limits instead.

Cloud block storage has provisioned IOPS and throughput caps, and some volume types use burst credits. When w/s flattens at a round number while await climbs, you have probably hit the volume's limit, not the disk's.

Network: ss, sar -n

ss -s                         # totals: estab, timewait, orphaned
ss -ltn                       # listening sockets: Recv-Q vs Send-Q
ss -tan state time-wait | wc -l
sar -n DEV 1                  # rxkB/s, txkB/s per interface
sar -n TCP,ETCP 1             # active/s passive/s, retrans/s
nstat -az | grep -E 'ListenOverflows|ListenDrops|TCPRetransSegs'
  • Listen queue: for a listening socket in ss -ltn, Recv-Q is the current accept queue and Send-Q is its maximum (the backlog). If Recv-Q reaches Send-Q, or ListenOverflows grows, the application isn't calling accept() fast enough and new connections are dropped. Clients see connect timeouts and SYN retries of 1, 3, 7 seconds.
  • Retransmits: retransmitted segments above about 1% of sent segments under load mean packet loss or congestion somewhere on the path.
  • TIME_WAIT: tens of thousands of TIME_WAIT sockets on the client side means connections are not being reused. That costs a handshake per request and can exhaust ephemeral ports. Fix keep-alive before touching kernel settings.
  • Bandwidth: compare txkB/s with the instance's network limit, which on cloud VMs is often lower than the NIC speed and may be a burst figure.

Per process: pidstat

pidstat -u 1 -p ALL       # CPU per process (%usr %system %wait)
pidstat -t -p <PID> 1     # per thread: find the hot thread
pidstat -w -p <PID> 1     # cswch/s (voluntary) nvcswch/s (involuntary)
pidstat -d 1              # disk read/write per process

High voluntary context switches mean threads keep blocking (I/O, locks). High involuntary switches mean they are being preempted: more runnable threads than cores. %wait in pidstat -u is time the task was runnable but waiting for a CPU, a direct measure of CPU queueing for that process.

To map a hot thread to Java code, take the thread ID from pidstat -t, convert it to hex (printf '%x\n' 12345) and find nid=0x3039 in a thread dump. See the JVM guide.

History: sar

Most tools only show now. sar from sysstat records history if its collector is enabled (systemctl enable --now sysstat on most distributions). Then you can look back at a test that ran overnight:

sar -u -s 02:00:00 -e 02:30:00     # CPU for a time window today
sar -q                             # run queue and load average
sar -r                             # memory
sar -d -p                          # disks, with device names
sar -n DEV -f /var/log/sysstat/sa15   # a previous day (path varies by distro)

The default collection interval is often 10 minutes, too coarse for a load test. Lower it in the sysstat timer or cron entry on test servers, or run sar -o /tmp/test.sar 1 for the duration of the test and read it back with sar -f.

Containers and CPU throttling

In Kubernetes, a CPU limit is enforced by the CFS quota: a container with a limit of 2 CPUs gets 200 ms of CPU time per 100 ms period across all its threads. A multi-threaded app can burn its quota in the first 30 ms of a period and then sit throttled for 70 ms. Latency spikes, while average CPU usage looks well under the limit.

# cgroup v2, from inside the container or on the node
cat /sys/fs/cgroup/cpu.stat
# nr_periods 120000
# nr_throttled 18000         <- 15% of periods throttled
# throttled_usec 950000000

In Prometheus with cAdvisor metrics, the share of throttled periods is:

rate(container_cpu_cfs_throttled_periods_total[1m])
  / rate(container_cpu_cfs_periods_total[1m])

Anything above a few percent on a latency-sensitive service is worth fixing, by raising or removing the limit or by reducing thread counts so the runtime doesn't assume it owns every core on the node.

CPU profiling: perf and flame graphs

When CPU is the bottleneck, the question becomes which code. perf samples stacks across the whole system, and a flame graph shows where the time goes: width is the share of samples, the y-axis is stack depth. Look for wide plateaus near the top.

# sample all CPUs at 99 Hz with call stacks for 30 seconds
sudo perf record -F 99 -a -g -- sleep 30
sudo perf report --stdio | head -50

# flame graph with Brendan Gregg's FlameGraph scripts
git clone https://github.com/brendangregg/FlameGraph
sudo perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > cpu.svg
  • 99 Hz rather than 100 avoids sampling in lockstep with periodic timers.
  • JIT-compiled languages (Java, Node.js) need symbol maps, or you'll see hex addresses. For Java, use async-profiler instead (see the JVM guide). Node.js has --perf-basic-prof.
  • A CPU flame graph shows on-CPU time only. If latency is high and CPU is low, the time is off-CPU (waiting on locks, I/O, pools), and you need an off-CPU or wall-clock profile, or a thread dump.
