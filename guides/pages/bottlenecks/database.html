Database bottlenecks under load

The app servers are at 30% CPU, the database is at 40%, and checkout still takes 6 seconds at peak. Everyone looks at the database because it is the database. The database might be fine. The slow part could be the pool in front of it, one lock every request queues behind, or 200 tiny queries per page. This is how to tell which.

Is it the database at all?

Compare two numbers: how long the application waits for the database (from APM spans or pool metrics) and how long the database spends executing the queries (from its own statistics). If the app sees 800 ms per call and the database reports 15 ms per execution, the time is spent before the query runs: waiting for a pool connection, waiting for a lock, or on the network. If the two match, the queries themselves are slow.

Then apply the USE method to the database host: CPU, memory (buffer cache hit ratio), disk latency for data and log/WAL volumes, and the connection count against its limit.

Find the expensive queries

Rank queries by total time (calls × mean), not by the single slowest execution. A 3 ms query called 40,000 times a minute costs far more than a 4-second report that runs once.

PostgreSQL: pg_stat_statements

Add it to shared_preload_libraries (needs a restart), then CREATE EXTENSION pg_stat_statements; in the database. Reset before the test, read after it:

SELECT pg_stat_statements_reset();   -- before the run

-- after the run: top 15 by total execution time (PostgreSQL 13+ column names)
SELECT round(total_exec_time::numeric, 0)  AS total_ms,
       calls,
       round(mean_exec_time::numeric, 2)   AS mean_ms,
       rows,
       round(100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS hit_pct,
       left(query, 120)                    AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 15;

On PostgreSQL 12 and older the columns are total_time and mean_time. A low hit_pct means the query reads from disk, often because the test data doesn't fit in memory, or because a missing index forces large scans.

PostgreSQL: slow query log

# postgresql.conf, or ALTER SYSTEM SET ... then SELECT pg_reload_conf();
log_min_duration_statement = 200    # log statements slower than 200 ms
log_lock_waits = on                 # log waits longer than deadlock_timeout (default 1s)
# auto_explain logs the plan of slow statements too
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = 500

MySQL: slow query log and performance_schema

SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;         -- seconds
SET GLOBAL log_queries_not_using_indexes = ON;
-- summarise afterwards: mysqldumpslow -s t /var/lib/mysql/host-slow.log
-- or pt-query-digest from Percona Toolkit

-- top statements by total latency, from performance_schema (MySQL 5.7+/8.0)
SELECT DIGEST_TEXT, COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1e12, 2)  AS total_s,
       ROUND(AVG_TIMER_WAIT/1e9, 2)   AS avg_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 15;

Timer columns in performance_schema are in picoseconds. A big gap between SUM_ROWS_EXAMINED and SUM_ROWS_SENT means the query reads many rows to return few: an index problem.

Read the plan: EXPLAIN and EXPLAIN ANALYZE

EXPLAIN shows the plan the optimiser intends to use, with estimates. EXPLAIN ANALYZE actually runs the query and shows real row counts and timings. Run it on a database with production-like data volumes. Plans on a 1,000-row test table tell you nothing about a 50-million-row table.

-- PostgreSQL
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;

-- MySQL 8.0.18+
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;

EXPLAIN ANALYZE executes the statement. For INSERT, UPDATE or DELETE, wrap it in BEGIN; ... ROLLBACK;.

What to look for:

  • Estimated rows far from actual rows (PostgreSQL shows rows= in both the estimate and the actual). Off by 100× or more means stale statistics or correlated columns, and the optimiser is choosing the plan blind. Run ANALYZE and look again.
  • Sequential scan (Seq Scan, or type: ALL in MySQL) on a large table with a selective filter: a missing or unusable index. Functions on the column (WHERE lower(email) = ...) and implicit type casts make an index unusable.
  • Sort or hash spilling to disk: Sort Method: external merge Disk in PostgreSQL (raise work_mem for that query, or add an index that returns rows in order).
  • Nested loop with a big outer side: fine for 10 rows, painful for 100,000.
  • BUFFERS read vs hit: many read blocks mean disk I/O.

Load tests also find plans that change. The same query can use a good plan for most parameter values and a bad one for a few "big" customers. Test with a realistic spread of parameter values, not the same ID every time (see parameterisation).

Locks and waits

When queries are fast alone but slow under load, they are probably waiting. Ask the database what sessions are waiting on, during the test:

-- PostgreSQL: what every active session is waiting on right now
SELECT wait_event_type, wait_event, state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY 1, 2, 3 ORDER BY 4 DESC;

-- PostgreSQL: who blocks whom
SELECT blocked.pid  AS blocked_pid, left(blocked.query, 60)  AS blocked_query,
       blocking.pid AS blocking_pid, left(blocking.query, 60) AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));
-- MySQL 8.0: InnoDB lock waits (sys schema)
SELECT * FROM sys.innodb_lock_waits\G
-- recent deadlocks
SHOW ENGINE INNODB STATUS\G

Typical causes: a hot row everyone updates (a counter, an inventory row, a sequence table), long transactions that hold locks while calling an external service, and foreign keys without an index on the child table, which forces wider lock checks. See lock contention and database deadlocks. In PostgreSQL, sessions idle in transaction are a red flag: the app opened a transaction and is doing something else while holding locks.

Connection pools

The pool is the most common database "bottleneck" that isn't in the database. If 200 request threads share a pool of 10 connections, 190 of them wait, and their wait shows up as database time in most APM tools.

  • Measure pool wait, not just pool usage. HikariCP exposes hikaricp_connections_pending and hikaricp_connections_acquire_seconds through Micrometer. Active connections pinned at the maximum and pending above zero means the pool is the limit.
  • Bigger is not automatically better. A database with 8 cores can only run so many queries in parallel. 500 connections all doing work cause context switching and lock contention inside the database and make throughput worse. Size the pool to what the database can actually execute in parallel, and let the extra requests queue in the app where you can see them.
  • Multiply by instances. 20 pods × a pool of 30 = 600 connections. Check that against max_connections, and remember PostgreSQL uses a process per connection. A pooler such as PgBouncer in transaction mode is the usual fix when you need many app instances.
  • Pool timeouts in the logs ("Connection is not available, request timed out after 30000ms") confirm it. A 30-second acquisition timeout also means your users wait 30 seconds before getting an error.

The connection pool glossary entry has the Little's Law sizing maths.

N+1 queries

An N+1 query loads a list with one query, then runs one more query per item. With 20 test items it costs 21 fast queries and nobody notices. With 400 items in production it costs 401 round trips per page. Under load, the round-trip latency and pool time add up, not the query time.

  • Detect it in traces: a single request with dozens of identical database spans that differ only in a parameter.
  • Detect it in statistics: a cheap query whose calls count in pg_stat_statements is a large multiple of the request count.
  • Fix it: fetch joins or batch fetching in the ORM (JPA JOIN FETCH or entity graphs, Hibernate @BatchSize, Django select_related/prefetch_related, Rails includes), or one query with WHERE id IN (...).
  • Make test data realistic so the N in N+1 matches production. See database load testing.

SQL Server: Query Store

On SQL Server 2016 and later, and Azure SQL Database where it is on by default, Query Store keeps per-query runtime statistics and plan history in the database. It answers the two questions a load test raises: which queries cost the most during the run, and did any query change plan. Enable it with ALTER DATABASE [YourDb] SET QUERY_STORE = ON;, then use the "Top Resource Consuming Queries" and "Regressed Queries" reports in SQL Server Management Studio. A plan that regressed can be pinned to the known good one there while you fix the root cause. For live waits, sys.dm_exec_requests and sys.dm_os_wait_stats play the role of pg_stat_activity, and SQL Server 2017+ also records wait statistics per query in Query Store.
