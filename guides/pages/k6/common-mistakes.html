12 k6 mistakes that make your load test lie

The test passed. Every number was green. Production fell over at half the load. In most cases the system wasn't the problem. The test was measuring something other than what everyone thought. These are the mistakes behind that.

Mistakes that give wrong results

1. No checks, so fast errors count as fast responses

A 503 from the load balancer returns in 2 ms. Without a check, k6 records a 2 ms response and p95 improves as the system collapses. http_req_failed catches status codes, but not a 200 with an error page or an empty list. Check the body on the calls that matter, and put a threshold on checks.

2. Using VUs when the target is requests per second

"Handle 1,000 requests a second" is an open-model target. constant-vus and stages are closed: when latency rises, the request rate falls and the test eases off exactly when it should push. Use constant-arrival-rate or ramping-arrival-rate. Details in scenarios and executors.

3. Same user, same product, same search

One account and one id for every VU means every request hits a warm cache and the same database rows. You measure the cache. Feed varied data and give each VU its own identity: test data in k6.

4. A saturated load generator

If the machine running k6 is at 100% CPU, or out of network bandwidth, the latency you measure includes k6 waiting for its own CPU. Watch the generator's CPU, memory and network during every run. Warning signs: dropped_iterations while the server looks healthy, http_req_blocked growing, or latency that rises on k6 but not in the server's own metrics. Fix it with a bigger machine, less per-iteration work, or several generators.

5. Testing from a laptop over Wi-Fi and a VPN

Home broadband and a corporate VPN have far less capacity than a production network, and they add their own latency and jitter. The VPN concentrator becomes the bottleneck you measure. Run from a machine in the same cloud region as real users or clients would be.

6. Reporting the average

The average hides the slow tail, and averaging per-endpoint p95s does not give an overall p95. Report p50, p95 and p99 with the request count. See why averages lie.

7. Too short, no steady state

Two minutes is a warm-up: JIT compilation, connection pools filling, caches loading, the autoscaler reacting. Measure a steady state of at least 10-15 minutes after the ramp, and exclude the ramp when you quote numbers. Memory leaks and pool exhaustion need hours: that's a soak test.

Mistakes in the script

8. Untagged dynamic URLs

/products/1, /products/2 and so on each become their own metric series. With thousands of ids, k6's memory grows, outputs struggle and the summary is useless. Add a name tag, or use the http.url template tag, which names the request after the template rather than the concrete URL.

9. Big files without SharedArray

JSON.parse(open('data.json')) at the top level runs in every VU. A 20 MB file at 500 VUs is 10 GB of memory. Wrap it in SharedArray.

10. Keeping every response body

By default k6 reads every response body into memory, even when the script never looks at it. For large responses at high rates that's a lot of memory and CPU you don't need. Set discardResponseBodies: true and ask for the body only on requests you check or extract from.

11. sleep() in an arrival-rate scenario

With an arrival-rate executor, the rate sets the pacing. A sleep(3) at the end doesn't reduce load, it holds each VU three seconds longer, so you need far more VUs and may drop iterations. Use sleeps between steps of a journey, not as pacing at the end.

12. A threshold that matches nothing

A threshold on 'http_req_duration{name:GET /product}' when the tag is GET /products has no data, and a threshold with no data passes. The test has never been able to fail on that endpoint. After changing tags or thresholds, check that each threshold shows a value in the summary.

The fixes in one script

import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = {
  discardResponseBodies: true, // don't keep bodies in memory unless a request asks for one
  scenarios: {
    browse: {
      executor: 'constant-arrival-rate', // a rate target needs an open model
      rate: 50, timeUnit: '1s', duration: '10m',
      preAllocatedVUs: 20, maxVUs: 200,
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    'http_req_duration{name:GET /products/:id}': ['p(95)<300'],
    checks: ['rate>0.99'],
    dropped_iterations: ['count<1'],
  },
};

export default function () {
  // Body needed for the check, so ask for it on this request only
  const list = http.get(`${BASE_URL}/products`, { responseType: 'text' });
  check(list, { 'list ok': (r) => r.status === 200 && r.json('items.#') > 0 });

  const id = Math.floor(Math.random() * 10) + 1;
  // One name for every id: one metric series, not one per URL
  const item = http.get(`${BASE_URL}/products/${id}`, { tags: { name: 'GET /products/:id' } });
  check(item, { 'item ok': (r) => r.status === 200 });
}

And three process mistakes

  • Load testing without permission. Third-party APIs, payment gateways, CDNs and WAFs may block, bill or ban you. Stub third parties or agree a test window with them. Never load test a system you don't own or have written permission to test.
  • No monitoring on the system under test. k6 tells you that latency went up, not why. Have server, database and APM metrics running during the test. See the monitoring guide.
  • Changing three things between runs. If you change the code, the config and the load at once, you can't tell which one moved the result. Change one thing per run.
