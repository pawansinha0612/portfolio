k6 outputs and dashboards: see the test while it runs

The end-of-test summary says p95 was 400 ms. It doesn't say that p95 was 150 ms for 25 minutes and 4 seconds for the last five, when the connection pool ran dry. A summary is one number per metric. To find bottlenecks you need the time series.

You can use several at once: repeat --out.

The built-in web dashboard and HTML report

# Live dashboard on http://localhost:5665 while the test runs
K6_WEB_DASHBOARD=true k6 run script.js

# Also save a self-contained HTML report at the end
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=report.html k6 run script.js

# In CI: no server, just the report
K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_PORT=-1 K6_WEB_DASHBOARD_EXPORT=report.html k6 run script.js

Other settings: K6_WEB_DASHBOARD_OPEN=true opens a browser, K6_WEB_DASHBOARD_HOST and K6_WEB_DASHBOARD_PORT change where it listens, and K6_WEB_DASHBOARD_PERIOD (default 10s) sets how often it aggregates.

The report needs a run longer than three periods. A 20-second debug run with the default 10 s period logs "the test run was short, report generation was skipped" and writes no file. That's the usual reason a CI artifact is missing.

The report is one HTML file with charts over time. It's the quickest way to show a stakeholder what happened, and it's fine for a single run. For comparing runs, or lining up k6 latency with database CPU, you need a time-series database.

Custom summaries with handleSummary()

Export a handleSummary(data) function and k6 calls it at the end with every metric's aggregated values. Return an object of file name to content. stdout and stderr are special keys.

import http from 'k6/http';
import { textSummary } from 'https://jslib.k6.io/k6-summary/0.1.0/index.js';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = {
  vus: 5,
  duration: '1m',
  thresholds: { http_req_duration: ['p(95)<500'] },
};

export default function () {
  http.get(`${BASE_URL}/products`);
}

// Runs once at the end. Whatever you return replaces the default summary output.
export function handleSummary(data) {
  const p95 = data.metrics.http_req_duration.values['p(95)'];
  const failed = data.metrics.http_req_failed.values.rate;
  return {
    stdout: textSummary(data, { indent: ' ', enableColors: true }), // keep the console summary
    'summary.json': JSON.stringify(data, null, 2),                   // everything, for tooling
    'budget.md': `| p95 | failed |\n|---|---|\n| ${p95.toFixed(0)} ms | ${(failed * 100).toFixed(2)}% |\n`,
  };
}

Once you return anything, the default console summary is replaced, which is why the example returns textSummary() for stdout. In k6 v1.0 and later, --summary-mode=full adds per-group and per-scenario detail to the normal console summary, which is often enough on its own.

To turn a summary into findings, paste it into the k6 results analyser.

JSON and CSV files

k6 run --out json=results.json script.js
k6 run --out csv=results.csv script.js
k6 run --out json=results.json.gz script.js   # gzipped, by file extension

These contain every sample: one line per request per metric, with all its tags. That's complete and easy to post-process, and large: a 30-minute test at 1,000 requests a second writes tens of millions of lines. Use them for short runs, or gzip them and post-process with a script, jq or DuckDB. Each JSON line is either a Metric definition or a Point with a value and tags.

Prometheus remote write and Grafana

If your services are already monitored with Prometheus, push k6 metrics into the same place. Then one Grafana dashboard shows the load, the latency and the server's CPU, memory and pool saturation on the same time axis. That's where bottlenecks become obvious.

# Prometheus must accept remote writes: start it with --web.enable-remote-write-receiver
K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
K6_PROMETHEUS_RW_TREND_STATS='p(95),p(99),min,max' \
k6 run --out experimental-prometheus-rw --tag testid=checkout-2026-11-06 script.js
  • Metrics arrive with a k6_ prefix. Grafana publishes ready-made dashboards for this output: "k6 Prometheus" (ID 19665) and a native histogram version (ID 18030).
  • By default only p99 is sent for trends. Set K6_PROMETHEUS_RW_TREND_STATS to the stats you actually report.
  • Percentiles sent as gauges can't be combined. Each value is the p95 of one short window from one k6 process. Averaging them over time or across load generators does not give the p95 of the test. If you need correct percentiles over any time range, set K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true and run Prometheus with --enable-feature=native-histograms.
  • Add a testid tag on every run so you can filter and compare runs in Grafana.
  • The output name still says experimental, so its options can change between releases.

InfluxDB and others

# InfluxDB 1.x: built in
k6 run --out influxdb=http://localhost:8086/k6 script.js

InfluxDB 2.x and later needs the xk6-output-influxdb extension. OpenTelemetry is built in as --out opentelemetry in current k6 (in k6 v1.0 it was still called experimental-opentelemetry), configured with K6_OTEL_* environment variables. Datadog, New Relic, Dynatrace, Elasticsearch, Kafka, StatsD and others work through their own outputs or extensions.
