NeoLoad scenarios: from "500 users" to a workload

The brief says "test with 500 users". You put one User Path in a population, set a constant load of 500 for an hour, and press Run. Every user starts in the first second, logs in at once, and the authentication service falls over in a way it never does in production. A scenario is where you turn a headline number into a mix of journeys, a rate and a shape over time.

1. Populations: the mix

A population is a group of User Paths with a percentage each, adding up to 100%. For example, a "Retail banking" population might be 60% Check balance, 25% Transfer and 15% Pay bill. Build the percentages from production analytics, not guesses. See workload model.

populations:
- name: RetailBanking
  user_paths:
  - name: CheckBalance
    distribution: 60%
  - name: Transfer
    distribution: 25%
  - name: PayBill
    distribution: 15%

Use separate populations when journeys need different load shapes: steady browsing traffic in one, a batch-like burst of statement downloads in another. Each population in a scenario gets its own load policy.

2. Load policies

In the Runtime section, a scenario lists populations, each with one load policy:

PolicyShapeUse it for
ConstantA fixed number of users, optionally started gradually with a ramp-up delaySteady-state load and soak tests
Ramp-upStart with N users and add M every interval, up to an optional maximumFinding where response times bend, step tests, breakpoint tests
PeaksAlternate between a minimum and maximum phaseChecking the system recovers after peaks, see spike testing
CustomA list of points: user count at given times or iterationsReproducing a real day's curve or any shape the others can't express

The same policies in as-code, using the setting names from the neoload-models reference:

scenarios:
- name: PeakHour
  populations:
  - name: RetailBanking
    rampup_load:
      min_users: 50
      max_users: 500
      increment_users: 50
      increment_every: 2m
      increment_rampup: 30s
      duration: 60m
  - name: StatementDownloads
    constant_load:
      users: 40
      duration: 45m
      start_after: 15m
      rampup: 60s
      stop_after: current_iteration

Here the main population ramps from 50 to 500 users over 18 minutes in steps of 50, spreading each step's new users over 30 seconds, then holds until 60 minutes. A second population of 40 users starts 15 minutes in. A peaks policy uses minimum and maximum phases (each with users and duration) and a start phase, and a custom policy uses a list of steps with when and users. This is a sketch built from the reference: run neoload validate before you rely on it.

3. Duration, start and stop

  • Duration can be unlimited, a time or a number of iterations. Time-based is the usual choice for load tests. Iteration-based suits data-driven runs where each row must be used once.
  • Start policy: start with the test, after a delay, or after another population finishes. Useful for "batch job starts at minute 20 while online traffic continues".
  • Ramp-up delay: start new users simultaneously or spread over a delay. Never start hundreds of users in the same second unless that is the scenario you are testing.
  • Stop policy: stop immediately, give users a set time to finish, or let each finish its current iteration. Letting iterations finish avoids a burst of half-done journeys and false errors at the end.
  • Monitoring before and after: scenarios can keep monitors running before and after the load, so you see the system's baseline and its recovery.

Report on the steady state, after the ramp and before the stop, and filter the results to that window.

4. Getting the rate right

Users are a closed workload: each user waits for a response before going on. The rate you generate depends on response time, think time and pacing. Set pacing on the Actions container so each user runs at a known rate, then size users with Little's Law:

Target 3,600 transfers per hour = 1 per second. With pacing of 90 seconds per Transfer iteration, you need 1 × 90 = 90 users on the Transfer path. If Transfer is 25% of the population, the population needs 360 users in total, and the other paths' pacing should be set so they hit their own targets.

Check in the results that achieved throughput matched the target. If iterations take longer than the pacing, users fall behind and the test ran a lighter load than you planned. The workload model tool does this arithmetic for several journeys at once. For why closed models can understate trouble, see open vs closed workload models.

5. Load generators and zones

  • From the GUI, assign generators to each population in the scenario. A local generator is fine for checks. For real load use remote generators.
  • From NeoLoad Web or the CLI, choose a zone and a generator count in the test settings. Dynamic zones start generator containers on demand.
  • Watch generator CPU and memory. NeoLoad monitors its generators. Keep CPU well under saturation, a generator at 100% adds its own delay to every response time.
  • Size by protocol. HTTP users are cheap. Browser-based and packaged-application users (Citrix, SAP GUI) are far heavier. Calibrate with a small run per generator.
  • Place generators deliberately. Inside the data centre tests the backend. Outside, through the WAN and CDN, tests what users experience. Both are valid, but decide which question you are answering.

6. Rendezvous policies

A Rendezvous action in a User Path makes users wait until a share of them arrive, and the scenario's rendezvous policy decides when to release them (for example when 50% have arrived, with a timeout). It looks like the way to test "everyone clicks Pay at once", but real users don't synchronise to the millisecond, and waiting users distort the rest of the workload. For bursts, use a peaks or custom load policy, or a short population with a steep ramp. Keep rendezvous for genuine concurrency tests, such as two users updating the same record to test locking.

7. Pre-run checklist

  • Every User Path passes Check User Path with several different data rows.
  • Variables use the right scope (Unique for owned data) and files are sized for the run.
  • Pacing set, think times realistic, ramp-up spread out.
  • SLA profiles attached, so the run produces a pass or fail. See analysis and SLAs.
  • Server monitors or APM integration ready, clocks aligned. See monitoring during a test.
  • A short smoke run of the full scenario before the real one.
