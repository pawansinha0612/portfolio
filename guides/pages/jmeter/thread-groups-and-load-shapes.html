JMeter thread groups: shape the load on purpose

You set 1,000 threads with a 10-second ramp-up to "see what happens". 100 new users per second all log in at once, the login service queues, and the test measures a thundering herd that never happens in production. The thread group decides the shape of the load. Pick the shape first, then the element that draws it.

1. The standard Thread Group

FieldWhat it does
Action to be taken after a Sampler errorContinue, Start Next Thread Loop, Stop Thread, Stop Test, Stop Test Now. Use Start Next Thread Loop when a failed step makes the rest of the iteration meaningless (no basket ID, no checkout)
Number of Threads (users)Concurrent virtual users
Ramp-up period (seconds)Time to start all threads
Loop Count / InfiniteIterations per thread. For timed tests tick Infinite and set a duration
Same user on each iterationKeep cookies, cache and connections between iterations. Untick to simulate a new visitor each loop (new connections cost more)
Delay Thread creation until neededCreate threads when they are due rather than all at start. Saves memory for long ramps
Specify Thread lifetimeDuration (seconds) and Startup delay (seconds). Duration includes the ramp-up

Drive all of these from properties so one plan serves smoke, load and soak runs:

Number of Threads:  ${__P(users,1)}
Ramp-up period:     ${__P(rampup,1)}
Loop Count:         Infinite
Duration (seconds): ${__P(duration,60)}

jmeter -n -t plan.jmx -Jusers=300 -Jrampup=600 -Jduration=3600 -l results.jtl

When the duration ends, JMeter stops each thread after its current sample. It does not interrupt a sampler that is waiting for a response, so a hung request can delay the end of the test.

2. Ramp-up maths

JMeter starts the first thread at once and spaces the rest evenly: thread k starts at (k − 1) × ramp-up ÷ threads seconds.

10 threads, ramp-up 100 s  → one thread every 10 s, the 10th starts at 90 s
300 threads, ramp-up 600 s → one thread every 2 s, full load at about 598 s
1 thread, any ramp-up       → starts immediately

Choosing a ramp-up:

  • Arrival rate of new sessions. 300 threads over 600 s is 0.5 new sessions per second. If every thread logs in first, that is also your login rate during ramp-up. Check it against what the identity service sees at peak.
  • Warm-up. JIT compilation, connection pools and caches need time. Give the system a ramp it would see in real life, then treat the ramp as warm-up and analyse only the steady state. The HTML report can be cut to a time window with the jmeter.reportgenerator.start_date and end_date properties.
  • Finding the knee. A slow linear ramp to well above the expected peak shows where response times start to bend. A step shape (below) makes the knee easier to read, because each level holds long enough to settle.

Ramp-up controls when threads start, not the request rate. With no think time, each new thread adds as much load as the server will serve it, so the rate during ramp-up depends on response times. See ramp-up and think time and pacing.

3. Workload mix with several groups

Real traffic is a mix. Model each user type as its own thread group with its own threads, think time and data:

Test Plan
├── Thread Group "Browsers"   ${__P(browsers,140)} threads   search, view product   think 5–10 s
├── Thread Group "Buyers"     ${__P(buyers,40)} threads      add to basket, checkout think 8–15 s
└── Thread Group "Back office" ${__P(admins,5)} threads      reports, refunds        think 20–40 s

Thread groups run in parallel unless you tick Run Thread Groups consecutively on the Test Plan. Inside one group, a Throughput Controller (Percent Executions) or a Switch Controller with a random value can split iterations between paths, for example 5% of browsers also leave a review. Derive the percentages from production analytics, not from guesswork. The glossary entry on workload models covers how.

4. Custom Thread Groups (plugin)

These come from the Custom Thread Groups plugin on jmeter-plugins.org (plugin id jpgc-casutg). They are not part of Apache JMeter. Install through Options → Plugins Manager, or on a headless machine:

# with the Plugins Manager jar already in lib/ext
bin/PluginsManagerCMD.sh install jpgc-casutg

A plan that uses them will not open on a machine without the plugin, so install it on CI runners and every remote node too.

Concurrency Thread Group

The one to reach for in most step and soak tests. It keeps a target concurrency, starts threads as needed rather than all up front, and replaces a thread that finishes.

FieldExample: step test to 200 users
Target Concurrency200
Ramp Up Time10 (minutes, per the Time Unit selector)
Ramp-Up Steps Count5 → +40 users every 2 minutes
Hold Target Rate Time20 minutes at 200
Thread Iterations LimitEmpty (unlimited)

The preview graph updates as you type, which makes it easy to sanity-check the shape before a run. Paired with the Throughput Shaping Timer, Target Concurrency can be set to ${__tstFeedback(timerName,10,500,10)} so the plugin adds threads as needed to hold a requests-per-second schedule. Read the plugin's documentation for the exact arguments.

Stepping Thread Group

The original LoadRunner-style step group: start N threads every M seconds, hold, then stop in steps. The plugin's own documentation now points to the Concurrency Thread Group as the better alternative. Keep it for old plans, use Concurrency for new ones.

Ultimate Thread Group

A table of rows, each with Start Threads Count, Initial Delay, Startup Time, Hold Load For and Shutdown Time (seconds). Rows overlap, so you can draw almost any shape, including spikes on top of a baseline:

Start Threads  Initial Delay  Startup Time  Hold Load For  Shutdown Time
100            0              300           3300           60      ← baseline for an hour
300            1200           30            120            30      ← spike at minute 20

The same schedule can come from the threads_schedule property, for example -Jthreads_schedule="spawn(100,0s,5m,55m,1m) spawn(300,20m,30s,2m,30s)", which keeps shapes out of the .jmx.

Arrivals and Free-Form Arrivals Thread Groups

These schedule iteration starts (arrivals) rather than threads. If all threads are busy, the group creates more. That is an open model: the arrival rate holds even when the server slows. Always fill in Concurrency Limit, because a slow system plus a constant arrival rate means ever more concurrent threads and eventually an out-of-memory error on the load generator. Free-Form Arrivals lets you define the rate as a table of segments.

5. Open Model Thread Group (core)

Since JMeter 5.5, core JMeter has its own open-model group, marked experimental in the 5.6 documentation. You write the schedule as text:

rate(0) random_arrivals(5 min) rate(40/sec)    // ramp from 0 to 40 arrivals per second
random_arrivals(30 min)                          // hold 40/sec for 30 minutes
rate(40/sec) random_arrivals(5 min) rate(0)      // ramp down
pause(2 min)                                     // let in-flight iterations finish

Units are ms, sec, min, hour and day. Properties work inside it: rate(${__P(rps,10)}/sec) random_arrivals(${__P(mins,10)} min). The schedule is read once at test start. Threads are interrupted when the schedule ends, which is why the trailing pause matters. It does not offer a concurrency cap, so watch the generator's memory during long, slow runs.

6. Which shape, which element

TestShapeGood fit
Smoke1–5 users for a few minutesStandard Thread Group
LoadRamp to expected peak, hold 30–60 minStandard or Concurrency, or Open Model for arrival rates
Stress / breakpointSteps above peak until something givesConcurrency (steps) or Open Model with rising rate
SpikeBaseline, sudden jump, back to baselineUltimate Thread Group, or two groups with a Startup delay
SoakRealistic load for hoursConcurrency or standard with Duration, with pacing

The load profiles explainer lets you draw these shapes and export them as k6 scenarios, which is a quick way to agree a shape with stakeholders before building it in JMeter.
