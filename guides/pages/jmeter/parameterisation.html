JMeter parameterisation: 500 users, not one user 500 times

Your test logs in as the same account from 500 threads and searches for the same product every time. The database serves everything from cache, the account lock-out kicks in at minute three, and the report says the system is fast. Parameterisation gives each virtual user its own data so the server does real work.

1. CSV Data Set Config

The workhorse. Prepare a file such as data/users.csv:

username,password,postcode
ana.k@example.test,Pa55-0001,3000
ben.t@example.test,Pa55-0002,3121
chloe.w@example.test,Pa55-0003,3056

Add it with Thread Group → Add → Config Element → CSV Data Set Config:

FieldSettingNotes
Filenamedata/users.csvRelative paths resolve from the .jmx file's folder. Avoid absolute paths, they break on CI and remote nodes
File encodingUTF-8Set it explicitly, the platform default differs between Windows and Linux
Variable Names(empty)Empty means "read names from the header line". Or list them: username,password,postcode
Ignore first lineFalseOnly applies when Variable Names is filled in. Set True then, so the header is not used as data
Delimiter,Use \t for tab-separated files
Allow quoted data?FalseSet True if values contain the delimiter: "Smith, Jo"
Recycle on EOF?See below
Stop thread on EOF?See below
Sharing modeAll threadsSee below

Then use ${username}, ${password} and ${postcode} in samplers. A new line is read at the start of each thread iteration, not on each request. So one iteration of the scenario sees one consistent row.

2. Sharing mode and EOF behaviour

Sharing modeBehaviourUse it for
All threads (default)One file pointer for the whole test. Each iteration of any thread takes the next lineUnique data across the test, e.g. one account per login
Current thread groupOne pointer per thread group that contains the elementTwo groups reading the same file independently
Current threadEvery thread reads the file from the topPer-thread files, e.g. user${__threadNum}.csv
Identifier (type any text)Elements with the same identifier share a pointerSharing one pointer across selected thread groups
Recycle on EOFStop thread on EOFAt the end of the file
True (default)ignoredStart again from line 1. Data is reused
FalseTrueThe thread stops. Use for "each row exactly once", such as single-use vouchers
FalseFalse (default)Every variable becomes <EOF> and requests carry that text. Almost never what you want

Size the file for the test, not the smoke run. A 1-hour test at 50 iterations per second needs 180,000 rows if every iteration must be unique. With "Stop thread on EOF", a short file quietly ends the test early and the report shows a throughput drop that looks like a server problem.

For distributed tests, each remote node reads its own local copy of the file. Give every node a different slice, or all nodes will log in as the same users.

3. Generated data: __Random, __UUID, __time

Functions are written as ${__name(arg1,arg2)} and are evaluated each time the field is used. Escape a literal comma inside an argument as \,.

FunctionReturns
${__Random(1,500)}Integer from 1 to 500 inclusive
${__Random(1,500,qty)}Same, and stores it in ${qty} for reuse
${__RandomString(8,abcdef0123456789)}8 characters from the given set
${__UUID()}A random type 4 UUID, e.g. for idempotency keys or correlation IDs
${__time()}Current time in epoch milliseconds
${__time(/1000)}Epoch seconds
${__time(yyyy-MM-dd'T'HH:mm:ss)}Formatted with Java DateTimeFormatter patterns
${__timeShift(yyyy-MM-dd,,P7D,,)}Today plus 7 days, e.g. a booking date
${__RandomDate(yyyy-MM-dd,2026-01-01,2026-12-31,,)}Random date in a range
${__threadNum}Thread number within its thread group, from 1
${__counter(FALSE,)}Global counter shared by all threads (TRUE gives one per thread)
${__RandomFromMultipleVars(skus)}Random value from an extractor's skus_1..N results

Generating unique values at run time costs CPU on the load generator. For large volumes, prepare data in advance and combine it with a cheap run-time element, for example order-${__time()}-${__threadNum}.

Random is not the same as realistic. Real traffic is skewed: a small share of products gets most of the views. A uniform __Random over 50,000 products defeats every cache, so it often tests worse than production. Build the CSV from real access patterns where you can, with popular items appearing more often.

4. User Defined Variables

For constants used across the plan (base path, API version, tenant), use the table on the Test Plan element or Add → Config Element → User Defined Variables.

Name          Value
apiBase       /api/v2
tenant        ${__P(tenant,demo)}
thinkMs       ${__P(think,3000)}

These are evaluated once at the start, so they are cheap but not dynamic. Do not put __Random in a User Defined Variable expecting a new number per request. Put the function directly in the sampler field instead.

5. Properties: -J and __P

Variables belong to a thread. Properties belong to the JMeter process and are the way to pass settings in from outside. Set them on the command line or in a file:

jmeter -n -t plan.jmx -Jusers=200 -Jrampup=300 -Jhost=staging.example.com -l results.jtl

# or keep environments in files and load one with -q
jmeter -n -t plan.jmx -q env/staging.properties -l results.jtl
# env/staging.properties
host=staging.example.com
users=200
rampup=300
duration=1800

Read them in the plan:

${__P(users,10)}                  value of "users", or 10 if not set
${__P(host)}                      no default: returns 1 if unset (rarely what you want)
${__property(host,,localhost)}    long form: name, variable to save in, default

Always give __P a default. Without one it returns 1, which is handy for a thread count but sends requests to a host called "1" if you forget -Jhost. On remote nodes use -G instead of -J so the property is sent to every server.

6. Data design rules

  • One row per iteration, consistent within it. Username, password and the account's own order ID belong on the same row.
  • Single-use data needs a plan. Vouchers, one-time passwords and "register new user" consume data. Use Stop thread on EOF, size the file, and have a reset script for the environment.
  • Match the production mix. If 70% of real searches return results, a CSV where every search term hits is optimistic.
  • Keep secrets out of git. Pass passwords and client secrets with -J from a CI secret, not in the CSV or .jmx.
  • Watch the test, not just the server. A <EOF> or ${username} in a request body means the data broke, not the system.
