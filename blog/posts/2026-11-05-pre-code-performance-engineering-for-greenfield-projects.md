## Introduction\n\nGreenfield projects give performance engineers a clean slate.\nYet the first line of code can lock in a capacity ceiling that is hard to lift later.\nBy treating performance as a first‑class requirement—measurable NFRs, hop budgets, a queueing‑based capacity model, a risk review and a scaling test strategy—you lock in a system that can grow without hidden regressions.\n\n## Measurable NFRs\n\nNFRs are not wish lists; they are metrics that can be asserted in a test.\nTypical measurable NFRs for a service that expects 1 M requests per day are:\n\n| NFR | Metric | Target | Rationale |\n|-----|--------|--------|------------|\n| Latency | 95th percentile response time | 200 ms | Meets user experience thresholds |\n| Throughput | Requests per second | 1 200 req/s | Sustains peak traffic |\n| Error rate | 5xx responses | < 0.1 % | Prevents cascading failures |\n| CPU utilisation | Average | < 70 % | Leaves headroom for spikes |\n| Memory utilisation | Peak | < 80 % of node | Avoids OOM kills |\n\nDefine each metric with a unit, a percentile or a rate.\nUse a single source of truth: a monitoring system that can be queried via an API.\nFor example, Prometheus can expose `http_request_duration_seconds_bucket{quantile=\"0.95\"}`.\n\n## Latency Budgets per Hop\n\nA *hop* is a logical boundary a request crosses: client → CDN → load balancer → API gateway → service → database → disk → network.\nA *latency budget* is the maximum time you allow each hop to consume before the end‑user sees a penalty.\nAllocate budgets by percentage of the overall target, but adjust for the hop’s inherent variance.\n\n### Example Budget\n\n| Hop | Budget | Reason |\n|-----|--------|--------|\n| CDN | 50 ms | Edge caching is fast; 20 % of 200 ms |\n| Load Balancer | 20 ms | Simple TCP handshake |\n| API Gateway | 100 ms | Business logic + auth |\n| Service | 30 ms | Core processing |\n| Database | 10 ms | Optimised query |\n| Disk | 10 ms | SSD read |\n| Network | 10 ms | Inter‑AZ latency |\n\nSum = 200 ms.\nIf any hop exceeds its budget, you know where to focus optimisation.\nUse the latency histogram from your instrumentation to detect *coordinated omission*: if a request is queued, the measured latency is longer than the actual processing time. Mitigate by enabling `--latency` flag in k6 or by using a queue‑aware profiler.\n\n## Capacity Model\n\nA capacity model predicts how many instances you need to satisfy the NFRs.\nQueueing theory gives you the tools.\nFor a single‑threaded service, an M/M/1 model suffices:\n\n```
L = λ / (μ - λ)
```
Where `L` is the average number of requests in system, `λ` is arrival rate, `μ` is service rate.\nIf `λ = 1 200 req/s` and you aim for `μ = 2 500 req/s` (service time 400 µs), then\n\n```
L = 1200 / (2500 - 1200) = 0.92 requests
```
You are comfortably below saturation.\nIf you have `c` parallel workers, use an M/M/c model:\n\n```
W = (C(ρ, c) * ρ^c) / (c! * (1-ρ)^2) * (1/μ)
```
Where `ρ = λ / (c * μ)` and `C(ρ, c)` is Erlang‑C formula.\nPlug in your numbers to estimate average waiting time `W`.\nIf `W` exceeds the allocated latency budget for the service hop, increase `c`.\n\n**Detecting bottlenecks**: use a profiler that reports *off‑CPU time* and *safepoint bias*.\nIf a thread spends most of its time in GC safepoints, the service rate `μ` collapses.\nAdjust `-XX:+UseG1GC` or reduce object churn.\n\n## Architecture Risk Review\n\nA risk review is a checklist of architectural decisions that can become performance traps.\n| Risk | Indicator | Mitigation |\n|------|------------|------------|\n| Single point of failure | One load balancer node | Deploy HA pair |\n| Resource contention | Shared database connection pool | Separate pools per service |\n| Cold start latency | Serverless function > 300 ms | Warm‑up strategy |\n| Ops overhead | Manual scaling | Auto‑scaling policy |\n| Cloud limits | API rate limits | Exponential backoff |\n\nFor each risk, ask: *What is the worst‑case latency contribution?*\nIf a risk adds 30 ms to a hop, you may need to re‑budget or redesign.\n\n## Test Strategy That Grows\n\nPerformance testing should evolve with the system.\nStart with a *smoke test* that asserts the latency budget for a single request.\nThen layer:\n\n| Test type | Frequency | Tool | Focus |\n|-----------|-----------|------|-------|\n| Unit perf | CI | k6 (single request) | Hot path code |\n| Integration | CI | k6 + Docker | Service boundaries |\n| Load | Weekly | k6 + Grafana | Sustained throughput |\n| Stress | Monthly | k6 + Chaos | Limits and resilience |\n| Chaos | On‑call | Gremlin | Failure modes |\n\nAutomate the smoke test in the CI pipeline.\nUse k6’s `--out csv` to feed a histogram into Grafana, then alert if the 95th percentile exceeds the hop budget.\n\n**Data‑driven regression**: keep a baseline CSV.\nWhen a new deployment runs, compare the new histogram to baseline using `k6 stats compare`.\nIf the 99th percentile rises by > 10 %, investigate.\n\n## Checklist Before First Line\n\n1. Define measurable NFRs – latency, throughput, error rate, utilisation.\n2. Allocate latency budgets per hop – client, CDN, LB, gateway, service, DB, disk, network.\n3. Build a capacity model – start with M/M/1, move to M/M/c as parallelism grows.\n4. Conduct architecture risk review – identify single points, contention, cold starts.\n5. Draft a test strategy – unit, integration, load, stress, chaos.\n6. Set up monitoring – Prometheus + Grafana, k6 CSV, alerting on budget breaches.\n7. Automate smoke test – CI pipeline triggers k6 single‑request test.\n8. Document assumptions – service rate, queue discipline, network latency.\n\nWhen you hit the first commit, the system already has a performance contract and a path to prove it.\n\n## Conclusion\n\nGreenfield projects are tempting to optimise for code rather than capacity.\nBy treating performance as a first‑class requirement—measurable NFRs, hop budgets, a queueing‑based capacity model, a risk review and a scaling test strategy—you lock in a system that can grow without hidden regressions.\nStart with the checklist above and let the data guide every optimisation.
