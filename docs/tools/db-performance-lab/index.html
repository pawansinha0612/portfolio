How it works

From a wall of plan text to the one change that matters

  1. Parse. The plan becomes a tree of nodes with estimated and actual rows, loops, time, buffers and conditions. Indentation decides the tree in text plans.
  2. Exclusive time. Each node's time times its loops, minus its children. Under a parallel Gather, time is divided by the number of processes that ran it, so shares stay honest.
  3. Misestimates. Estimated versus actual rows per loop. Only the deepest wrong estimate in a chain is reported, because errors spread upwards.
  4. Rules. Each finding is a written rule: a full scan that keeps under 10% of 10,000+ rows, a nested loop running 1,000+ times, a sort or hash on disk, a lossy bitmap, a key lookup, missing parallel workers, slow JIT or planning. Each quotes the numbers that triggered it.
  5. Fixes. Index suggestions put equality columns first and only one range column after them, add INCLUDE columns where they avoid lookups, and use expression indexes or range rewrites for functions on columns.

Getting a plan

  • PostgreSQL: EXPLAIN (ANALYZE, BUFFERS) SELECT …; in psql, or add FORMAT JSON. ANALYZE runs the query, so wrap writes in BEGIN; … ROLLBACK;. For queries in production, auto_explain logs plans of slow statements.
  • MySQL 8: EXPLAIN ANALYZE SELECT …; (runs the query) or EXPLAIN FORMAT=JSON SELECT …; (estimates only). Use \G or the mysql client's raw output so the tree keeps its indentation.
  • SQL Server: in SSMS, turn on Include Actual Execution Plan (Ctrl+M), run the query, right-click the plan and choose Show Execution Plan XML or save it as .sqlplan.
  • Statistics: \copy (SELECT * FROM pg_stat_statements) TO 'stats.csv' CSV HEADER; for MySQL, export performance_schema.events_statements_summary_by_digest or mysql.slow_log, or drop the slow query log file itself.

FAQ

Is my query plan uploaded anywhere?

No. The plan, the SQL and any file you choose are read and analysed in your browser. Plans contain table names, column names and sometimes literal values, so nothing is sent to a server.

Which plan formats does it read?

PostgreSQL EXPLAIN in text and FORMAT JSON, ideally with ANALYZE and BUFFERS; MySQL EXPLAIN ANALYZE and FORMAT=TREE output and EXPLAIN FORMAT=JSON (version 1 and 2); and SQL Server showplan XML (.sqlplan) with basic support. It also reads pg_stat_statements, MySQL performance_schema and slow_log exports and SQL Server query stats as CSV, and the MySQL slow query log file.

What does SQL Server basic support cover?

The operator tree, estimated and actual rows, executions, elapsed time and logical reads per operator, predicates, key and RID lookups, tempdb spills, missing index suggestions, implicit conversions, no-join-predicate warnings and memory grants. It analyses the most expensive statement in a batch. It does not show parallelism per thread or batch-mode details beyond operator time.

What is the difference between exclusive and inclusive time?

Inclusive time is what a plan node reports: its own work plus everything below it. Exclusive time subtracts the children, so it shows the work the node itself did. The node with the biggest exclusive time is where to start. Times are multiplied by loops, because PostgreSQL and MySQL report the average for one loop.

Why does a row misestimate matter?

The planner chooses join methods, join order and memory from its row estimates. If it expects 10 rows and gets 100,000, it may pick a nested loop that runs 100,000 times or a hash table that spills to disk. Fresh statistics (ANALYZE), extended statistics for related columns or histograms usually fix it.
