How it works

The four numbers behind any capacity plan

1. Little's Law

The number of users in a system equals how fast they arrive times how long each one stays:

virtual users = throughput × (response time + think time) 50 iterations/s × (0.8 s + 5 s) = 290 users

That's for a closed model (a fixed pool of users with think time). An arrival-rate test (k6's constant-arrival-rate) fixes the throughput instead, so it keeps the pressure on when the system slows down, which is what real traffic does.

2. Peak-hour factor

Traffic is never spread evenly. Retail often sees 15–30% of a day's orders in the busiest hour, and the busiest minute inside that hour runs another 2–3× above the hour's average. Size for the peak minute, not the daily average: averages are how systems pass a test and fall over at 8pm.

3. Headroom

Plan for CPU around 60–70% at peak. Above that, queueing makes response times climb steeply, and you need spare capacity for a node failing or a deploy rolling pods. Then prove it: run the load test at 1.5–2× the forecast peak.

4. The event multiplier

Black Friday, a ticket release or a TV ad isn't a busier normal day. Peaks of 3–10× normal traffic are common, they arrive in minutes, and they hit the paths that are hardest to scale: search, cart, checkout and payment. Multiply orders per day by your expected uplift and check the database connection line first, because it's usually the first limit you hit.

FAQ

Should I use virtual users or arrival rate?

Arrival rate for anything that models real users hitting a website or API: they don't wait for your server before clicking. Virtual users suit fixed-size client pools, like batch workers or a mobile app with a known number of connected devices.

Where do I get the CPU cost per request?

From a short load test: CPU seconds used divided by requests served, at a steady rate. Until then the default of 15 ms is a reasonable guess for a typical JSON API.

Why does the database connection count matter so much?

Every pod opens its own pool. Scale out from 10 to 40 pods and the database suddenly sees four times the connections, and many managed databases cap them in the low hundreds. Autoscaling the app can take the database down.
