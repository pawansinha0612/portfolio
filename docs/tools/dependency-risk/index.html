    How it works
    
      
    Know what you ship
    
      
    A typical web app pulls in hundreds of open source packages, most of them through other packages. Any one of them can carry a known security hole, stop being maintained, or come with a licence that does not suit your business.
    
      
      
        
    1. Read the files. Each format is parsed in your browser into a list of packages with exact versions, marked direct or transitive and runtime or dev-only.
      2. 
        
    2. Check known vulnerabilities. The names and versions go to OSV.dev in one batch. Each match comes back with its severity and the versions that fix it.
      3. 
        
    3. Check freshness and licences. For npm and PyPI packages, the public registries give the latest version, deprecation notices and the licence.
      4. 
        
    4. Plan the upgrades. Security fixes first, worst first. The smallest upgrade that fixes every known issue is suggested, and majors are flagged because they can break things.

    Reading the risk score
    
      
    Each package scores up to 100 from its worst vulnerability, deprecation, how far behind it is and its licence. Transitive and dev-only packages count for less, because they are harder to reach or never ship. The project score adds these up: under 20 is low, 20–49 medium, 50–79 high, 80 and over critical.
    

      
    FAQ
    
      
    What is sent over the internet?
    
      
    Your files are read in the browser and never uploaded. Only when you press Check online, package names, versions and ecosystems are sent to api.osv.dev, and the names of npm and PyPI packages to registry.npmjs.org and pypi.org. No file content, project name or paths are sent.
    
      
    Where does the vulnerability data come from?
    
      
    From OSV.dev, Google's free open source vulnerability database. It combines the GitHub Advisory Database, the Python, Go and Rust advisory databases and others, and lists the versions that fix each issue.
    
      
    Which files can I use?
    
      
    package.json, package-lock.json, yarn.lock, requirements.txt, poetry.lock, pom.xml, build.gradle, go.mod, Gemfile.lock, composer.lock and .csproj files. Lockfiles are best because they list the exact versions you install, including transitive packages.
    
      
    Why does it say latest unknown for some packages?
    
      
    The npm and PyPI registries allow a web page to ask for the latest version. Maven Central, Go, RubyGems, Packagist and NuGet do not, so for those ecosystems the latest version is not shown. Vulnerability checks work for all of them.
    
      
    How is the upgrade plan ordered?
    
      
    Security fixes come first, worst severity first. Within each group, patch and minor upgrades, which rarely break anything, come before major upgrades, which are flagged. Then deprecated packages, then plain updates.
