    How it works

    Coverage tells you what ran, not what is safe

    80% coverage sounds good until the missing 20% is the payment code that changes every week. This tool puts coverage next to the other things that predict where bugs come from.

    1. Read the coverage. Line and branch counts for every file, from any of the common formats. Long CI runner paths are shortened to the repository root.
    2. Add the context you have. Test results show what is failing or flaky. Git history shows what changes often. Requirements show what the business expects to be tested.
    3. Rank the risk. Each file gets a 0–100 score: untested share × change frequency × size, plus weight for failing and flaky tests. The top of the list is where a new test pays off most.
    4. Compare and gate. Against a baseline report you see the coverage change and the newly untested lines. The CI snippets turn today's numbers into a gate so coverage can only go up.

    Getting the files

    • Jest / Vitest: --coverage with the lcov and json-summary reporters writes coverage/lcov.info.
    • Python: pytest --cov=src --cov-branch --cov-report=xml writes coverage.xml (Cobertura).
    • Java / Kotlin: the JaCoCo plugin writes target/site/jacoco/jacoco.xml (Maven) or build/reports/jacoco/test/jacocoTestReport.xml (Gradle).
    • .NET: dotnet test --collect:"XPlat Code Coverage" writes Cobertura XML.

    FAQ

    Is my coverage report uploaded anywhere?

    No. Coverage reports, test results and git history are read and analysed in your browser. Nothing is sent to a server or an AI model.

    Which coverage formats does it read?

    LCOV (lcov.info from Jest, Vitest, c8, nyc, Karma, gcov and others), Cobertura XML (coverage.py, pytest-cov, .NET Coverlet, many CI tools), JaCoCo XML (Java and Kotlin), and Istanbul coverage-summary.json or coverage-final.json.

    How is the risk score worked out?

    For each file: the share of code that no test runs, multiplied by how often the file changed (from git log --numstat) and by its size, plus extra weight when failing or flaky tests point at it. Code that is big, changes often and has few tests is where bugs usually come from.

    What coverage percentage should we aim for?

    There is no magic number. A gate that stops coverage going down, plus a stricter gate of around 80% on the lines each pull request changes, works better than a single high target that teams game with weak tests.

    How does it link tests to requirements?

    Either load a CSV of requirement IDs and test names, or tag tests with the requirement ID, for example @REQ-123 in the test title. A requirement with no test that ran is listed as untested.
