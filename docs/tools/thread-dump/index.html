Java thread dump analyser

Paste or drop one or more thread dumps from jstack, jcmd Thread.print or kill -3. See which threads are stuck where, who holds the lock everyone is waiting for, whether there is a deadlock, and which pool ran dry.

🔒 Runs 100% in your browser. Nothing is uploaded or stored. Thread dumps contain internal class, host and sometimes user names, so they never leave this page.

One dump or several taken a few seconds apart (paste them one after another, or drop several files). HotSpot format from JDK 6 to 25; jcmd Thread.dump_to_file text or JSON (includes virtual threads); OpenJ9 javacore best effort.

    How to capture

    Take 3 dumps, 5–10 seconds apart, while it is slow

    One dump is a photo: a thread caught in a database call might have been there for 2 ms or 2 minutes. Three dumps a few seconds apart show which threads did not move. Take them during the slowdown or load test, not after.

    With jcmd or jstack (same host, same user as the JVM)

    jcmd                                  # list Java processes and their PIDs
for i in 1 2 3; do jcmd <pid> Thread.print -l > dump-$i.txt; sleep 7; done

jstack -l <pid> > dump.txt               # older equivalent; -l adds ownable synchronizers

    With kill -3 (no JDK tools installed)

    kill -3 <pid>     # the dump goes to the JVM's stdout: the console log, catalina.out, or container logs

    In Docker or Kubernetes

    kubectl exec <pod> -c <container> -- jcmd 1 Thread.print -l > dump-1.txt
docker exec <container> jcmd 1 Thread.print -l > dump-1.txt
# JRE-only image? kubectl exec <pod> -- kill -3 1, then kubectl logs <pod>

    Virtual threads (JDK 21+)

    jstack only shows platform threads. To include virtual threads: jcmd <pid> Thread.dump_to_file -format=json threads.json, then drop the file here.

    What to look for

    Reading a thread dump in five minutes

    1. The biggest group of identical stacks. Healthy apps have idle workers waiting for tasks. Problems show up as dozens or hundreds of busy threads in the same frame: an exhausted connection pool (HikariPool.getConnection), a slow downstream (socketRead0, NioSocketImpl.read), or one lock.
    2. BLOCKED threads and who they wait for. The lock table shows each monitor's holder. If the holder is doing I/O inside synchronized, that is your lock contention.
    3. Pool saturation. If every thread in the request pool is busy, new requests queue. Before raising the size of the thread pool, check what they are waiting on: more threads behind a shared bottleneck only makes the queue longer.
    4. Deadlocks. The JVM detects monitor and ReentrantLock deadlocks and prints "Found one Java-level deadlock". This tool shows that section and also checks the lock graph itself.
    5. Busy GC threads. If the GC threads have used a big share of CPU, the problem may be memory, not threads: see GC pauses, memory leaks and the GC log analyser.

    What this can't tell you

    "RUNNABLE" only means the JVM is not blocking the thread; a thread waiting on a socket is RUNNABLE too. A dump shows where threads are, not why a downstream is slow. Hints point at likely causes; confirm them with metrics (pool usage, DB slow-query logs, CPU per thread with top -H) from the same moment.
