    How it works

    Test design rules, written down

    Everything here follows standard test design techniques (ISTQB-style) applied by rules, not guesses. You get a solid first draft in seconds, then use your judgement to edit it.

    1. Scenarios. Each requirement gets a happy path and one check per acceptance criterion. Words in the text add more: login, email, payment, upload, date, search and duplicates add matching negative tests; roles add permission tests; form words add empty and whitespace checks; and performance, security and accessibility prompts appear only when the requirement hints at them.
    2. Boundaries. Limits such as between 8 and 64 characters give 7, 8, 9, 63, 64 and 65. at least 18 gives 17, 18 and 19. Equivalence classes add one typical valid value and the invalid classes on each side.
    3. Strategy. Exit criteria tighten with risk (90% pass for low risk, 100% for regulated work), defect fix targets shorten, and fast release cadences shift the automation advice.
    4. Estimate. Bottom-up hours for design, execution per cycle, automation build and upkeep, defect retests, regression, setup and management. PERT turns the range into an expected value: E = (O + 4M + P) / 6, with a 95% figure of E + 1.645σ.
    5. Release risk. Up to 35 points for missing checks, 30 for open defects (25 for each critical), 15 for coverage gaps, 10 for failed tests, 10 for flaky tests and 5 for a large release. Under 30 is a go; 30 to 59 is a go with conditions; 60 or more, an open critical defect, coverage under 60% or a pass rate under 85% is a no-go.

    Importing into Jira

    Zephyr Scale: Tests → Import → CSV, then map Name, Precondition, Action (step), Data, Expected Result, Priority and Labels. Xray: Test Case Importer → CSV, with Action, Data and Result as the step columns. The Requirement column holds the requirement ID so you can link the tests after import.

    FAQ

    Does it use AI, and is my data uploaded?

    No to both. Every result comes from written rules that run in your browser, so the same input always gives the same output and nothing is sent anywhere. The coverage tracker is saved in this browser's local storage only.

    What requirement formats can I paste?

    User stories (As a … I want … so that …) with acceptance criteria, Gherkin features and scenarios, and plain requirement lines with must, should or shall. IDs such as REQ-12, US-3 or Jira keys at the start of a line are kept.

    How are boundary values chosen?

    Numbers in phrases such as between 1 and 100, max 50 characters, at least 8, 18 or older, less than 10 and exactly 4 digits become boundaries, with values just below, at and just above each limit.

    Can I import the scenarios into Jira, Zephyr or Xray?

    Yes. The CSV columns map straight onto Zephyr Scale and Xray CSV import. There is also a Gherkin export for Cucumber, SpecFlow or Behave.

    How is the test estimate worked out?

    Bottom-up from your counts and rates, which gives the most likely value. Optimistic and pessimistic values come from the uncertainty you choose, and the PERT formula gives the expected effort and a 95% confidence figure to plan with.
