How it works

From an API definition to a test suite

  1. One positive test per endpoint. Each operation you tick gets a test that sends valid example data and checks the success status your definition documents. It also checks the response content type. Where the success response lists required fields, it checks they are there. Tests are grouped in a test.describe block per tag.
  2. Example data. Values come from the example and examples in your definition first, then default and enum. After that they're made from the schema, such as a UUID for format: uuid. $ref and allOf are followed, and read-only fields are left out of request bodies.
  3. Negative tests where they apply. A body with a required field missing, and a required field with the wrong type, should get a 4xx. An endpoint with security should refuse a request with no credentials (401 or 403). An ID in the path that doesn't exist should get a 404. When your definition documents the exact code, such as 422, the test expects that code.
  4. Data-driven tests. When a required parameter or body field has an enum, or a parameter has several named examples, the file loops over the values with for (const value of [...]). You get one test per value.
  5. Auth from environment variables. Bearer tokens and OAuth 2 read API_TOKEN. Basic auth reads API_USER and API_PASS. API keys read a variable named after the key, like X_API_KEY. No secret ends up in the file.
  6. Run it. Put api.spec.ts in a tests folder next to the config. Install with npm init playwright@latest, or npm i -D @playwright/test. Then run npx playwright test --reporter=html. API tests use the request fixture, so no browser is needed.

What the tests check, and what they can't know

  • They check the contract. Status codes, content types, required fields, and how the API handles bad input and missing auth. That catches broken deploys, missing validation and auth gaps early.
  • They don't know your business rules. The definition says a price is a number. It doesn't say the price must match the catalogue, or that a cancelled order can't be shipped. Add those assertions yourself.
  • They don't know your data. Example IDs like /pet/1 may not exist in your test environment. Swap in real test IDs, or create the record in the test first.
  • They only know what's documented. If the definition leaves out a 404 or a 422, the test accepts any 4xx. A gap in the definition is worth fixing too.

FAQ

Can I use a Swagger 2.0 file?

Yes. Swagger 2.0 and OpenAPI 3.0 and 3.1 all work, in JSON or YAML. For Swagger 1.x, convert the file to 2.0 or 3.0 first.

My definition is split across several files.

References to other files can't be followed in the browser. Bundle it into one file first, for example with npx @redocly/cli bundle openapi.yaml -o bundled.yaml. Then upload that.

Why does a negative test fail against my API?

Sometimes the API is right and the definition is wrong. Sometimes it's the other way round. A 200 for a body with a required field missing usually means validation is missing. A 500 means the API crashed on bad input. Both are worth a bug report.

Where do the tokens and keys go?

In environment variables, never in the file. Set them in your shell or in CI secrets. Use a test account, not a real user's credentials.

Can I load test the same API?

Yes. The OpenAPI to k6 converter turns the same definition into a k6 load test. Run the Playwright tests first to check each endpoint works, then load test it.
