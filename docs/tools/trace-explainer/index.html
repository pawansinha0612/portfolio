How it works

From a wall of spans to the one thing slowing the request

  1. Parse and join. Spans are read from Jaeger, Zipkin or OTLP, grouped by trace id and joined into a tree by parent id. Zipkin client and server halves that share an id are split, so each service gets its own span.
  2. Clock skew. A child on another host that starts before its parent is a clock problem, not time travel. Those spans are moved into the middle of their parent, as Jaeger does.
  3. Self time. For each span, the time not covered by any child. Big self time in a span with children is a gap: queueing, CPU work, GC or a call that is not instrumented.
  4. Critical path. From the end of the root span, follow the child that finished last, then the one that finished before it started, and so on. Only work on this path makes the request slower.
  5. Patterns. Siblings with the same operation (N+1), calls to different services that never overlap (could be parallel), the same call repeated after an error (retries), wide fan-outs and errors, with the deepest error marked as where the failure starts.
  6. Many traces. Percentiles per service and operation, how often each service is on the critical path, a caller → callee graph and outliers: traces much slower than typical for their entry point, with the service that took the extra time.

Getting a trace out of your tool

  • Jaeger: open the trace, then the menu at the top right, then Download JSON. Or call /api/traces/<traceId>, or /api/traces?service=checkout&limit=200 for many.
  • Zipkin: the JSON button on a trace, or /api/v2/trace/<traceId>; /api/v2/traces?serviceName=… returns many.
  • Grafana Tempo: /api/traces/<traceId> returns OTLP JSON. In Grafana, use Inspect → Data and download the trace.
  • OpenTelemetry Collector: add the file exporter; each line is an OTLP JSON document.
  • Datadog, Honeycomb, New Relic: export spans as OTLP JSON where the tool allows it, or send a copy of your OpenTelemetry data to a local Jaeger.

FAQ

Are my traces uploaded anywhere?

No. The files are read and analysed in your browser, in a background thread. Traces often hold URLs, user ids and SQL, so nothing is sent to a server.

Which trace formats does it read?

Jaeger JSON (the UI's Download JSON and the API's data array, with references and processes), Zipkin v2 JSON (an array of spans, or an array of traces), and OpenTelemetry OTLP JSON (resourceSpans, scopeSpans and spans, with hex or base64 ids and nanosecond times). Grafana Tempo's batches format and newline-delimited files from the OpenTelemetry Collector file exporter also work.

What is the critical path?

The chain of spans that decides how long the request takes. Starting from the end of the root span, it follows the child that finished last, then the child that finished before that one started, and so on. Work that runs in parallel with something slower is not on the critical path, so speeding it up does not help.

How does it handle clock skew?

A child span on another service that starts before its parent, or runs past its parent while being shorter, is almost always a clock difference between hosts. Those spans and everything under them are moved into the middle of the parent, the same correction Jaeger applies. You can turn this off.

Can it read many traces at once?

Yes. Choose several files or one export with many traces. You get latency percentiles per service and per operation, the services most often on the critical path, a dependency graph with call counts and p95, and outlier traces with the service that made each one slow.
