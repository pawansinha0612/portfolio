    How it works

    The first error, not the last one

    The red line at the bottom of a failed job is almost never the problem. Process completed with exit code 1, BUILD FAILED and ERROR: Job failed only say that something above went wrong. This tool reads the log the way an experienced engineer does.

    1. Clean the log. ANSI colour codes, carriage-return progress bars and the timestamp prefixes that GitHub, GitLab and Jenkins add are removed, and the CI system is detected.
    2. Match known failures. Each line is checked against 90+ signatures in 12 categories, from npm ERR! ERESOLVE to ImagePullBackOff. Each has a plain-English cause and a fix.
    3. Pick the root cause. Exit codes and summary lines are marked as follow-on noise. The earliest real error is the candidate; a more specific error just after it, or a severe one such as a full disk, takes priority.
    4. List the failed tests. Jest, pytest, JUnit (Maven and Gradle), Playwright, Go, .NET and RSpec output is recognised, including tests that passed only on retry.

    Finding flaky tests

    One failed run cannot tell you whether a test is flaky. Several runs can. Load the last few nightly runs (JUnit XML is the most reliable). A test that both passes and fails, or passes only on retry, is flagged. Consistent failures are listed separately: those are real bugs or broken tests, not flakiness.

    Common exit codes

    • 1: general failure. The reason is printed above.
    • 127: command not found. The tool is not installed on the runner or not on the PATH.
    • 137: killed, almost always out of memory. Lower parallel workers or give the job more memory.
    • 143: terminated, usually a timeout or a cancelled run.

    FAQ

    Is my build log uploaded anywhere?

    No. The log is analysed in your browser with a fixed list of patterns. Build logs can hold internal host names, package names and sometimes secrets, so nothing is sent to a server or an AI model.

    Which CI systems does it support?

    GitHub Actions, GitLab CI and Jenkins are detected by their markers, and Azure Pipelines and CircleCI logs work too. Colour codes, progress bars and timestamp prefixes are removed before matching.

    How does it decide which error is the root cause?

    Lines like Process completed with exit code 1 are results, not causes, so they are marked as follow-on noise. The earliest real error is the candidate, and a more specific error close to it, or a severe one such as a full disk or out of memory, takes priority.

    How does it find flaky tests?

    Load several logs or JUnit XML files from runs of the same suite. A test that passes in one run and fails in another, or passes only on retry, is flagged as flaky.

    What if my error is not recognised?

    The first line that looks like an error is shown with its context, so you still have a starting point. If a common failure is missing, tell me through the chat and I'll add it.
