Turn access logs into a workload model

Drop your production access logs and get the numbers a load test should be built on: peak requests per second, the transaction mix at the busiest hour, an estimate of concurrent users, and a k6 script that sends that mix at your target rate.

🔒 Your logs never leave your computer. Files are read in your browser by a background worker; nothing is uploaded, stored or sent anywhere. IPs and user agents are only hashed in memory to estimate sessions and are never shown.

A k6 script with one arrival-rate scenario per endpoint group, rates and VUs filled in. Arrival-rate executors keep the request rate fixed even when the system slows, which is what production traffic does.

How to get the logs

Where your access logs live

  • nginx: /var/log/nginx/access.log plus rotated access.log.1, access.log.2.gz. To get response times, add $request_time to the end of your log_format (bare or as rt=$request_time).
  • Apache: /var/log/apache2/access.log (Debian, Ubuntu) or /var/log/httpd/access_log (RHEL). Add %D (microseconds) at the end of the LogFormat for response times.
  • AWS ALB: enable access logs on the load balancer; they land in S3 under AWSLogs/<account>/elasticloadbalancing/<region>/YYYY/MM/DD/ as .log.gz files, every 5 minutes. Download a day's folder (aws s3 cp --recursive) and drop all of them.
  • AWS CloudFront: standard logs go to the S3 bucket you chose, named <distribution-id>.YYYY-MM-DD-HH.<id>.gz. Times are UTC: pick your timezone above.
  • IIS: %SystemDrive%\inetpub\logs\LogFiles\W3SVC<n>\u_exYYMMDD.log. Make sure time-taken is ticked in the logging fields.
  • Anything else (Kong, Envoy, an APM export, a SIEM query): export CSV or JSON lines with a timestamp, method, path, status and, if you can, response time. You'll be asked which column is which.

How much to take

Take the busiest day you can find (a sale, a campaign, end of month, payroll day), or a whole week if you want to see the weekly shape. One normal Tuesday will under-sell your peak. If several servers write their own logs, include all of them, or set “Logs cover 1 of N servers”.

How to use the model

From numbers to a test you can trust

  1. Check the peak. Design for the 99th percentile second or the busiest minute, not the daily average. The single busiest second is usually a burst you test separately as a spike test.
  2. Agree the growth factor. Ask the business what the next peak looks like: Black Friday, a campaign, a launch. 1.5 to 3× last year's peak is common. Headroom covers the gap between “survived” and “comfortable”.
  3. Clean up the mix. Merge endpoints that hit the same code path, add rules for slugs, and drop anything the test can't or shouldn't call (third-party callbacks, admin pages).
  4. Make the script real. Swap the random {id} values for real test data, add logins and request bodies, then run it at 10% of target first to check every request succeeds.
  5. Run it, then compare. The test should reproduce the production mix and response times at today's peak before you trust what it says at tomorrow's. See the load profiles explainer for which shape to run when.

Honest limitations

What logs can't tell you

  • Logs show requests, not intent. You see that someone called POST /api/cart/items, not why, or which journeys matter to the business. Check the mix against analytics and product owners.
  • Caching hides traffic. Requests answered by a CDN, browser cache or reverse proxy never reach origin logs. Use CDN logs for edge traffic and origin logs for what your servers actually do, and don't mix them up.
  • Sessions are an estimate. One IP and user agent can be many people (offices, mobile carriers, NAT) or one person can change IP. Think time counts gaps of one second or more inside a 30-minute session.
  • Payloads aren't in the logs. Request bodies, search terms that hit cold cache paths, and the data your users touch all change the cost of a request. The script needs real test data.
  • Response times are from your log. nginx $request_time includes slow clients; ALB adds its own processing time. Treat p95 here as a guide, not your SLO.
