AI prompts for testers

Copy-paste prompts that get useful work out of any AI chat assistant, plus what good output looks like and the mistakes to check for. AI is a fast junior tester: brilliant at first drafts, confidently wrong at the edges. You stay the reviewer.

Before you paste anything

  • Check your company's AI policy. Don't paste customer data, secrets, tokens or internal code into a tool your company hasn't approved.
  • Give it context, not just a task. The product, the users, the tech stack and what "done" means. Every prompt below has [square brackets] for that.
  • Run everything it writes. Generated scripts often look right and fail on the first run. That's normal; paste the error back and ask it to fix it.
Show

1. Test cases from acceptance criteria

Use when a story is ready for testing and you want a first set of cases fast.

You are a senior QA engineer. Write test cases for this user story.

Product: [what it is and who uses it]
Story: [paste the story]
Acceptance criteria:
[paste the criteria]
Out of scope: [anything you know isn't tested here]

For each test case give: ID, title, type (positive / negative / boundary / edge),
preconditions, steps, expected result, and which acceptance criterion it covers.
Cover every criterion at least once. Then list:
- questions or gaps you found in the criteria (don't guess the answers)
- risky areas that need exploratory testing rather than scripted cases.
Use a table.

Good output: every criterion is traced to cases; boundaries (empty, max length, zero, negative) appear; it asks questions instead of inventing business rules.

Check for: invented rules stated as fact ("passwords must be 12 characters"), duplicate cases with different wording, and no negative cases for permissions and errors.

2. Review my test plan

Use when you have a plan or checklist and want a second pair of eyes before the review meeting.

Act as a critical test lead reviewing this test plan for [feature / release].
Context: [users, platforms, integrations, deadline, known risks]

[paste the plan]

Tell me:
1. The 5 biggest risks this plan does not cover, ranked, with why each matters.
2. Anything tested twice or tested at the wrong level (UI vs API vs unit).
3. Missing non-functional checks: performance, security, accessibility, data migration.
4. Which tests to cut first if we lose two days.
Be specific to this plan. No generic testing advice.

Good output: risks tied to your context (that payment provider, that migration), and a clear cut list you could defend.

Check for: textbook lists ("consider usability testing") that would fit any plan. If you get those, add more context and ask again.

3. Write a k6 load test script

Use when you know the user journey and the traffic target. Converting an existing JMeter, Postman or OpenAPI file? The free converters are more reliable for that.

Write a k6 (v1.x) load test in JavaScript.

Journey: [e.g. open home, search "boots", open a product, add to cart]
Endpoints: [method + path + example body for each step]
Auth: [e.g. POST /login returns a token in JSON field "token"]
Test data: [e.g. users from users.csv with columns email,password]
Target: [e.g. ramp to 200 VUs over 5 min, hold 15 min] or [N requests per second]
Budgets: p95 under [ms], errors under [%]

Requirements:
- base URL and secrets from __ENV, never hard-coded
- group() per step and a check() on every response
- correlate the token and any IDs from earlier responses
- realistic think time with sleep()
- thresholds for the budgets
Explain any assumption you made in a comment.

Good output: runs with k6 run after small fixes, uses SharedArray for CSV data, and the thresholds match your budgets.

Check for: imports of modules that don't exist, Node.js APIs (fs, require) that k6 doesn't support, old option names, and a test that hammers one URL with no think time.

4. Write a Playwright test

Use for a first draft of a UI test. Paste real HTML so it can choose good locators.

Write a Playwright test in TypeScript for this flow: [describe the steps].
App URL: [url or "baseURL from config"]
Here is the relevant HTML (or accessibility snapshot) of each page:
[paste]

Rules:
- prefer getByRole / getByLabel / getByTestId; no XPath, no CSS chains
- no fixed waits (waitForTimeout); rely on auto-waiting and web-first assertions
- one test per behaviour, with a clear name
- put repeated steps in a page object only if used more than twice
After the code, list anything in the HTML that makes the test brittle,
and what test IDs or labels the developers could add.

Good output: role-based locators, expect(...).toBeVisible()-style assertions, and a useful list of testability fixes for developers.

Check for: locators for elements that aren't in your HTML (it guessed), sleeps hidden in helper functions, and assertions that only check the page loaded.

5. Analyse k6 results

Use after a run. The end-of-test summary plus your infrastructure graphs give it far more to work with than the summary alone.

You are a performance engineer. Analyse this load test.

System: [architecture in 3-5 lines: app servers, DB, cache, queues]
Test: [profile: e.g. ramp to 300 VUs in 10 min, hold 20 min]
Budgets: [p95 / error targets]
k6 summary:
[paste the end-of-test summary or summary JSON]
What we saw on servers during the test:
[CPU, memory, DB connections, GC, errors in logs, with times]

Tell me:
1. Did we meet the budgets? Quote the numbers.
2. When did behaviour change (time or load level), and what changed?
3. The most likely bottleneck, the evidence for it, and the evidence against.
4. The next experiment that would confirm it.
Say clearly when the data isn't enough to be sure.

Good output: numbers quoted back correctly, a hypothesis tied to evidence, and a cheap next test to confirm it.

Check for: averages treated as the headline, misread percentiles, and a confident root cause with no server-side evidence. AI can't see what you didn't paste.

6. Explain a flaky test

Use when a test passes locally and fails in CI, or fails one run in ten.

This automated test is flaky. Help me find out why.

Framework: [Playwright / Cypress / Selenium / pytest / ...]
Fails: [how often, where (CI / local), since when]
Test code:
[paste]
Error and stack trace from a failing run:
[paste]
What changed recently: [deps, infra, test data, parallelism]

List the likely causes ranked by probability, each with:
how to confirm it, and the fix. Consider timing and waits, shared test data,
test order, parallel runs, environment differences, and real product bugs.
Don't suggest retries as the fix.

Good output: a ranked list with a concrete way to confirm each cause, and it considers that the product might really be broken.

Check for: "add a wait" or "increase the timeout" as the answer. That hides the problem; it doesn't fix it.

7. Turn my notes into a bug report

Use when you found something during exploratory testing and want a clean ticket in a minute.

Turn these rough notes into a bug report a developer can act on.

Notes: [paste what you saw, in any order]
Environment: [app version, browser/device, OS, test env, account type]

Format: title (what's wrong + where, under 80 characters), steps to reproduce
(numbered, from a clean start), expected, actual, frequency, impact on users,
attachments to add, and a suggested severity with one-line reasoning.
Don't add steps or details that aren't in my notes. Mark anything missing as [NEEDED].

Good output: a specific title, steps someone else can follow, and [NEEDED] where your notes had gaps.

Check for: invented steps or error messages that make the report look complete but can't be reproduced.

8. Build a workload model

Use before writing any load test, to turn business numbers into a test target.

Help me build a workload model for a load test.

Business numbers: [e.g. 40,000 orders on Black Friday, 3% conversion, peak hour = 18% of the day]
Analytics: [page views per session, top pages and their share of traffic]
Response times today: [rough p95 per key page]

Work out, showing the maths step by step:
1. Peak sessions per hour and peak requests per second, per page
2. Target load with a safety margin, and why that margin
3. The mix of user journeys as percentages
4. VUs needed using Little's law, and think time per step
Flag any number you had to assume.

Good output: maths you can follow and check line by line, with assumptions flagged.

Check for: arithmetic slips (redo the key numbers with a calculator) and a peak that's simply "daily total ÷ 24". Real traffic has peaks.

Why these prompts work

  • A role and real context. "Senior QA engineer" plus your product and stack gets answers about your system, not testing in general.
  • An exact output format. Tables and numbered sections are quicker to review and paste into Jira or a test tool.
  • Permission to say "I don't know". Asking for gaps, assumptions and [NEEDED] markers makes invented details easier to spot.
  • You check everything. Run the scripts, recalculate the numbers, read every test case. AI drafts; you sign off.
