The hockey stick: why latency explodes at 80% busy

Little's law: how many requests are in flight?

Requests in the system = arrival rate × time each one spends inside. It holds for any stable system, whatever the traffic pattern.

What this means for your system

  • Don't plan to run hot. Above about 70–80% utilisation, a small rise in traffic gives a large rise in response time. Leave headroom for peaks; see headroom.
  • More servers share the load better. At the same utilisation, 16 servers queue far less than 1 server. That's why a single slow worker or a tiny connection pool hurts so much.
  • Cutting work per request moves the whole curve. A query that's 30% faster lets you take more traffic at the same latency.
  • Use Little's law to size pools. 200 req/s at 250 ms means about 50 requests in flight: your thread pool, connection pool and k6 VUs need at least that. See Little's law and thread pool sizing from first principles.

The model here is the textbook M/M/c queue: random arrivals, random service times, c identical servers. Real systems are messier, with slow dependencies, retries and garbage collection pauses. But the shape of the curve is the same, and that's why load tests that stop at "expected traffic" miss the cliff.
