Learn performance testing, step by step

1. The basics

The ideas every performance conversation uses. Skip this stage only if you can explain why an average response time hides problems and why latency jumps when a server gets busy.

  • Load, stress and soak testingGlossary

    The test types and the question each one answers. Then read stress testing and soak testing.

  • Why averages lieExplainer

    Percentiles (p50, p95, p99) and why targets are written with them. Play with the chart until the tail makes sense.

  • The hockey stick: why latency explodes at 80% busyExplainer

    Queueing in one picture. This is why "it was fine at 70%" is not a capacity plan.

  • Little's LawGlossary

    Users = throughput × time in the system. Read it with throughput, virtual user and think time.

  • Load, stress, spike, soak and breakpoint tests explainedExplainer

    Draw the shape of each test and export it as a k6 script.

  • Open vs closed workload modelsGlossary

    Fixed users or a fixed arrival rate. Getting this wrong hides slowdowns, see coordinated omission.

2. Your first test

Pick one tool and get a small test running against a safe target. Don't learn two tools at once.

  • Pick a toolTool picker

    Six questions about your team and system, one recommendation. Or read the tool comparisons.

  • Getting started with k6Guide

    Install k6, write a script and read the summary. Or take the free k6 email course, one lesson a day.

  • Getting started with JMeterGuide

    Your first test plan, run without the GUI the way it should be. Optional if you chose k6.

  • Thresholds and checksGuide

    Make the test able to fail: pass/fail on p95 and error rate. See also thresholds.

  • Run a smoke test firstGlossary

    One to five users, a few minutes. It proves the script and environment work before you spend an hour on a real test.

3. Realistic tests

A test that replays one recorded session with one user's data proves very little. This stage makes your tests behave like real traffic.

  • Correlation: handling dynamic valuesGuide

    Capture session IDs, CSRF tokens and IDs from responses instead of replaying stale ones. Short version: correlation.

  • Login and auth tokensGuide

    OAuth and JWT tokens, refresh, and why every virtual user should not share one login.

  • Parameterisation: test data per userGuide

    CSV data, unique users and avoiding cache-friendly repeats. In k6: data and parameterisation.

  • Scenarios and executorsGuide

    Run several journeys at once, each at its own rate, with an open model.

  • Build a workload modelTool

    Turn your busiest production hour into rates, virtual users and pacing. Write it up with the free workload model sheet.

4. Analysis

Running the test is the easy half. This stage is about reading results and finding out why the system is slow, with evidence.

  • Read your results properlyTool

    Percentiles, errors and throughput over time from a JMeter JTL file. For k6, use the k6 results viewer.

  • Compare two runsTool

    Before and after a change. Is the difference real, or noise?

  • Finding bottlenecksGuide

    A method, not guesswork: start at saturation and follow the queue. Then the deep dives on Linux servers, the JVM and databases.

  • Read a thread dumpTool

    Find blocked threads, lock contention and exhausted pools in a Java thread dump.

  • Read a GC logTool

    Pause times and heap trends, so you can tell a memory leak from an undersized heap.

  • Write a results reportTemplate

    Verdict first, numbers against targets, findings with evidence.
