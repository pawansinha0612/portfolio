Go-live performance sign-off checklist

Fourteen checks to run through before a release or peak season, with a GO, GO WITH CONDITIONS or NO-GO decision and the names of the people who made it.

Download as Markdown

How to use it

  • Tick only with evidence. Each check has an Evidence slot. A link to a report or dashboard, not "should be fine".
  • Unticked means a condition or a NO-GO. Every gap goes in the conditions table with an owner and a date, or the release waits.
  • Run it a week before go-live, not on the day. That leaves time to close the gaps it finds.
  • Planning for a known peak? The capacity calculator checks the "breaking point above peak" line.

Performance

  • All response-time and error-rate targets met at peak load, with the report linked. Evidence: link
  • Soak test run for long enough to show no leaks or slow degradation. Evidence: link
  • Breaking point known, and it sits above expected peak with agreed headroom. Evidence: link
  • Results from a production-like environment, or the gaps written down and accepted. Evidence: link

Capacity

  • Autoscaling tested: it scales out fast enough for the expected ramp and scales back in. Evidence: link
  • Connection pools, thread pools and database connection limits sized for peak. Evidence: link
  • Third-party rate limits and quotas known and above peak demand. Evidence: link

Resilience

  • A slow or failing dependency tested: timeouts, retries and circuit breakers behave. Evidence: link
  • Rollback tested, and the time it takes is known. Evidence: link

Observability

  • Dashboards show latency percentiles, throughput, errors and saturation for every key journey. Evidence: link
  • Alerts set on SLOs (not only CPU), routed to an on-call person. Evidence: link

Operations and release

  • Runbook covers the known failure modes found in testing. Evidence: link
  • Release window avoids peak trading, with a named person watching the first peak. Evidence: link
  • Feature flags or a kill switch ready for new heavy features. Evidence: link
