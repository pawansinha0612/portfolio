Gatling in CI: assertions that fail the build

The nightly Gatling job has been green for months. Someone opens the report and finds 30% of requests failed every night. Without assertions, Gatling reports problems but doesn't fail anything. Here's how to make the pipeline care.

Assertions: the pass/fail budget

Assertions are checked once, at the end of the run, against the whole simulation's statistics. Add them to setUp:

.assertions(
    global().responseTime().percentile(95.0).lt(500),        // p95 under 500 ms overall
    global().responseTime().percentile(99.0).lt(1500),
    global().failedRequests().percent().lt(1.0),             // under 1% KO
    global().requestsPerSec().gte(100.0),                    // and the load was actually generated
    details("Pay").responseTime().percentile(95.0).lt(800),  // one request by name
    details("Checkout", "Pay").failedRequests().count().is(0L), // a request inside a group
    forAll().responseTime().percentile(99.0).lt(2000))       // every request, individually
  • Scope: global() is all requests together, forAll() applies the rule to each request separately, and details(...) targets one request or group by name.
  • Always pair latency with errors. Failed requests are often fast, so a p95 budget alone can pass while the system returns errors.
  • Assert the throughput too. If the load generator couldn't produce the planned load, a latency budget passes for the wrong reason.
  • Percentiles, not the mean. Gatling can assert mean(), but the mean hides the tail. See percentiles and set the numbers from your SLO.

How a failed assertion reaches CI

With the Maven plugin, a failed assertion fails the build, so mvn exits non-zero and the CI job goes red. That's the plugin's failOnError setting, on by default. Two other plugin settings matter in CI:

  • More than one simulation: in non-interactive mode the plugin stops and asks you to pick one. Pass -Dgatling.simulationClass=..., or -Dgatling.runMultipleSimulations=true to run them all.
  • Keep going after a failure: with several simulations, -Dgatling.continueOnAssertionFailure=true runs the rest and fails at the end, so you get every report.

The Gradle plugin's gatlingRun task fails the same way when assertions fail.

GitHub Actions

# .github/workflows/gatling.yml
name: Gatling load test
on:
  workflow_dispatch:
  schedule:
    - cron: '0 14 * * 1-5'            # weekdays 14:00 UTC (overnight in Australia)

jobs:
  gatling:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      - name: Run simulation
        run: >
          ./mvnw --batch-mode gatling:test
          -Dgatling.simulationClass=example.CheckoutSimulation
          -DbaseUrl=${{ vars.STAGING_URL }}

      - uses: actions/upload-artifact@v4
        if: always()                    # keep the report when assertions fail
        with:
          name: gatling-report
          path: target/gatling/

if: always() keeps the report when assertions fail, which is when you need it. Load tests usually run on a schedule or on demand rather than on every pull request: a Gatling run with a realistic ramp and steady state takes 20 minutes or more. For a quick check on pull requests, keep a short smoke simulation with a handful of users.

GitLab CI

# .gitlab-ci.yml
gatling:
  stage: test
  image: maven:3-eclipse-temurin-21
  script:
    - mvn --batch-mode gatling:test -Dgatling.simulationClass=example.CheckoutSimulation -DbaseUrl=$STAGING_URL
  artifacts:
    when: always
    paths: [target/gatling/]
  rules:
    - if: $CI_PIPELINE_SOURCE == 'schedule'
    - if: $CI_PIPELINE_SOURCE == 'web'

Reports and comparing runs

Each run writes a self-contained HTML report folder under target/gatling/ (Maven) or build/reports/gatling/ (Gradle). Upload the whole folder: the index.html needs the files next to it.

What to read, in order:

  1. Errors: anything above a trickle invalidates the latency numbers. Fix or explain errors first.
  2. Active users and requests per second over time: did the injection profile happen as planned?
  3. Response time percentiles over time: flat during the steady state, or climbing? A steady climb under constant load is a queue or a leak filling up.
  4. Per-request table: the slowest request names and their p95 and p99.

The open-source report covers one run. To compare runs, keep the reports as artifacts with the commit or build number in the name, and track the key numbers (p95, p99, error rate, throughput) per run in a spreadsheet or dashboard. Line them up with server metrics from the same time window to find the cause: see the monitoring guide.

Scaling past one machine

Gatling is efficient, and one well-sized machine generates a lot of HTTP load. Watch the load generator's CPU and network during the run: if it's saturated, the response times include Gatling waiting for its own CPU. The open-source version runs on one machine. To spread load across several, you can run the same simulation on several machines and combine the results yourself (request counts and error counts add up, percentiles don't: averaging each machine's p95 is not the overall p95), or use Gatling Enterprise, the commercial edition, which handles distributed load generators and run-to-run comparison.
