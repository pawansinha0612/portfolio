Gatling injection profiles: open or closed, then the shape

You set atOnceUsers(1000) to simulate "1,000 users". The test fires 1,000 journeys in the same millisecond, the server queues them all, and the report shows a spike nobody will ever see in production. The injection profile is your workload model, so it has to match how real traffic arrives.

Open vs closed in Gatling

Gatling makes you choose explicitly: injectOpen(...) or injectClosed(...). You can't mix open and closed steps for one scenario.

  • Open: you control the arrival rate of new users. Each user runs the scenario and leaves. If the system slows down, users pile up inside it, as on a real public website. Use it when you have a throughput target.
  • Closed: you control how many users are active at once. A new user starts only when one finishes. Use it when the real population is fixed: a call centre, a pool of workers, a ticket queue that admits N people at a time.

A closed model under-reports latency when the system struggles, because it sends less work exactly then. That's coordinated omission. The background is in the open vs closed workload model glossary entry and the load profiles explainer.

Open injection steps

StepDoes
nothingFor(d)Wait
atOnceUsers(n)n users at the same moment. Fine for a smoke test, unrealistic for load.
rampUsers(n).during(d)n users spread evenly over d
constantUsersPerSec(r).during(d)r new users every second. The core of a load test.
constantUsersPerSec(r).during(d).randomized()Same average rate, random gaps between arrivals
rampUsersPerSec(r1).to(r2).during(d)Arrival rate changes linearly from r1 to r2
stressPeakUsers(n).during(d)n users following a smooth S-curve, for a spike
incrementUsersPerSec(r).times(k)...A staircase of rates, for capacity tests

Closed injection steps

StepDoes
constantConcurrentUsers(n).during(d)Keep n users active
rampConcurrentUsers(n1).to(n2).during(d)Change the active count linearly
incrementConcurrentUsers(n).times(k)...A staircase of concurrency levels

In a closed model, a user who finishes is replaced by a new one to keep the count steady. Every replacement starts a fresh session: a new login, new connections, empty caches. If real users stay logged in and keep working, loop the journey inside during(...) or forever() instead.

Both in one simulation

Different scenarios can use different models in the same setUp. Here, public visitors arrive at a rate while a fixed team of agents works in a loop:

package example;

import static io.gatling.javaapi.core.CoreDsl.*;
import static io.gatling.javaapi.http.HttpDsl.*;

import io.gatling.javaapi.core.*;
import io.gatling.javaapi.http.*;

public class InjectionSimulation extends Simulation {

  HttpProtocolBuilder httpProtocol = http.baseUrl(System.getProperty("baseUrl", "http://localhost:8080"));

  // Open model: one visit per virtual user, then the user leaves
  ScenarioBuilder visitors = scenario("Visitors")
      .exec(http("Home").get("/products"))
      .pause(2)
      .exec(http("Item").get("/products/3"));

  // Closed model: a fixed pool of users looping, like a call centre or a batch of workers
  ScenarioBuilder agents = scenario("Agents")
      .during(java.time.Duration.ofMinutes(10)).on(
          exec(http("Agent lookup").get("/products"))
              .pause(5));

  {
    setUp(
        visitors.injectOpen(
            nothingFor(5),                                  // wait 5 s
            atOnceUsers(10),                                // 10 users at once
            rampUsers(100).during(60),                      // 100 users spread over 60 s
            constantUsersPerSec(20).during(120),            // 20 new users every second for 2 min
            constantUsersPerSec(20).during(120).randomized(), // same rate, random gaps (Poisson-like)
            rampUsersPerSec(20).to(60).during(180),         // arrival rate climbs 20 -> 60 users/s
            stressPeakUsers(500).during(20),                // 500 users on a smooth peak over 20 s
            incrementUsersPerSec(10)                        // capacity search: +10 users/s per step
                .times(5)
                .eachLevelLasting(60)
                .separatedByRampsLasting(10)
                .startingFrom(10)),
        agents.injectClosed(
            constantConcurrentUsers(50).during(300),        // keep 50 users active for 5 min
            rampConcurrentUsers(50).to(150).during(300)))   // then grow the pool to 150
        .protocols(httpProtocol)
        .maxDuration(java.time.Duration.ofMinutes(30));     // hard stop
  }
}

The steps in one injectOpen run one after another, so this example is a tour of every step, not a sensible test. A real load test is usually just two steps: a ramp, then a steady rate for long enough to measure.

setUp(
    scn.injectOpen(
        rampUsersPerSec(0).to(50).during(Duration.ofMinutes(5)),   // ramp to peak arrival rate
        constantUsersPerSec(50).during(Duration.ofMinutes(20))))   // hold peak, and measure this part
    .protocols(httpProtocol);

Sizing it: if 50 users arrive per second and each journey takes about 30 s including think time, roughly 50 × 30 = 1,500 users are active at once (Little's Law). The capacity calculator does this for you. If you only know "1,500 concurrent users" from analytics, divide by the journey length to get the rate.

Finding capacity with incrementUsersPerSec

scn.injectOpen(
    incrementUsersPerSec(10)          // add 10 users/s per level
        .times(8)                     // 8 levels: 10, 20 ... 80 users/s
        .eachLevelLasting(Duration.ofMinutes(3))
        .separatedByRampsLasting(Duration.ofSeconds(30))
        .startingFrom(10))

Each level holds long enough for latency to settle. In the report, find the last level where p95 stayed flat and errors stayed near zero. That's your sustainable throughput. The level where p95 starts climbing within the level is where queues begin to grow. This is a breakpoint test: run it against an environment you can afford to break.

Throttling and pacing

  • throttle(reachRps(100).in(10), holdFor(Duration.ofMinutes(5))) caps requests per second across the simulation. It only limits, so you still need enough users injected to reach the cap. Most teams are better served by an open injection profile than by throttling a closed one.
  • pace(Duration.ofSeconds(10)) inside a loop makes each iteration take at least 10 s, including the request time. That's pacing: it keeps a closed-model user's rate steady.
  • maxDuration(...) on setUp is a hard stop, a useful guard for CI.
