Gatling getting started: a first simulation in Java

Your team writes Java or Kotlin all day, and the load test lives in a separate tool nobody else can read. Gatling puts the load test in the same language, the same build and the same code review as the service it tests.

On this page

  1. Set up a project
  2. The first simulation
  3. Run it
  4. Read the report
  5. Concepts that trip people up

Set up a project

Gatling 3 runs on the JVM. You write simulations in Java, Kotlin or Scala (there's also a JavaScript/TypeScript SDK). This guide uses the Java DSL, which is what most teams pick today. You need a JDK (a current LTS such as 17 or 21) and either Maven or Gradle.

The quickest start is Gatling's official demo project: gatling-maven-plugin-demo-java or gatling-gradle-plugin-demo-java. Both include a wrapper, so you don't need Maven or Gradle installed. To add Gatling to an existing Maven project, you need the dependency and the plugin:

<!-- pom.xml (the relevant parts) -->
<properties>
  <maven.compiler.release>21</maven.compiler.release>
  <gatling.version>3.16.0</gatling.version>
  <gatling-maven-plugin.version>4.21.12</gatling-maven-plugin.version>
</properties>

<dependencies>
  <dependency>
    <groupId>io.gatling.highcharts</groupId>
    <artifactId>gatling-charts-highcharts</artifactId>
    <version>${gatling.version}</version>
    <scope>test</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>io.gatling</groupId>
      <artifactId>gatling-maven-plugin</artifactId>
      <version>${gatling-maven-plugin.version}</version>
    </plugin>
  </plugins>
</build>

These were the current versions when this guide was written (Gatling 3.16, Maven plugin 4.21). Check Maven Central for newer ones. For Gradle:

// build.gradle
plugins {
  id 'java'
  id 'io.gatling.gradle' version '3.16.0'
}

repositories {
  mavenCentral()
}

The layout for Maven:

my-load-tests/
├── pom.xml
├── mvnw, .mvn/                     # Maven wrapper: no global Maven needed
└── src/test/
    ├── java/example/
    │   └── BasicSimulation.java    # simulations live with the test sources
    └── resources/
        ├── users.csv               # feeders
        └── logback-test.xml        # logging (set to DEBUG to see requests)

With the Gradle plugin, simulations go in src/gatling/java and resources in src/gatling/resources, not under src/test. Putting them in the wrong folder is the usual reason Gradle says it found no simulations.

The first simulation

A simulation has three parts: the protocol (base URL, common headers), one or more scenarios (the user journey), and setUp (how many users arrive and when, plus the pass/fail assertions).

package example;

import static io.gatling.javaapi.core.CoreDsl.*;
import static io.gatling.javaapi.http.HttpDsl.*;

import io.gatling.javaapi.core.*;
import io.gatling.javaapi.http.*;

public class BasicSimulation extends Simulation {

  // Base URL from a system property, so CI can point it at any environment
  private static final String BASE_URL = System.getProperty("baseUrl", "http://localhost:8080");

  HttpProtocolBuilder httpProtocol = http
      .baseUrl(BASE_URL)
      .acceptHeader("application/json")
      .userAgentHeader("gatling-load-test");

  ScenarioBuilder browse = scenario("Browse products")
      .exec(
          http("List products")
              .get("/products")
              .check(status().is(200))
              .check(jsonPath("$.items[0].id").saveAs("productId")))
      .pause(1, 3) // think time: random 1 to 3 seconds
      .exec(
          http("Get product")
              .get("/products/#{productId}") // Gatling Expression Language reads the session
              .check(status().is(200)));

  {
    setUp(
        browse.injectOpen(
            rampUsersPerSec(1).to(20).during(60), // ramp arrivals from 1 to 20 users/s over 60 s
            constantUsersPerSec(20).during(300))  // then hold 20 new users/s for 5 minutes
    )
        .protocols(httpProtocol)
        .assertions(
            global().responseTime().percentile(95.0).lt(500),
            global().failedRequests().percent().lt(1.0));
  }
}
  • check(...) validates each response. Unlike k6, a failed check in Gatling marks the request as failed (KO) and, by default, the user's next requests still run. Use exitHereIfFailed() to stop a user whose journey is broken.
  • saveAs stores an extracted value in the user's session, and #{productId} reads it back. This is Gatling's Expression Language.
  • pause(1, 3) is a random 1-3 second think time.
  • injectOpen with constantUsersPerSec is an open model: new users arrive at a rate, whatever the response times. More in injection profiles.
  • assertions fail the build when a budget is missed.

Run it

# Maven
./mvnw gatling:test                                         # asks which simulation if there are several
./mvnw gatling:test -Dgatling.simulationClass=example.BasicSimulation
./mvnw gatling:test -DbaseUrl=https://staging.example.com   # read with System.getProperty

# Gradle
./gradlew gatlingRun --simulation example.BasicSimulation
./gradlew gatlingRun --all                                  # every simulation, one after another

# Record a browser session into a simulation (a starting point, not a finished test)
./mvnw gatling:recorder

Pass test parameters as system properties with -D and read them with System.getProperty, Integer.getInteger or Long.getLong in the simulation. That keeps URLs and user counts out of the code.

Read the report

At the end Gatling prints a text summary and writes an HTML report: with Maven under target/gatling/<simulation>-<timestamp>/index.html, with Gradle under build/reports/gatling/. Open it in a browser. The parts to look at first:

  • Response time percentiles over time: is p95 flat during the steady state, or climbing? Climbing under constant load means something is filling up: a queue, a pool, the heap. See queueing.
  • Active users and requests per second on the same time axis: in an open model, active users growing while the arrival rate is constant is the first sign of saturation.
  • Errors table: every KO with its reason. Fix errors before you read any latency number.
  • Per-request stats: the slowest request names, where to start profiling.

Report percentiles (p95, p99), not the mean. Here's why averages lie.

Concepts that trip people up

  • A Gatling "user" runs the scenario once and leaves, unless you add a loop. With constantUsersPerSec(20) you get 20 new journeys a second, not 20 users looping. That's an open model, and usually what you want for public traffic.
  • Sessions are immutable. session.set(...) returns a new session. Return it from your function or the change is lost.
  • The DSL builds the test, it doesn't run it. Code in the class body runs once when the simulation loads. Code that must run per user goes inside exec(session -> ...).
