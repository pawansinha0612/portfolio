Getting started with JMeter 5.6

You press the green Start button with 500 threads and the JMeter window freezes. The laptop fans spin up, the graphs stop updating and the numbers you get back describe your laptop, not the server. This guide sets JMeter up the way it is meant to be used: GUI to build, command line to run.

1. Install Java and JMeter

JMeter is a Java application. JMeter 5.6.x runs on Java 8 or later, but there is no good reason to use Java 8 today. Install a current long-term support JDK such as 17 or 21 (Eclipse Temurin is a free, common choice) and check it:

java -version
# openjdk version "21.0.x" ...

Then get JMeter itself. The latest 5.x release at the time of writing is 5.6.3. Check the download page for anything newer.

  • Any OS: download the binary apache-jmeter-5.6.3.zip or .tgz, verify the SHA-512 checksum, extract it anywhere (avoid paths with spaces on Windows), then run bin/jmeter on macOS or Linux, or bin\jmeter.bat on Windows.
  • macOS with Homebrew: brew install jmeter puts jmeter on your PATH.
curl -sSfLO https://archive.apache.org/dist/jmeter/binaries/apache-jmeter-5.6.3.tgz
tar xzf apache-jmeter-5.6.3.tgz
export PATH="$PWD/apache-jmeter-5.6.3/bin:$PATH"
jmeter -v

If you have several JDKs installed, set JAVA_HOME so the jmeter script picks the one you expect.

Add the Plugins Manager

Most teams end up needing at least one community plugin (custom thread groups, WebSocket samplers). Download jmeter-plugins-manager-<version>.jar from jmeter-plugins.org, drop it into lib/ext/ and restart JMeter. It appears under Options → Plugins Manager. Install only what the plan uses, and install the same plugins on every machine that will run the plan, including CI runners and remote load generators.

2. GUI mode vs CLI mode

JMeter prints a warning every time the GUI starts: do not use GUI mode for load testing, only for creating and debugging tests. Take it literally.

GUI modeCLI (non-GUI) mode
Use it forBuilding the plan, recording, debugging with 1–5 threadsEvery real test run, CI, remote runs
Start withjmeterjmeter -n -t plan.jmx -l results.jtl
CostSwing rendering and live listeners eat CPU and heap on the load generatorMinimal overhead, results streamed to a file
ResultsListeners such as View Results TreeA JTL file plus the HTML dashboard

The rule of thumb: if a number will go in a report, it came from a CLI run.

3. Build a first test plan

A test plan is a tree. Elements apply to their parent and siblings by scope, so where you put something matters as much as what it is. Build this in the GUI:

  1. Thread Group: right-click Test Plan → Add → Threads (Users) → Thread Group. Set Number of Threads (users) to 5, Ramp-up period to 10 and Loop Count to 10. Each thread is one virtual user.
  2. HTTP Request Defaults: on the Thread Group, Add → Config Element → HTTP Request Defaults. Set Protocol https and Server Name test.example.com. Every HTTP Request in scope inherits them, so a host change is a one-field edit.
  3. HTTP Cookie Manager: Add → Config Element → HTTP Cookie Manager. Without it, session cookies are silently dropped and logged-in flows fail in confusing ways.
  4. HTTP Request: Add → Sampler → HTTP Request. Name it after the business step (GET /products or 01 Home), leave the server blank and set the Path, for example /api/products. The name becomes the label in every report, so make it meaningful.
  5. Response Assertion: on the HTTP Request, Add → Assertions → Response Assertion, Field to Test Response Code, Pattern Matching Rule Equals, pattern 200. A load test without assertions counts a friendly error page as a success. See assertions.
  6. View Results Tree: on the Test Plan, Add → Listener → View Results Tree. Use it while debugging, then disable it (right-click → Disable) before any load.
  7. Save as plan.jmx.

To check the script, right-click the Thread Group and choose Validate. That runs one thread, one iteration, with timers ignored. Open View Results Tree and read the request and response of every sample. Green ticks only mean the assertions passed, so make sure the assertions are meaningful.

Make load settings overridable

Hard-coded thread counts force you to edit the plan for every run. Replace them with property lookups using __P, which reads a property or falls back to a default:

Number of Threads (users):  ${__P(users,5)}
Ramp-up period (seconds):   ${__P(rampup,10)}
Loop Count:                 ${__P(loops,10)}
Server Name or IP:          ${__P(host,test.example.com)}

Now -Jusers=200 on the command line changes the load without touching the file. More on this in parameterisation.

4. Run it from the command line

jmeter -n -t plan.jmx -l results.jtl -e -o report/
FlagMeaning
-nNon-GUI (CLI) mode
-t plan.jmxThe test plan to run
-l results.jtlWrite one line per sample to this results file (CSV by default)
-eGenerate the HTML dashboard when the test ends
-o report/Dashboard output folder. It must not exist or must be empty
-fDelete an existing results file and report folder before starting
-Jname=valueSet a JMeter property, read in the plan with ${__P(name)}
-j jmeter.logWhere to write the run log

Two traps on the first run. If results.jtl already exists, JMeter appends to it, so the new report silently mixes two runs. If report/ is not empty, report generation fails with "folder is not empty". Use -f, or give every run its own folder, for example -l runs/$(date +%Y%m%d-%H%M)/results.jtl.

While the test runs, JMeter prints a summary line every 30 seconds: samples, throughput, average, min, max and error percentage. It is a sanity check, not a result. When the run ends, open report/index.html in a browser. The results and reports guide explains every chart.

You can also rebuild a dashboard from an existing JTL at any time, which is handy after changing report settings:

jmeter -g results.jtl -o report-v2/

5. What a .jmx file looks like

A plan is XML. You will rarely edit it by hand, but it belongs in version control, and it helps to recognise the structure in a code review. Each element is followed by a hashTree holding its children. This stripped-down version has one HTTP Request with the server set directly (no defaults, cookie manager, assertion or listener). Save it as first-plan.jmx and it runs as is:

<?xml version="1.0" encoding="UTF-8"?>
<jmeterTestPlan version="1.2" properties="5.0" jmeter="5.6.3">
  <hashTree>
    <TestPlan guiclass="TestPlanGui" testclass="TestPlan" testname="First plan">
      <elementProp name="TestPlan.user_defined_variables" elementType="Arguments" guiclass="ArgumentsPanel" testclass="Arguments">
        <collectionProp name="Arguments.arguments"/>
      </elementProp>
    </TestPlan>
    <hashTree>
      <ThreadGroup guiclass="ThreadGroupGui" testclass="ThreadGroup" testname="Shoppers">
        <stringProp name="ThreadGroup.num_threads">${__P(users,5)}</stringProp>
        <stringProp name="ThreadGroup.ramp_time">${__P(rampup,10)}</stringProp>
        <boolProp name="ThreadGroup.same_user_on_next_iteration">true</boolProp>
        <stringProp name="ThreadGroup.on_sample_error">continue</stringProp>
        <elementProp name="ThreadGroup.main_controller" elementType="LoopController" guiclass="LoopControlPanel" testclass="LoopController">
          <stringProp name="LoopController.loops">${__P(loops,10)}</stringProp>
          <boolProp name="LoopController.continue_forever">false</boolProp>
        </elementProp>
      </ThreadGroup>
      <hashTree>
        <HTTPSamplerProxy guiclass="HttpTestSampleGui" testclass="HTTPSamplerProxy" testname="GET home">
          <stringProp name="HTTPSampler.protocol">${__P(protocol,https)}</stringProp>
          <stringProp name="HTTPSampler.domain">${__P(host,test.example.com)}</stringProp>
          <stringProp name="HTTPSampler.port">${__P(port,443)}</stringProp>
          <stringProp name="HTTPSampler.path">/</stringProp>
          <stringProp name="HTTPSampler.method">GET</stringProp>
          <boolProp name="HTTPSampler.follow_redirects">true</boolProp>
          <boolProp name="HTTPSampler.use_keepalive">true</boolProp>
          <elementProp name="HTTPsampler.Arguments" elementType="Arguments" guiclass="HTTPArgumentsPanel" testclass="Arguments">
            <collectionProp name="Arguments.arguments"/>
          </elementProp>
        </HTTPSamplerProxy>
        <hashTree/>
      </hashTree>
    </hashTree>
  </hashTree>
</jmeterTestPlan>
jmeter -n -t first-plan.jmx -Jhost=staging.example.com -Jusers=20 -Jloops=50 -l results.jtl -f

6. A sensible project layout

perf/
  plan.jmx              # the test plan, in git
  data/users.csv        # test data, small files in git, large ones generated
  env/staging.properties   # host, ports, load settings per environment
  check_jtl.py          # pass/fail thresholds for CI
runs/                   # results and reports, git-ignored

Run with jmeter -n -t perf/plan.jmx -q perf/env/staging.properties -l runs/r1/results.jtl -e -o runs/r1/report. The -q flag loads an extra property file, which keeps environment differences out of the plan.
