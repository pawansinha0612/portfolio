JMeter beyond HTTP: WebSockets, gRPC and Kafka

Your new trading screen streams prices over WebSockets, the back end talks gRPC and orders flow through Kafka. The HTTP Request sampler covers none of it. JMeter can still test all three, through community plugins of varying maturity. This guide says which ones exist, how to use the solid one, and when another tool is the better choice.

1. What core JMeter supports

Apache JMeter 5.6 ships samplers for HTTP(S), JDBC, JMS (publish, subscribe, point-to-point), LDAP, FTP, SMTP and mail reading, raw TCP, Java and JUnit classes, and Neo4j Bolt. Anything else needs a plugin or a JSR223 (Groovy) sampler using the protocol's Java client library.

The core HTTP Request sampler speaks HTTP/1.1. For HTTP/2 there is a BlazeMeter plugin in the Plugins Manager ("BlazeMeter - HTTP Plugin", id bzm-http2).

Judging a plugin. Check when it was last released, whether it works with your JMeter version, and whether its issue tracker is active. A plugin that breaks on the next JMeter upgrade turns into technical debt. Install plugins the same way on every workstation, CI runner and load generator.

2. WebSockets: Peter Doornbosch's samplers

The established choice is WebSocket Samplers by Peter Doornbosch (Plugins Manager id websocket-samplers, version 1.3.x at the time of writing). It is a community plugin, not part of Apache JMeter, but it is mature and widely used. It adds six samplers:

SamplerUse
WebSocket Open ConnectionThe upgrade handshake. Server, port, path, TLS, connect and read timeouts
WebSocket request-response SamplerSend a frame and wait for one response frame. Covers the most common case
WebSocket Single Write SamplerSend a frame without waiting
WebSocket Single Read SamplerWait for the next frame, for server pushes
WebSocket Ping/Pong SamplerKeep-alive checks
WebSocket CloseClose the connection with a status code

The connection belongs to the JMeter thread. Later samplers in the same thread choose "use existing connection" and reuse it. A typical streaming-prices flow:

Thread Group  (each thread = one connected client)
├── HTTP Request             POST /auth/login  → JSON Extractor token
├── WebSocket Open Connection   server prices.example.com, path /stream, TLS on
│   └── HTTP Header Manager     Authorization: Bearer ${token}
├── WebSocket request-response  {"action":"subscribe","symbols":["BHP","CBA"]}
│   └── Response Assertion      Substring: "subscribed"
├── Loop Controller (${__P(reads,100)})
│   └── WebSocket Single Read Sampler   use existing connection, read timeout 5000 ms
│       └── JSON Extractor               price ← $.price
└── WebSocket Close           status 1000

Frame filters (text, binary and ping/pong) let a sampler skip frames you do not care about, such as heartbeats, so they do not get read as "the response". To measure push latency, not just "a frame arrived", have the server include its send timestamp and compute the difference in a JSR223 PostProcessor. The clocks of the server and the load generator must then be in sync.

Each open connection is a thread blocked on a socket. 10,000 concurrent WebSocket clients means 10,000 JMeter threads, with the memory that implies. Size the generators for it, or spread the load across several (see distributed testing).

3. gRPC

Core JMeter has no gRPC sampler. The best-known plugin is JMeter gRPC Request (Plugins Manager id jmeter-grpc-request), originally published by zalopay-oss on GitHub. You point it at your .proto files, choose the full method name, and send the request as JSON. It suits unary calls. Check its documentation and recent release activity for your case, especially if you need streaming RPCs, and test it on your JMeter version before you commit to it.

The fallback that always works is a JSR223 Sampler using the generated Java stubs and grpc-java, with the jars in lib/. It is flexible but means maintaining Java build output inside a JMeter project, which few teams enjoy.

4. Kafka

The Plugins Manager lists several Kafka plugins, including DI KafkaMeter (id di-kafkameter, producer and consumer config elements and samplers) and the older Kafka Support (id kafkameter). They are small community projects, so check maintenance before relying on one.

The dependable route is a JSR223 Sampler with the official kafka-clients library. Copy kafka-clients-<version>.jar and its compression dependencies (lz4, snappy, zstd) into JMeter's lib/ folder and restart. This is a sketch to adapt, not a drop-in script:

// JSR223 Sampler, language groovy. One producer per JMeter thread, created on first use.
import org.apache.kafka.clients.producer.KafkaProducer
import org.apache.kafka.clients.producer.ProducerRecord

def producer = vars.getObject('producer')
if (producer == null) {
    def cfg = new Properties()
    cfg.put('bootstrap.servers', props.getProperty('kafkaBrokers', 'localhost:9092'))
    cfg.put('key.serializer', 'org.apache.kafka.common.serialization.StringSerializer')
    cfg.put('value.serializer', 'org.apache.kafka.common.serialization.StringSerializer')
    cfg.put('acks', 'all')
    producer = new KafkaProducer<String, String>(cfg)
    vars.putObject('producer', producer)
}

def key = vars.get('orderId')
def value = '{"orderId":"' + key + '","amount":42.50}'
// .get() blocks until the broker acknowledges, so the sample time is the ack latency
def meta = producer.send(new ProducerRecord<String, String>('orders', key, value)).get()
SampleResult.setResponseData('partition=' + meta.partition() + ' offset=' + meta.offset(), 'UTF-8')
  • Never write ${...} inside a JSR223 script. JMeter substitutes it before Groovy sees the code, which breaks script caching and can inject data into code. Read values with vars.get() and props.getProperty() as above.
  • Calling .get() on every send measures per-message acknowledgement latency, but limits each thread to one in-flight message. For raw throughput, send asynchronously and measure at batch level, and remember that the sample time then means something different.
  • Close producers at the end, for example from a tearDown Thread Group or a JSR223 Listener, or brokers log abrupt disconnects.
  • End-to-end latency (produce to consume) needs a consumer that matches messages by key and timestamp. That is a small application in itself, and usually worth building outside JMeter.

For MQTT there is also a plugin: MQTT Protocol Samplers by XMeter (id mqtt-xmeter), with connect, publish, subscribe and disconnect samplers.

5. When k6 is the better fit

If most of the system under test is streaming or RPC rather than request-response HTTP, consider k6. It has built-in gRPC (k6/net/grpc) and WebSocket support, with Kafka available through the community xk6-kafka extension. Scripts are JavaScript, which suits developers who already write the services. Its virtual users are lighter than JMeter threads, which matters with tens of thousands of open sockets. The trade-offs are covered in k6 vs JMeter, and the k6 guides show the code. Existing plans can be moved over with the JMeter to k6 converter.

Staying on JMeter is reasonable when the team, CI and reporting are already built around it and the non-HTTP part is small. A WebSocket feed alongside a mostly-HTTP journey is a good fit for the Doornbosch samplers.
