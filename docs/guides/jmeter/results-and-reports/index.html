Reading JMeter results without fooling yourself

The dashboard says p95 is 640 ms, under the 800 ms target. But 6% of requests failed in under 20 ms with connection resets, and the percentile chart only counts successful responses. Or the one-minute granularity flattened a 40-second stall into a gentle bump. The HTML report is good, once you know what each number includes and leaves out.

1. The JTL file, column by column

With default settings, -l results.jtl writes CSV with this header in JMeter 5.6:

timeStamp,elapsed,label,responseCode,responseMessage,threadName,dataType,success,failureMessage,bytes,sentBytes,grpThreads,allThreads,URL,Latency,IdleTime,Connect
ColumnMeaning
timeStampSample start time, epoch milliseconds (the default sampleresult.timestamp.start=true)
elapsedResponse time in ms: from just before sending to the last byte received
labelSampler or transaction name. Group and filter on it
responseCodeHTTP status, or an exception class name such as Non HTTP response code: java.net.SocketTimeoutException
responseMessageHTTP reason phrase or error text
threadNameThread group name plus thread number, e.g. Buyers 1-17
dataTypetext or bin, empty for transaction parents
successtrue or false after status and assertions
failureMessageFirst failing assertion's message
bytesBytes received, headers included
sentBytesBytes sent
grpThreadsActive threads in this sample's thread group at that moment
allThreadsActive threads across all groups (per node in distributed runs)
URLFinal URL requested
LatencyTime to first byte of the response, in ms
IdleTimeTime not spent sampling, usually 0. Used by transaction parents
ConnectTime to establish the connection, TLS included. 0 when a kept-alive connection was reused

Columns are controlled by the jmeter.save.saveservice.* properties. The dashboard needs the defaults, so do not trim them to save disk. Do keep jmeter.save.saveservice.response_data off (the default). Saving bodies for every sample produces multi-gigabyte files and slows the generator.

The JTL analyser reads a JTL in the browser and gives you percentiles per label, error breakdowns and timelines without uploading the file anywhere.

2. Elapsed, Latency and Connect

|— Connect —|— request sent, server working —|— first byte … last byte —|
|——————————————— Latency ——————————————————|
|———————————————————————————— elapsed ——————————————————————————————|
  • Connect high, Latency − Connect low: connection setup is the cost. New TLS handshakes on every iteration ("Same user on each iteration" unticked), DNS issues, or a load balancer struggling with new connections.
  • Latency high: the server is slow to produce the first byte. Application, database or a queue in front of them. See TTFB.
  • elapsed much larger than Latency: the body takes long to arrive. Big payloads, bandwidth limits, or a server that streams slowly.

None of these include timer delays. They do include time the load generator spends on its own work, which is why a saturated generator inflates every number.

3. The HTML dashboard

Generate it at the end of a run with -e -o report/, or later from any JTL with jmeter -g results.jtl -o report/. The first page shows:

  • Test and Report information: file, start and end time, and the time window used for the report.
  • APDEX table: per label, using the satisfied threshold (500 ms by default) and the tolerated threshold (1500 ms by default). Set them to your real targets or ignore the table. See APDEX.
  • Requests Summary: pass and fail share.
  • Statistics: per label: samples, errors, error %, average, min, max, median, the three configured percentiles (90th, 95th and 99th by default), throughput, and received and sent KB/s.
  • Errors: each error type with its share of errors and of all samples.
  • Top 5 Errors by sampler: where the errors came from.

The same statistics are written to report/statistics.json, which is handy for CI gates and trend charts.

4. What each graph tells you

GraphLook for
Response Times Over TimeAverage per label over time. Drift upward in a soak test suggests a leak, growing queue or bloating table
Response Time Percentiles Over Time (successful responses)The tail over time. Spikes lined up across all labels point to a shared cause: GC pauses, a cron job, autoscaling
Active Threads Over TimeThe load shape you actually applied. Compare it with what you planned
Bytes Throughput Over TimeA flat line while threads rise can mean a network ceiling
Latencies Over Time / Connect Time Over TimeSeparate server time from connection setup (section 2)
Hits Per SecondRequests sent per second. If it stops rising while threads rise, something is saturated
Codes Per SecondWhen errors started and which codes: 429 means rate limiting, 502 or 503 the proxy or load balancer, 500 the application
Transactions Per SecondPer-label throughput, split by success and failure
Response Time Vs RequestMedian response time against request rate. The knee is where capacity runs out
Response Time PercentilesThe full distribution curve for the whole run. A long flat tail with a sharp jump at the end shows a bimodal pattern such as cache hits and misses
Response Time OverviewCounts in the APDEX buckets plus failures
Time Vs ThreadsResponse time against concurrency. Rising roughly linearly beyond a point is the signature of a queue (queueing explainer)
Response Time DistributionHistogram per label. Two humps mean two populations of requests that deserve separate analysis

Some graphs include Transaction Controller samples and some exclude them. The dashboard documentation lists which is which. Use "Apply Naming Policy" on Transaction Controllers if you want only the transaction names to appear.

5. Percentiles in JMeter

The Statistics table and Aggregate Report show the 90th, 95th and 99th percentiles by default (properties aggregate_rpt_pct1, pct2 and pct3). Things to keep in mind:

  • Read the error rate first. Failed requests are often very fast (connection refused, instant 503) or very slow (timeouts). Either way they distort the latency numbers. Fix errors, then trust the percentiles.
  • A run-wide percentile hides time. A p95 over one hour can look fine while minutes 40 to 45 were terrible. Use the percentiles-over-time graph for that.
  • Small samples are noisy. A p99 from 300 samples rests on three requests.
  • Never average percentiles across labels, nodes or runs. Recompute from the raw samples. That is why merging JTLs and regenerating the report is correct, and averaging three reports' p95s is not.
  • A closed model under-reports the tail. When the server stalls, JMeter threads wait instead of sending, so the slow period has fewer samples than real users would have produced. That is coordinated omission, shown in the percentiles explainer.

6. Report settings worth changing

Put these in user.properties, or pass them with -J when generating the report:

# Over-time graphs default to 1-minute points. Use 5-10 s for tests under ~30 min.
# Must be above 1000 ms or throughput graphs are wrong.
jmeter.reportgenerator.overall_granularity=5000

# Your real targets instead of 500 / 1500 ms
jmeter.reportgenerator.apdex_satisfied_threshold=800
jmeter.reportgenerator.apdex_tolerated_threshold=2000

jmeter.reportgenerator.report_title=Checkout API, release 4.2, 400 rps

# Leave warm-up out of the report (format set by jmeter.reportgenerator.date_format)
jmeter.reportgenerator.date_format=yyyyMMddHHmmss
jmeter.reportgenerator.start_date=20261106100500
jmeter.reportgenerator.end_date=20261106110500

# Hide setup and token calls from the graphs (regular expression on labels)
jmeter.reportgenerator.exporter.html.series_filter=^(01|02|03|04).*
jmeter -g results.jtl -o report-steady/ -q report.properties

7. Live results while the test runs

The CLI summariser prints a line every 30 seconds by default (summariser.interval). For a live dashboard, add a Backend Listener with the InfluxdbBackendListenerClient implementation and point it at InfluxDB, then chart it in Grafana. It sends aggregated metrics, not every sample, so it is cheap. Keep the JTL as the source of truth for the final analysis.

Do not use View Results Tree, Aggregate Report or graph listeners during load. They hold results in memory and cost CPU. See common mistakes.

8. A reading order

  1. Did the test do what you planned? Active threads, hits per second and total samples against the plan.
  2. Was the load generator healthy? Its CPU, memory and GC during the run. If not, stop here.
  3. Errors: when they started, which codes and which labels.
  4. Latency over time, then the percentile table for the steady-state window.
  5. Correlate with server-side metrics for the same window: CPU, saturation, pools, GC, database. The report tells you what happened. Server telemetry tells you why. The USE method is a good checklist.
