JMeter assertions: a 200 is not a pass

Your report shows 0% errors at 800 requests per second. Then someone opens a response and finds the "Sorry, something went wrong" page, served with HTTP 200 and fast because it skips the database. Without assertions, JMeter judges success only by the status code. With too many, the load generator burns CPU checking instead of sending.

1. How JMeter decides pass or fail

A sample starts as successful unless the sampler itself fails. For HTTP, any 4xx or 5xx status, a connection error or a timeout is a failure. Then every assertion in scope runs, and any failing assertion marks the sample failed and writes its message into the failureMessage column of the JTL. The success column is what the HTML report's error rate and APDEX use.

Assertions apply to every sampler in their scope. Put an assertion under one sampler to check that sampler. Put it on the Thread Group to check every sampler in it, which is handy for a blanket "no error page" check.

2. Response Assertion

Add → Assertions → Response Assertion. The general-purpose check.

FieldOptions
Apply toMain sample only, Sub-samples only, Main sample and sub-samples, or a JMeter Variable
Field to TestText Response, Response Code, Response Message, Response Headers, Request Headers, URL Sampled, Document (text), Request Data
Ignore StatusTreat 4xx/5xx as success before the patterns are checked
Pattern Matching RulesContains and Matches (regular expressions), Equals and Substring (plain text). Plus Not and Or modifiers
Custom failure messageReplaces the generated message in the JTL

Three patterns that cover most cases:

1. Right page:      Field: Text Response   Rule: Substring        Pattern: "orderId"
2. No error page:   Field: Text Response   Rule: Substring + Not  Pattern: Something went wrong
3. Expected status: Field: Response Code   Rule: Equals           Pattern: 201
  • Prefer Substring over Contains when you do not need a regex. Substring is a plain, case-sensitive text search and is cheaper.
  • Equals and Matches test the whole field, which suits Response Code but rarely a body.
  • Expecting a 404 or 409? Tick Ignore Status and assert on Response Code equals 404. Ignore Status clears earlier failures on that sample, so only use it on the first assertion.
  • Use the custom failure message, for example Checkout returned error page. The HTML report groups errors by message, so a good message turns a list of failures into a diagnosis.

3. JSON Assertion

Add → Assertions → JSON Assertion. Parses the response as JSON, fails if it is not valid JSON, then checks a JSONPath.

FieldExample
Assert JSON Path exists$.status
Additionally assert valueTicked
Match as regular expressionUnticked for an exact value
Expected ValueCONFIRMED
Expect nullFor fields that must be null
Invert assertionFail if the conditions are met, e.g. $.errors exists

If the path returns an array, the assertion passes when any element matches the expected value. With an indefinite path such as $.items[*].status, always set an expected value. Since JMeter 5.5, an indefinite path that returns an empty list with no expected value fails.

The JSON Assertion parses the full body on every sample. On a 500 KB response at high throughput that is real CPU. If you already have a JSON Extractor on the same sampler, a cheaper check is a Response Assertion on the extracted variable (Apply to: JMeter Variable) that it is not your default value.

4. Duration Assertion

Add → Assertions → Duration Assertion, with one field: Duration in Milliseconds. Any sample slower than this is marked failed.

Use it carefully. It turns a latency question into an error-rate question, so a slow run shows up as "3% errors" rather than as a latency distribution. It also cannot express a percentile target. A p95 under 800 ms target allows 5% of requests above 800 ms, but a Duration Assertion at 800 ms fails every one of them. Good uses are a hard timeout the business really has (a payment gateway that gives up at 10 seconds) and smoke tests. For percentile targets, compute them from the JTL afterwards, as shown in CI pipelines. See also thresholds.

5. Size Assertion

Add → Assertions → Size Assertion: a size in bytes and a comparison (equal, not equal, greater than, less than, and the inclusive versions). It is the cheapest content check there is, because JMeter already knows the size.

Product page:   Size in bytes: 20000   Type of Comparison: >
→ catches the 3 KB error template served with a 200

It suits pages with a predictable size. It is less useful for APIs whose responses vary a lot.

6. What assertions cost

Every assertion runs on the load generator's CPU, for every sample in scope, while the thread that made the request waits. At 2,000 samples per second, 5 assertions per sample means 10,000 checks per second. When the generator's CPU saturates, threads queue for CPU and response times grow. That latency comes from your tool, not from the system under test.

AssertionRelative costWhy
Size, DurationVery lowCompares numbers JMeter already has
Response (Substring, Equals)LowPlain string search
Response (Contains, Matches)MediumRegex over the whole body. Patterns like .* can backtrack badly
JSON, JSON JMESPathMedium to highParses the full document
XPath, XML SchemaHighBuilds a DOM, and XPath with tolerant parsing runs HTML through a cleaner first
JSR223 (Groovy)Depends on the codeFast if compiled and cached, very slow if the script contains ${...}

Watch the load generator's CPU during every test. Above about 70–80%, treat the results as suspect. A useful check is to run the same load with assertions disabled. If response times drop noticeably, the generator was the bottleneck.

7. A sensible assertion strategy

  1. One meaningful check per business request. A Substring on something only the correct response contains ("orderId", the product name).
  2. One blanket negative check at Thread Group level for the site's error page text.
  3. Correlation doubles as validation. If the extractor's default value shows up in the next request, that request will fail anyway. Assert on extracted variables instead of parsing again.
  4. Keep latency judgement out of assertions. Compute percentiles from the results and apply targets there.
  5. Heavier checks during functional debugging, lighter ones under load. Disable the expensive ones in the tree (right-click → Disable) before the big run. The glossary entry on checks and assertions covers the idea in tool-neutral terms.
