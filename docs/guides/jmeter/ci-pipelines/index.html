JMeter in CI: make the pipeline go red

You wire JMeter into the pipeline and it has been green for a month. Then you open a report and find 40% errors in last Tuesday's run. The job was green because JMeter exits with code 0 even when every sample fails. A CI load test needs an explicit pass/fail step, or it is just a slow way to produce artefacts nobody reads.

1. What to run in CI

  • On every merge: a short smoke or baseline test, 5–10 minutes at modest load against a stable environment. It catches the obvious regressions: a new N+1 query, a missing index, a broken endpoint.
  • Nightly or weekly: the full load test at target rate, for 30–60 minutes.
  • Not in CI: stress, spike and soak tests that need someone watching dashboards.

Hosted runners are shared, small machines. They are fine for tens of requests per second. For more, use a self-hosted runner sized for the job, or have the pipeline trigger dedicated load generators. Compare a run only with earlier runs on the same kind of runner against the same environment. The baseline entry explains why.

2. Why the job stays green

In CLI mode JMeter's exit code reports whether the run worked (the plan loaded, the test started and ended), not whether the samples passed. A test with 100% failed requests still exits 0. Assertions mark samples as failed in the results file, and nothing more. You need a step afterwards that reads the results and exits non-zero when targets are missed.

3. A threshold check that fails the build

Save this as perf/check_jtl.py. It uses only the Python standard library, reads the default CSV JTL, computes p95 per label and the overall error rate, prints a table, and exits 1 on any breach.

#!/usr/bin/env python3
"""Fail a CI job when a JMeter CSV results file (JTL) breaks its thresholds.

Usage: python3 check_jtl.py results.jtl --p95 800 --error-rate 1.0 [--ignore "^setUp"]
Exit code 0 = pass, 1 = a threshold failed, 2 = no samples found.
"""
import argparse
import csv
import math
import re
import sys
from collections import defaultdict


def percentile(sorted_ms, p):
    """Nearest-rank percentile: the value at or below which p% of samples fall."""
    rank = max(1, math.ceil(p / 100 * len(sorted_ms)))
    return sorted_ms[rank - 1]


ap = argparse.ArgumentParser()
ap.add_argument("jtl")
ap.add_argument("--p95", type=float, default=800, help="max p95 per label, in ms")
ap.add_argument("--error-rate", type=float, default=1.0, help="max overall error rate, in %%")
ap.add_argument("--ignore", default="", help="regex of labels to leave out")
args = ap.parse_args()

skip = re.compile(args.ignore) if args.ignore else None
times = defaultdict(list)
errors = total = 0
with open(args.jtl, newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f):
        if skip and skip.search(row["label"]):
            continue
        times[row["label"]].append(int(row["elapsed"]))
        total += 1
        if row["success"] != "true":
            errors += 1

if total == 0:
    print("No samples found - did the test run at all?")
    sys.exit(2)

failed = False
print(f"{'label':40} {'count':>7} {'p95 ms':>8}")
for label, ms in sorted(times.items()):
    ms.sort()
    p95 = percentile(ms, 95)
    flag = "  <-- over budget" if p95 > args.p95 else ""
    failed |= bool(flag)
    print(f"{label[:40]:40} {len(ms):7d} {p95:8d}{flag}")

rate = 100 * errors / total
print(f"\nerrors: {errors}/{total} = {rate:.2f}% (limit {args.error_rate}%)")
if rate > args.error_rate:
    failed = True
print("FAIL" if failed else "PASS")
sys.exit(1 if failed else 0)
$ python3 perf/check_jtl.py results.jtl --p95 800 --error-rate 1 --ignore "^00 "
label                                      count   p95 ms
01 Home                                     4210      212
02 Search                                   4188      655
03 Product                                  4175      931  <-- over budget

errors: 12/12573 = 0.10% (limit 1.0%)
FAIL

The percentile uses the nearest-rank method, so it is a value that actually occurred. The HTML dashboard may differ slightly because it uses a different percentile calculation. Both are fine for a gate as long as you compare like with like. If you use Transaction Controllers with "Generate parent sample", their parent samples are in the JTL too, and you may want to exclude either the parents or the children with --ignore. To see the full distribution of a JTL interactively, open it in the JTL analyser.

4. GitHub Actions

Runs on demand with a chosen user count and on a weekday schedule. The JMeter download is cached, the secret comes from repository secrets, and the report is uploaded even when the threshold step fails.

# .github/workflows/load-test.yml
name: load-test

on:
  workflow_dispatch:
    inputs:
      users:
        description: Concurrent users
        default: "20"
  schedule:
    - cron: "0 15 * * 1-5"   # 15:00 UTC on weekdays

jobs:
  jmeter:
    runs-on: ubuntu-latest
    timeout-minutes: 45
    env:
      JMETER_VERSION: "5.6.3"
      USERS: ${{ inputs.users || '20' }}
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"

      - name: Cache JMeter
        id: cache-jmeter
        uses: actions/cache@v4
        with:
          path: apache-jmeter-${{ env.JMETER_VERSION }}
          key: jmeter-${{ env.JMETER_VERSION }}

      - name: Download JMeter
        if: steps.cache-jmeter.outputs.cache-hit != 'true'
        run: |
          curl -sSfL "https://archive.apache.org/dist/jmeter/binaries/apache-jmeter-${JMETER_VERSION}.tgz" | tar xz

      - name: Run test
        env:
          CLIENT_SECRET: ${{ secrets.PERF_CLIENT_SECRET }}
        run: |
          apache-jmeter-${JMETER_VERSION}/bin/jmeter -n -t perf/plan.jmx \
            -q perf/env/staging.properties \
            -Jusers="$USERS" -JclientSecret="$CLIENT_SECRET" \
            -l results.jtl -j jmeter.log -e -o report

      - name: Check thresholds
        run: python3 perf/check_jtl.py results.jtl --p95 800 --error-rate 1

      - name: Upload results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: jmeter-report
          path: |
            report/
            results.jtl
            jmeter.log

Notes:

  • if: always() on the upload step matters. Without it the report disappears exactly when you need it, on a failed run.
  • If the plan uses plugins, install them in the cached folder: download the Plugins Manager jar into lib/ext, then run bin/PluginsManagerCMD.sh install jpgc-casutg (with your plugin ids). Better still, commit a list of plugin ids and install from it, so CI matches your workstation.
  • Pin the JMeter version. Results from different JMeter versions are not always comparable.

5. GitLab CI

The eclipse-temurin images are Ubuntu-based, so apt-get can add curl and python3. Add PERF_CLIENT_SECRET as a masked CI/CD variable.

# .gitlab-ci.yml
stages:
  - perf

load-test:
  stage: perf
  image: eclipse-temurin:17-jre
  timeout: 45m
  variables:
    JMETER_VERSION: "5.6.3"
    USERS: "20"
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
    - if: $CI_PIPELINE_SOURCE == "web"
  cache:
    key: jmeter-$JMETER_VERSION
    paths:
      - apache-jmeter-$JMETER_VERSION/
  before_script:
    - apt-get update -qq && apt-get install -y -qq curl python3 > /dev/null
    - |
      if [ ! -d "apache-jmeter-$JMETER_VERSION" ]; then
        curl -sSfL "https://archive.apache.org/dist/jmeter/binaries/apache-jmeter-$JMETER_VERSION.tgz" | tar xz
      fi
  script:
    - >
      apache-jmeter-$JMETER_VERSION/bin/jmeter -n -t perf/plan.jmx
      -q perf/env/staging.properties
      -Jusers="$USERS" -JclientSecret="$PERF_CLIENT_SECRET"
      -l results.jtl -j jmeter.log -e -o report
    - python3 perf/check_jtl.py results.jtl --p95 800 --error-rate 1
  artifacts:
    when: always
    expire_in: 14 days
    paths:
      - report/
      - results.jtl
      - jmeter.log

The folded block (>) joins the JMeter command into a single line, so no backslashes are needed. artifacts: when: always keeps the report on failed jobs. Trigger it from Build → Pipeline schedules, or run it by hand from the pipeline page.

6. Alternative: gate on statistics.json

When you generate the HTML report with -e -o report, JMeter also writes report/statistics.json: one object per label plus Total, with fields such as sampleCount, errorPct, meanResTime, medianResTime, pct1ResTime, pct2ResTime, pct3ResTime and throughput. The three percentiles default to p90, p95 and p99 (properties aggregate_rpt_pct1 to pct3). A one-line gate with jq, which is preinstalled on GitHub's Ubuntu runners:

jq -e '.Total.errorPct < 1 and .Total.pct2ResTime < 800' report/statistics.json

jq -e exits 1 when the expression is false. This gates on the overall numbers only. Use the Python check for per-label budgets.

The dashboard also shows an APDEX score, with thresholds set by jmeter.reportgenerator.apdex_satisfied_threshold (default 500 ms) and apdex_tolerated_threshold (default 1500 ms). APDEX is not in statistics.json, though, and a single index hides which transaction regressed. For gating, percentiles and error rate per label are clearer.

7. Making CI results trustworthy

  • Fail on "no samples". A typo in the host gives a run with zero or all-failed samples. The script exits 2 on an empty JTL.
  • Leave headroom in thresholds. Shared environments are noisy. A gate that fails one run in five gets switched off. Start with the baseline plus 20–30% and tighten it as the environment stabilises.
  • Keep history. Upload statistics.json somewhere durable (an artefact store, a metrics database through the Backend Listener) and chart it per build. Trends catch slow creep that no single threshold will.
  • Pin the environment. Record the app version, environment and data volume with each run. A faster result on an empty database is not an improvement.
