JMeter auth tokens: log in once, not on every loop

Your four-hour soak test is green for exactly one hour. From minute 60 every request returns 401, because the access token expired and nothing renewed it. Or the opposite: every iteration logs in again, and the identity provider becomes the bottleneck you end up reporting. This guide covers the patterns that avoid both.

1. Pick the right pattern

SituationPattern
Each virtual user is a different person (web or mobile app)Per-thread login in a Once Only Controller, token in a variable
Service-to-service API with one client IDOne token fetched in a setUp Thread Group, shared as a property
Test is longer than the token lifetimeExpiry check in an If Controller (per thread) or a refresher thread group (shared)
You are load testing the login itselfLogin is a normal sampler inside the loop, with its own target rate

The question to ask the product owner is how often real users log in. A banking app might log in on almost every session. A B2B dashboard might keep a session for a full working day. Copy that ratio, do not default to "every iteration" or "never".

2. Per-user login with Once Only Controller

Thread Group  (Same user on each iteration: ticked)
├── CSV Data Set Config          users.csv → username, password
├── HTTP Cookie Manager
├── HTTP Header Manager          Authorization: Bearer ${token}
├── Once Only Controller
│   └── POST /auth/login         body: {"username":"${username}","password":"${password}"}
│       └── JSON Extractor       token ← $.accessToken   default TOKEN_NOT_FOUND
├── GET  /api/accounts
└── POST /api/transfers

The Once Only Controller (Add → Logic Controller → Once Only Controller) runs its children only on the first iteration of each thread. Every later iteration reuses that thread's ${token}. Variables are per thread, so 200 threads hold 200 independent tokens.

The CSV row is read at the start of every iteration, but the login only runs on the first. From iteration 2 onwards ${username} no longer matches the logged-in token. If later requests use the username, copy it into another variable during login, for example with a JSR223 PostProcessor: vars.put('loginUser', vars.get('username')), and use ${loginUser} afterwards.

3. Sending the Bearer header

Add Config Element → HTTP Header Manager with Authorization = Bearer ${token}. Where you place it decides which requests get it:

  • At Thread Group level it applies to every sampler, including the login call. Most identity providers ignore an invalid Bearer TOKEN_NOT_FOUND header on the token endpoint, but some reject it. If yours does, move the business requests under a Simple Controller and put the Header Manager there.
  • Several Header Managers in scope are merged into one list. If two of them set the same header name, only one value is sent, so avoid duplicates rather than relying on which one wins.

Header values are evaluated per request, so Bearer ${token} always uses the thread's current value, and Bearer ${__P(accessToken)} always reads the current property.

4. OAuth2 client credentials

The client-credentials grant is a form POST to the token endpoint. In an HTTP Request sampler:

FieldValue
Method / PathPOST /oauth2/token (check your provider's discovery document)
Parameters tabgrant_type = client_credentials
client_id = ${__P(clientId)}
client_secret = ${__P(clientSecret)}
scope = payments.read
Header ManagerContent-Type = application/x-www-form-urlencoded
JSON ExtractorNames token;expiresIn, paths $.access_token;$.expires_in, match 1;1, defaults TOKEN_NOT_FOUND;300
Response AssertionResponse Code equals 200, so a failed token call stops looking like success

Pass the secret in at run time (-JclientSecret=$CLIENT_SECRET from a CI secret), never in the .jmx. Some providers want the client ID and secret in a Basic auth header instead of the body. A JSR223 PreProcessor on the token request can build it:

// JSR223 PreProcessor, language groovy
def raw = props.get('clientId') + ':' + props.get('clientSecret')
vars.put('basicAuth', 'Basic ' + raw.bytes.encodeBase64().toString())
// then Header Manager: Authorization = ${basicAuth}

5. One shared token: setUp Thread Group and properties

When every thread can use the same token, fetch it once. A setUp Thread Group (Add → Threads (Users) → setUp Thread Group) runs to completion before normal thread groups start. Variables do not cross thread boundaries, so hand the value over as a property:

setUp Thread Group  (1 thread, 1 loop)
└── POST /oauth2/token
    ├── JSON Extractor        token ← $.access_token
    └── JSR223 PostProcessor  props.put('accessToken', vars.get('token'))

Thread Group  (the real load)
├── HTTP Header Manager       Authorization: Bearer ${__P(accessToken)}
└── ... business requests ...

Post-processors under the same sampler run in tree order, so keep the JSR223 PostProcessor below the JSON Extractor. If you prefer functions to scripts, any evaluated field can call __setProperty. A common idiom is a Debug Sampler in the setUp group named Save token ${__setProperty(accessToken,${token},)}. It works, but the script version is easier for the next person to spot.

In distributed mode every remote node runs its own setUp Thread Group, so each node fetches its own token. That is usually fine. If the provider limits token issuance per client, plan for one call per node.

6. Refreshing before expiry

Per-thread tokens: an If Controller in front of the work

Replace the Once Only Controller with an If Controller that fetches a token when there is none or it is about to expire. The same branch handles the first login and every refresh.

Thread Group
├── HTTP Header Manager            Authorization: Bearer ${token}
├── If Controller                  "If token missing or expiring"
│   │  Condition (Interpret Condition as Variable Expression: ticked):
│   │  ${__groovy(System.currentTimeMillis() > (vars.get('tokenExpiry') ?: '0').toLong(),)}
│   └── POST /oauth2/token
│       ├── JSON Extractor         token;expiresIn ← $.access_token;$.expires_in
│       └── JSR223 PostProcessor   (script below)
└── ... business requests ...
// JSR223 PostProcessor, language groovy: refresh 60 s before the real expiry
long ttl = (vars.get('expiresIn') ?: '300').toLong()
vars.put('tokenExpiry', String.valueOf(System.currentTimeMillis() + (ttl - 60) * 1000))

The If Controller runs at the start of each iteration. With a 3-second iteration and a 1-hour token, that is one token call per user per hour, which matches how a real client behaves. If your API offers a refresh_token grant, use it inside the same branch with grant_type=refresh_token.

Shared token: a refresher thread group

Thread Group "Token refresher"   1 thread, Loop Count: Infinite,
│                                Specify Thread lifetime: same duration as the test
├── POST /oauth2/token
│   ├── JSON Extractor           token;expiresIn
│   └── JSR223 PostProcessor     props.put('accessToken', vars.get('token'))
└── Flow Control Action          Logical action: Pause, Duration (ms):
                                 ${__groovy(((vars.get('expiresIn') ?: '300').toLong() - 60) * 1000,)}

Keep the setUp group too, so the first token exists before load starts. The worker threads read ${__P(accessToken)} on every request and pick up the new value as soon as it is stored.

7. Pitfalls

  • Token calls in the results. They are real samples. Name them clearly (00 Auth token) and exclude them from SLA checks if they are not part of what you are testing. They still count toward error rate, which is what you want.
  • Rate limits on the identity provider. Ramping 2,000 threads with ramp-up 0 sends 2,000 logins at once. Ramp up gradually, as real users arrive. See ramp-up.
  • MFA and captchas. Ask for a test-only bypass or pre-issued tokens in the test environment. Do not try to script around them.
  • Silent failures. A distinctive default (TOKEN_NOT_FOUND) plus a Response Assertion on the token call turns a confusing wall of 401s into one obvious error.
  • Cookie-based sessions. If the app uses session cookies rather than tokens, the HTTP Cookie Manager does the work. Tick "Same user on each iteration" on the Thread Group so the cookies survive between iterations.
