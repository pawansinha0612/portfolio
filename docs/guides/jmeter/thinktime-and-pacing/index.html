JMeter think time and pacing: 50 users is not a load level

Your test has 50 threads and no timers. Each thread fires the next request the instant the last one returns, so 50 "users" generate 2,000 requests per second. That can be more traffic than your real peak of 20,000 users ever produces. Or you add think time and the rate collapses the moment the server slows down. Timers decide what load you are really applying.

1. How timers work (and why they stack)

  • A timer runs before each sampler in its scope. Its delay is not included in the sample's response time.
  • A timer at Thread Group level applies to every sampler in the group. Ten samplers means ten pauses per iteration.
  • Several timers in the same scope add up. A Constant Timer of 1 s plus a Uniform Random Timer of 0–2 s gives 1–3 s before each sampler.
  • To pause before one sampler only, make the timer its child. To pause after a step, add a Flow Control Action sampler (Logical action: Pause, Duration 0) and put the timer under it. Flow Control Action does not write a sample to the results.

Model think time where a real user pauses: after a page loads and before the next click. API calls a browser fires together with no pause between them should have no timer between them.

Inside a Transaction Controller, the tick box "Include duration of timer and pre-post processors in generated sample" decides whether think time inflates the transaction's time. Leave it unticked unless you really want to measure user journey time including pauses.

2. Constant, Uniform and Gaussian timers

TimerFieldsDelayExample
Constant TimerThread Delay (ms)Exactly the value3000 → 3 s every time

Gaussian Random TimerDeviation, Constant Delay Offset (ms)offset + normal(0, 1) × deviationoffset 3000, deviation 500 → about 68% within 2.5–3.5 s

Avoid constant think time under load. Identical pauses keep threads in lockstep, so requests arrive in synchronised waves rather than the smooth, random stream real users produce. A Uniform or Gaussian timer around the same mean breaks the pattern. For Gaussian timers, keep the offset at least three times the deviation so delays stay clearly positive.

Make think time adjustable so smoke tests run fast: ${__P(thinkMs,3000)} in the offset field, then -JthinkMs=0 for a quick functional pass.

3. Pacing a whole iteration

Pacing fixes how often an iteration starts, whatever its response times. For example, "each user places one order every 30 seconds". If the iteration took 12 seconds, wait 18. JMeter has no pacing field, but two elements and a Groovy expression give you one:

Thread Group
├── Flow Control Action "Iteration start"    Pause, Duration 0
│   └── JSR223 PreProcessor (groovy)
│         vars.put('iterStart', String.valueOf(System.currentTimeMillis()))
├── ... the business steps, with their own think times ...
└── Flow Control Action "Pacing"             Logical action: Pause
      Duration (milliseconds):
      ${__groovy(long left = ${__P(pacingMs,30000)} - (System.currentTimeMillis() - vars.get('iterStart').toLong()); left > 0 ? left : 0,)}

The expression avoids commas on purpose, because a bare comma would end the function argument. If the iteration overruns the pacing interval, the pause is zero and the next iteration starts at once. The achieved rate then falls below plan, which is exactly what you want to notice.

4. Constant vs Precise Throughput Timer

Both timers hold a target rate by adjusting delays. Neither creates threads. If there are not enough threads to reach the target, or the server slows down, you get less than you asked for.

Repeatable runsNot applicableSet a non-zero Random seed to replay the same schedule
Best for"Hold 1,200 requests per minute" in a simple wayRealistic random arrivals at a business rate

Where you put them matters. A throughput timer counts every sampler in its scope, so one at Thread Group level with five samplers per iteration controls requests, not iterations. To control iterations, put it under the first sampler of the iteration (or under a Flow Control Action at the top).

Precise Throughput Timer for "300 orders per hour" during a 1-hour test:
  Target throughput (in samples per 'throughput period'):  300
  Throughput period (seconds):                             3600
  Test duration (seconds):                                 3600
  Number of threads in the batch:                          1
  Delay between threads in the batch (ms):                 0
  Random seed:                                             0  (or a fixed value for repeatable runs)

The JMeter-Plugins Throughput Shaping Timer (a community plugin) goes further: it takes a schedule of requests per second over time and, paired with the Concurrency Thread Group, can adjust thread counts through its __tstFeedback function. See thread groups and load shapes.

5. Open vs closed model, honestly

A standard Thread Group is a closed workload model: a fixed number of threads, each sending its next request only after the previous one finishes. When the server slows down, every thread waits longer, so the arrival rate drops. The test eases off exactly when the system struggles. Throughput timers do not change this. They only add delay, so they can cap the rate but cannot keep it up once response times exceed the gaps.

The side effect is coordinated omission: the requests that would have arrived during a stall are never sent, so they are never measured, and the percentiles look better than what users experienced. The percentiles explainer shows the effect interactively.

Real public traffic is mostly open: new users arrive whether or not your server is coping. JMeter's options for that:

  • Open Model Thread Group (core, added in JMeter 5.5, still marked experimental). You give it a schedule such as rate(0) random_arrivals(5 min) rate(50/sec) random_arrivals(30 min) pause(2 min) and it starts a new thread for each arrival.
  • Arrivals Thread Group (Custom Thread Groups plugin). Target arrival rate per minute or second, with a Concurrency Limit as a safety valve.

Neither is magic. An open model with a slow server keeps adding threads, and the load generator needs the memory and CPU for them. Set a concurrency cap and watch the generator.

Which to use? A closed model is right when the user population really is fixed: 200 call-centre agents, a batch of 40 workers. An open model is right for anything internet-facing where arrivals are independent of your response time. The glossary entry on open vs closed workload models and the load profiles explainer go deeper.

6. Sizing threads with Little's Law

For a closed model, Little's Law tells you how many threads you need: threads = throughput × (response time + think time).

Target:          20 iterations per second
Iteration time:  6 steps × 0.4 s response = 2.4 s
Think time:      6 pauses × 3 s           = 18 s
Threads needed:  20 × (2.4 + 18) = 408 threads

If responses slow to 1.5 s each: 20 × (9 + 18) = 540 threads needed.
With only 408 threads the rate falls to 408 / 27 ≈ 15 per second.

Provision headroom of 20–30% more threads than the calculation says, and let a throughput timer or pacing cap the rate. Then the plan still reaches its target when response times rise. The queueing explainer shows why response times climb so sharply near saturation.
