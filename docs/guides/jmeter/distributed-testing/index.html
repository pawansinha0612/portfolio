JMeter distributed testing without the RMI pain

One load generator tops out at 85% CPU and your response times start rising, but the application's dashboards look calm. The bottleneck is your test rig. Distributed mode spreads the plan across several machines, and comes with its own traps: RMI ports, keystores, and every node logging in as the same user.

1. Do you actually need it?

First make one generator efficient: CLI mode, no View Results Tree, light assertions, enough heap (see common mistakes). A tuned generator with 4–8 vCPUs often drives a few thousand HTTP requests per second, though the real number depends heavily on response sizes, TLS and scripting. Measure it: increase load until the generator's CPU passes about 70%, and that is its budget.

Distribute when one machine cannot reach the target within that budget, when the network link saturates, or when you need traffic from several regions.

2. How it works

                 ┌──────────────► jmeter-server  (node A) ──┐
 controller ─────┼──────────────► jmeter-server  (node B) ──┼──► system under test
 (jmeter -n -R)  └──────────────► jmeter-server  (node C) ──┘
       ▲                                 │
       └──────── samples streamed back ──┘
  • The controller sends the .jmx to each server. Each server runs the full plan. 300 threads × 3 servers = 900 threads.
  • Data files (CSV, bodies, certificates) are not sent. Each server reads its own local copy.
  • Results come back to the controller over RMI. The default sender mode is StrippedBatch: response data of successful samples is dropped and samples are sent in batches. The controller writes the JTL.
  • All nodes need the same JMeter version, the same plugins and ideally the same Java version.

3. Setting up the nodes

On each load generator (server):

# same JMeter build and plugins as the controller
export HEAP="-Xms4g -Xmx4g -XX:MaxMetaspaceSize=256m"
export RMI_HOST_DEF=-Djava.rmi.server.hostname=10.0.1.21   # this node's reachable IP
bin/jmeter-server -Jserver.rmi.localport=50000

jmeter-server starts its own RMI registry on port 1099 and then waits for tests. java.rmi.server.hostname tells RMI which address to advertise. Set it whenever the machine has more than one interface or sits behind NAT, or connections fail in confusing ways. The bin/jmeter-server script reads it from RMI_HOST_DEF.

4. The RMI SSL keystore

Since JMeter 4.0, RMI traffic uses SSL by default, so every node and the controller need the same keystore. Create it once:

cd apache-jmeter-5.6.3/bin
./create-rmi-keystore.sh
# answer "rmi" for "What is your first and last name?"
# (it must match server.rmi.ssl.keystore.alias, default "rmi")
# → writes rmi_keystore.jks

Copy rmi_keystore.jks into bin/ on the controller and every server, or point server.rmi.ssl.keystore.file at it. The certificate the script creates is valid for seven days. If distributed runs suddenly fail after a week, regenerate it, or generate your own with keytool and a longer validity.

On an isolated, trusted test network you can switch SSL off instead. Set it on every node, controller included:

# user.properties on every machine
server.rmi.ssl.disable=true

5. Running with -R

jmeter -n -t plan.jmx \
  -R 10.0.1.21,10.0.1.22,10.0.1.23 \
  -Gusers=300 -Grampup=600 -Gduration=3600 -Ghost=staging.example.com \
  -l results.jtl -e -o report/ -X
FlagMeaning
-R host1,host2Start these remote servers (overrides remote_hosts)
-rStart all servers listed in the remote_hosts property
-Gname=valueSet a property on all servers. Use this, not -J, for anything __P reads in the plan
-XExit the remote servers when the test ends

-Jusers=300 sets the property only on the controller, so the servers fall back to the plan's default and you get a different load than you planned. In distributed runs, every load setting goes through -G. Remember the per-node multiplication: -Gusers=300 on 3 nodes is 900 users. Divide your targets, including any throughput timer rate, by the number of nodes.

The "Active Threads Over Time" graph in the HTML report shows threads per server, not the total. That is a known limitation.

6. Test data per node

Each server reads data/users.csv relative to its own working directory. If the files are identical, all three nodes log in as the same users in the same order. Split the file instead:

# split users.csv round-robin into 3 files, each with the header line
awk -v n=3 'NR==1 {for (i=0; i<n; i++) print > ("users_" i ".csv"); next}
            {print > ("users_" (NR-2)%n ".csv")}' users.csv
# → users_0.csv, users_1.csv, users_2.csv
# copy users_0.csv to node A as data/users.csv, users_1.csv to node B, and so on

Alternatively, keep a different filename per node and set it with a node-local property: user.properties on node A holds datafile=users_0.csv, and the CSV Data Set Config Filename is data/${__P(datafile,users.csv)}. For generated values, add the host to keep them unique: order-${__machineName}-${__threadNum}-${__time()}.

7. Ports, firewalls and NAT

DirectionPortProperty
Controller → server (registry)1099server_port
Controller → server (engine)Random unless setserver.rmi.localport
Server → controller (results)Random unless set, up to 3 ports from the baseclient.rmi.localport

Results flow back on a new connection from the server to the controller, so the controller must be reachable from every server. Fix the ports (for example server.rmi.localport=50000 and client.rmi.localport=60000), open them in security groups, and set java.rmi.server.hostname on the controller too. This return connection is why distributed JMeter rarely works across NAT or between a laptop on VPN and cloud servers.

8. Independent runs or cloud instead

The controller is a single point of failure and a bottleneck: all samples funnel through it. A simpler pattern many teams prefer:

  1. Start the same plan in CLI mode on each generator at the same time (Ansible, SSH loop, or a CI matrix job), each with its own -J settings and data slice.
  2. Collect each node's JTL and concatenate them, keeping one header line.
  3. Build one report: jmeter -g all.jtl -o report/.
head -1 node-a.jtl > all.jtl
for f in node-*.jtl; do tail -n +2 "$f" >> all.jtl; done
jmeter -g all.jtl -o report/

Keep the generators' clocks in sync with NTP, because timestamps from different machines end up on one timeline.

If you would rather not run infrastructure at all, managed services run your .jmx across many engines. Azure Load Testing and BlazeMeter both accept JMeter scripts, and there are others. You trade money and some flexibility for not dealing with RMI, keystores and scaling. Kubernetes-based setups are a middle path when the team already runs a cluster. If you are rethinking the tool as well, k6 vs JMeter covers how the two scale differently.
