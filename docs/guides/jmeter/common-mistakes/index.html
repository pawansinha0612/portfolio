12 JMeter mistakes that quietly invalidate a test

Your test "proves" the system handles 3,000 users. In production it falls over at 1,200. Nothing crashed in the test, and the report looked clean. The load was simply wrong: the generator was the bottleneck, users never paused, the cache was never cold, or slow responses were never sent. These are the mistakes to rule out before you trust a number.

1. Running load in GUI mode

The Swing GUI repaints trees and graphs while your threads compete for the same CPU. Results get slower as the GUI gets busier, and long runs can freeze it. Build and debug in the GUI with a handful of threads, then run every real test in CLI mode: jmeter -n -t plan.jmx -l results.jtl -e -o report/. See getting started.

2. Listeners enabled during load

View Results Tree keeps every request and response in memory. Aggregate Report, Summary Report and the graph listeners compute on every sample. In CLI mode they still run, and some write their own files. Remove or disable them before a load run, keep only -l for results, and generate the HTML report afterwards. The one listener worth keeping is a Backend Listener feeding InfluxDB for live monitoring, which sends aggregates. See results and reports.

3. Running on the default 1 GB heap

The jmeter start script defaults to -Xms1g -Xmx1g -XX:MaxMetaspaceSize=256m. That suits debugging, not hundreds of threads with large responses. Override it with the HEAP environment variable rather than editing the script:

# macOS / Linux
HEAP="-Xms4g -Xmx4g -XX:MaxMetaspaceSize=256m" jmeter -n -t plan.jmx -l results.jtl

# Windows (cmd)
set HEAP=-Xms4g -Xmx4g -XX:MaxMetaspaceSize=256m
jmeter.bat -n -t plan.jmx -l results.jtl

Leave room for the operating system and network buffers. Around half to three quarters of the machine's RAM is a sensible ceiling. Setting -Xms equal to -Xmx avoids heap resizing during the run. Signs you need more: OutOfMemoryError in jmeter.log, or long GC pauses showing up as latency spikes across every label at once.

4. Not watching the load generator

If the generator's CPU is saturated, threads queue for CPU before sending and before timing the response, so every measurement includes your own bottleneck. Watch CPU, memory, GC and network on every generator during the run. Above about 70–80% CPU, add generators or reduce per-sample work (fewer assertions, less regex, no saved response data). Never run the generator on the same host as the system under test. See distributed testing.

5. Missing cookie and cache managers

  • HTTP Cookie Manager: without it, Set-Cookie is ignored and sessions break, sometimes with 200 responses that are really login pages. Add one at Thread Group level in almost every web test. Tick "Clear cookies each iteration" if each iteration should be a new visitor.
  • HTTP Cache Manager: browsers cache static content. Without a cache manager, every iteration re-downloads every embedded resource, and the test over-loads static content. With one, honour Cache-Control and Expires on GET requests and decide whether each iteration is a new visitor ("Clear cache each iteration" ticked) or a returning one.
  • Tick Same user on each iteration on the Thread Group for returning visitors. Untick it and every iteration opens new connections, with a new TLS handshake each time. That is realistic for first visits but costly, so make it a decision, not an accident.

6. Embedded resources handled wrongly

JMeter does not run JavaScript. It fetches only what you script, plus embedded resources parsed from HTML if you ask it to. In the HTTP Request's Advanced tab (or HTTP Request Defaults):

  • Retrieve All Embedded Resources: parses HTML for images, CSS and scripts and fetches them as sub-samples.
  • Parallel downloads (called "Use concurrent pool" in the reference docs): how many embedded resources each thread fetches at once, like a browser's connection pool. Around 6 per host is typical for browsers.
  • URLs must match: a regex to keep only your own domains, for example https?://([^/]+\.)?example\.com/.*. Do not load test Google Analytics, a payment provider's widget or a third-party CDN without permission. "URLs must not match" does the opposite, for example to skip fonts or images.

API calls made by front-end JavaScript (XHR, fetch) are never discovered this way. Record them with the HTTP(S) Test Script Recorder or add them by hand. And if static content is served by a CDN in production, decide whether the test should hit the origin at all. Usually it should not. See CDN hit ratio.

7. No think time

Without timers, each thread fires requests back to back. 100 threads become a far heavier load than 100 real users, and the thread count stops meaning anything. Add Uniform or Gaussian random timers where users pause, or pace the iteration to a target rate. If the goal is a request rate rather than a user count, say so and use a throughput timer or an arrivals-based thread group. See think time and pacing and think time.

8. Ramp-up of zero

All threads start in the same second: logins collide, connection pools and autoscalers get a thundering herd, and the first minutes of data describe an event production never sees. Ramp at a realistic rate of new sessions and analyse only the steady state. If a sudden surge is what you want to test, design a spike test on purpose. See thread groups and load shapes.

9. One user, one search term

Every thread logging in as testuser1 and searching for "shoes" exercises one cache entry and one row lock. Results are either far too good (everything cached) or far too bad (contention on one record). Use CSV data with enough rows for the test, and a realistic spread of popular and rare items. See parameterisation.

10. No timeouts

The HTTP Request's Connect and Response timeouts are empty by default, so a hung request holds its thread until the operating system or server gives up, often minutes later. Threads silently drop out of the load and the arrival rate falls. Set timeouts in HTTP Request Defaults to match your clients, for example Connect 5000 and Response 30000 ms. A timeout then appears as an error you can count, not as missing load.

11. BeanShell, or ${} inside Groovy

BeanShell is interpreted and much slower than Groovy under load. Use JSR223 elements with language groovy and keep "Cache compiled script if available" ticked. Never write ${var} inside the script body. JMeter substitutes it before compilation, so the script text changes on every call and cannot be cached. Read values with vars.get('var') and properties with props.get('name'). Pass values in through the Parameters field (as args) if needed.

12. Ignoring coordinated omission

In a standard Thread Group, a thread waiting on a slow response sends nothing else. During a 5-second stall, the requests real users would have sent in those 5 seconds are never made, so the slowest period is the least sampled. Percentiles then look better than what users lived through. This is coordinated omission.

Signs of it: hits per second dips at the same moment response times spike. Mitigations: keep enough threads that the target rate holds even at degraded response times, use the Open Model Thread Group or Arrivals Thread Group when arrivals should not depend on your server, and report the achieved rate next to the latency. The percentiles explainer shows the effect, and this article goes deeper.

Before you trust the numbers

  1. CLI mode, listeners off, heap sized, generator healthy throughout.
  2. Achieved request rate and thread count matched the plan.
  3. Error rate understood, with assertions that catch error pages.
  4. Realistic data, think time, ramp-up and caching behaviour.
  5. Steady-state window analysed, warm-up excluded.
