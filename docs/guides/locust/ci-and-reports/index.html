Locust in CI: reports and a budget that fails the build

Locust in CI either fails on every single error, including the one timeout in 50,000 requests, or never fails at all. Neither is useful. What you want is a budget: p95 under a limit and failures under a rate, the same way you'd write an SLO.

What Locust does by default

A headless run exits with code 1 if any request failed, and 0 otherwise. You can change the code used with --exit-code-on-error. That's all-or-nothing: one timeout in a long run fails the build, and a very slow but error-free run passes. Locust has no built-in latency budget.

A pass/fail budget with an event listener

Locust fires a quitting event just before it exits. A listener can read the final statistics and set environment.process_exit_code, which replaces the default:

import logging

from locust import HttpUser, task, constant, events


class ApiUser(HttpUser):
    wait_time = constant(1)

    @task
    def browse(self):
        self.client.get("/products")


@events.quitting.add_listener
def enforce_budget(environment, **kwargs):
    """Set the process exit code from the results, so CI fails on a breach."""
    stats = environment.stats.total
    p95 = stats.get_response_time_percentile(0.95)
    if stats.num_requests == 0:
        logging.error("No requests were made")
        environment.process_exit_code = 1
    elif stats.fail_ratio > 0.01:
        logging.error(f"Failed: {stats.fail_ratio:.2%} of requests failed (budget 1%)")
        environment.process_exit_code = 1
    elif p95 > 500:
        logging.error(f"Failed: p95 {p95:.0f} ms (budget 500 ms)")
        environment.process_exit_code = 1
    else:
        environment.process_exit_code = 0
  • environment.stats.total is the aggregate of all requests. environment.stats.get(name, method) gives one request, for per-endpoint budgets.
  • fail_ratio is a fraction: 0.01 is 1%.
  • Setting the exit code to 0 when within budget is deliberate: it overrides the default "any failure means 1", so a single timeout inside a 1% budget doesn't fail the build.
  • The "no requests" branch catches a broken test (wrong host, every user crashed in on_start) that would otherwise pass with perfect numbers.
  • In a distributed run, put the listener in the locustfile used by the master. The master has the aggregated statistics from all workers.

Set the numbers from your SLO or with the SLO calculator, not from a single lucky run.

CSV, HTML and JSON reports

locust -f locustfile.py --headless -u 50 -r 5 -t 15m \
  --csv results/run --csv-full-history \
  --html results/report.html \
  --json-file results/stats
FileContains
run_stats.csvFinal numbers per request: counts, failures, median, average, percentiles, req/s
run_stats_history.csvThe aggregate over time, a row every few seconds. Add --csv-full-history for every request name.
run_failures.csvEach distinct failure and how often it happened
run_exceptions.csvPython exceptions in your locustfile
report.htmlSelf-contained report with charts, the one to attach to a ticket
--json / --json-fileFinal stats as JSON, for your own tooling

Folders in the --csv prefix are created for you. The stats history is what you chart to see whether latency climbed during the steady state. Always read run_exceptions.csv: a non-empty file means part of your test didn't run.

GitHub Actions

# .github/workflows/locust.yml
name: Locust load test
on:
  workflow_dispatch:
  pull_request:

jobs:
  locust:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r perf/requirements.txt     # pins locust==<version>

      - name: Run Locust
        working-directory: perf
        env:
          LOCUST_HOST: ${{ vars.STAGING_URL }}
        run: >
          locust -f ci_exit.py --headless
          -u 20 -r 5 -t 2m
          --csv results/run --html results/report.html --only-summary

      - uses: actions/upload-artifact@v4
        if: always()                                  # keep the report when the budget fails
        with:
          name: locust-report
          path: perf/results/

Locust reads LOCUST_HOST (and any other option as LOCUST_ plus the name) from the environment, which keeps URLs out of the workflow file. The upload step runs with if: always() so you get the report from a failed run.

Making CI results trustworthy

  • Small load on pull requests, real load on a schedule. 20 users for two minutes catches broken endpoints and big regressions. Capacity questions need a full run against a production-like environment.
  • Watch the runner's CPU. Hosted runners are small. If Locust prints a CPU warning, the latency numbers include Locust's own delay. Use FastHttpUser, fewer users, or a bigger runner.
  • Budget from data. Run the test several times, take the worst p95 and add headroom. A budget inside the run-to-run noise fails randomly, and gets disabled.
  • Keep reports. Name artifacts by commit and keep a few weeks of them, so you can find when a regression started.
