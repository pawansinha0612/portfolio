Distributed Locust: when one core isn't enough

You ask for 2,000 users. Locust prints a CPU warning, the request rate flattens at 600 a second, and response times climb. The server is fine. The load generator is maxed out on one core, and the test is now measuring Locust.

On this page

  1. Why Locust needs to be distributed
  2. One machine, many cores: --processes
  3. Several machines: master and workers
  4. Docker Compose

Why Locust needs to be distributed

A Locust process runs your users as gevent greenlets in one Python process, so it uses one CPU core. How many requests a second one core can drive depends on your task code, the response sizes and the client (FastHttpUser is much cheaper than HttpUser). Measure it: run one process, raise the users until its CPU nears 100%, and note the request rate. That's your per-process budget, and you need enough processes to stay well below it.

Locust logs a warning when a process goes over 90% CPU. Treat that warning as "this run's response times are not trustworthy".

One machine, many cores: --processes

# One master plus 4 worker processes on this machine
locust -f locustfile.py --processes 4 -H https://staging.example.com

# One worker per CPU core
locust -f locustfile.py --processes -1 --headless -u 2000 -r 50 -t 20m

This forks worker processes and wires them to a local master for you. It's the easiest way to use a big machine, though Locust still labels the flag experimental. It isn't available on Windows. Use WSL or the master/worker setup there.

Several machines: master and workers

# On the master machine (web UI on :8089, workers connect on :5557)
locust -f locustfile.py --master -H https://staging.example.com

# On each worker machine (same locustfile, same Locust version)
locust -f locustfile.py --worker --master-host 10.0.0.10

# Headless: wait until 4 workers have connected, then start
locust -f locustfile.py --master --headless --expect-workers 4 \
  -u 4000 -r 100 -t 30m -H https://staging.example.com --csv results/run --html results/report.html
  • The master runs no users. It hands out users, collects statistics from the workers and serves the UI and reports.
  • Workers need network access to the master on port 5557 (change it with --master-bind-port and --master-port).
  • Each worker needs the locustfile and any data files. Locust doesn't copy them for you, so bake them into an image or a shared volume.
  • Users are spread evenly across workers, and a custom load shape runs on the master unchanged.

Docker Compose

# docker-compose.yml: one master, N workers. Start with: docker compose up --scale worker=4
services:
  master:
    image: locustio/locust:2.47.0          # pin the same version everywhere
    ports:
      - "8089:8089"                        # web UI
    volumes:
      - ./:/mnt/locust
    command: -f /mnt/locust/locustfile.py --master -H https://staging.example.com

  worker:
    image: locustio/locust:2.47.0
    volumes:
      - ./:/mnt/locust
    command: -f /mnt/locust/locustfile.py --worker --master-host master

The same pattern carries over to Kubernetes: a master Deployment with a Service on 5557 and 8089, and a worker Deployment you scale. Put the workers on nodes with spare CPU, not next to the system under test, or the two compete for the same cores.

Splitting test data between workers

Every worker loads its own copy of the locustfile and the data. If each one cycles through the same users.csv from the top, worker 1's first user and worker 2's first user log in as the same account. Give each worker its own slice, using the index the master assigns:

import csv
import itertools
import os

from locust import HttpUser, task, between, events

WORKER_COUNT = int(os.environ.get("WORKER_COUNT", "1"))  # set to the number of workers you start
with open(os.path.join(os.path.dirname(__file__), "users.csv"), newline="") as f:
    ALL_USERS = list(csv.DictReader(f))

my_users = None  # this worker's slice, set once the worker knows its index


@events.test_start.add_listener
def pick_slice(environment, **kwargs):
    global my_users
    index = getattr(environment.runner, "worker_index", 0)  # 0 when not distributed
    if index < 0:  # the master (or not yet connected): nothing to do
        return
    # Worker 0 gets rows 0, N, 2N..., worker 1 gets rows 1, N+1... No overlap between workers.
    my_users = itertools.cycle(ALL_USERS[index::WORKER_COUNT])


class AccountUser(HttpUser):
    wait_time = between(1, 2)

    def on_start(self):
        self.creds = next(my_users)
        self.client.post("/login", json=self.creds)

    @task
    def me(self):
        self.client.get("/me")
WORKER_COUNT=4 locust -f distributed_data.py --worker --master-host 10.0.0.10

The worker index is assigned when a worker connects, which is why the slice is picked in the test_start event rather than at import time.

Pitfalls

  • Version mismatch. Master and workers must run the same Locust version. Pin it in requirements or the image tag.
  • Fewer users than workers. 3 users on 10 workers leaves 7 idle. Not an error, but it surprises people during smoke runs.
  • Unequal machines. Users are spread evenly, not by capacity. One small worker becomes the bottleneck. Use identical worker machines.
  • The network between workers and target. Workers in another region add latency to every request. Keep them where real clients would be, or at least report where they ran.
