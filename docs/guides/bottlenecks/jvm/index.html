JVM bottlenecks under load

At 300 users the Java service is fine. At 400, p99 jumps to 3 seconds and CPU sits at 55%. Restarting it helps for twenty minutes. That pattern has four usual suspects: threads waiting on something, the garbage collector, a leak, or hot code. Each has its own evidence, and all of it can be collected from a running JVM without a restart.

Use jcmd from the same JDK version as the target JVM, run as the same OS user. jcmd with no arguments lists Java processes, and jcmd <PID> help lists what that JVM supports.

Thread dumps

A thread dump is a snapshot of every thread's stack and state. One dump is a photo. Three to five dumps taken 5 to 10 seconds apart at the load where latency climbs is a film: a thread stuck in the same frame across all of them is your answer.

PID=$(pgrep -f my-service.jar)
for i in 1 2 3 4 5; do
  jcmd $PID Thread.print -l > threads.$i.txt
  sleep 5
done
# alternatives: jstack -l $PID, or kill -3 $PID (dump goes to the JVM's stdout)

What to look for:

  • Many threads BLOCKED with "waiting to lock <0x...>", all on the same monitor. Find the one thread that "locked" it and see what it is doing. That is lock contention.
  • Request threads WAITING or TIMED_WAITING in a pool's borrow method, for example HikariCP's ConcurrentBag.borrow or Apache HttpClient's pool lease. That is pool exhaustion, and raising the database's capacity won't help until the pool is right-sized.
  • Request threads RUNNABLE in SocketInputStream.read or NioSocketImpl.read: they are waiting on a downstream call. RUNNABLE here doesn't mean using CPU.
  • All worker threads busy and the acceptor idle: the thread pool is the limit. Check what the busy threads are doing before making the pool bigger.
  • "Found one Java-level deadlock" at the end of the dump: the JVM detected a deadlock for you.

Paste dumps into the thread dump analyser to group threads by state and identical stack, which turns 400 threads into five groups you can actually read. To find which thread is burning CPU, use top -H -p $PID, convert the thread ID to hex (printf '%x\n' 23817 gives 5d09) and search the dump for nid=0x5d09.

GC logs

Turn GC logging on in every performance test environment. It costs almost nothing and is the only reliable record of pauses. On JDK 9 and later, unified logging does it:

-Xlog:gc*,safepoint:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=50m

On JDK 8 the old flags are -XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log.

  • Pause times: compare the longest pauses with your p99 target. A 400 ms pause every 30 seconds puts a 400 ms floor under every request in flight at that moment. See GC pauses.
  • GC overhead: total pause time divided by wall time. Above about 5% is worth tuning. Above 10 to 20% the service is spending its life collecting garbage.
  • Old gen (or heap) occupancy after each full or mixed collection: if this floor keeps rising across a soak test, something is retaining memory. That is the leak signature. The peak is irrelevant, the floor after collection is what matters.
  • Allocation rate: a high allocation rate (several GB/s) drives frequent young collections. The fix is usually in the code (fewer temporary objects), not GC flags.
  • Collector choice: G1 is the default since JDK 9. ZGC (production-ready from JDK 15, generational from JDK 21) keeps pauses to around a millisecond at the cost of some throughput and memory. If pauses are the problem on a large heap and you are on a recent JDK, test ZGC before hand-tuning G1.

Upload a log to the GC log analyser for pause percentiles, overhead and the heap-after-GC trend. Safepoint logging (the safepoint tag above) catches pauses that aren't GC: time-to-safepoint problems, biased lock revocation on older JDKs, and deoptimisation.

Heap dumps and Eclipse MAT

A heap dump captures every object on the heap. It is how you find out what is leaking.

# live objects only (forces a full GC first)
jcmd $PID GC.heap_dump /tmp/app-heap.hprof

# all objects, including unreachable ones (no full GC)
jcmd $PID GC.heap_dump -all /tmp/app-heap-all.hprof

# capture automatically when the JVM runs out of heap
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app/

Heap dumps pause the JVM for seconds to minutes on a large heap and write a file roughly the size of the used heap. Take them out of rotation or after the test, check disk space first, and treat the file as sensitive: it contains whatever was in memory, including customer data and secrets.

Open the file in Eclipse Memory Analyzer (MAT). Give MAT enough memory to load it (edit -Xmx in MemoryAnalyzer.ini). Then:

  1. Leak Suspects report: runs automatically and is right surprisingly often.
  2. Dominator tree: objects sorted by retained size, the memory that would be freed if that object were collected. A single HashMap or cache retaining 60% of the heap is the classic find.
  3. Path to GC roots (excluding weak and soft references) on the suspect: shows the chain keeping it alive, usually a static field, a cache without eviction, a ThreadLocal on a pooled thread, or a listener that was never removed.
  4. Compare two dumps taken an hour apart in a soak test. The class whose instance count grows in step with requests is the leak. See memory leak.

For a quick look without a full dump, jcmd $PID GC.class_histogram | head -30 lists instance counts and bytes per class. Two histograms a few minutes apart often point straight at the leak.

async-profiler

async-profiler is a low-overhead sampling profiler for HotSpot JVMs. It doesn't suffer from safepoint bias, the distortion where profilers that can only sample at safepoints over-report the code near safepoint polls. It produces flame graphs directly.

# CPU profile for 60 seconds during the load test (async-profiler 3.x / 4.x)
asprof -d 60 -e cpu -f /tmp/cpu.html $PID

# wall-clock: all threads, running or waiting. Best for "slow but CPU is low"
asprof -d 60 -e wall -t -f /tmp/wall.html $PID

# allocation profile: who creates the garbage
asprof -d 60 -e alloc -f /tmp/alloc.html $PID

# lock contention
asprof -d 60 -e lock -f /tmp/lock.html $PID

In versions before 3.0 the launcher was profiler.sh with the same options. On Linux, CPU mode uses perf_events, which may need sysctl kernel.perf_event_paranoid=1 and kernel.kptr_restrict=0. Inside containers that may not be allowed. -e itimer is the fallback that needs no special permissions. Check the project's README for your version.

Reading the output: in a CPU flame graph, look for wide frames in your code or in libraries you call (JSON serialisation, regex, logging, crypto). In a wall-clock profile filtered to request threads, wide frames in socket reads, pool borrows or park show where requests wait.

JDK Flight Recorder

JFR is built into the JDK (open source since JDK 11, backported to OpenJDK 8u262). Its default settings are designed for production use with low overhead, and it records CPU samples, allocations, GC, locks, I/O and thread states in one file.

# start a 5-minute recording with the more detailed "profile" settings
jcmd $PID JFR.start name=loadtest settings=profile duration=5m filename=/tmp/loadtest.jfr

# or from JVM start
-XX:StartFlightRecording=settings=profile,duration=5m,filename=/tmp/loadtest.jfr

# check and dump an ongoing recording
jcmd $PID JFR.check
jcmd $PID JFR.dump name=loadtest filename=/tmp/now.jfr

Open the file in JDK Mission Control. The Automated Analysis page flags common problems. The most useful views under load are Method Profiling, Lock Instances (monitor blocked time per lock), Socket I/O (time per remote host) and Garbage Collections. The jfr command-line tool (jfr print --events jdk.GarbageCollection /tmp/loadtest.jfr) is handy on a server without a GUI.

JVMs in containers

  • Modern JDKs (10+, and 8u191+) read cgroup memory and CPU limits. Size the heap with -XX:MaxRAMPercentage=70 or so, leaving room for metaspace, thread stacks, direct buffers and the code cache. A heap equal to the container limit ends in OOM kills, not OutOfMemoryError.
  • The JVM sizes GC threads, the common ForkJoinPool and many frameworks' pools from the CPU count it sees. With a CPU limit of 1 or 2 it may pick a serial collector or tiny pools. Check with java -XX:+PrintFlagsFinal -version | grep -E 'ActiveProcessorCount|UseG1GC|UseSerialGC' inside the container.
  • CPU throttling from the CFS quota looks like random latency spikes. See containers and CPU throttling.
