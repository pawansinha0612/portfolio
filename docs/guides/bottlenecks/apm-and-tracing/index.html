Reading a trace waterfall

You open the APM during the test and the service map is all red. Every service looks slow because every service is waiting on something else. Dashboards tell you which transaction is slow. A trace tells you where that one request spent its 4 seconds. This guide is about reading traces well, whichever tool draws them.

Traces, spans and the waterfall

A distributed trace follows one request across services. Each unit of work (an HTTP handler, a database call, an outgoing request, a message publish) is a span with a start time, a duration, attributes and a parent. The trace ID travels between services in a header, now usually the W3C traceparent header, so spans from different processes join up into one tree.

The waterfall view draws that tree on a timeline: each span is a bar, indented under its parent. Two durations matter for each span:

  • Total (inclusive) time: from the span's start to its end, including children.
  • Self (exclusive) time: total time minus time covered by children. High self-time is work (or untraced waiting) in that span's own code.

Pick the right traces

  • Filter to the slow transaction and the slow time window. Pick traces from the knee of the test, with duration above your p95 or p99. A trace from the warm-up period describes a different system.
  • Open several slow traces and a few fast ones of the same endpoint. The bottleneck is the difference between them. If slow and fast traces have the same shape but every span is proportionally longer, look at a shared resource (CPU, GC, the host). If one span grows and the rest don't, look at that span.
  • Check the aggregate view next. Most APMs can break down a transaction's time by downstream call or span type across many traces. Use it to confirm that what you saw in five traces holds across thousands.

Reading the waterfall: six patterns

1. One long span on the critical path

The critical path is the chain of spans that determines the end time. Shortening a span that runs in parallel with a longer one achieves nothing. Follow the longest chain down until you reach a span with high self-time or a leaf (a database or external call). That is where to look.

2. A long database span with a fast query

The span says 1.8 seconds, but the database reports the statement at 6 ms. The time went on getting a connection from the pool, waiting for a lock, or the network. Some agents show connection acquisition as its own span, many don't. Check pool metrics. See the database guide.

3. Gaps between spans

Whitespace in a parent span with no children under it is time nobody measured: queueing in an executor before the work started, a GC pause, CPU throttling, serialising a large payload, a synchronous log write, or a library the agent doesn't instrument. Gaps at the very start of a server span often mean the request waited in a thread pool or accept queue. Correlate the timestamp with GC logs and host metrics.

4. A staircase of identical spans

Dozens of the same query or HTTP call one after another, each short. That is an N+1 or a loop of remote calls that should be batched or run in parallel. The total is what hurts.

5. Wide fan-out

A request that calls 20 services in parallel is as slow as the slowest of the 20. Each one's p99 becomes something most requests experience. That is fan-out amplification and the core of Dean and Barroso's "The Tail at Scale". Look at the slowest child each time, and at whether it is always the same one.

6. Retries and timeouts

A call span that ends at exactly 1.000 or 5.000 seconds, followed by an identical call, is a timeout and a retry. Under load these multiply traffic on the struggling dependency. See retry storms and circuit breakers.

The same ideas in each tool

Commercial APMs and open-source tracing backends use different names for the same things. Features and names change between versions and plans, so check your tool's documentation for specifics.

If you are choosing, instrument with OpenTelemetry where you can. The same instrumentation can then send data to any of these backends, and you aren't locked into one agent. For a quick query in Tempo, TraceQL like { resource.service.name = "checkout" && duration > 2s } finds slow spans directly.

Making load test traffic easy to find

  • Tag the traffic. Send a header from the load script and have the service record it as a span attribute, or set a distinctive user agent. Then you can filter test traffic from real traffic in shared environments.
  • Send your own traceparent. If the script generates the trace ID, you can log it next to each slow response in the test results and jump straight from a failed request to its trace. For k6, the http-instrumentation-tempo jslib module adds a traceparent header to every request (it replaced the removed k6/experimental/tracing module). JMeter can set the header with a JSR223 pre-processor.
  • Check sampling. Head-based sampling at 1% means most slow requests have no trace at all. During a load test, raise the sampling rate if the backend can take it, or use tail-based sampling that keeps slow and failed traces. Also check the agent's own limits on spans per minute, which can quietly drop data at high throughput.
  • Watch agent overhead. Instrumentation costs CPU and memory. Keep the same agent configuration in the test environment as in production, so the overhead is included in your results.

What traces won't tell you

  • Resource saturation. A trace shows that a request waited. Host and runtime metrics show why: CPU, GC, pools. Use the USE method alongside.
  • Code-level hotspots inside a span. For that you need a profiler. Some APMs include a continuous profiler, otherwise use async-profiler or perf.
  • Requests that never arrived. Connections refused at the load balancer or dropped from a full accept queue produce no server-side trace. Only the client side (your load tool) sees them.
