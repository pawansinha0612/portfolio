Network and CDN bottlenecks

The server says it answered in 40 ms. The user in Perth waited 900 ms. Somewhere between them sat a DNS lookup, a TCP handshake, a TLS handshake, a CDN that missed its cache and went back to the origin in Sydney, and twelve round trips that could have been three. "It's the network" is usually true, and rarely specific enough to fix.

Latency vs bandwidth

Bandwidth is how much data per second the pipe carries. Latency is how long one round trip takes. For typical API calls and web pages, latency dominates: a 20 KB JSON response takes about 0.2 ms to transmit at 1 Gbit/s, but each round trip between Melbourne and Singapore is roughly 80 to 100 ms, and light in fibre can't do much better.

That is why the number of round trips matters more than payload size for small requests. A rough cost for a cold HTTPS request:

Total before any body arrivesabout 4 to 5320 to 400 ms + server

On a reused connection, the same request costs one round trip plus server time. Larger responses add more round trips while TCP's congestion window grows (slow start), which is why the first 14 KB or so of a response is cheap and the next few hundred KB on a fresh connection are not.

Break a request into phases

Every serious tool can split a request's time into phases. Use them before guessing.

curl -s -o /dev/null -w '
dns:      %{time_namelookup}s
connect:  %{time_connect}s
tls:      %{time_appconnect}s
ttfb:     %{time_starttransfer}s
total:    %{time_total}s
' https://www.example.com/

curl's values are cumulative from the start, so TLS time is time_appconnect − time_connect. In k6, the same phases are separate metrics: http_req_blocked (waiting for a free connection slot, and DNS), http_req_connecting, http_req_tls_handshaking, http_req_waiting (time to first byte, see TTFB) and http_req_receiving. In JMeter, Connect and Latency columns in the JTL give a coarser split. In a browser, the Timing tab in DevTools shows the same breakdown per request.

Reading them: high waiting with fast connect and TLS means the server (or what is behind it) is slow. Rising connecting under load means the server's accept queue or a load balancer is struggling. Rising blocked means the client has run out of connections or is waiting on DNS.

TCP and TLS handshakes

  • TLS 1.3 needs one round trip for a full handshake, TLS 1.2 needs two. Both support resumption, which skips certificate exchange and the expensive key agreement on reconnects.
  • Handshakes cost server CPU. The asymmetric crypto in a full handshake is far more expensive than encrypting the data afterwards. A test that opens a new connection per request can make a load balancer or ingress saturate on handshakes, at traffic levels it would handle easily with reuse.
  • Certificate chain size matters. A long chain or large certificates can push the server's handshake reply beyond the initial congestion window and add a round trip. Serve the leaf and intermediates only, not the root.
  • OCSP stapling saves the client a separate lookup to the certificate authority on some clients. Enable it if your server supports it.

Keep-alive and connection reuse

HTTP/1.1 keeps connections open by default. HTTP/2 multiplexes many requests on one connection. In practice reuse breaks in a few predictable places:

  • Idle timeout mismatches. If a load balancer closes idle connections after 60 seconds and the backend's keep-alive timeout is 5 seconds, the backend may close a connection the load balancer is about to reuse. The result is intermittent 502s under moderate load. The usual rule: the backend's idle timeout must be longer than the load balancer's.
  • Client libraries without pooling, or a new HTTP client created per request. Look for thousands of TIME_WAIT sockets on the calling host (ss -tan state time-wait | wc -l).
  • Pool limits per host. Many HTTP clients cap connections per destination host, sometimes at a small number. Requests then queue inside the client, and the time appears as latency of the downstream call even though the downstream is idle.
  • Server-side limits such as keepalive_requests in nginx (the number of requests per connection before it closes) cause periodic reconnects.

DNS

  • TTL vs failover: short TTLs (30 to 60 seconds) let you move traffic quickly but increase lookups. Clients and runtimes that cache DNS forever ignore your TTL. The JVM caches successful lookups for 30 seconds by default when no security manager is installed (networkaddress.cache.ttl). Check what your runtime does.
  • Resolver limits: in Kubernetes, the default ndots:5 setting means a lookup of an external name such as api.partner.com can try several cluster search domains first. Under load this multiplies queries to CoreDNS. Use fully qualified names with a trailing dot, or tune ndots. Cloud VPC resolvers also have per-interface query rate limits.
  • Load test DNS behaviour: k6 caches DNS for 5 minutes by default (the dns option, ttl=5m). If you are testing DNS-based failover or a load balancer that scales by adding IPs, lower the TTL (for example dns: { ttl: '30s', select: 'roundRobin' }) so load spreads across new addresses the way real clients would.

CDN hit ratio and origin load

A CDN helps in two ways: it serves cached content from an edge near the user, and it keeps that traffic off your origin. The cache hit ratio decides both.

  • Request hit ratio vs byte hit ratio. A 95% request hit ratio with a 60% byte hit ratio means large files (images, video, downloads) are missing the cache. Check both.
  • Origin load = total requests × (1 − hit ratio). At 20,000 requests per second, going from 95% to 90% hit ratio doubles origin traffic from 1,000 to 2,000 req/s. Small changes in hit ratio are big changes for the origin.
  • Cache key fragmentation. Query strings (tracking parameters, cache-busters), cookies or headers in the cache key create a separate cache entry per variant. One stray Vary: User-Agent header can make an object almost uncacheable.
  • Cold cache after a purge or deploy. Every edge location fetches from the origin at once. That is a thundering herd. Request collapsing and an origin shield (a mid-tier cache) reduce it. Test it deliberately.
  • Check the response headers. CDNs report hits and misses in headers such as X-Cache, CF-Cache-Status or Age. Record them in your load test to measure the hit ratio you actually got.

Network traps in load tests

  • Testing through the CDN from one location warms one edge and measures cache performance, not your origin. Decide which you want to test. To test the origin, bypass the CDN or send uncacheable requests. To test the CDN, use realistic URL variety.
  • WAFs and DDoS protection will rate-limit or block a load test from a few IPs. Agree an allow-list with the security team first, or you will be measuring the WAF. See rate limiting and HTTP 429.
  • Load generator bandwidth. 2,000 requests per second of 500 KB pages is 8 Gbit/s. Few single generators can push that. Check the generator's network throughput before blaming the server.
  • Unrealistic connection behaviour. Real browsers open a handful of connections per origin and reuse them. A script that reuses one connection per VU for an hour hides handshake costs. A script that opens a new connection per request exaggerates them. k6's noConnectionReuse and noVUConnectionReuse options and JMeter's keep-alive checkbox control this.
  • Latency from the wrong place. A generator in the same data centre as the servers shows sub-millisecond network time. Your users don't have that. Either run some load from the regions users are in, or add the measured real-world round-trip time to your analysis.
