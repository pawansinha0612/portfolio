k6 auth and correlation: tokens, logins and dynamic values

You record a journey, replay it under load and every request after login returns 401. The recording captured a token that expired an hour ago. Correlation means reading dynamic values from responses and sending them back, the way a real client does.

Which login pattern?

PatternLogin loadRealistic?Use when
Token in setup()One login in totalNo: every VU is the same userService-to-service APIs with a client-credentials token, or when login is out of scope.
Login once per VUOne per VU, plus refreshesYes, for logged-in sessionsMost user-facing APIs. Each VU is a different user with their own session.
Login every iterationOne per iterationOnly if users really log in that oftenTesting the login service itself. Otherwise it overloads auth and skews results.

The trap with one shared token: per-user caches, rate limits and row locks all key on the user. A thousand VUs sharing one identity hit one cache entry and one rate-limit bucket. The result can be far too fast (cache) or far too slow (rate limiting, lock contention).

One token for the whole test, in setup()

import http from 'k6/http';
import { check, fail } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = { vus: 20, duration: '5m' };

// setup() runs once, before any VU starts. Its return value is passed to every VU.
export function setup() {
  const res = http.post(`${BASE_URL}/auth/token`, JSON.stringify({
    username: __ENV.API_USER,
    password: __ENV.API_PASSWORD,
  }), { headers: { 'Content-Type': 'application/json' } });

  if (!check(res, { 'got token': (r) => r.status === 200 && !!r.json('access_token') })) {
    fail(`login failed: ${res.status} ${res.body}`); // stops the test before any load is sent
  }
  return { token: res.json('access_token') };
}

export default function (data) {
  const params = { headers: { Authorization: `Bearer ${data.token}` } };
  const res = http.get(`${BASE_URL}/me`, params);
  check(res, { 'authorised': (r) => r.status === 200 });
}

setup() runs once, and its return value is serialised as JSON and handed to every VU. So you can pass strings, numbers and plain objects, not functions or class instances. If the token expires during a long test, use the per-VU pattern instead.

One login per VU, with refresh

Module-level variables belong to one VU, so a token stored there is that VU's session. Log in on the first iteration, reuse the token, and log in again before it expires:

import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
const users = new SharedArray('users', () => JSON.parse(open('./data/users.json')));

export const options = { vus: 10, duration: '10m' };

// Module-level variables are per VU: each VU has its own copy.
let token = null;
let tokenExpiresAt = 0;

function login() {
  const user = users[(exec.vu.idInTest - 1) % users.length];
  const res = http.post(`${BASE_URL}/login`, JSON.stringify(user), {
    headers: { 'Content-Type': 'application/json' },
    tags: { name: 'POST /login' },
  });
  check(res, { 'login 200': (r) => r.status === 200 });
  token = res.json('access_token');
  // Refresh a minute early so a token never expires mid-iteration
  tokenExpiresAt = Date.now() + (res.json('expires_in') - 60) * 1000;
}

export default function () {
  if (!token || Date.now() > tokenExpiresAt) login();

  const res = http.post(`${BASE_URL}/cart`, JSON.stringify({ productId: 7 }), {
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
    tags: { name: 'POST /cart' },
  });
  if (res.status === 401) token = null; // force a fresh login next iteration
  check(res, { 'added to cart': (r) => r.status === 201 });
  sleep(1);
}

Tagging the login with name keeps its latency separate, so the slower login calls don't hide inside the cart numbers. With 10 VUs and a one-hour token, you get about 10 logins an hour. If production does 200 logins a second at peak, model that as its own scenario.

Extracting values: JSON, HTML, regex

import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = { vus: 5, duration: '1m' };

export default function () {
  // 1. JSON: res.json() takes a GJSON path
  const list = http.get(`${BASE_URL}/products`);
  const firstId = list.json('items.0.id');            // first item's id
  const ids = list.json('items.#.id');                // array of every id
  const cheap = list.json('items.#(price<15)#.id');   // ids where price < 15
  const productId = ids[Math.floor(Math.random() * ids.length)];

  // 2. Cookies: k6 keeps a cookie jar per VU, so a Set-Cookie from login
  //    is sent back automatically on later requests to the same domain.
  http.post(`${BASE_URL}/login`, JSON.stringify({ username: 'u1', password: 'p' }), {
    headers: { 'Content-Type': 'application/json' },
  });
  const me = http.get(`${BASE_URL}/me`); // no Authorization header: the session cookie does it
  check(me, { 'cookie session works': (r) => r.status === 200 });

  // 3. HTML: pull a hidden CSRF token out of a form
  const page = http.get(`${BASE_URL}/checkout`);
  const csrf = page.html().find('input[name=csrf]').attr('value');

  // 4. Anything else: a regex, as a last resort
  const csrfAgain = (page.body.match(/name="csrf" value="([^"]+)"/) || [])[1];

  // submitForm() would also do this for you: res.submitForm({ fields: { ... } })
  const pay = http.post(`${BASE_URL}/checkout`, { csrf: csrf, productId: String(productId) });
  check(pay, {
    'csrf extracted': () => csrf !== undefined && csrf === csrfAgain,
    'checkout ok': (r) => r.status === 200,
    'ids parsed': () => firstId === 1 && cheap.length > 0,
  });
}
  • JSON: res.json(path) takes a GJSON path: items.0.id, items.#.id for all ids, items.#(price<15)#.id to filter. Without a path it parses the whole body, which is slower for big responses.
  • HTML: res.html() gives a jQuery-like selection. .find(selector).attr(name) covers hidden form fields. For a whole form, res.submitForm() reads the fields and posts them for you.
  • Regex: works on anything, breaks when the markup changes. Use it when there is no structure to parse.

Always check the extraction worked. A missing token becomes the string undefined in the next URL, and the 404s look like a performance problem. See correlation in the glossary.

Cookies and sessions

Each VU has its own cookie jar. Cookies set by a response go back automatically on later requests to the same domain, so cookie-based sessions usually just work. You only touch the jar to set, read or clear cookies yourself:

import http from 'k6/http';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export default function () {
  const jar = http.cookieJar(); // this VU's jar

  // Set a cookie yourself (for example a feature flag or a consent cookie)
  jar.set(BASE_URL, 'consent', 'yes');

  // Read what the server set
  http.post(`${BASE_URL}/login`, JSON.stringify({ username: 'u1', password: 'p' }), {
    headers: { 'Content-Type': 'application/json' },
  });
  const session = jar.cookiesForURL(BASE_URL).session; // array of values
  console.log(`session cookie: ${session && session[0]}`);

  // Remove one cookie, or all cookies for a URL, mid-iteration
  jar.delete(BASE_URL, 'consent');
  jar.clear(BASE_URL);
}

// k6 empties every VU's jar at the end of each iteration, so each iteration starts
// as a new visitor. To keep cookies across iterations (a returning, logged-in user):
// export const options = { noCookiesReset: true };

Cookies are cleared at the end of every iteration by default. If each iteration should continue the same logged-in session, set noCookiesReset: true, or log in at the start of every iteration.

OAuth, SSO and MFA

  • Client credentials (machine-to-machine): one POST to the token endpoint with grant_type=client_credentials. Fits the setup() pattern.
  • Password grant or a test login API: fits the per-VU pattern.
  • Browser redirects, SSO and MFA: don't load test your identity provider unless that's the goal (and you have permission: many IdPs rate-limit or ban it). Ask for a test-only way to mint tokens, or pre-generate tokens for test accounts and load them as data. For TOTP-based MFA in a test environment, there's a totp jslib.
