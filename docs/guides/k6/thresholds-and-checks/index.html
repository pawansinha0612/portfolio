k6 thresholds and checks: a test that can fail

Your pipeline has run the load test on every merge for six months and never failed once. That's not a fast system. That's a test with no budgets, or with a typo in one. Here's how to make k6 fail for the right reasons.

Checks verify, thresholds decide

A check is an assertion on one response: status is 200, body has an id. A failed check does not stop the iteration and does not fail the test. It adds a 0 to the checks rate metric. It's closer to a counter than an assertion. See checks and assertions.

A threshold is a pass/fail rule on a whole metric across the test: p95 of http_req_duration under 500 ms, checks rate over 99%. If any threshold fails, k6 exits with a non-zero code. See thresholds.

You need both. Checks catch "fast but wrong" responses. A threshold on checks turns them into a pass/fail. A test with checks but no threshold on them prints red crosses and still exits 0.

import { check } from 'k6';

// check() returns true only if every condition passed, so you can branch on it
const ok = check(res, {
  'status 200': (r) => r.status === 200,
  'body has id': (r) => r.json('id') !== undefined,
  'under 1 s': (r) => r.timings.duration < 1000,
});
if (!ok) {
  console.warn(`bad response ${res.status} for ${res.url}`);
}

Threshold syntax per metric type

Each threshold is an expression aggregation operator value. Which aggregations you can use depends on the metric type:

Metric typeBuilt-in examplesAggregationsExample
Trendhttp_req_duration, iteration_duration, group_durationavg min max med p(N)'p(95)<500'
Ratehttp_req_failed, checksrate'rate<0.01'
Counterhttp_reqs, iterations, dropped_iterationscount rate'count<10'
Gaugevusvalue'value<500'

Several expressions on one metric are all required: ['p(95)<500', 'p(99)<1500']. Budgets on the median alone are close to useless, because the median hides exactly the slow requests users complain about. Use p95 and p99, with an error-rate budget beside them. To pick the numbers, start from your SLO or the SLO calculator.

Per-endpoint and per-scenario budgets

One p95 across all endpoints mixes a 20 ms health check with a 900 ms search. Put the tag filter in braces after the metric name to create a sub-metric with its own threshold:

  • 'http_req_duration{name:GET /products}': one endpoint, using the name tag you set on the request.
  • 'http_req_duration{scenario:buy}': one scenario.
  • 'http_req_duration{status:200}': successful responses only, so fast errors don't drag p95 down.
  • 'checks{check:order created}': one named check.
  • 'group_duration{group:::checkout}': one group. The group tag value starts with ::, so the filter has three colons.
  • 'http_req_duration{name:GET /products,method:GET}': several tags at once.

A complete example

import http from 'k6/http';
import { check, group, sleep } from 'k6';
import { Trend } from 'k6/metrics';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
const checkoutTime = new Trend('checkout_duration', true); // true = values are times

export const options = {
  vus: 10,
  duration: '5m',
  thresholds: {
    // Whole-test budgets
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500', 'p(99)<1500'],

    // Per-endpoint budgets via the name tag (set below)
    'http_req_duration{name:GET /products}': ['p(95)<300'],
    'http_req_duration{name:GET /products/:id}': ['p(95)<200'],

    // Every check must pass at least 99% of the time
    checks: ['rate>0.99'],
    'checks{check:order created}': ['rate>0.995'],

    // Group duration (system metric, tagged by group path)
    'group_duration{group:::browse}': ['p(95)<2000'],

    // Custom metric
    checkout_duration: ['p(95)<1200'],

    // Stop early if things are clearly broken. Wait 30 s so a cold start doesn't trip it.
    'http_req_failed{scenario:default}': [{ threshold: 'rate<0.10', abortOnFail: true, delayAbortEval: '30s' }],
  },
};

export default function () {
  group('browse', () => {
    const list = http.get(`${BASE_URL}/products`, { tags: { name: 'GET /products' } });
    check(list, { 'list 200': (r) => r.status === 200 });
    const id = list.json('items.0.id');
    const item = http.get(`${BASE_URL}/products/${id}`, { tags: { name: 'GET /products/:id' } });
    check(item, { 'item 200': (r) => r.status === 200 });
  });

  group('checkout', () => {
    const start = Date.now();
    const login = http.post(`${BASE_URL}/login`, JSON.stringify({ username: 'u1', password: 'p' }), {
      headers: { 'Content-Type': 'application/json' },
    });
    const order = http.post(`${BASE_URL}/orders`, '{}', {
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${login.json('access_token')}` },
    });
    check(order, { 'order created': (r) => r.status === 201 });
    checkoutTime.add(Date.now() - start);
  });

  sleep(1);
}

The Trend custom metric measures the whole checkout, login and order together, which no single request metric shows. Passing true as the second argument tells k6 the values are times, so it formats them as ms in the summary.

Stopping early with abortOnFail

A 60-minute soak test that is 90% errors after five minutes is wasting an hour. Use the object form of a threshold to stop the test as soon as it fails:

thresholds: {
  http_req_failed: [
    'rate<0.01',                                                         // the real budget
    { threshold: 'rate<0.10', abortOnFail: true, delayAbortEval: '1m' }, // the emergency brake
  ],
},

Thresholds are evaluated during the run, about every two seconds. delayAbortEval waits before the first evaluation, so a handful of failures during warm-up can't abort the test. Without it, one early error out of five requests is a 20% failure rate and the test stops. I set the abort threshold looser than the budget: abort when the run is clearly useless, and let the real budget decide pass or fail at the end.

Exit codes in CI

CI tools only see the exit code. These are the ones you'll meet (checked on k6 v1.x):

CodeMeaning
0Test finished and every threshold passed. Also: no thresholds at all, failed checks without a threshold, or errors thrown inside the default function.
99One or more thresholds failed, including an abortOnFail stop.
104Invalid config, for example a threshold on a metric that doesn't exist.
107Script error: a syntax error, an exception in init code, or fail() in setup().
108The script called exec.test.abort().

Any non-zero code fails a CI step by default, which is what you want. If you need the report even when the test fails, make the report step run on failure too (if: always() in GitHub Actions). Pipelines are covered in k6 in CI.

An exception thrown in the default function is logged and that iteration is abandoned, but the test carries on and can still exit 0. If a broken journey must fail the test, guard it with checks and a checks threshold.

Traps

  • A threshold on a sub-metric with no data passes. If you write {name:GET /product} but the tag is GET /products, the sub-metric gets no samples and the threshold silently passes. After any change, look for the threshold's value in the summary. If it shows nothing, the filter matched nothing.
  • --no-thresholds turns them all off. Fine locally, a disaster if it ends up in a pipeline file.
  • Failed requests are fast. A p95 budget passes happily when half the requests are 503s returned in 2 ms. Always pair a latency budget with http_req_failed and a checks rate.
  • Expected 4xx count as failures. If a 404 or 409 is correct for a call, use http.setResponseCallback(http.expectedStatuses(200, 404)) or the per-request responseCallback param, so it doesn't count in http_req_failed.
