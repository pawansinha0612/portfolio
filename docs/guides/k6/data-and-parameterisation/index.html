k6 test data: realistic, unique and cheap on memory

Your load test logs in as the same user 500 times a second. The cache answers everything, p95 is 12 ms, and production falls over at a tenth of that load. Test data decides whether a load test measures your system or your cache.

Why the data matters

Repeating the same id, search term or account changes what you're measuring. Caches stay hot, the database reads the same pages from memory, and one user's rows become a lock hot spot. Real traffic spreads across many keys. Parameterisation means feeding each request realistic, varied data so the system does the same work it does in production.

SharedArray: load once, share with every VU

Each VU is a separate JavaScript runtime. If you JSON.parse(open(...)) a 50 MB file at the top level, every VU parses and holds its own copy: 1,000 VUs means 50 GB. A SharedArray runs the loader function once, stores the result once, and lets every VU read it.

import http from 'k6/http';
import { check } from 'k6';
import { SharedArray } from 'k6/data';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// Runs once in the init context. Every VU then reads the same in-memory copy.
const products = new SharedArray('products', function () {
  return JSON.parse(open('./data/products.json')); // must return an array
});

export const options = { vus: 20, duration: '1m' };

export default function () {
  const p = products[Math.floor(Math.random() * products.length)];
  const res = http.get(`${BASE_URL}/products/${p.id}`, { tags: { name: 'GET /products/:id' } });
  check(res, { 'status 200': (r) => r.status === 200 });
}
  • open() only works in init code (top level), and paths are relative to the script file. It can't read files during the test.
  • The function must return an array. The array is read-only.
  • Each element you read is copied out to the VU, so read the element you need, not the whole array in a loop.
  • The first argument is a name. Two SharedArrays with the same name share the same data, so give each data set its own name.

CSV files: papaparse or the csv module

k6 has no built-in CSV parser in the core k6/data module. The long-standing way is papaparse from jslib, inside a SharedArray. This script uses each row exactly once:

import http from 'k6/http';
import { check } from 'k6';
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';
import papaparse from 'https://jslib.k6.io/papaparse/5.1.1/index.js';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// users.csv:
// username,password
// user001,Passw0rd!
// user002,Passw0rd!
const users = new SharedArray('users', function () {
  return papaparse.parse(open('./data/users.csv'), { header: true, skipEmptyLines: true }).data;
});

export const options = {
  scenarios: {
    login: {
      executor: 'shared-iterations',
      vus: 10,
      iterations: users.length, // one login per row, each row used exactly once
      maxDuration: '5m',
    },
  },
};

export default function () {
  // iterationInTest is unique across all VUs (0, 1, 2, ...), so no two VUs get the same row
  const user = users[exec.scenario.iterationInTest];
  const res = http.post(`${BASE_URL}/login`, JSON.stringify(user), {
    headers: { 'Content-Type': 'application/json' },
  });
  check(res, { 'logged in': (r) => r.status === 200 && r.json('access_token') !== undefined });
}

The newer k6/experimental/csv module, with k6/experimental/fs, parses in Go rather than JavaScript and is lighter on memory for big files. It's still under experimental, which means its API can change between minor releases. This version picks random rows, with helpers from the k6-utils jslib:

import http from 'k6/http';
import { check } from 'k6';
import { open } from 'k6/experimental/fs';
import csv from 'k6/experimental/csv';
import { randomItem, randomIntBetween, uuidv4 } from 'https://jslib.k6.io/k6-utils/1.4.0/index.js';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// Parsed once, held in memory once, shared by every VU (like SharedArray). Top-level await is allowed.
const users = await csv.parse(await open('./data/users.csv'), { asObjects: true });

export const options = { vus: 10, duration: '1m' };

export default function () {
  const user = randomItem(users); // random row: fine for read-only journeys
  const res = http.post(`${BASE_URL}/login`, JSON.stringify(user), {
    headers: { 'Content-Type': 'application/json', 'X-Request-Id': uuidv4() },
  });
  check(res, { 'logged in': (r) => r.status === 200 });
  http.get(`${BASE_URL}/products/${randomIntBetween(1, 10)}`, { tags: { name: 'GET /products/:id' } });
}

Unique data per VU and per iteration

The k6/execution module tells you where you are in the test. These are the ids you'll use for data:

PropertyUnique acrossStarts atTypical use
exec.vu.idInTestAll VUs in the test1One account per VU for the whole test
exec.vu.iterationInScenarioThis VU's iterations in this scenario0Combine with the VU id for a unique key
exec.scenario.iterationInTestAll iterations of this scenario, across all VUs0Each data row used once, in order
exec.scenario.name--Branch on the scenario in shared code

The older globals __VU and __ITER still work. __VU matches exec.vu.idInInstance, which is only unique on one machine. Prefer the exec properties, so a test split across several load generators doesn't hand out the same rows twice.

import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';
const users = new SharedArray('users', () => JSON.parse(open('./data/users.json')));

export const options = { vus: 10, duration: '2m' };

export default function () {
  // One account per VU for the whole test: VU ids start at 1.
  // Fails loudly if you run more VUs than you have accounts, instead of silently sharing.
  const idx = exec.vu.idInTest - 1;
  if (idx >= users.length) {
    exec.test.abort(`need ${exec.vu.idInTest} users, users.json has ${users.length}`);
  }
  const user = users[idx];

  const res = http.post(`${BASE_URL}/login`, JSON.stringify(user), {
    headers: { 'Content-Type': 'application/json' },
  });
  check(res, { 'logged in': (r) => r.status === 200 });

  // Unique per iteration and across VUs: safe for "create" calls with unique keys
  const orderRef = `load-${exec.vu.idInTest}-${exec.vu.iterationInScenario}`;
  http.post(`${BASE_URL}/orders`, JSON.stringify({ ref: orderRef }), {
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${res.json('access_token')}` },
  });
  sleep(1);
}

The abort matters. Without it, 60 VUs with 50 accounts would quietly read undefined and send broken logins, which look like a performance problem. Fail loudly when the data doesn't fit the load.

Need each row once with no repeats? Use shared-iterations with iterations: rows.length and index by exec.scenario.iterationInTest, as in the papaparse example. With an arrival-rate executor, use modulo (% rows.length) and accept that rows repeat.

Environment variables and secrets

Pass settings with -e NAME=value and read them as __ENV.NAME. By default k6 also exposes the real system environment variables through __ENV, so CI secrets set as env vars work without -e.

k6 run -e BASE_URL=https://staging.example.com -e API_USER=loadtest script.js

# or from the environment, which keeps secrets out of shell history and CI logs
export API_PASSWORD='...'
k6 run script.js   # __ENV.API_PASSWORD is set

Recent k6 versions also have a k6/secrets module with secret sources that redact the values from logs. If you're on k6 v1.0 or later and log request details in CI, it's worth a look.

Rules for test data

  • Size the data to the test. Enough accounts for the peak VU count, enough ids to match the production spread. 50 products for a catalogue of 2 million tests the cache, not the database.
  • Match the distribution. Real traffic is skewed: a few products get most views. A uniform random pick is a start. A weighted list from access logs is better.
  • Plan for writes. Tests that create orders or users change the data for the next run. Use unique references (as above), clean up in teardown() or reset the environment between runs.
  • Never use real customer data in a test environment. Generate it.
