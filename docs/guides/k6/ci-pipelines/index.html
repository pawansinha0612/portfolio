k6 in CI: catch the slow merge before it ships

A pull request adds one innocent-looking database call per item in a list. Unit tests pass. Two weeks later the product page takes three seconds. A small load test on every pull request catches that in the review, when it's cheap to fix.

What to run where

TriggerTestLoadFails the build on
Every pull requestSmoke or small load5-10 VUs, 1-2 minutesErrors, failed checks, p95 well over budget
Nightly or before releaseFull load testExpected peak, 15-60 minutesSLO-based thresholds
Weekly or on demandStress or soakAbove peak, or hours longUsually reviewed by a person, not gated

A pull request check is a regression alarm, not a capacity test. Shared CI runners and shared staging environments are noisy, so it can only catch big changes. That's still worth having, because the costly regressions are often step changes, like an N+1 query or a missing index, and those show up even in a small, noisy test.

A CI-ready script

Thresholds give CI its exit code. handleSummary() writes a JSON summary and a JUnit file, so the thresholds appear in your CI's test report view.

import http from 'k6/http';
import { check, sleep } from 'k6';
import { textSummary, jUnit } from 'https://jslib.k6.io/k6-summary/0.1.0/index.js';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = {
  vus: 5,
  duration: '1m',
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
    checks: ['rate>0.99'],
  },
};

export default function () {
  const res = http.get(`${BASE_URL}/products`);
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}

export function handleSummary(data) {
  return {
    stdout: textSummary(data, { indent: ' ', enableColors: false }),
    'summary.json': JSON.stringify(data),
    'junit.xml': jUnit(data), // one test case per threshold, for CI test reports
  };
}

handleSummary() doesn't create folders. Write to the working directory, or create the folder in an earlier step. If a file can't be written, k6 logs an error but still exits 0.

GitHub Actions with Grafana's actions

grafana/setup-k6-action installs k6 (and Chrome, with browser: true). grafana/run-k6-action runs one or more scripts, with globs, parallel and fail-fast options. It runs locally on the runner by default. Set K6_CLOUD_TOKEN only if you also want results in Grafana Cloud k6.

# .github/workflows/k6.yml
name: k6 smoke test
on:
  pull_request:
  workflow_dispatch:

jobs:
  k6:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: grafana/setup-k6-action@v1
        with:
          k6-version: '2.3.0'          # pin the version you tested with

      - uses: grafana/run-k6-action@v1
        env:
          BASE_URL: ${{ vars.STAGING_URL }}
          API_PASSWORD: ${{ secrets.LOADTEST_PASSWORD }}
          K6_WEB_DASHBOARD: 'true'
          K6_WEB_DASHBOARD_PORT: '-1'  # no dashboard server in CI, just the exported report
          K6_WEB_DASHBOARD_EXPORT: report.html
        with:
          path: tests/perf/smoke.js
          flags: --vus 5 --duration 1m

      - uses: actions/upload-artifact@v4
        if: always()                    # keep the report when thresholds fail
        with:
          name: k6-report
          path: |
            report.html
            summary.json
            junit.xml

if: always() on the upload step is the line people forget. Without it, the report is thrown away exactly when the test fails and you need it.

Budgets and PR comments

I wrote a free action, k6-performance-budget, for the most common case: fail the pull request when p95 or the error rate is over budget, or when p95 is more than a set percentage slower than a baseline from main. It writes the result to the job summary and, optionally, a comment on the pull request.

# .github/workflows/perf-budget.yml
name: Performance budget
on: pull_request

permissions:
  contents: read
  pull-requests: write                  # for the PR comment

jobs:
  budget:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pawansinha0612/k6-performance-budget@v1
        with:
          script: tests/perf/smoke.js
          p95-ms: 400                   # fail if p95 is over 400 ms
          error-rate: 1                 # fail if more than 1% of requests fail
          args: --vus 10 --duration 1m -e BASE_URL=${{ vars.STAGING_URL }}
          comment-on-pr: true

Thresholds inside your script still apply, so you can keep per-endpoint budgets in the script and the headline budget in the workflow. To compare against main, save the k6-budget.json it writes from a main run and pass it as baseline. The action's README has a full workflow for that.

GitLab CI

Use the official grafana/k6 image. Its entrypoint is k6, so clear it or GitLab can't run your script lines.

# .gitlab-ci.yml
stages: [perf]

k6-smoke:
  stage: perf
  image:
    name: grafana/k6:latest            # pin a version tag in a real pipeline
    entrypoint: ['']                   # the image's entrypoint is k6 itself; GitLab needs a shell
  variables:
    BASE_URL: https://staging.example.com
    K6_WEB_DASHBOARD: 'true'
    K6_WEB_DASHBOARD_PORT: '-1'
    K6_WEB_DASHBOARD_EXPORT: report.html
  script:
    - k6 run tests/perf/smoke.js       # exit code 99 on a failed threshold fails the job
  artifacts:
    when: always
    paths: [report.html, summary.json]
    reports:
      junit: junit.xml                 # thresholds show up in the merge request test report
  rules:
    - if: $CI_PIPELINE_SOURCE == 'merge_request_event'
    - if: $CI_PIPELINE_SOURCE == 'schedule'

Jenkins, Azure DevOps and CircleCI work the same way: install k6 or use the image, run k6 run, keep the reports as artifacts, and let the exit code fail the stage.

Keeping CI results trustworthy

  • Test a stable target. A staging environment that's also running three other teams' tests gives random results. A dedicated environment, or at least a quiet time slot, matters more than any tool setting.
  • Set budgets from data. Run the test five or ten times, take the worst p95 and add headroom. A budget tighter than the run-to-run noise fails randomly, and a flaky gate gets switched off within a month.
  • Pin the k6 version. Metrics and summary formats change between major versions.
  • Watch the runner. A 2-vCPU hosted runner is fine for tens of VUs. For hundreds, use a bigger self-hosted runner and check its CPU during the run.
  • Never point PR tests at production unless the test is read-only, tiny and agreed with whoever runs production.

For trends across runs, send results to a time-series database: see outputs and dashboards. To set budgets properly, read performance budget and shift-left performance testing.
