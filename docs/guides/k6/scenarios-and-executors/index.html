k6 scenarios and executors: pick the model before the numbers

Your test says 200 VUs held p95 under 300 ms. In production, 200 requests a second took the site down. Both can be true, because VUs are not requests per second. The executor you choose decides which question your test answers.

Open vs closed: the one decision that matters

In a closed model a fixed number of users loop: send a request, wait for the response, think, repeat. When the server slows down, every user waits longer, so the request rate falls. The test quietly backs off at the exact moment the system is struggling.

In an open model new work arrives on a schedule whether or not earlier requests finished, like real visitors on a public site. When the server slows down, requests pile up and queues grow, which is what actually happens in production.

The closed model's backing off has a name: coordinated omission. The tool coordinates with the problem and never sends the requests that would have been slow, so your p99 looks better than reality. The percentiles explainer shows it happening.

My rule: use an arrival-rate (open) executor when you have a throughput target, such as "500 checkouts a minute" or "2,000 requests a second at peak". Use a VU-based (closed) executor when the real system has a fixed population, such as 300 call-centre agents, a pool of batch workers, or a mobile app with a known number of logged-in sessions. More in open vs closed workload model and the load profiles explainer.

Every executor, and when to use it

ExecutorModelWhat it controlsUse it for
shared-iterationsClosedA total number of iterations shared by N VUs. Fast VUs do more."Run this 1,000 times as fast as possible": data seeding, one-pass-per-row CSV tests.
per-vu-iterationsClosedEach VU does exactly N iterations.Each user must do the journey a fixed number of times.
constant-vusClosedN VUs looping for a duration. The default with --vus and --duration.Smoke tests, soak tests with a known user population.
ramping-vusClosedVU count follows stages. What the stages shortcut creates.Ramp a fixed population up and down.
constant-arrival-rateOpenStarts rate iterations per timeUnit, whatever the latency.Steady throughput targets: "hold 300 requests/s for 30 minutes".
ramping-arrival-rateOpenIteration rate follows stages.Load, stress, spike and breakpoint tests with a rate target.
externally-controlledClosedVUs changed at runtime through the REST API.Removed in k6 v2.0. Don't start new tests with it.

Here is every current executor in one script, staggered with startTime:

import http from 'k6/http';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// One scenario per executor, staggered with startTime so they don't overlap.
export const options = {
  scenarios: {
    shared: {
      executor: 'shared-iterations', // 200 iterations in total, shared by 10 VUs
      vus: 10, iterations: 200, maxDuration: '1m',
    },
    perVu: {
      executor: 'per-vu-iterations', // every VU does exactly 20 iterations
      vus: 10, iterations: 20, maxDuration: '1m', startTime: '1m',
    },
    constantVus: {
      executor: 'constant-vus', // 10 VUs looping for 1 minute
      vus: 10, duration: '1m', startTime: '2m',
    },
    rampingVus: {
      executor: 'ramping-vus', // closed model with stages
      startVUs: 0,
      stages: [{ duration: '30s', target: 20 }, { duration: '30s', target: 0 }],
      startTime: '3m',
    },
    constantRate: {
      executor: 'constant-arrival-rate', // open model: 50 iterations/s, whatever the latency
      rate: 50, timeUnit: '1s', duration: '1m',
      preAllocatedVUs: 20, maxVUs: 100, startTime: '4m',
    },
    rampingRate: {
      executor: 'ramping-arrival-rate', // open model with stages of iterations per timeUnit
      startRate: 10, timeUnit: '1s',
      preAllocatedVUs: 20, maxVUs: 200,
      stages: [{ duration: '30s', target: 100 }, { duration: '30s', target: 100 }],
      startTime: '5m',
    },
  },
};

export default function () {
  http.get(`${BASE_URL}/health`);
}

Scenarios run in parallel unless you stagger them with startTime. That's how you model "background traffic all day, plus a spike at 9 am".

Arrival-rate maths: sizing preAllocatedVUs

An arrival-rate executor still needs VUs to run the iterations. A VU is busy for the whole iteration, including any sleep(). Little's Law tells you how many are busy at once:

VUs needed = arrival rate (iterations/s) x iteration duration (s)

For example, you want 100 iterations a second. One iteration makes two calls of about 150 ms each, so it takes about 0.3 s. You need 100 × 0.3 = 30 VUs busy on average.

Now the server degrades and the iteration takes 1.5 s. You need 100 × 1.5 = 150 VUs to keep the same rate. That's the whole point of an open model: it needs more concurrency as latency grows. So size two numbers:

  • preAllocatedVUs: enough for normal latency plus some headroom. k6 creates these before the test starts, so they cost nothing during the run. Here, 50.
  • maxVUs: the ceiling for when latency grows. k6 creates extra VUs mid-test if it needs them, which costs CPU and memory on the load generator. If you leave maxVUs out, it equals preAllocatedVUs. Here, 300 gives room for iterations to get 10 times slower.

Two consequences people miss. First, a sleep() at the end of an arrival-rate iteration does not slow the rate down. It only holds a VU longer, so you need more VUs. In an open model, pacing comes from the rate, not from sleep. Second, rate counts iterations, not requests. An iteration with five requests at 100 iterations/s sends 500 requests a second.

import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// Open model: requests arrive at a fixed rate, like real traffic.
// Peak target: 100 browse iterations/s. One iteration takes about 0.3 s at normal latency.
// Little's Law: VUs busy = rate x iteration time = 100 x 0.3 = 30. Pre-allocate with headroom.
export const options = {
  scenarios: {
    browse: {
      executor: 'ramping-arrival-rate',
      exec: 'browse',
      startRate: 0,
      timeUnit: '1s',
      preAllocatedVUs: 50,
      maxVUs: 300, // room for iterations to get 10x slower before k6 drops any
      stages: [
        { duration: '2m', target: 100 }, // ramp to 100 browse/s
        { duration: '10m', target: 100 },
        { duration: '1m', target: 0 },
      ],
    },
    buy: {
      executor: 'constant-arrival-rate',
      exec: 'buy',
      rate: 20, // 20 purchases per minute
      timeUnit: '1m',
      duration: '13m',
      preAllocatedVUs: 5,
      maxVUs: 30,
    },
  },
  thresholds: {
    'http_req_duration{scenario:browse}': ['p(95)<400'],
    'http_req_duration{scenario:buy}': ['p(95)<800'],
    dropped_iterations: ['count<10'], // the generator itself kept up
  },
};

export function browse() {
  const res = http.get(`${BASE_URL}/products`);
  check(res, { 'browse 200': (r) => r.status === 200 });
}

export function buy() {
  const login = http.post(`${BASE_URL}/login`, JSON.stringify({ username: 'buyer', password: 'secret' }), {
    headers: { 'Content-Type': 'application/json' },
  });
  const token = login.json('access_token');
  const order = http.post(`${BASE_URL}/orders`, JSON.stringify({ productId: 3 }), {
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
  });
  check(order, { 'order created': (r) => r.status === 201 });
}

dropped_iterations: when k6 can't keep up

If every VU up to maxVUs is busy when the next iteration is due, k6 can't start it. It skips it and counts it in dropped_iterations, with a warning in the console. Read that metric as:

  • A few dropped at the start: preAllocatedVUs too low for the ramp. Raise it.
  • Many dropped as load rises: the system under test is slowing down and concurrency has hit maxVUs. This is a finding, not a tool problem: latency grew until the offered load could not be served. Raise maxVUs to see how far it degrades, or report the rate where drops began.
  • Dropped while the load generator's CPU is near 100%: the generator is the bottleneck. Your results are invalid. Use a bigger machine or split the load.

Put a threshold on it, as in the script above, so a test where k6 failed to send the planned load cannot pass.

A mixed workload with several scenarios

Real traffic is a mix: lots of browsing, fewer searches, a few purchases. Model each journey as its own scenario with its own rate and its own exec function, as in open-model.js above. Then:

  • Each scenario's metrics carry a scenario tag, so you can set thresholds per journey: 'http_req_duration{scenario:buy}': ['p(95)<800'].
  • Get the ratios from production analytics or access logs, not guesses. A workload model built from real data is what makes a load test credible.
  • Check the arithmetic with the capacity calculator before the run.

Scenario options you will need

OptionDefaultWhat it does
exec"default"Name of the exported function this scenario runs.
startTime"0s"Delay before the scenario starts.
gracefulStop"30s"How long running iterations may finish after the scenario ends, before they're interrupted.
gracefulRampDown"30s"Same, for VUs removed during a ramp-down (ramping-vus only).
envnoneExtra __ENV variables for this scenario only.
tagsnoneTags added to every metric from this scenario.
optionsnonePer-scenario options, for example { browser: { type: 'chromium' } }.

CLI flags like --vus, --duration and --iterations replace your whole scenarios block with one simple scenario. Handy for a quick debug run, confusing if you forget you passed them.
