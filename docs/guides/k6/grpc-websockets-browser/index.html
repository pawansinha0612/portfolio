k6 beyond HTTP: gRPC, WebSockets and real browsers

Your REST endpoints pass the load test. Then the trading screen falls over, because 20,000 open WebSocket connections were never part of the test. Here's how to cover the protocols that don't fit a request-response loop.

Which module, which version

These modules moved around before k6 1.0, and old blog posts still show the old paths. Current names:

ProtocolImportStatus and history
gRPCk6/net/grpcStable. Unary and streaming calls. The old k6/experimental/grpc was folded into it and now errors.
WebSocketsk6/websocketsCurrent. Browser-style API with an event loop and timers. Earlier releases (k6 v1.0 included) had it as k6/experimental/websockets.
WebSockets (legacy)k6/wsThe original blocking API. Still works, but new scripts should use k6/websockets.
Browserk6/browserStable and async (Playwright-like). k6/experimental/browser now errors and tells you to switch.

If an import fails, run k6 version first. A path error almost always means a version mismatch, not a typo.

gRPC

Load the .proto files in init code, connect once per VU, then invoke. The response has a status you compare with the grpc.Status* constants and a message object.

syntax = "proto3";
package hello;
service HelloService {
  rpc SayHello (HelloRequest) returns (HelloReply);
}
message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }
import grpc from 'k6/net/grpc';
import { check, sleep } from 'k6';

const client = new grpc.Client();
// Load the .proto in the init context (or use client.connect(addr, { reflect: true }))
client.load(['./proto'], 'hello.proto');

export const options = { vus: 10, duration: '1m' };

export default function () {
  // Connect once per VU, not once per iteration
  if (__ITER === 0) {
    client.connect(__ENV.GRPC_ADDR || 'localhost:50051', { plaintext: true, timeout: '5s' });
  }

  const res = client.invoke('hello.HelloService/SayHello', { name: 'k6' }, {
    metadata: { 'x-request-id': `k6-${__VU}-${__ITER}` },
    timeout: '2s',
  });

  check(res, {
    'status OK': (r) => r && r.status === grpc.StatusOK,
    'has message': (r) => r && r.message && r.message.message !== '',
  });
  sleep(1);
}
  • Connect once per VU. Connecting every iteration measures TLS and HTTP/2 setup, not your service. Real gRPC clients keep long-lived channels.
  • No proto files? If the server has reflection enabled, client.connect(addr, { reflect: true }) loads the definitions from it.
  • Streaming (client, server or bidirectional) uses new grpc.Stream(client, 'pkg.Service/Method') with on('data'), write() and end().
  • Metrics: unary calls go into grpc_req_duration, so set thresholds on that, not on http_req_duration.
  • Load balancing: one HTTP/2 connection carries every call from a VU. Behind an L4 load balancer that pins a connection to one pod, a few VUs can load one pod and leave the rest idle. That's a real production behaviour worth knowing about, but it can also make your test unrepresentative.

WebSockets

A WebSocket test is about concurrent connections and message flow, not requests per second. Each VU opens a socket, keeps it open, and sends and receives messages. The iteration ends when the socket closes.

import { WebSocket } from 'k6/websockets';
import { check } from 'k6';
import { Counter } from 'k6/metrics';

const received = new Counter('ws_app_messages');
const WS_URL = __ENV.WS_URL || 'ws://localhost:8080/ws';

export const options = {
  vus: 50,
  duration: '5m',
  thresholds: { ws_connecting: ['p(95)<500'] },
};

export default function () {
  const ws = new WebSocket(WS_URL);

  ws.onopen = () => {
    ws.send(JSON.stringify({ type: 'subscribe', channel: 'prices' }));
    // Send a ping-style message every 10 s while the socket is open
    const timer = setInterval(() => ws.send(JSON.stringify({ type: 'ping' })), 10000);
    // Keep each connection for 60 s, then close: the iteration ends when the socket closes
    setTimeout(() => { clearInterval(timer); ws.close(); }, 60000);
  };

  ws.onmessage = (e) => {
    received.add(1);
    const msg = JSON.parse(e.data);
    check(msg, { 'message has type': (m) => m.type !== undefined });
  };

  ws.onerror = (e) => console.error(`ws error: ${e.error}`);
}

On k6 v1.0 and earlier, change the import to k6/experimental/websockets. The rest of the script is the same.

  • ws_connecting (handshake time), ws_sessions, ws_msgs_sent, ws_msgs_received and ws_session_duration are built in.
  • Application latency (time from a server event to the client receiving it) is not built in. Put a timestamp in the message and record the difference in a custom Trend.
  • The number to target is usually peak concurrent connections. 5,000 VUs holding sockets for an hour is 5,000 connections. Ramp them up slowly: real users don't connect in the same second, unless you're testing reconnect storms after a deploy, which is a good test in its own right.

Browser tests

The browser module drives a real Chromium. It measures what users see: page load, Core Web Vitals and how long the UI takes to respond. It does not generate meaningful backend load: one browser costs roughly as much as hundreds of protocol-level VUs.

import { browser } from 'k6/browser';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = {
  scenarios: {
    ui: {
      executor: 'shared-iterations',
      vus: 2,
      iterations: 10,
      options: { browser: { type: 'chromium' } }, // required for browser scenarios
    },
  },
  thresholds: {
    browser_web_vital_lcp: ['p(75)<2500'],
    browser_web_vital_inp: ['p(75)<200'],
  },
};

export default async function () {
  const page = await browser.newPage();
  try {
    await page.goto(`${BASE_URL}/login`);
    await page.locator('input[name="username"]').fill('user001');
    await page.locator('input[name="password"]').fill('Passw0rd!');
    await Promise.all([
      page.waitForNavigation(),
      page.locator('button[type="submit"]').click(),
    ]);
    const heading = await page.locator('h1').textContent();
    check(heading, { 'logged in': (h) => h.includes('Welcome') });
  } finally {
    await page.close();
  }
}
  • The scenario needs options: { browser: { type: 'chromium' } }. Without it, browser.newPage() fails.
  • The API is async: await every page and locator call, and make the default function async.
  • k6 needs Chrome or Chromium installed on the machine. In Docker, use the grafana/k6:latest-with-browser image. To point k6 at a specific binary, set K6_BROWSER_EXECUTABLE_PATH. To watch it run, set K6_BROWSER_HEADLESS=false.
  • Web vitals arrive as browser_web_vital_lcp, _inp, _cls, _fcp and _ttfb. Google rates these at p75, so set the thresholds at p75. See LCP, INP and CLS. The old FID metric was removed in k6 v2.0.
  • Always close the page in finally, or failed iterations leak browser contexts and memory.

Hybrid: protocol load plus a few browsers

The useful pattern is both at once. Generate the load with cheap protocol-level VUs and run one or two browsers beside them, to see what a real user experiences while the backend is busy:

import http from 'k6/http';
import { browser } from 'k6/browser';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

// Most of the load at protocol level (cheap), plus a few real browsers measuring what users see.
export const options = {
  scenarios: {
    api: {
      executor: 'constant-arrival-rate', exec: 'api',
      rate: 50, timeUnit: '1s', duration: '10m', preAllocatedVUs: 50, maxVUs: 200,
    },
    ui: {
      executor: 'constant-vus', exec: 'ui', vus: 2, duration: '10m',
      options: { browser: { type: 'chromium' } },
    },
  },
};

export function api() {
  http.get(`${BASE_URL}/products`);
}

export async function ui() {
  const page = await browser.newPage();
  try {
    await page.goto(`${BASE_URL}/`);
  } finally {
    await page.close();
  }
}

This answers the question stakeholders actually ask: "what does the page feel like at peak load?" The API numbers say the backend held. The browser numbers say whether the front end, third-party scripts and CDN held too.
