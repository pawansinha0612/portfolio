k6 getting started: a first test that can actually fail

You run your first k6 script, it prints a wall of green numbers and exits 0. Nobody knows if that's good. This guide gets you to a script that checks responses, has pass/fail budgets, and tells CI the truth.

Install k6

k6 is a single Go binary. Pick one:

# macOS
brew install k6

# Windows
winget install k6 --source winget

# Debian/Ubuntu: add Grafana's apt repo first (see the k6 install docs), then
sudo apt-get install k6

# Docker, no install at all
docker run --rm -i grafana/k6 run - <script.js

k6 version

Scripts are JavaScript (or TypeScript), but k6 is not Node.js. There is no npm install at runtime, no fs, no require of npm packages. You get the k6 modules, ES module imports of local files and remote URLs, and a fast Go HTTP client underneath.

This guide uses k6 v1.x and v2.x syntax. Everything here runs on both unless a note says otherwise. If you're on a 0.x release, upgrade first: the browser, gRPC and summary modules changed a lot before 1.0.

The first script

Save this as first-test.js. It sends traffic to BASE_URL, checks each response and sets two budgets.

import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = {
  vus: 5,
  duration: '30s',
  thresholds: {
    http_req_failed: ['rate<0.01'],   // under 1% failed requests
    http_req_duration: ['p(95)<500'], // 95% of requests under 500 ms
  },
};

export default function () {
  const res = http.get(`${BASE_URL}/products`);
  check(res, {
    'status is 200': (r) => r.status === 200,
    'has items': (r) => r.json('items.#') > 0,
  });
  sleep(1); // think time: a real user pauses between actions
}

Run it against your own API (never someone else's):

k6 run -e BASE_URL=https://staging.example.com first-test.js

Three things in this script do the real work:

  • check() verifies the response. A check that fails does not stop the test or fail it. It only records a pass or a fail in the checks metric. Without checks, a fast 500 error page looks like great performance.
  • thresholds are the pass/fail budgets. If one is crossed, k6 exits with code 99 and CI goes red. This is what turns a script into a test. More in thresholds and checks.
  • sleep(1) is think time. Without it each virtual user fires requests back to back, so 5 VUs can mean 500 requests a second instead of 5. See think time.

The four parts of a k6 script

PartRunsUse it for
Init code (top level)Once per VU, plus once more to read optionsImports, options, open() files, SharedArray. No HTTP calls allowed here.
setup()Once, before the load startsGet a token, create test data. Its return value goes to every VU.
default function (or a scenario's exec)Over and over, by every VUThe user journey. One run is one iteration.
teardown(data)Once, after the load endsClean up test data.

Module-level variables are per VU. Each VU is its own JavaScript runtime, so a counter you increment in one VU is invisible to the others. That's a feature: it's how you keep a per-user token (see auth and correlation).

Reading the summary

At the end k6 prints thresholds first, then the metrics. The lines that matter most:

  • http_req_duration: time from sending the request to receiving the whole response (sending + waiting + receiving). It excludes DNS, connect and TLS time, which are in http_req_connecting and http_req_tls_handshaking. Look at p(95) and p(99), not avg. Here's why averages lie.
  • http_req_failed: share of requests with a status outside 200-399 (by default) or a network error.
  • checks: share of checks that passed.
  • iterations and http_reqs: how much work was done, as totals and per second. This is your throughput.
  • vus and vus_max: how many VUs were running.

The summary is per test, not per endpoint, unless you add tags. For a time series, a per endpoint breakdown or a shareable HTML report, see outputs and dashboards. To make sense of a summary you already have, paste it into the k6 results analyser.

A realistic ramp

A flat 5 VUs is a smoke test. A load test ramps up, holds a steady state long enough to measure, and ramps down. The stages shortcut does that:

import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:8080';

export const options = {
  stages: [
    { duration: '2m', target: 50 },  // ramp up to 50 VUs
    { duration: '10m', target: 50 }, // hold: this is the part you measure
    { duration: '2m', target: 0 },   // ramp down
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500', 'p(99)<1500'],
  },
};

export default function () {
  const list = http.get(`${BASE_URL}/products`);
  check(list, { 'list 200': (r) => r.status === 200 });
  sleep(Math.random() * 2 + 1); // 1-3 s think time

  const id = list.json('items.0.id');
  const item = http.get(`${BASE_URL}/products/${id}`, { tags: { name: 'GET /products/:id' } });
  check(item, { 'item 200': (r) => r.status === 200 });
  sleep(Math.random() * 2 + 1);
}

Two details here matter more than they look. The name tag groups every /products/123, /products/456 into one row, otherwise your metrics explode into one series per id. And the think time is random, so VUs don't fall into lockstep and hit the server in waves.

stages controls the number of VUs, not the request rate. If the server slows down, each VU makes fewer requests and the load drops just when it should stay high. For a fixed request rate you need an arrival-rate executor. That's the single most important idea in k6, covered in scenarios and executors.

Useful CLI overrides while you develop a script:

k6 run --vus 1 --iterations 1 script.js   # one pass, to debug the journey
k6 run --http-debug=full --iterations 1 script.js  # print requests and responses
k6 run -e BASE_URL=http://localhost:8080 script.js
