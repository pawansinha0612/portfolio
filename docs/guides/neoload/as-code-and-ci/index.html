NeoLoad as code: tests that live next to the app

The API team ships twice a day. The performance team runs NeoLoad from a shared workstation once a sprint, when someone remembers. By the time a slow endpoint is found, it is buried under 20 merges. NeoLoad's as-code YAML and the neoload command line let a pipeline upload a project, run it on a zone in NeoLoad Web and fail the build on SLAs, without anyone opening the GUI.

1. As-code YAML

A NeoLoad project can be written as YAML: servers, variables, User Paths, populations, scenarios and SLA profiles. The schema is documented in Tricentis's neoload-models repository on GitHub and in the NeoLoad docs ("YAML format"). Files must end in .yaml or .yml. A small but complete project:

# default.yaml
name: accounts-api

sla_profiles:
- name: api_sla
  thresholds:
  - perc-transaction-resp-time (p95) warn >= 500ms fail >= 800ms per test
  - error-rate warn >= 1% fail >= 2% per test
  - error-rate fail >= 5% per interval

servers:
- name: api
  host: accounts-staging.example.com
  scheme: https
  port: 443

variables:
- file:
    name: users
    path: data/users.csv
    is_first_line_column_names: true
    change_policy: each_iteration
    scope: unique

user_paths:
- name: ViewAccounts
  actions:
    pacing: 20s
    steps:
    - transaction:
        name: 01_Login
        sla_profile: api_sla
        steps:
        - request:
            server: api
            url: /v1/login
            method: POST
            headers:
            - Content-Type: application/json
            body: |
              {"username": "${users.username}", "password": "${users.password}"}
            extractors:
            - name: token
              jsonpath: $.access_token
    - think_time: 3s
    - transaction:
        name: 02_Accounts
        sla_profile: api_sla
        steps:
        - request:
            server: api
            url: /v1/accounts
            headers:
            - Authorization: Bearer ${token}

populations:
- name: pop_accounts
  user_paths:
  - name: ViewAccounts
    distribution: 100%

scenarios:
- name: ci_smoke
  populations:
  - name: pop_accounts
    rampup_load:
      min_users: 5
      max_users: 30
      increment_users: 5
      increment_every: 30s
      duration: 10m

Every key here comes from the as-code reference (SLA threshold syntax, servers, file variables, pacing on the actions container, transactions, requests with extractors, populations and a ramp-up policy). I could not run it here, so treat it as a sketch and validate it with neoload validate default.yaml before use. Thirty users pacing at 20 seconds gives about 1.5 iterations per second, a sensible smoke load.

Split larger projects with includes:, for example a common design file plus per-environment files for servers, variables and SLAs, and choose the environment file at run time.

2. Mixing GUI projects and YAML

You don't have to write everything in YAML. A common pattern is to design complex User Paths in the GUI (recording and correlation are much faster there) and keep scenarios, servers and SLAs in YAML that the pipeline overrides per environment. A YAML scenario with the same name as one in the project replaces it entirely, and a new name adds one. Recent releases can also open a YAML file or zipped project directly in the GUI.

3. The neoload CLI

The command line client is a Python package called neoload (version 1.4.1 on PyPI at the time of writing). It talks to the NeoLoad Web API with a token, so it runs anywhere Python 3 does, not just on Windows.

pip3 install neoload

# authenticate (SaaS by default, --url for an on-premises NeoLoad Web API)
neoload login $NLW_TOKEN
neoload login --url https://neoload-api.internal.example.com/ --workspace "Default Workspace" $NLW_TOKEN

# create or update test settings: zone, generator count, scenario
neoload test-settings --zone $NLW_ZONE --lgs 2 --scenario ci_smoke createorpatch accounts-ci

# upload the project folder to those test settings
neoload project --path ./perf upload accounts-ci

# check YAML syntax and schema
neoload validate ./perf/default.yaml

# run, naming the result after the build
neoload run --name "accounts-ci-$CI_PIPELINE_IID" --description "commit $CI_COMMIT_SHORT_SHA"

# export SLA results as JUnit XML for the CI test report
neoload test-results --junit-file junit-sla.xml junitsla

Behaviour worth knowing, from the CLI's README and source:

  • neoload run blocks and streams progress, prints a summary with passed and failed SLAs, and exits non-zero when the result fails its SLAs. --return-0 turns that off. --detached starts the test and returns at once.
  • If the scenario doesn't exist in the project, NeoLoad Web falls back to its "Custom" scenario (10 users for 5 minutes). Always pass or set the scenario explicitly.
  • When chaining commands on one line, the exit code is that of the last command, so don't chain run with test-results junitsla. Run them as separate steps.
  • If the uploaded folder contains other YAML files (such as .gitlab-ci.yml), add a .nlignore file, or NeoLoad Web tries to parse them as as-code and fails.
  • neoload fastfail with a detached run stops a test early when SLAs are being violated, so a broken environment fails the pipeline in minutes instead of after the full duration.

4. GitLab CI

# .gitlab-ci.yml (sketch)
performance:
  stage: test
  image: python:3.12-slim
  variables:
    NLW_ZONE: "defaultzone"
  script:
    - pip3 install neoload
    - neoload login $NLW_TOKEN
    - neoload test-settings --zone $NLW_ZONE --lgs 2 --scenario ci_smoke createorpatch accounts-ci
    - neoload project --path ./perf upload accounts-ci
    - neoload run --name "accounts-ci-$CI_PIPELINE_IID" --external-url "$CI_JOB_URL" --external-url-label "GitLab job $CI_JOB_ID"
  after_script:
    - neoload test-results --junit-file junit-sla.xml junitsla
  artifacts:
    when: always
    reports:
      junit: junit-sla.xml

Store NLW_TOKEN as a masked CI variable. The JUnit export sits in after_script because that still runs when neoload run fails the job on SLAs. It relies on the CLI's config file (login and current result) still being there, which holds when after_script runs in the same job container. If your runner differs, log in again there and select the result explicitly. The CLI repository has maintained pipeline examples for GitLab, Jenkins, Azure DevOps, GitHub Actions, AWS and Bamboo. Start from those and compare against this sketch.

5. Jenkins, Azure DevOps and GitHub Actions

  • Jenkins: run the same CLI commands in sh steps, and publish junit-sla.xml with the junit step. The CLI repository includes a Jenkinsfile that uses detached mode with fastfail. Tricentis has also published a NeoLoad plugin for Jenkins over the years. Check whether your Jenkins uses it, but the CLI approach is the same across CI systems.
  • Azure DevOps: a script step on a Linux or Windows agent with Python, the same commands, and Publish Test Results for the JUnit file. Tricentis maintains Azure DevOps examples in the CLI repository.
  • GitHub Actions: actions/setup-python, then the CLI. Keep the token in repository or environment secrets.

NeoLoad 2026.2 added DevOps Workspaces, aimed at early-stage tests in CI/CD with dedicated capacity. If your licence includes them, they are worth a look for pipeline runs.

6. NeoLoadCmd

Before the CLI and NeoLoad Web, pipelines ran the desktop install headless with NeoLoadCmd. It still exists and still appears in the current docs, for example running a project with extra YAML files:

NeoLoadCmd.exe -project "C:\perf\MyProject\MyProject.nlp" "C:\perf\myproject-scenarios.yaml" "C:\perf\myproject-environment.yaml" -launch MyScenario

It needs NeoLoad installed on the agent and its own access to generators and a licence. For new pipelines, prefer the neoload CLI and NeoLoad Web zones, and check your version's NeoLoadCmd reference for its other arguments.

7. Designing the gate

  • Small, fast, every day. 10 to 15 minutes at a fraction of peak, on merges to main or nightly. Keep full-scale tests in a scheduled window.
  • Percentiles and error rate per transaction, with thresholds a little above the current baseline. Add a per-interval error-rate rule so a bad few minutes fails the run. See thresholds.
  • Stable environment and data. Gates on noisy shared environments get flaky, and flaky gates get switched off.
  • Name results after the build so NeoLoad Web trends line up with commits.
  • Budget licence capacity. Pipeline runs lease users from the same pool as big tests.
