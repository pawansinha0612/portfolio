NeoLoad results: green is not the same as good

The run finishes, the quality status says Passed and the summary shows an average transfer time of 900 ms. Two weeks later production users complain about 6-second transfers at lunchtime. The SLA was an average over the whole test, including the ramp-up, and the slow minutes were averaged away. NeoLoad gives you per-interval SLAs, percentiles and comparisons. Use them, and decide what "pass" means before the run.

1. What to check first

  1. Did the load run as designed? Users over time matched the scenario, and throughput (transactions or requests per second) reached the target. If throughput flattened while users kept rising, that is your first finding.
  2. Did it work? Error count and rate, which requests failed and with what. A run with 8% errors has different response times from the one you planned.
  3. Were the generators healthy? Check the load generators' CPU and memory in the monitors. A saturated generator adds its own delay.
  4. Only then: how fast? Percentiles per transaction in the steady state.

2. Results in the GUI

The Results section of the desktop app holds every run of the project. The main views:

ViewAnswers
Test summaryHeadline statistics, SLA status, hot spots, errors and alerts
ValuesA table of statistics per transaction, page and request: average, min, max, percentiles, counts, errors
GraphsDrag any statistic or monitor counter onto a chart to plot it against time, several on one chart
ErrorsEach error with the request and response that caused it
AlertsSLA and monitor threshold breaches during the run

The useful view is usually two lines on one chart: users with transaction response time, or throughput with server CPU. If response time climbs while throughput flattens and CPU sits at 60%, the bottleneck is not CPU. Look at pools, locks and downstream calls. See finding bottlenecks and saturation.

3. Results in NeoLoad Web

When the GUI or CLI sends results to NeoLoad Web, the team sees them live and afterwards, without access to the tester's machine. NeoLoad Web adds:

  • Live view during the run, including (from 2026.2) adding or stopping virtual users on a running test.
  • Dashboards you build from results and monitors, shareable across the team.
  • Trends across many runs of the same test, the view that catches gradual regressions.
  • Comparison: 2026.2 added comparison dashboards for up to four results and a scatter plot of durations.
  • Augmented analysis (from 2025.1): an AI-assisted view, starting with RED statistics (rate, errors, duration), that points out which parts of a result deserve a closer look. Treat its findings as leads to check, not conclusions. See the RED method.
  • APM integrations, such as Dynatrace, so server-side data sits next to load data. See monitoring during a test.

4. Percentiles and the steady state

Averages hide the users having a bad time. If 95% of transfers take 1 second and 5% take 20 seconds, the average is 1.95 seconds and describes nobody. Report the 90th or 95th percentile per transaction and say which one.

  • Filter to the steady state. Exclude the ramp-up and ramp-down by filtering the result to a time range before reading statistics. See steady state.
  • Separate failed transactions. Fast failures pull percentiles down. Report error rate on its own line.
  • Look at the distribution over time, not just one number. A 5-second stall every two minutes, from a cache refresh or garbage collection, disappears in a whole-run percentile and shows clearly on a graph. See tail latency and the percentiles explainer.

5. SLA profiles

An SLA profile is a named set of thresholds you attach to transactions, pages, requests or containers (and in as-code, to a whole scenario). Each threshold has a warning and a failure level, and is evaluated either per test (over the whole run) or per interval (continuously during the run). In as-code:

sla_profiles:
- name: payments_sla
  thresholds:
  - perc-transaction-resp-time (p95) warn >= 1s fail >= 2s per test
  - error-rate warn >= 1% fail >= 2% per test
  - avg-resp-time warn >= 1500ms fail >= 3s per interval
  - error-rate warn >= 2% fail >= 5% per interval
ScopeIndicators (as-code names)Good for
Per testavg-request-resp-time, avg-page-resp-time, avg-transaction-resp-time, perc-transaction-resp-time (pNN), avg-request-per-sec, avg-throughput-per-sec, errors-count, count, throughput, error-rateThe release decision: did the run meet its targets?
Per intervalavg-resp-time, avg-elt-per-sec, avg-throughput-per-sec, errors-per-sec, error-rateCatching bad minutes, live alerts and stopping a broken run early

The percentile threshold applies to transactions and defaults to p90 if you don't specify one. Which indicator applies to which element type is listed in the as-code SLA reference. Check it, because not every indicator applies to every element.

  • Per-transaction targets. Login, search and payment do not share a target. Create a profile per class of transaction.
  • Percentile for the decision, per-interval for safety. A per-test percentile answers "did we meet the target". A per-interval error rule catches a 5-minute outage the whole-run numbers hide, and lets the CLI's fast-fail stop a broken run.
  • Agree numbers before the run. An SLA set after seeing the results is a description, not a test. See SLA, SLO and the SLO calculator.

SLA results drive the run's quality status in NeoLoad Web, the CLI's exit code and the JUnit export for CI. See as-code and CI.

6. Comparing runs

  • Compare like with like. Same scenario, same data volumes, same environment size. Otherwise you are comparing environments, not builds.
  • Use a baseline. Mark a known-good run as the baseline and compare each new build against it, in the GUI's comparison mode or NeoLoad Web's comparison dashboards.
  • Look for direction and size together. A 3% change in p95 is usually noise between runs. A 30% change in one transaction with the rest flat is a finding. Run the baseline twice to learn your noise level.
  • Use trends for the long view. Many small regressions add up. The trend across 20 nightly runs shows what no single comparison does.

7. Writing it up

NeoLoad generates reports from a result (and comparison reports from two), in formats that vary by version. Use them as appendices. The report people read should lead with the answer: did it meet the targets, at what load did it stop scaling, what is the bottleneck, and what do you recommend. Put the scenario, environment and data assumptions on the first page, because a result without them cannot be compared later.
