NeoLoad correlation: trust the wizard, then check its work

The post-recording wizard found 14 dynamic parameters and the User Path check is green. You run 200 users and 30% of them fail at payment. The wizard correlated the session token and the CSRF value, but the basket ID comes back in a JSON response it treated as static, and every user is paying for the same basket. Automatic correlation gets you most of the way. The rest is knowing where to look.

1. Dynamic parameters and the search

A dynamic parameter is a value the server generates and the client sends back later: session IDs, CSRF tokens, OAuth tokens, IDs created during the journey. NeoLoad handles them two ways:

  • Framework dynamic parameters: predefined rules for known frameworks and applications. NeoLoad ships frameworks for common platforms, including a SAP Fiori framework added in 2026.2.
  • Generic dynamic parameters: detected by comparing values across requests and responses, then configured automatically.

The post-recording wizard runs a dynamic parameter search for you. You can run it again from the User Path at any time, which is worth doing after you fix a correlation, because a broken early value can hide later ones.

2. Variable extractors

When the search misses something, add a variable extractor on the request whose response contains the value (select the request, open its advanced settings and the Variable extractors tab). The main fields:

FieldMeaning
Variable nameUse it later as ${basketId}
Extract fromBody, headers or both. Narrower is safer
Starting with / Ending withText immediately before and after the value, the boundary method
Regular expressionAlternative to boundaries, with a value template such as $1$
XPath / JSONPathLocate the value in XML or JSON first, optionally then apply a regex
OccurrenceWhich match: the first (default), a specific one, random, or all (for loops)
DecodeHTML or URL decoding
Default value / assertionWhat to return if nothing matches, and whether that raises an assertion error

After you create an extractor, NeoLoad searches later requests for the extracted value and offers to replace it: Replace all, or Replace manually to review each one. Review manually when the value is short or common (like 1), or you will replace things that only looked the same.

The as-code equivalent, on the request that returns the basket:

- request:
    url: /api/basket
    server: shop
    method: POST
    headers:
    - Content-Type: application/json
    body: |
      {"sku": "${products.sku}", "qty": 1}
    extractors:
    - name: basketId
      jsonpath: $.basket.id
    - name: csrfToken
      from: header
      regexp: 'X-CSRF-Token: (.+)'
      extract_once: true

Treat this as a sketch: it follows the as-code reference, but I could not run it here, and the header regex depends on how your server formats the header. Run neoload validate on the file before using it. Later requests use ${basketId}. The extractor settings (from, jsonpath, xpath, regexp, match_number, template, decode, extract_once, default, throw_assertion_error) are documented in the neoload-models as-code reference. In it, match_number: -1 extracts all occurrences and 0 picks one at random.

Leave the assertion on for anything critical. By default a missed extraction raises an assertion error. For a session token, that is exactly right: the user fails at the step that broke, not three steps later with a confusing 400. Turn it off only when "not found" is a valid outcome you handle with an If action.

3. Framework parameters

If the same kind of value appears in many places (a token on every form, a view state on every page), turn the extractor into a framework parameter. Use Add to framework parameters from the extractor, or manage frameworks in Edit → Preferences → Frameworks. A framework rule says where to extract the value from and where to inject it (a parameter name or value, a path, a header or text content). Then run the dynamic parameter search again and NeoLoad applies the rule everywhere.

Frameworks live in preferences, so they apply across projects, and they can be exported and imported. Build a framework for your organisation's common platform once, share it, and every new recording against that platform correlates more of itself.

4. Variables for test data

Variables are defined in the Design section (the variables manager) or in as-code. The common types:

TypeGives you
FileRows from a CSV-style file: usernames, passwords, accounts, search terms
ListA small inline table of values
CounterA number that increments between a start and an end
Random number, Random string, Random UUIDGenerated values
Current date, DateFormatted dates
SQLValues from a database query
JavaScriptA value computed by a script
Shared queueValues passed between virtual users, for example IDs created by one User Path and consumed by another
Secret vaultA secret read from an external vault at launch (2026.2, configured in NeoLoad Web)
Constant (and Password in recent as-code)Fixed values

Reference a file variable column as ${users.username}, that is ${variableName.columnName}.

5. Change policy, scope and order

These three settings decide which virtual user gets which value, and when it changes. In as-code they look like this:

variables:
- file:
    name: users
    path: data/users.csv
    is_first_line_column_names: true
    change_policy: each_user
    scope: unique
    order: sequential
    out_of_value: stop_test
SettingOptionsMeaning
Change policyeach use, each request, each page, each iteration (default), each userWhen the variable takes a new value. "Each iteration" changes it between Init, Actions and End too
Scopelocal, global (default), uniqueLocal: values per virtual user. Global: shared across users. Unique: shared, but a value is used by only one user at a time
Ordersequential, random, any (default)How values are handed out
Out of valuescycle (default), stop test, no-value codeWhat happens when the file runs out
NeedChange policyScope
One customer per virtual user, logged in once in InitEach userUnique
A new customer per iteration, never shared at the same timeEach iterationUnique
Search terms or product IDs, sharing is fineEach iterationGlobal, random order
Single-use data such as vouchersEach iterationUnique, stop test when out, file sized for the run

Global is the default, and it is not unique. With Global scope, two virtual users can hold the same row at the same time. For logins, that means two users sharing an account, session clashes and lock-outs that look like application bugs. Use Unique for anything a real user would own.

Size files for the whole test: users × (duration ÷ pacing) rows for per-iteration unique data, plus margin. The glossary entry on parameterisation covers data design in tool-neutral terms.

6. When correlation fails

  1. Run Check User Path and open the first failing request. Compare the request NeoLoad sent with the recorded one.
  2. Look at the variables tab of the check: which variables were used, and which were extracted with what value. A <NOT FOUND> value points straight at the broken extractor.
  3. Check the extractor is on the right request. Values often arrive in a redirect, or in an API call made after the page loads.
  4. Check encoding. The same value can be URL-encoded in one place and raw in another. Use the decode option or encode on injection.
  5. If the value is generated in the browser by JavaScript, there is nothing to extract. Reproduce it in a JavaScript action, or ask the developers for a test-only bypass.
