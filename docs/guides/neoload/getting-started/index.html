NeoLoad in 2026: the pieces and how they fit

You are handed a NeoLoad project folder, a NeoLoad Web URL and a note that says "run it on the dynamic zone". You open the desktop app and find Design, Runtime and Results tabs, and the web UI shows tests, results and workspaces that don't obviously match. This guide maps the components, so you know which one does what before you press Run.

1. What NeoLoad is today

NeoLoad was built by Neotys and bought by Tricentis in 2021. Releases are numbered by year: at the time of writing the documentation's latest release is 2026.2, and the as-code reference already lists additions for 2026.3. Recent releases added a new NeoLoad Web front end (also on-premises from 2026.1), Azure Service Bus testing, MCP server testing, a SAP Fiori correlation framework, secrets from external vaults, and the ability to run JMeter tests from NeoLoad Web.

Its strengths compared with open-source tools are fast GUI design with strong automatic correlation, packaged-application protocols (SAP, Citrix, Oracle Forms and others, depending on licence) and a shared web platform for results. See JMeter vs NeoLoad for the trade-offs.

2. The components

ComponentJob
NeoLoad GUI (desktop, often just called "NeoLoad")Design User Paths, record, correlate, build scenarios, run tests and analyse results. Projects are folders with an .nlp file
NeoLoad WebThe web platform: test settings, launching tests, live and historical results, dashboards, trends, comparison, workspaces, users and licence server. Available as SaaS or installed on-premises
ControllerOrchestrates a test run and collects results. The GUI acts as controller when you run from the desktop. Headless controllers run tests launched from NeoLoad Web or the CLI
Load generatorsExecute virtual users. Installed on Windows or Linux machines, or run as containers
Zones (NeoLoad Web)Named pools of controllers and generators. Static zones are machines you registered. Dynamic zones start containers on demand on a configured infrastructure provider such as Kubernetes or OpenShift

Two ways to run. From the GUI, your workstation is the controller and you pick generators. From NeoLoad Web or the CLI, you choose a zone and a number of generators, and a controller in that zone runs the project you uploaded. CI uses the second way. See as-code and CI.

3. The desktop GUI: Design, Runtime, Results

  • Design: User Paths (what a virtual user does), populations (mixes of User Paths), monitors, variables, servers and SLA profiles. See User Paths and recording.
  • Runtime: scenarios, which combine populations with load policies and durations, plus the generators to use. Run and watch the test here. See populations and scenarios.
  • Results: summaries, values, graphs, errors and alerts for each run, plus comparison. See analysis and SLAs.

Results can also be sent to NeoLoad Web as the test runs, which is where most teams share them.

4. Licensing

NeoLoad is commercial, and pricing depends on your agreement, so I won't quote numbers. The current docs describe three ways to get virtual users:

  • Licence file on a workstation, permanent or temporary. A rental licence lasts 24 hours from first launch.
  • Licence server: NeoLoad Web holds a pool of virtual users. You lease what a test needs and release it afterwards. This suits teams sharing capacity.
  • Virtual User Hours (VUH): run cloud tests without a fixed licence, or top up when a licence is not enough.

Protocols are licensed too. SAP tests, for example, need SAP virtual users in the licence. Without a licence, NeoLoad can run in "no key mode", which lets you design and analyse but not launch tests. Tricentis has offered free editions and trials in the past, but the current licensing page does not describe a free tier. Check the Tricentis site for what is available now.

5. Your first test, end to end

  1. Create a project in the GUI and record a User Path: home page, log in, one search, log out.
  2. Let the post-recording wizard search for dynamic parameters, then Check the User Path (a single-user validation run) and fix what fails. See correlation and variables.
  3. Add data: a file variable for users, so each virtual user logs in as someone different.
  4. Create a population containing the User Path, then a scenario with a ramp-up load policy and a duration.
  5. Run with a small number of users on a local or remote generator. Watch errors first, then response times.
  6. Analyse the result in the Results tab or NeoLoad Web, with an SLA profile attached so pass or fail is explicit.

6. Habits worth having from day one

  • Version-control the project. A NeoLoad project is a folder. Commit it (or its as-code YAML), and keep results out of the repository.
  • Agree the workload first. Virtual user count is an output of the workload model, not an input. Use target throughput and Little's Law to size it.
  • Check every request's content, not just its status. Add validations so a 200 error page fails. NeoLoad calls these assertions or validations, depending on where you look.
  • Watch the generators. NeoLoad monitors its own generators' CPU and memory. A saturated generator makes the system look slow.
  • Monitor the servers. Response times tell you something is slow. Server and APM metrics tell you why. See monitoring during a test.
