NeoLoad User Paths: structure before speed

NeoLoad records a journey in two minutes and the post-recording wizard correlates most of it for you. That speed is the tool's selling point, and also the trap. A recorded User Path with the login in the wrong container, no transactions and no content checks will run beautifully and tell you very little. Here is how to structure one so the results mean something.

1. Init, Actions and End containers

Every User Path has three top-level containers:

ContainerRunsPut here
InitOnce per virtual user, at startLog in, if real users stay logged in across many actions
ActionsRepeatedly, once per iterationThe journey you are measuring
EndOnce per virtual user, at stopLog out, clean up

Where the login goes is a workload decision. If each real session is "log in, check balance, log out", record all of it into Actions, otherwise the authentication service is barely tested. LoadRunner users will recognise the pattern: it maps directly to vuser_init, Action and vuser_end.

Each User Path also has a user session setting (reset cookies and cache between iterations or not). Match it to how real users behave: a new session per iteration for "log in, do one thing, leave" journeys, a kept session when one virtual user is one long-lived user.

2. Recording

  • Start recording from the toolbar, choose the User Path and the container to record into, and NeoLoad opens a browser routed through its recording proxy. Mobile apps and non-browser clients can record through the same proxy if you point them at it.
  • Name steps as you go. The recording bar lets you type a transaction name before each step. Doing it during recording saves an hour of renaming later.
  • Exclude third parties. Analytics, ads, chat widgets and fonts are not your system. Filter them out in recording preferences or delete them after, so the test does not load someone else's servers.
  • Post-recording wizard. When you stop, NeoLoad offers to process the recording: searching for dynamic parameters, configuring push or WebSocket messages and similar steps, depending on what it detected. Let it run, then review what it changed. See correlation and variables.
  • Record twice with different users if a journey is complex. Values that differ between the two recordings are correlation or data candidates.

3. Pages, requests and transactions

NeoLoad groups recorded HTTP requests into pages: the main request plus its embedded resources, timed together like a browser page load. API calls usually appear as single-request pages.

A transaction groups one or more pages into a business step, and it is what you report on. Name transactions so they sort in journey order and read well in a report: 01_Home, 02_Login, 03_Search. One transaction per user-visible step. A single transaction around the whole journey hides a slow login in a long total.

In NeoLoad as-code, the same structure looks like this (a fragment, see as-code for a whole project):

user_paths:
- name: Checkout
  actions:
    steps:
    - transaction:
        name: 01_Home
        steps:
        - request:
            url: /
            server: shop
    - think_time: 5s
    - transaction:
        name: 02_Login
        steps:
        - request:
            url: /login
            server: shop
            method: POST
            headers:
            - Content-Type: application/x-www-form-urlencoded
            body: |
              username=${users.username}&password=${users.password}
    - think_time: 8s

4. Logical actions

Drag logical actions from the actions panel into the User Path to add control flow:

ActionUse
TransactionGroup pages into a timed business step
Delay / Think timePauses. Keep them outside transactions so they don't inflate the timings
Loop, WhileRepeat steps, for example add three items to a basket
If...Then...Else, SwitchBranch on a variable, such as an extracted value
ForkRun steps in parallel within one virtual user, like a browser's concurrent API calls
Try...CatchHandle a failure in part of the path without ending the iteration
JavaScriptCompute values or custom logic. Keep it small, it runs on the generators for every user
RendezvousMake users wait for each other. Rarely realistic, see populations and scenarios
Wait Until, Stop Virtual User, Go to next iterationFlow control on conditions and errors
Shared containersReuse a block such as login across several User Paths

Prefer a weighted mix of User Paths in the population over a random branch inside one giant User Path. It is easier to read, and the mix is visible in the scenario.

5. Think time and pacing in the User Path

Recorded think times reflect how fast you clicked during recording. Replace them with values based on analytics where you can. At the User Path level you can override all think times (for example 5 seconds ± 10%) or scale them by a factor (150%), without editing each one.

Pacing is set on a container, typically Actions, either fixed or as a random range. It sets the time from the start of one iteration to the start of the next, so each virtual user runs at a known rate. That turns a virtual user count into a throughput you can defend with Little's Law: users = iterations per second × pacing.

6. Validations and error behaviour

  • Add content validations to key requests: text that appears only on the success page, or a JSON field that must exist. HTTP 200 with an error page is still a 200.
  • Add duration and size checks where a response that is suspiciously fast or small means something is wrong.
  • Choose what happens on error: the User Path settings let a virtual user go to the next iteration or stop and start a new virtual user when an error or failed assertion occurs. Going to the next iteration avoids the rest of the journey running with a broken session and inflating error counts.

7. Check the User Path

Check User Path runs a single virtual user through the path and shows every request and response, with errors and warnings and suggested fixes in a sanity-check dialog. Fix and re-run until it is clean. Then run it twice more with different data rows. A path that passes once but fails on the second user usually has an uncorrelated value or single-use data.
