Linux performance cheat sheet

Every command worth running on a Linux server during a load test, the column to read and the point where it starts to hurt. Thresholds are rules of thumb for latency-sensitive services. Compare against your own baseline, and print it: the nav and buttons drop out on paper.

First 60 seconds

uptime; dmesg -T | tail; vmstat 1 5; mpstat -P ALL 1 3; pidstat 1 3
iostat -xz 1 3; free -m; sar -n DEV 1 3; sar -n TCP,ETCP 1 3; ss -s

Install sysstat for mpstat, pidstat, iostat and sar. Ignore the first line of vmstat and iostat: it is the average since boot.

CPU

CommandLook atDanger when
uptime1, 5, 15-minute load averageLoad above core count (nproc). Includes disk waits (D state).
vmstat 1r run queuer above core count for more than a few seconds
vmstat 1us sy wa stsy over 20-30%, wa over 10%, st over 5%
vmstat 1cs context switches/sLarge jump vs baseline at the same throughput
mpstat -P ALL 1%usr per core, %softOne core near 100% while others idle (single-thread or IRQ bottleneck)
top then 1, H, PPer core, threads, sort by CPUSame hot thread every refresh
pidstat -u 1%wait per processOver 10%: process is queueing for CPU
pidstat -t -p PID 1Per-thread CPUOne thread pinned at 100%
pidstat -w 1nvcswch/s involuntary switchesHigh and rising: more runnable threads than cores
cat /sys/fs/cgroup/cpu.statnr_throttled ÷ nr_periodsOver about 5% for a latency-sensitive container

Memory

CommandLook atDanger when
free -mavailable (not free)Under 10% of total
vmstat 1si so swap in/outAny sustained non-zero value
sar -B 1majflt/s, pgscank/sMajor faults or kswapd scanning climbing under load
dmesg -T | grep -i oomOOM killer messagesAny, during a test
ps -eo pid,rss,vsz,comm --sort=-rss | headResident memory per processRSS still growing after warm-up (leak or unbounded cache)
cat /sys/fs/cgroup/memory.eventsoom_kill, highCounters increasing

Disk

CommandLook atDanger when
iostat -xz 1r_await w_await (ms)SSD over a few ms, cloud volume over about 10 ms, or rising with load
iostat -xz 1aqu-sz queue lengthGrowing steadily with load
iostat -xz 1%utilNear 100% on spinning disks. On SSD/NVMe/cloud, judge by await and IOPS limits.
iostat -xz 1r/s w/s vs volume limitFlat at a round number while await rises: provisioned IOPS cap
pidstat -d 1kB_rd/s kB_wr/s per processUnexpected writer (logging, swap, temp files)
df -h, df -iSpace and inodesOver 90% used, or inodes exhausted

Network

CommandLook atDanger when
sar -n DEV 1rxkB/s txkB/sNear the NIC or cloud instance bandwidth limit
sar -n EDEV 1, ip -s linkErrors and dropsAny non-zero and rising
sar -n TCP,ETCP 1retrans/s vs oseg/sRetransmits over about 1% of segments sent
ss -sestab, timewait totalsTens of thousands of timewait: no connection reuse
ss -ltnRecv-Q vs Send-Q on listenersRecv-Q reaching Send-Q (accept queue full)
nstat -az | grep -i listenTcpExtListenOverflows, ListenDropsIncreasing during the test
ss -tnp state established '( dport = :5432 )'Connections to a dependencyCount pinned at the pool maximum
sysctl net.ipv4.ip_local_port_rangeEphemeral port range (client side)Outbound connections near the range size: port exhaustion
cat /proc/sys/net/netfilter/nf_conntrack_countvs nf_conntrack_maxOver about 80%. Full table drops new connections ("table full" in dmesg).

Files, processes and limits

CommandLook atDanger when
ls /proc/PID/fd | wc -lOpen files of a processNear Max open files in /proc/PID/limits
cat /proc/sys/fs/file-nrSystem-wide open filesNear the third number (file-max)
ps -eLf | wc -lTotal threadsNear kernel.threads-max or the cgroup pids.max
ps -eo state | sort | uniq -cProcesses in D stateMany in D: stuck on I/O or NFS

Profiling and history

CommandUse it for
perf topLive view of the hottest functions system-wide
perf record -F 99 -a -g -- sleep 30Record stacks on all CPUs for 30 s, then perf report or a flame graph
perf stat -p PID -- sleep 10Instructions per cycle, cache misses, context switches for one process
strace -c -f -p PIDSyscall counts and time. High overhead: short bursts only, never at peak in production.
sar -o /tmp/run.sar 1Record everything every second during a test, read back with sar -f /tmp/run.sar -u
sar -u -s 14:00:00 -e 14:30:00CPU history for a time window (needs the sysstat collector)

Reading it together

PatternProbably
High load, CPUs idle, b and wa upDisk or NFS bound
Latency up, CPU low, nothing saturated on the hostWaiting on a pool, lock or downstream. Take thread dumps or traces.
Average CPU 40%, one core 100%Single-threaded bottleneck or IRQs on one core
Container latency spikes, CPU usage under the limitCFS throttling
Connect timeouts, listen overflows risingAccept queue full: app too slow to accept, or backlog too small
st rising on a VMNoisy neighbour or burst credits exhausted

The full explanations are in reading a Linux server under load, and the order to use them in is the bottleneck playbook. Definitions: saturation, USE method, headroom.
