LoadRunner parameterisation: why vuser 37 keeps getting locked out

Your test runs 300 vusers across six load generators. Around minute ten, a handful of accounts start failing with "account locked", and they are always the same accounts. Two vusers on different generators are logging in as the same customer at the same time, and the second login kills the first session. The data file was fine. The parameter settings were not.

1. Parameter types

Select a value in the script, right-click, Replace with Parameter, then open the Parameter List (Ctrl+L, or from the Design menu) to set its type and properties. In the script it appears as {ParamName}. Braces are the default delimiters and can be changed in the general options.

FileRows from a .dat (CSV-style) fileUsernames, passwords, account numbers, search terms
TableSeveral columns from one row at once, in table-style APIsMainly non-web protocols
Random NumberInteger in a range, with a formatQuantities, page numbers
Unique NumberA block of numbers per vuser that never overlapUnique references without a data file

Group Name, Load Generator Name, Iteration Number, Vuser IDRun-time contextBuilding unique values, debugging, per-generator data

2. File parameters

A file parameter reads from a .dat file in the script folder. The first line is the column header. Several parameters can share one file, each bound to a column:

Username,Password,AccountNo
ana.k@example.test,Pa55-0001,40001001
ben.t@example.test,Pa55-0002,40001002
chloe.w@example.test,Pa55-0003,40001003

Create Username as the file parameter with Select next row = Unique, then create Password and AccountNo on the same file with Select next row = Same line as Username. Now one row always stays together. If each parameter picks its own row, you will log in with Ana's username and Ben's password.

3. Select next row and update value on

Two settings decide which value a vuser gets and when it changes.

Select next rowBehaviour
SequentialEvery vuser starts at the top of the file and walks down it. Vuser 1 and vuser 2 both get row 1 first
RandomA random row each time the value updates. Different vusers can get the same row
UniqueEach vuser gets its own rows. No two vusers share a row at the same time
Same line as <param>Follows another parameter on the same file
Update value onBehaviour
Each iterationNew value at the start of each iteration, the same value for every use within it
Each occurrenceNew value every time the parameter appears in the script
OnceOne value for the vuser's whole life

With Unique, a third setting appears: When out of values, with Abort Vuser, Continue in a cyclic manner or Continue with last value.

Sequential is not unique. With Sequential, every vuser walks the same file from the top, so 300 vusers all log in as row 1 in their first iteration. That is the locked-account scenario in the opening. Use Unique for anything a real user would own.

5. Unique data across vusers: block size

With Unique, the Controller splits the file into blocks and hands one block to each vuser. The setting is Allocate Vuser values in the Controller, enabled only when Unique is selected:

  • Automatically allocate block size: the Controller works out a block per vuser from the number of iterations. Good when the iteration count is fixed.
  • Allocate X values for each Vuser: you set the block size. Use this for duration-based scenarios, where the Controller cannot know how many iterations each vuser will run.

Worked example: a 60-minute test, 200 vusers, pacing of 90 seconds per iteration. Each vuser runs at most 3600 / 90 = 40 iterations, so allocate 40 values per vuser, plus a margin, call it 45. You need 200 × 45 = 9,000 unique rows. If the file has 5,000 rows, either the late vusers abort or, with cyclic, they reuse rows that earlier vusers already consumed. The VuGen help also notes that when values run out, a warning goes to the vuser log if extended logging with parameter substitution is on.

The Simulate Parameter button in the parameter properties shows which rows each vuser would get for a given vuser count and iteration count. Use it before a big run.

Unique allocation works across generators because the Controller hands out the blocks. If you run scripts outside the Controller (standalone, or split across separate Controllers), uniqueness is no longer guaranteed. Give each run its own slice of data.

6. Parameters in code

// read a parameter's current value as a C string
char *user = lr_eval_string("{Username}");

// save a string into a parameter (creates it if needed)
lr_save_string("GOLD", "Tier");

// save an integer
lr_save_int(atoi(lr_eval_string("{Qty}")) * 2, "DoubleQty");

// build a unique reference: generator name + vuser id + iteration
lr_param_sprintf("OrderRef", "PT-%s-%s-%s",
    lr_eval_string("{LGName}"),
    lr_eval_string("{VuserId}"),
    lr_eval_string("{Iteration}"));

// force the next value of a file parameter mid-iteration
lr_advance_param("SearchTerm");

Here LGName, VuserId and Iteration are parameters you create with the Load Generator Name, Vuser ID and Iteration Number types. The cheat sheet lists the rest of the lr_* parameter functions.

7. Data rules for real tests

  • Size data for the test, not the smoke run. Work it out from duration, pacing and vuser count before the run, as in the example above.
  • Match production skew. Real traffic hits a few products and accounts far more than others. Uniform random data across 50,000 products defeats every cache and tests a worse case than production. Build data files from real access patterns where you can.
  • Give each load generator its own data when uniqueness matters outside the Controller.
  • Keep secrets out of the script folder. Passwords in .dat files end up in source control. Use test accounts with test-only passwords, or inject them at run time.
  • Plan the environment reset. Single-use data is consumed. Agree how the test database is restored between runs before the first run, not after.
