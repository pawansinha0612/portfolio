VuGen scripting: a recording is not a script

You record the login journey, press Replay and it goes green. You run it with 200 vusers and every one of them passes, at 40 milliseconds per transaction. Then someone opens the response bodies and finds 200 copies of "Your session has expired". A recording captures one user's traffic at one moment. Turning it into a script means choosing the right protocol, giving it structure and making it check what came back.

1. Choosing a protocol

The protocol decides what VuGen records and what a vuser sends. Pick the lowest level that still exercises the server the way users do. Lower level means more vusers per generator and more control, but more correlation work.

ProtocolRecordsUse it forCost per vuser
Web - HTTP/HTMLHTTP requests as web_url, web_submit_data, web_custom_requestMost websites and HTTP APIs. The default choiceLow
TruClient - WebUser actions in a real browser (Chromium-based)Heavy single-page apps where scripting the HTTP layer is impractical, or when you need browser timingsHigh: a browser per vuser
Citrix ICAMouse, keyboard and screen events in a Citrix sessionThick-client apps published through Citrix, common in banks and insurersHigh
SAP GUISAP GUI scripting eventsSAP ERP transactions through the desktop clientMedium to high
SAP - WebHTTP traffic with SAP-specific correlation rulesSAP Fiori / web front endsLow
Web ServicesSOAP and REST calls, often generated from a WSDL or by importSOAP services and contract-first APIsLow
DevWebHTTP in JavaScript, also runs outside VuGenTeams that want scripts developers can read, and CI. See DevWebLow

There are many more (Oracle NCA, RTE terminal, Java, .NET, Kafka, MQTT, gRPC, and an LLM protocol in recent releases). The protocol list in File → New Script and Solution shows what your install supports, and your licence bundle decides what you can run at scale.

My default: start with Web - HTTP/HTML for anything browser-based. Reach for TruClient only when the HTTP layer is genuinely unscriptable, such as heavy client-side crypto or a protocol buried in a framework, or when the requirement is browser-side timing. A TruClient test that needs 1,000 vusers needs a lot of generator hardware.

2. Recording cleanly

  • Recording mode. In Recording Options → Recording, an HTML-based script groups page resources under one web_url step and is easier to read. A URL-based script records every request as its own step, which suits non-browser clients. HTML-based with "a script containing explicit URLs only" is a sensible default for web apps.
  • Filter third parties. Analytics, ad, chat and font hosts are not your system. Exclude them in the recording options (or delete them after) so you do not load-test someone else's CDN.
  • Record each business step on purpose. Pause, type a meaningful step name in the floating toolbar or use the transaction buttons while recording. You will thank yourself when reading the script.
  • Record twice. Record the same journey twice with different users and compare the scripts (Tools → Compare with Script in many versions). Every value that differs is a correlation or parameterisation candidate.
  • Check recording options before you blame correlation. Proxy settings, SSL interception and the browser used for recording cause most "nothing was recorded" problems.

3. Script structure: vuser_init, Action, vuser_end

A C-based VuGen script has three sections by default. The runtime settings decide how often each runs.

SectionRunsPut here
vuser_initOnce per vuser, at startLog in, if real users stay logged in across many actions
Action (and any extra actions)Every iterationThe business journey you are measuring
vuser_endOnce per vuser, at stopLog out, clean up

Where the login goes is a workload decision, not a style choice. If real users log in once and do 20 searches, log in during vuser_init. If each real session is "log in, check balance, log out", put all of it in Action, otherwise you never test the authentication service at its real rate. Split long journeys into several actions (right-click in the Solution Explorer → Create New Action) and set their order and weights in Run Logic.

Action()
{
    lr_start_transaction("01_Home");

    web_reg_find("Text=Sign in", "Fail=NotFound", LAST);
    web_url("home",
        "URL=https://{BaseUrl}/",
        "Resource=0",
        "Mode=HTML",
        LAST);

    lr_end_transaction("01_Home", LR_AUTO);

    lr_think_time(5);

    lr_start_transaction("02_Login");

    web_reg_find("Text=Welcome back", "Fail=NotFound", LAST);
    web_submit_data("login",
        "Action=https://{BaseUrl}/login",
        "Method=POST",
        "Mode=HTML",
        ITEMDATA,
        "Name=username", "Value={Username}", ENDITEM,
        "Name=password", "Value={Password}", ENDITEM,
        LAST);

    lr_end_transaction("02_Login", LR_AUTO);

    lr_think_time(8);

    return 0;
}

{BaseUrl}, {Username} and {Password} are parameters, see parameterisation. Every argument list ends with LAST. That is a VuGen convention, and forgetting it is a classic compile error.

4. Transactions

A transaction is the timer you will report on. Name them so they sort in journey order and survive being read by a manager: 01_Home, 02_Login, 03_Search.

  • lr_start_transaction("name") starts the timer. lr_end_transaction("name", LR_AUTO) stops it. The name must match exactly.
  • Status. LR_AUTO lets LoadRunner set pass or fail from the step results (a failed web_reg_find fails the transaction). LR_PASS, LR_FAIL and LR_STOP set it yourself.
  • Keep think time outside transactions. If lr_think_time sits inside a transaction, the reported time includes it. Analysis can exclude think time, but it is cleaner not to include it in the first place.
  • One transaction per user-visible step. Do not wrap the whole journey in one transaction. A slow login hides inside a 30-second "journey" total.
  • Sub-transactions (lr_start_sub_transaction) break a step into parts, for example the API calls behind one page. Use them sparingly, every transaction adds rows to the results.

5. Text checks: catching soft failures

HTTP 200 does not mean success. Error pages, maintenance pages, "session expired" and empty search results all come back as 200. web_reg_find registers a check on the next request, so place it before the step:

// fail the step if the text is missing
web_reg_find("Text=Account summary", "Fail=NotFound", LAST);

// fail the step if an error message appears
web_reg_find("Text=Something went wrong", "Fail=Found", LAST);

// count matches instead of failing, then decide yourself
web_reg_find("Text=result-item", "SaveCount=ResultCount", LAST);
web_url("search", "URL=https://{BaseUrl}/search?q={Term}", "Mode=HTML", LAST);
if (atoi(lr_eval_string("{ResultCount}")) == 0) {
    lr_error_message("No results for %s", lr_eval_string("{Term}"));
}

Pick check text that appears only on the success page: the account holder's name, a specific heading, a JSON field name. A word like "Welcome" that is also in the footer of the error page proves nothing.

6. REST and JSON APIs

For HTTP APIs inside a Web - HTTP/HTML script, web_custom_request sends any method with any body:

web_add_header("Authorization", "Bearer {AccessToken}");

web_reg_save_param_json("ParamName=OrderId", "QueryString=$.orderId",
    SEARCH_FILTERS, "Scope=Body", LAST);

lr_start_transaction("05_CreateOrder");
web_custom_request("create_order",
    "URL=https://{ApiHost}/v1/orders",
    "Method=POST",
    "EncType=application/json",
    "Body={\"sku\":\"{Sku}\",\"qty\":{Qty}}",
    LAST);
lr_end_transaction("05_CreateOrder", LR_AUTO);

web_add_header applies to the next request only. Use web_add_auto_header for a header that every following request needs, and web_remove_auto_header to stop it. Newer releases also offer REST-specific steps and import from OpenAPI or Postman in some protocols. Check what your version offers before hand-writing dozens of calls.

7. Debugging a replay

  • Turn on extended logging while debugging (Runtime Settings → Log → Extended log, with parameter substitution and data returned by server). Turn it off again before a load test, see log settings.
  • Read the Replay Log and Snapshot views together. The first failing step is rarely the step that broke. Usually a value captured three steps earlier was wrong.
  • Use lr_output_message and lr_eval_string to print parameter values: lr_output_message("token=%s", lr_eval_string("{Token}"));
  • Replay twice in a row. If the second replay fails, you have an uncorrelated value or single-use data.
