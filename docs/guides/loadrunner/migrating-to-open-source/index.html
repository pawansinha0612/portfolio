Leaving LoadRunner: what moves, what stays, what breaks

The licence renewal lands on the CIO's desk and someone asks, "Can't we just use JMeter?" Six months later the web scripts are in k6, the team is happy, and the quarter-end Citrix test of the claims system has nowhere to run. Moving off LoadRunner can be a good decision. It goes wrong when it is treated as a tool swap instead of an inventory of what you actually test.

1. When moving makes sense

Moving tends to pay off when:

  • Most of what you test is HTTP: websites, REST and GraphQL APIs, microservices.
  • Developers or SREs want to own performance tests in the same repos and pipelines as their code.
  • You want to run tests from containers or Kubernetes, scale generators on demand, and avoid Windows-only infrastructure.
  • Your team's skills are moving to JavaScript, Groovy or Python and away from C.

Staying, or keeping LoadRunner for part of the estate, makes sense when:

  • Critical journeys run through Citrix, SAP GUI, Oracle Forms, terminal emulation (RTE) or other thick-client protocols.
  • You depend on Enterprise Performance Engineering for shared scheduling, trending and audit across many teams, and would have to rebuild that.
  • You have hundreds of stable, maintained scripts and the licence is already paid for the next term. Migration is effort. Spend it where it buys something.

The JMeter vs LoadRunner comparison and the tool picker go through the trade-offs in more detail.

2. Start with an inventory

Before anyone rewrites a script, list every script and scenario you actually run, with:

  • Protocol (Web HTTP/HTML, TruClient, Citrix, SAP GUI, Web Services, DevWeb...)
  • How often it runs and who relies on the results (release gate, quarterly peak test, regulatory evidence)
  • Complexity: number of steps, correlations, custom C code, external DLLs
  • Data and environment dependencies

Typically a minority of scripts carry most of the value, and some scripts have not run in years. Retire those instead of migrating them.

There is no reliable automatic converter from VuGen C scripts to JMeter or k6. The practical route is to re-record each journey (JMeter's HTTP(S) Test Script Recorder, or a browser HAR file converted to k6), then rebuild correlation and data using the LoadRunner script as the specification. The old script tells you exactly which values were correlated and where they came from, which is the hard part. If your team already moved some tests to JMeter, the JMeter to k6 converter gives you a first draft of a k6 script.

Custom C code is the hidden cost. Scripts with hand-written encryption, hashing, signature or date logic in C need that logic rewritten in Groovy or JavaScript and tested. Count those scripts separately in the inventory.

4. What doesn't translate

  • Citrix ICA. Neither JMeter nor k6 drives a Citrix session. Options are to keep LoadRunner (or NeoLoad) for Citrix, or test the services behind the Citrix-published app at the HTTP or database layer instead, which is a different test.
  • SAP GUI. Same story. SAP Fiori and other web front ends are HTTP and migrate fine. The desktop SAP GUI protocol does not.
  • Oracle Forms (NCA), RTE terminal, proprietary binary protocols. Usually no practical open-source equivalent.
  • TruClient browser tests. Partly: k6 has a browser module and Playwright can measure browser timings, but browser-level load is expensive in any tool. Often a handful of browser vusers on top of protocol-level load answers the real question.
  • Analysis-style reporting. JMeter's HTML dashboard and Grafana dashboards for k6 are good, but cross-run comparisons, SLA reports and templates need building. Budget for it.
  • Central governance. If Enterprise Performance Engineering is your system of record for test evidence, you need a replacement: results in a time-series store, reports archived per release.

5. JMeter or k6?

For LoadRunner teams, JMeter feels familiar: a GUI, recorders, many protocol plugins, and a large community. k6 suits teams that live in code review and want tests next to the application, with thresholds that fail a pipeline out of the box. I'd pick JMeter when testers own the tests and need breadth of protocols, and k6 when developers own them and most traffic is HTTP or gRPC. See k6 vs JMeter for the full comparison, and the JMeter guides or k6 guides to get started.

6. A phased plan

  1. Pilot one journey. Pick a valuable, HTTP-only journey with real correlation. Rebuild it, run it alongside the LoadRunner version in the same window, and compare.
  2. Build the platform once. Generators (containers or VMs), results storage, dashboards, CI integration and a report template. This is most of the effort and it is shared by every script after.
  3. Migrate by value. Release-gate journeys first, then peak-test journeys. Retire what nobody uses.
  4. Use the bridge if it helps. Professional Performance Engineering can run JMeter and Gatling tests alongside VuGen scripts (the licence page lists both). During the transition, that lets one scenario mix old and new scripts.
  5. Keep LoadRunner for what can't move, and right-size the licence to those protocols and vuser counts at the next renewal.
  6. Train the team. Correlation, workload modelling and analysis skills transfer. Tool habits don't.

7. Re-baseline, don't compare

The same journey measured by two tools will not report identical numbers. Tools differ in what a transaction includes (embedded resources, redirects, think time), in connection reuse and in how they time requests. Run both side by side in the same environment, understand the differences, then set a new baseline in the new tool. Don't fail a release because k6 reports 8% higher than last quarter's LoadRunner run.
