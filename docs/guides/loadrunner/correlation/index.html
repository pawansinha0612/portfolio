LoadRunner correlation: stop replaying yesterday's session

Your script replays fine at 4 pm. At 9 am the next day every vuser fails at step three with "invalid request". Nothing in the application changed. The script is sending a session token, a CSRF value and a basket ID that were valid yesterday. Correlation means capturing those server-generated values at run time and sending back the fresh ones.

1. Find what needs correlating

A value needs correlating when the server generates it and the client sends it back later. Typical suspects:

  • Session IDs in URLs or form fields (cookies are handled automatically by the Web protocol, as long as you don't clear them mid-journey)
  • CSRF and anti-forgery tokens, __VIEWSTATE and __EVENTVALIDATION in ASP.NET Web Forms
  • OAuth access tokens, refresh tokens and authorisation codes
  • IDs created during the journey: order, basket, quote, policy, payment intent
  • Timestamps and nonces the server echoes and validates

The quickest way to find them: record the same journey twice, compare the two scripts, and look at every long or random-looking value that differs. Then search each value in the earlier server responses (the Snapshot view or the recording log) to find where it first appears. That response is where the capture goes.

2. web_reg_save_param_ex

The workhorse. Like all web_reg_* functions, it registers a capture for the next request, so it goes immediately before the step whose response contains the value:

web_reg_save_param_ex(
    "ParamName=CsrfToken",
    "LB=name=\"csrf_token\" value=\"",
    "RB=\"",
    "Ordinal=1",
    SEARCH_FILTERS,
        "Scope=Body",
    LAST);

web_url("login_page",
    "URL=https://{BaseUrl}/login",
    "Mode=HTML",
    LAST);

// later: send it back
web_submit_data("login",
    "Action=https://{BaseUrl}/login",
    "Method=POST",
    "Mode=HTML",
    ITEMDATA,
    "Name=csrf_token", "Value={CsrfToken}", ENDITEM,
    "Name=username",   "Value={Username}",  ENDITEM,
    "Name=password",   "Value={Password}",  ENDITEM,
    LAST);

The OpenText function reference describes web_reg_save_param_ex as the replacement for the older, deprecated web_reg_save_param. You will still see the old one in legacy scripts. It works, but write new captures with the _ex form.

ArgumentMeaning
ParamNameParameter to save into. Use it later as {CsrfToken}
LB / RBLeft and right boundaries. Text immediately before and after the value. Add /IC to ignore case: LB/IC=...
OrdinalWhich match: 1 (default), 2, ALL or RANDOM
NotFoundERROR (default, fails the step) or WARNING
SaveLen / SaveOffsetSave only part of the match: length and starting offset
SEARCH_FILTERSMarker, followed by filters such as Scope=Body, Scope=Headers or Scope=All, and HeaderNames=... with Scope=Headers

3. Choosing boundaries

Most broken correlations are bad boundaries. Rules that keep them stable:

  • Make the left boundary unique. LB=value=" matches every input on the page. LB=name="csrf_token" value=" matches one. Check uniqueness by searching the response in the Snapshot view.
  • Keep the right boundary short. Usually just the closing quote, ampersand or angle bracket. Long right boundaries break when the markup changes.
  • Escape quotes in C strings with \". Backslashes in the response need \\.
  • Watch for encoding. The same token can appear URL-encoded in one place (%2B) and raw in another (+). Capture from the place whose encoding matches how you send it back, or convert with web_convert_param.
  • Narrow the scope. Scope=Body or Scope=Headers avoids accidental matches and saves generator CPU on large responses.

Large values get truncated silently in older scripts. Values such as __VIEWSTATE can be tens of kilobytes. If a captured value is cut short, raise the limit with web_set_max_html_param_len("100000"); at the start of the script and check whether your version still needs it.

4. Ordinal, arrays and NotFound

Ordinal=ALL saves every match into an array: {ProductId_1}, {ProductId_2}... and the count in {ProductId_count}. Pick one at random to spread load across the catalogue:

web_reg_save_param_ex(
    "ParamName=ProductId",
    "LB=data-product-id=\"",
    "RB=\"",
    "Ordinal=ALL",
    "NotFound=WARNING",
    SEARCH_FILTERS, "Scope=Body",
    LAST);

web_url("category", "URL=https://{BaseUrl}/c/shoes", "Mode=HTML", LAST);

if (atoi(lr_eval_string("{ProductId_count}")) > 0) {
    lr_save_string(lr_paramarr_random("ProductId"), "PickedProduct");
    web_url("product",
        "URL=https://{BaseUrl}/p/{PickedProduct}",
        "Mode=HTML",
        LAST);
} else {
    lr_error_message("No products on category page");
}

NotFound=WARNING is correct here because an empty category is a valid outcome you handle in code. For a session token, leave the default ERROR: if the token is missing, the vuser should fail at that step, not five steps later with a confusing error.

5. JSON, regex and other variants

FunctionCaptures byUse for
web_reg_save_param_exLeft and right boundariesHTML, headers, anything textual. The default
web_reg_save_param_jsonJSONPath queryJSON APIs. More robust than boundaries when field order changes
web_reg_save_param_regexpRegular expression with a capture groupValues without stable boundaries
web_reg_save_param_xpathXPathXML and SOAP responses
web_reg_save_param_attribHTML tag and attributeForm fields and links by attribute
 
web_reg_save_param_json(
    "ParamName=AccessToken",
    "QueryString=$.access_token",
    SEARCH_FILTERS, "Scope=Body",
    LAST);

web_reg_save_param_regexp(
    "ParamName=QuoteRef",
    "RegExp=quoteRef\":\"(Q-[0-9]+)\"",
    SEARCH_FILTERS, "Scope=Body",
    LAST);

Check the argument names against your version's function reference (F1 on the function name in VuGen). The capture functions have gained arguments over the years, and older releases may not support every one.

6. Correlation rules and Design Studio

VuGen can find many dynamic values for you:

  • Correlation rules (Recording Options → Correlations → Rules) are patterns applied while the script is generated. VuGen ships rules for common frameworks (ASP.NET, Java application servers, SAP and others). Add your own when an application repeats the same token pattern on every page, then export them for the team.
  • Design Studio scans a recording for dynamic values and proposes correlations. In current versions it scans by rules and by comparing recorded data. Older versions also scan by replay. Review every proposal before accepting it. It is good at finding candidates and less good at choosing stable boundaries.
  • Configuration options (Recording Options → Correlations → Configuration) control whether rules are applied automatically during a scan and how deep the scan goes.

Auto-correlation is a starting point. It sometimes correlates values that should be parameters (your username) or misses values that only appear in the second response of a redirect chain. Read the generated web_reg_save_param_* calls as if a junior wrote them: check boundaries, ordinals and scope, and rename parameters to say what they hold.

7. When a correlation fails

  1. Turn on Extended log with Parameter substitution and Data returned by server and replay once.
  2. Find the first failing step in the Replay Log, then scroll up to the capture that should have fed it. Was it registered before the right request? Was the value found?
  3. Open the response in the Snapshot view and search for the left boundary. Different markup (A/B tests, a different locale, a logged-in variant) is common.
  4. Check redirects. A value often sits in the response to the second or third request of a redirect chain.
  5. If the value is generated in the browser by JavaScript (a client-side nonce or hash), there is nothing to capture. Reproduce the logic in C, use a DevWeb or TruClient script, or ask the developers for a test-only bypass.
