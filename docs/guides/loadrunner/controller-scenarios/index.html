LoadRunner Controller: the scenario is the test

Every script passes in VuGen. You put them in a scenario, start 400 vusers at once and walk away. Ten minutes later half of them have failed during login, the load generators are at 100% CPU and the web servers are mostly idle. The scripts were fine. The scenario launched everyone in the same second on two overloaded generators. Here is how to build scenarios that test the system, not the setup.

1. Manual vs goal-oriented

When you create a scenario (File → New in Controller) you choose the type.

Manual scenarioGoal-oriented scenario
You defineVusers, groups, ramp, durationA goal: a number of vusers, hits per second, transactions per second, pages per minute or a transaction response time
Controller doesExactly what you scheduledAdds vusers, within a min and max you set, until the goal is reached
Good forRepeatable load, peak and soak tests, comparing buildsRough capacity questions: "how many vusers until 50 TPS?"
Watch outYou must do the workload maths yourselfThe load path differs between runs, so results are harder to compare. A response-time goal can be met by the system getting slower with fewer users

Use manual scenarios for almost everything. Work out vusers and pacing from the target throughput (see pacing maths) and you get the control a goal-oriented scenario promises, with runs you can compare.

2. Groups and percentage mode

In a manual scenario, scripts run either as Vuser groups (each script in a group with its own vuser count and generators) or in percentage mode (a total vuser count split across scripts by percentage, switched with Scenario → Convert Scenario to the Percentage Mode in many versions).

Groups give you more control: separate ramps per journey, different generators per group, and a group you can stop on its own. I use groups for any test with more than one business journey.

3. Schedules and ramps

The Scenario Schedule pane sets the schedule by (scenario, where all groups share one schedule, or group, where each has its own) and the run mode (real-world schedule with multiple actions, or basic schedule). A real-world schedule is a sequence of actions:

Initialize          Initialize each Vuser just before it runs
Start Vusers        400 Vusers: 20 every 00:00:30 (HH:MM:SS)
Duration            Run for 01:00:00
Stop Vusers         Stop all Vusers: 50 every 00:00:15
  • Initialise just before running. Initialising all vusers at the start runs every vuser_init at once, which is a login storm before the test begins.
  • Ramp gradually. Here 400 vusers arrive over 10 minutes. A ramp-up lets connection pools, caches and autoscaling warm up, and shows you the load level where response times start to bend.
  • Measure the steady state. Report on the period after the ramp, when all vusers are running. In Analysis, filter to that window. See steady state.
  • Step tests are just more actions. Start 100, run 15 minutes, start 100 more, run 15 minutes, and so on. That finds the knee in the throughput curve more cheaply than separate runs.

4. Load generators

Add generators in Scenario → Load Generators, check they connect, then assign them to groups. Rules that keep the generators out of your results:

  • Keep generator CPU under about 70% and memory well clear of the limit. Add Windows or Linux resource monitors for the generators themselves, not just the servers. A saturated generator adds time to every transaction it measures.
  • Size by protocol. One generator can hold many hundreds of Web HTTP/HTML vusers, but only tens of TruClient or Citrix vusers. Calibrate: run 50 vusers on one generator, watch its CPU and memory, and scale from there.
  • Spread groups across generators. If one generator fails, you lose part of every journey rather than all of one.
  • Put generators where users are. Generators in the same data centre as the servers skip the WAN, firewalls and CDN your users go through. That can be the right choice for a backend capacity test and the wrong one for an end-to-end one. Decide on purpose.
  • Firewalls. Generators behind a firewall can connect through the MI Listener (Monitor-over-Firewall) component. Agree ports with the network team early, it is often the slowest part of setting up a bank test.

5. Rendezvous points, and why to avoid them

lr_rendezvous("name") makes vusers wait at that point until a number of them arrive, then releases them together. The Controller's Scenario → Rendezvous dialog sets the policy: release when a percentage of all vusers or of running vusers arrive, with a timeout.

It sounds like the way to test "200 users click Pay at once". In practice it rarely tests anything real:

  • Real users don't synchronise. Even in a flash sale, arrivals spread over seconds. A perfect same-millisecond burst tests a load that never happens.
  • It distorts the rest of the test. Vusers wait at the rendezvous instead of running their pacing, so throughput before and after is wrong.
  • One slow vuser holds everyone. With timeouts, releases become irregular and results are hard to repeat.

For a burst, model the arrival rate instead: a short, steep ramp, or a separate group that starts many vusers with short pacing for a few minutes. Keep rendezvous for genuine concurrency bugs, such as two requests racing on the same record to test locking. See spike testing for the burst case.

6. Monitors and live graphs

The Run tab shows running vusers, transaction response times, hits per second, throughput and errors as the test runs. Add server monitors (Windows resources, UNIX/Linux resources, and others depending on version) so the results file holds server metrics on the same timeline as response times.

Most teams now monitor through an APM or observability stack instead, such as Dynatrace, AppDynamics, New Relic or Grafana. That is fine, but line up the clocks: note the scenario start time and use it to filter the APM data. Recent releases added integrations that push Controller data to some of these tools. See monitoring during a test and finding bottlenecks.

7. Pre-run checklist

  • Runtime settings in the scenario: logging set to errors only, think time on, pacing set, "simulate a new user" as intended.
  • Data files sized for the run, and unique parameters set to allocate enough values per vuser. See block size.
  • Every generator connected and calibrated, with its own resource monitor.
  • Results directory set with a meaningful name (Results → Results Settings), so run 7 is not overwritten by run 8.
  • Smoke run with a few vusers through the whole scenario before the real run.
  • Monitoring and APM dashboards open, the environment owners told, and a stop plan agreed if errors spike.
