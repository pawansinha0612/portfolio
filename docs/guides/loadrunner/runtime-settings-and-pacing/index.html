LoadRunner pacing: 100 vusers is not a workload

The requirement says "the system must handle 1,800 logins an hour". You run 100 vusers with think time ignored and pacing "as soon as the previous iteration ends". The server sees 9,000 logins an hour, falls over, and the project spends a week chasing a problem production will never have. Runtime settings are where vusers become a workload with a known rate.

1. Where runtime settings live

Runtime settings are stored with the script (default.cfg and related files). Open them in VuGen with F4 or Replay → Runtime Settings. In Controller, each script in a scenario has its own copy: select the script in the Design tab and open Runtime Settings. Changes made in Controller apply to that scenario only and do not flow back to VuGen.

Two copies, two truths. A common trap is fixing pacing in VuGen, re-running the scenario, and wondering why nothing changed. Controller kept its own copy. Check the settings in the scenario before every significant run, and record them in the test report. Release 26.3 redesigned the runtime settings UI, so labels below may sit in different places in your version.

2. Run logic and iterations

Run Logic sets how many times the Action section repeats and in what order the actions run. You can group actions into blocks and run them sequentially or randomly with percentages, which is the simplest way to build a mix such as 70% browse, 20% search, 10% buy inside one script.

The iteration count applies when you run in VuGen and when a Controller schedule is set to run until completion. In a duration-based Controller schedule, vusers keep iterating until the duration ends, regardless of the count. Run one iteration in VuGen when debugging, and let the Controller schedule decide in a load test.

3. Pacing options

Pacing controls the time from the start of one iteration to the start of the next. It is what gives a vuser a fixed rate. The options, in the wording most versions use:

OptionWhat happensUse it for
As soon as the previous iteration endsNo gap. Rate is set by response time, so it rises as the system gets faster and falls as it slowsDebugging and data loading only
After the previous iteration ends, with a fixed or random delayA gap after each iteration. Rate still depends on response timeRarely the right choice for load tests
At fixed intervals, every N secondsIterations start N seconds apart, if the previous one has finishedPrecise, repeatable rates
At random intervals, every N to M secondsStart-to-start gap randomised in a rangeThe usual choice: fixed average rate, no lock-step

Prefer the interval options. They keep the rate constant even when response times change, which is what a production arrival rate does. Random intervals stop vusers drifting into lock-step and hitting the server in waves.

If an iteration takes longer than the pacing interval, the next one starts immediately and that vuser falls below its target rate. Check in Analysis that achieved throughput matched the target. If it didn't, the test ran a lighter load than you think.

4. Pacing maths with Little's Law

Little's Law for a closed workload: vusers = throughput × time per iteration, where time per iteration is the pacing interval (as long as each iteration finishes inside it).

For the opening example: target 1,800 logins per hour = 0.5 per second. If each iteration is one login journey and you choose pacing of 120 seconds, you need 0.5 × 120 = 60 vusers. Check the journey fits: if response times plus think time come to 70 seconds, there is 50 seconds of headroom for slowdown before the rate drops.

Choose pacing first from realistic session length, then derive vusers. Not the other way round. The workload model tool and capacity calculator do this arithmetic for several journeys at once.

Closed model limits. Vusers with pacing are a closed model: when the system slows, each vuser waits longer and arrivals drop. Production traffic from the internet is closer to an open model. See open vs closed workload models and coordinated omission for why that matters when the system is struggling.

5. Think time

lr_think_time(n) pauses the vuser. The Think Time runtime setting decides what happens to those calls on replay:

  • Ignore think time: skip them. Fine for debugging, wrong for load tests.
  • Replay think time as recorded: use the values in the script.
  • Multiply recorded think time by a factor.
  • Use random percentage of recorded think time, for example 50% to 150%: realistic variation. A sensible default.
  • Limit think time to N seconds: caps long pauses from a slow recording.

Recorded think times reflect how fast you clicked during the recording. Replace them with values based on real user behaviour from analytics where you can. Think time and pacing work together: think time shapes the gaps inside a journey, pacing sets the rate of journeys.

6. Log settings

SettingWhen
Extended log, with parameter substitution and data returned by serverDebugging in VuGen only. Very heavy
Standard logShort runs in VuGen
Send messages only when an error occurs (log cache)Load tests. Logs the context around an error without logging everything
Disable loggingVery large tests where even error logging costs too much. You lose diagnostics

Extended logging on 500 vusers writes every response body to disk on the generators. It slows the vusers, fills disks, and inflates response times so the test measures the generator rather than the system. Before every load test, confirm logging is set to errors only in the scenario's runtime settings.

7. Other settings worth checking

  • Miscellaneous → Error Handling: "Continue on error" keeps a vuser going after a failed step. Off is usually better, so a broken iteration ends and the next one starts clean. Turn it on only with explicit checks in code.
  • Miscellaneous → Multithreading: run vusers as threads (lighter) or processes (more isolation). Threads are the default for most protocols.
  • Browser emulation → Simulate a new user on each iteration: clears cookies and cache between iterations. On for most journeys that log in and out per iteration. Off when one vuser is one long-lived session.
  • Internet Protocol → Preferences: download non-HTML resources (images, CSS, JS) or not. Turn it off if the CDN serves them in production and you are testing the origin.
  • Network → Speed Simulation: bandwidth emulation for mobile or branch-office users, when that is part of the requirement.
