LoadRunner Analysis: the summary page is not the answer

The summary says average login time was 1.2 seconds against a 3-second target. Green, ship it. But the average includes the ramp-up when the system was idle, and the 95th percentile during the busy hour was 7 seconds. The number you report depends on which window, which statistic and which graph you look at. Analysis gives you all of them. Choosing the right ones is the job.

1. Opening results

At the end of a run the Controller collates results from the generators into the results folder (a .lrr file plus data). Analysis opens it and builds an Analysis session (.lra). Save the session: it keeps your filters, graphs and notes. If collation fails, for example a generator went offline, use Results → Collate Results in Controller before opening.

For very long runs, Analysis can load summary data only, which is faster but limits filtering. Check the data import options in Tools → Options before opening a 12-hour soak test.

2. The graphs that matter

GraphAnswers
Running VusersDid the load profile run as designed? Did vusers drop out?
Transaction SummaryPassed, failed and stopped counts per transaction. Check failures first
Transaction Response Time (Percentile)The distribution per transaction. The one to report from
Average Transaction Response TimeTrend over time. Good for spotting when things changed, poor as a headline number
Transactions per SecondDid you reach the target throughput? Flat TPS with rising vusers means a bottleneck
Hits per Second and ThroughputHTTP requests and bytes per second from the server side
Errors per Second and Error StatisticsWhen errors started and which messages dominate
System resource graphs (if monitored)CPU, memory, disk on servers and generators, on the same timeline

Start every analysis with three questions, in order: did the load run as designed (Running Vusers, TPS against target), did it work (errors, failed transactions), and only then how fast was it (percentiles). Response times from a run that missed its throughput target or failed 10% of transactions describe a different test from the one you planned.

3. Filter to the steady state

Right-click a graph and choose Set Filter/Group By, or set a global filter for the session. Filter on Scenario Elapsed Time to exclude the ramp-up and ramp-down. For a 10-minute ramp, 60-minute hold and 5-minute ramp-down, report on minutes 10 to 70.

Also filter out failed transactions when reporting response times. A transaction that failed fast at 50 ms drags the percentiles down and makes a broken system look quick. Report error rate separately.

4. Percentiles, not averages

Averages hide the users having a bad time. A transaction with 95% of responses at 1 second and 5% at 20 seconds has an average of 1.95 seconds, which looks fine and describes nobody. Report the 90th or 95th percentile, and say which.

  • The summary report shows a percentile column. Its value is set in Analysis options (Tools → Options, the transaction percentile setting). Many teams leave the default without knowing what it is. Check it, and set it to the percentile in your SLA.
  • The Transaction Response Time (Percentile) graph shows the full curve. A curve with a sharp rise at the top end usually means a queue or timeout somewhere, see tail latency.
  • Check whether think time is included in transaction times. Analysis has an option for it. Keep think time out of transactions in the script and the question goes away.

The interactive percentiles explainer shows why averages mislead with real distributions.

5. Merging and correlating graphs

The useful insight is usually in the relationship between two graphs. Right-click a graph and choose Merge Graphs:

Merge typeShowsUse it for
OverlayBoth graphs on one chart sharing the x-axis, with two y-axesRunning vusers against response time over time
TileOne above the other, same x-axisComparing shapes with very different scales
CorrelateOne graph's y-axis against the other's y-axisResponse time as a function of vusers or TPS: where the knee is

The standard pair: overlay Running Vusers with Transaction Response Time, then overlay TPS with server CPU. If response time climbs while TPS flattens and CPU sits at 60%, the bottleneck is not CPU. Look at pools, locks and downstream calls. See finding bottlenecks and saturation.

6. Granularity

Granularity is the bucket size for time-based graphs. Right-click → Set Granularity. A coarse granularity (60 seconds) smooths spikes away, a fine one (1 to 5 seconds) shows them but looks noisy. Look at both. A 5-second stall every 2 minutes, from a cache refresh or garbage collection, is invisible at 60-second granularity. Use the same granularity on every graph you overlay.

7. SLAs

Analysis can evaluate SLAs against the results (Tools → Configure SLA Rules in most versions, or from the SLA section of the Summary Report). You can set goals such as a transaction response time percentile or average per transaction, and run-level goals such as errors per second or hits per second, checked over the whole run or in time intervals. The Summary Report then shows pass or fail per rule.

  • Define SLAs per transaction. Login and search do not share a target.
  • Prefer percentile SLAs to average ones.
  • Time-interval SLAs catch a bad 5 minutes that a whole-run SLA hides.
  • Agree the SLA numbers with the business before the run. An SLA set after seeing the results is a description, not a test. See SLOs and the SLO calculator.

8. Reports and comparing runs

  • Built-in reports. Analysis generates HTML and document reports from templates. Build a template once with your graphs, filters and SLA section, then apply it to every run so reports are comparable.
  • Templates in CI. The Jenkins and Azure DevOps plugins can apply an Analysis template after the run. See CI and DevOps.
  • Cross-result graphs. Open two or more result sets in one session to compare builds on the same graph. Keep the scenario identical between runs, or the comparison means nothing.
  • Export raw data (right-click a graph → export, or the graph data view) when you want your own charts or a statistical comparison.
  • Write the conclusion yourself. A report of 40 graphs is not an analysis. Lead with the answer: did it meet the targets, where is the limit, what is the bottleneck, what do you recommend.

Recent releases add Aviator, an AI assistant in Analysis that summarises results and builds widgets from prompts. Treat its summaries like a junior analyst's first draft and check every claim against the graphs.
