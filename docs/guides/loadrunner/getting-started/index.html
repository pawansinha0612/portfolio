LoadRunner in 2026: what you are actually installing

You join a bank's performance team and the handover note says "scripts are in VuGen, run them from the Controller, results in Analysis, LGs are in the DMZ". Then you search for LoadRunner downloads and find products called "Professional Performance Engineering" and "Core Performance Engineering". This guide maps the names to the pieces, so you know what each one does before you open it.

1. The product family today

LoadRunner has changed owners several times: Mercury Interactive built it, HP bought Mercury in 2006, Micro Focus took over HP's software business in 2017, and OpenText bought Micro Focus in 2023. In 2025 OpenText renamed the products. Your organisation may still call them by the old names, and older documentation, forum answers and job ads certainly do.

Current nameFormer nameWhat it is
OpenText Professional Performance EngineeringLoadRunner ProfessionalThe classic Windows install: VuGen, Controller, Analysis and load generators. What most people mean by "LoadRunner"
OpenText Enterprise Performance EngineeringLoadRunner Enterprise (earlier Performance Center)A shared, web-based server for many teams: projects, scheduling, a pool of load generators, timeslots and trending. Uses the same VuGen scripts
OpenText Core Performance EngineeringLoadRunner Cloud (earlier StormRunner Load)SaaS: run tests from OpenText-hosted cloud generators or your own on-premises ones, with a web UI for results
OpenText Performance Engineering for DevelopersLoadRunner DeveloperLightweight, scriptable DevWeb engine (JavaScript) aimed at developers and pipelines

At the time of writing the help centre covers releases 26.1 to 26.3. Recent releases added AI assistance (Aviator) in VuGen and Analysis, an LLM protocol and a Controller Service CLI. If you are on an older release such as 24.x or 2023, everything in these guides about scripts, parameters and Controller still applies, but some screens look different.

2. The four components

ComponentJobRuns on
VuGen (Virtual User Generator)Record, edit and debug scripts. One script models one business journey for one virtual userWindows workstation
ControllerBuild a scenario from scripts, decide how many vusers, how they ramp and which generators run them. Drives the run and collects live monitorsWindows
Load generatorsExecute vusers. Install the Load Generator component on as many machines as you needWindows or Linux (Linux supports fewer protocols, check the support matrix)
AnalysisOpen the collated results, build graphs, apply SLAs and percentiles, produce reportsWindows

The flow is always the same: script in VuGen, run in Controller on generators, open the result in Analysis. Enterprise Performance Engineering replaces the desktop Controller with a web UI and a server, but the scripts and Analysis are the same.

The Controller is not a load generator. It can host vusers ("localhost" generator) and that is fine for a smoke run. For a real test, keep vusers off the Controller machine so its CPU stays free for collating monitor data. A busy Controller produces gaps in the live graphs that look like application problems.

3. Licensing and the Community licence

LoadRunner is licensed by vusers, by protocol bundle and by duration, and the details depend on your contract. I won't quote prices, they are negotiated and change. What matters for day-to-day work:

  • The Community licence. A fresh Professional Performance Engineering install includes a free Community licence. The current help centre (26.x) states it covers 50 vusers for all protocols, including Gatling and JMeter, except the COM/DCOM, Templates and GUI bundles. That is plenty to learn on, build scripts and run a small smoke test. Check the licence page in your version's help, as allowances have changed before.
  • Protocol bundles matter. A licence for Web HTTP/HTML vusers does not let you run Citrix or SAP GUI vusers. Before you promise a 500-user Citrix test, check the bundle in the License Utility (Start → License Utility, or from Controller's Help menu, depending on version).
  • Heavy protocols cost more generator capacity. TruClient and Citrix vusers run a real browser or client, so a generator holds far fewer of them than Web HTTP/HTML vusers. Plan generator count per protocol, not per test.

4. Installing a learning setup

  1. Download Professional Performance Engineering from OpenText's software download portal. You need an OpenText account, and the download includes the Community licence.
  2. Install the full setup on a Windows machine with admin rights. This gives you VuGen, Controller, Analysis and a local load generator in one go.
  3. Open VuGen once to let it finish first-run setup, then open Controller and confirm that localhost appears as a load generator.
  4. For a second generator, install only the Load Generator component (Windows or Linux) on another machine and add it in Controller under Scenario → Load Generators.

Check the system requirements page for your release before installing on a corporate laptop. Endpoint protection, proxy settings and missing admin rights cause most install and recording failures.

5. Your first test, end to end

  1. Record. In VuGen, File → New Script and Solution, choose Web - HTTP/HTML, then record a short journey: home page, log in, one search, log out. See VuGen scripting.
  2. Make it replay. Wrap steps in transactions, correlate session IDs and tokens (correlation), and give it data (parameterisation). Replay with extended logging until it passes cleanly twice in a row.
  3. Set runtime settings. Think time and pacing turn a script into a realistic user. See runtime settings and pacing.
  4. Build a scenario. In Controller, add the script, set a small number of vusers and a gentle ramp. See Controller scenarios.
  5. Run and analyse. Let the scenario collate, open the results in Analysis and look at transaction response time percentiles, not averages. See Analysis.

6. Habits worth having from day one

  • Put scripts in version control. A VuGen script is a folder of text files (.c, .usr, .prm, default.cfg, data files). Commit the folder, ignore the replay result and data snapshot folders.
  • Every transaction gets a text check. A 200 response with an error page is still a pass unless you check for content. See text checks.
  • Agree the workload first. Vuser count is an output of the workload model, not an input. Work out target throughput, then derive vusers with Little's Law.
  • Monitor the servers, not just the response times. The run tells you something is slow. Server metrics tell you why. See monitoring during a test.
