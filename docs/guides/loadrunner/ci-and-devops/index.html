LoadRunner in CI: a performance gate, not a quarterly event

The release is on Friday. The performance test window is Wednesday night. On Thursday morning you find the login slowed by 40% three sprints ago, and nobody can say which change did it. Running a small LoadRunner test on every build turns that into a failed pipeline on the day the change went in. Here are the ways to do it, from a plain command line to DevWeb scripts a developer can read.

1. Which route fits

You haveRoute
Professional Performance Engineering on a Windows boxA Windows CI agent with Controller installed, running scenarios by command line or plugin
Enterprise Performance Engineering (a shared server)Its Jenkins or Azure DevOps plugin, which asks the server to run a test in a timeslot
Core Performance Engineering (SaaS)Its own CI integrations and API
Developers who want to own API testsDevWeb scripts in JavaScript, run by the DevWeb engine on Windows, Linux or macOS

OpenText documents each integration separately per product, and the plugins differ. Check you are reading the page for your product and release.

2. Command-line runs: wlrun and CLIControllerApp

The classic route is wlrun.exe, the Controller itself, started with arguments:

"%LR_PATH%\bin\wlrun.exe" -TestPath "C:\perf\scenarios\checkout_smoke.lrs" ^
    -Run -ResultName "C:\perf\results\checkout_%BUILD_NUMBER%" -InvokeAnalysis

Per the 26.x help: -Run runs the scenario, writes messages to output.txt in the results folder and closes Controller. Dialogs that would normally need a click are suppressed. -ResultName is the full results path (or use -ResultLocation and -ResultCleanName), and -InvokeAnalysis opens Analysis at the end. Arguments are case sensitive, only one Controller can run at a time, and results are overwritten, so put the build number in the result name. %LR_PATH% is a placeholder for your install folder.

Releases from 2021 onward also ship CLIControllerApp.exe in the bin folder, designed for headless runs:

"%LR_PATH%\bin\CLIControllerApp.exe" -TestPath C:\perf\scenarios\checkout_smoke.lrs ^
    -CollateAndAnalyze -ResultName C:\perf\results\Res_%BUILD_NUMBER%

It takes either -TestPath (an .lrs scenario) or -InputFile (an XML description of the run), a post-run action (-Run, -Collate or -CollateAndAnalyze), and optionally -OverrideLgs to swap load generators per environment and -SilentMode. Release 26.1 added a separate Controller Service CLI that runs .lrs files or YAML scenario definitions. At the time of writing the help describes it as a private beta, installed separately. Watch it if you want scenarios as code.

3. Jenkins

Install the OpenText Application Automation Tools plugin (plugin ID hp-application-automation-tools-plugin, a reminder of its history). Put the Controller on a Windows agent, not on the Jenkins controller. The plugin adds a freestyle build step for running tests from the file system and a pipeline step called loadRunnerTest.

// Jenkinsfile (sketch: generate the exact step with Pipeline Syntax → loadRunnerTest)
pipeline {
  agent { label 'lr-controller' }
  stages {
    stage('Performance smoke') {
      steps {
        loadRunnerTest(
          testPaths: 'C:\\perf\\scenarios\\checkout_smoke.lrs',
          archiveTestResultsMode: 'PUBLISH_HTML_REPORT',
          analysisTemplate: 'C:\\perf\\templates\\ci.tem',
          perScenarioTimeOut: '30',
          controllerPollingInterval: '30',
          ignoreErrorStrings: ''
        )
      }
    }
  }
}

The parameter names above come from the plugin's published step reference. The allowed values of archiveTestResultsMode are easiest to take from the Pipeline Syntax snippet generator in your Jenkins, so treat this as a sketch. The plugin reads the scenario's SLA results to pass or fail the build, so define SLAs in the scenario or Analysis template. Otherwise the build only fails on errors.

4. Azure DevOps

For Professional Performance Engineering, the 26.1 help points to an Azure DevOps Marketplace extension listed as LoadRunner Professional Tests Automation. It runs Controller scenarios on a self-hosted Windows agent where Controller is installed, with settings for the scenario path, results folder, task and scenario timeouts, an Analysis template and whether to treat failures as errors.

For Enterprise Performance Engineering there is a separate extension (installed from a .vsix file) that connects to the Enterprise server, runs a test, and can collate and analyse. Its task does not publish the results folder as a build artifact, so add a Publish Pipeline Artifact step after it.

If the extensions don't fit, a script step that calls CLIControllerApp.exe on a self-hosted Windows agent works in any CI system, including GitLab and GitHub Actions.

5. Enterprise and Core Performance Engineering

With Enterprise Performance Engineering, the CI job does not need Controller locally. The plugin (Jenkins or Azure DevOps) asks the server to run a named test in a project, reserves a timeslot and generators from the shared pool, waits, and pulls back results and trend data. That suits banks with a central performance team: pipelines run tests without anyone installing Controller on a build agent. Core Performance Engineering (SaaS) has its own plugins and a REST API. Check the integration pages for your release, as both products move faster than the desktop tools.

6. DevWeb: LoadRunner in JavaScript

DevWeb is a protocol and engine for HTTP-based scripts written in JavaScript. A DevWeb script is a folder with main.js, scenario.yml and optionally rts.yml for runtime settings. The same script runs in VuGen and Controller, in Enterprise and Core, and from the command line with the standalone engine (Performance Engineering for Developers). That makes it the natural format for developer-owned API tests.

// main.js (sketch, based on the DevWeb JavaScript SDK reference for 26.x)
load.initialize(async function () {
    // runs once per vuser, like vuser_init
});

load.action("Action", async function () {
    const tLogin = new load.Transaction("02_Login");
    tLogin.start();

    const login = new load.WebRequest({
        id: 1,
        url: "https://staging.example.com/api/login",
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: { username: load.params.Username, password: load.params.Password },
        extractors: [
            new load.JsonPathExtractor("token", "$.access_token")
        ]
    }).sendSync();

    tLogin.stop(login.status === 200 ? load.TransactionStatus.Passed
                                     : load.TransactionStatus.Failed);

    const tAccounts = new load.Transaction("03_Accounts");
    tAccounts.start();
    const accounts = new load.WebRequest({
        id: 2,
        url: "https://staging.example.com/api/accounts",
        headers: { "Authorization": `Bearer ${login.extractors.token}` }
    }).sendSync();
    tAccounts.stop(accounts.status === 200 ? load.TransactionStatus.Passed
                                           : load.TransactionStatus.Failed);

    load.log(`accounts returned ${accounts.status}`, load.LogLevel.info);
});

load.finalize(async function () {
});

Key parts of the SDK: load.initialize, load.action and load.finalize blocks (equivalent to vuser_init, Action and vuser_end), load.WebRequest with sendSync() or async send(), extractors (BoundaryExtractor, RegexpExtractor, JsonPathExtractor, XpathExtractor, TextCheckExtractor, HtmlExtractor, CookieExtractor) read from response.extractors.<name>, parameters from load.params.<name>, and load.log instead of console.log. A JavaScript object passed as body is serialised according to the Content-Type header. I wrote the sample from the 26.x SDK reference and could not run it here, so treat it as a sketch and check request options against your version's SDK page.

Run it locally from the command line:

# single vuser, a few iterations (Windows: DevWeb.exe)
DevWeb -mode=single -iterations=3 ./checkout_api

# load mode, using scenario.yml in the script folder
DevWeb -mode=load ./checkout_api

DevWeb only speaks HTTP-family protocols (HTTP/1.1, HTTP/2, WebSockets, gRPC and some others, depending on release). Citrix, SAP GUI and TruClient journeys stay in their own protocols. Recent releases also add an MCP server for DevWeb, so AI coding tools can record and edit scripts.

7. Designing the gate

  • Small and fast in the pipeline. A 10 to 15-minute run at a fraction of peak, on every merge to main or nightly. Save full-scale tests for a scheduled window.
  • Fixed environment, fixed data. A gate is only as stable as the environment. Noisy shared test environments produce flaky gates, and flaky gates get switched off.
  • Gate on percentiles and error rate, per key transaction, with thresholds a little above the current baseline. See thresholds and baselines.
  • Keep the history. Archive the Analysis report per build so you can see the trend, not just pass or fail.
  • Treat licence capacity as a resource. Pipeline runs consume vusers from the same licence or pool as the big tests. Agree a budget.
