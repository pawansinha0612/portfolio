Performance testing microservices and cloud systems

"It autoscales" is the most expensive sentence in cloud performance. The traffic spike arrives in 40 seconds. The metrics notice after 30, the autoscaler decides after 15 more, new pods wait 2 minutes for a node, then 50 seconds for the JVM to warm up. For four minutes the existing pods take the full spike alone, and that's when users see errors. Meanwhile a downstream SaaS API starts returning 429s at a limit nobody knew about.

What's different about microservices

  • Latency adds up and tails multiply. A request through six services pays six sets of network hops, serialisation and queueing. If a page calls 10 services in parallel, each with 1% of requests above 1 second, about 10% of page loads hit at least one slow call (1 − 0.9910). See fan-out amplification and tail latency.
  • The bottleneck moves. Scaling one service pushes load onto the next. Test the whole journey, not each service alone, then test individual services to find their limits.
  • Shared resources hide behind service boundaries. Five services sharing one database, cache cluster or message broker all slow down together. Testing services one at a time won't show it.
  • Timeouts and retries interact. If service A times out after 5 seconds and retries 3 times, and B does the same towards C, one slow call to C can become 9 calls. Check that timeouts get shorter as you go deeper, and that retries have budgets and jittered back-off.

Distributed tracing is close to essential here. See reading a trace waterfall.

Testing autoscaling

The question isn't whether autoscaling works. It's how long it takes and what users experience while it happens. Use the load profiles that stress it:

  • Step test: jump from 30% to 100% of peak in under a minute, hold for 20 minutes. Measures reaction time and the error window.
  • Slow ramp: grow over an hour. Checks that scaling keeps up smoothly and that thresholds are sensible.
  • Spike and drop: spike, drop back, spike again. Catches scale-down that is too aggressive (flapping) and in-flight requests failing on pods being removed.

Record a timeline for each step: when load changed, when the metric crossed the threshold, when the scaler acted, when new capacity was ready and taking traffic, and when latency recovered. Each delay is a separate knob.

Also test the ceiling: maximum replica counts, node group limits, IP addresses in the subnet, and database connections (each new pod opens its own pool). Autoscaling that works up to 20 pods can fail at 21 for reasons that have nothing to do with CPU. See autoscaling.

Cold starts

Serverless functions (AWS Lambda, Azure Functions, Google Cloud Run functions) start new execution environments on demand. The first request on a new environment pays for the runtime starting and your initialisation code. That can be tens of milliseconds for a small function or several seconds for a large JVM function with heavy frameworks.

  • Cold starts happen during scale-out, which is exactly when load rises. A test that warms up slowly never sees them. A spike test sees many at once.
  • Measure them separately. In Lambda, the REPORT log line includes Init Duration on cold starts. Split latency percentiles into cold and warm invocations, or the cold ones disappear into the average.
  • Mitigations to test: provisioned concurrency (pre-initialised environments, at a cost), Lambda SnapStart for supported runtimes, smaller deployment packages, lazy initialisation, and lighter frameworks.
  • Concurrency limits. Lambda has an account-level concurrency quota per region (1,000 by default, shared by all functions in the account and region) and a limit on how fast each function can scale out. A load test can throttle other functions in the same account. Check the current quotas for your account before testing.

Containers have cold starts too: a new pod on Kubernetes or a new task on ECS or Cloud Run must pull the image, start the runtime and warm up before it is fast. That is the warm-up delay in the autoscaling table above.

Rate limits and quotas

Cloud and SaaS systems are full of rate limits that never show up in functional tests:

  • Your own API gateway and WAF: per-client throttles and burst limits. A load test from a few IPs or one API key hits them long before real traffic would.
  • Cloud service quotas: API Gateway account throttles, Lambda concurrency, DynamoDB per-partition throughput, managed database connection limits, KMS and Secrets Manager request rates, and many more. Many are per account and region, shared with everything else running there.
  • Third-party APIs: payment, identity, address lookup, email and SMS providers all have rate limits, and many forbid load testing against their production endpoints. Use their sandbox, or stub them with a mock that reproduces their latency and their limits, including 429 responses.

Before the test, list every external call in the journey and its documented limit. Compare each limit with peak load × calls per transaction. Then test what the system does when a limit is hit: does it back off and queue, or retry immediately and make it worse?

Tell your cloud provider and third parties before large tests where their terms require it, and agree WAF and DDoS-protection allow-lists with your security team. A load test that looks like an attack can get IPs blocked or trigger an incident response.

Cost per transaction

In the cloud, performance and cost are the same conversation. A system that meets its latency target by running 3 times the infrastructure it needs has a cost problem. A load test is the cheapest place to measure that.

cost per 1,000 transactions = (cost of the system for the test hour) ÷ (transactions in that hour ÷ 1,000)

Example: 12 pods + database + cache + load balancer + data transfer ≈ $9.40 for one hour
         at 150 transactions/s = 540,000 transactions
         → about $0.017 per 1,000 transactions
  • Include everything that scales with traffic: compute, managed databases, data transfer between zones and to the internet, NAT gateway processing, request-priced services (serverless, API gateways, queues), and logging and APM ingestion, which often grow faster than expected under load.
  • Track it across runs. A release that holds latency but raises cost per transaction by 40% is a regression worth catching. Put it in the results report next to latency and throughput.
  • Use it to compare options: bigger instances vs more instances (horizontal vs vertical), ARM vs x86, provisioned vs on-demand capacity, caching vs a larger database.
  • Remember the test's own cost: load generators, data transfer from them, and the environment running for the test window. Tear environments down afterwards.

Test environments in the cloud

  • Same instance types, same limits. A test environment on smaller instances, with burstable CPU credits, or with a different database class tells you about a different system. Scaling results down from a smaller environment is guesswork, because bottlenecks don't scale linearly.
  • Same autoscaling configuration, including minimums and maximums, or the autoscaling test is meaningless.
  • Watch for burst behaviour: burstable instances, storage with burst credits and some network limits are fast for the first minutes of a test and slow after. Run tests long enough to drain the credits.
  • Noisy neighbours: results vary between runs on shared infrastructure. Run each important test at least twice and compare (the compare runs tool helps).
