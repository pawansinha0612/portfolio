Performance testing Kafka and messaging

The API returns 202 Accepted in 15 ms at three times peak load, and the load test passes. Behind it, the order consumer processes 400 messages a second while 1,100 arrive. Lag grows by 42,000 messages a minute, and customers get their confirmation emails two hours late. With asynchronous systems, the response time of the front door says almost nothing. You have to measure the queue.

What to measure in a messaging system

MetricWhy it matters
Producer throughput and send latencyCan the producers publish at peak rate? Latency depends heavily on acks, batching and replication.
Consumer throughputMust exceed the arrival rate with headroom, or lag grows forever
Consumer lag (messages and time)The size of the backlog. Lag in time is what the business feels.
End-to-end latencyTime from produce to processed. The true user-facing number for asynchronous flows.
Broker resourcesDisk throughput, network, request handler idle ratio, under-replicated partitions
RebalancesConsumer group rebalances pause consumption. Frequent ones under load are a problem on their own.

The rule that matters most: consumer throughput must be higher than the peak arrival rate, with enough margin to drain a backlog. If consumers can do 1,200 messages per second and peak arrival is 1,100, a 10-minute backlog of 660,000 messages takes 66 minutes to clear (660,000 ÷ the 100/s spare capacity). That is headroom in queue form.

Partitions set the ceiling

  • A partition is consumed by at most one consumer in a group. A topic with 12 partitions can use at most 12 consumers in parallel. The 13th sits idle. Partition count is the ceiling on consumer parallelism, unless each consumer processes records concurrently itself.
  • Ordering is per partition. Messages with the same key go to the same partition, which is how per-entity ordering is kept.
  • Key skew creates hot partitions. If 30% of messages share one key (one big customer, one popular product), one partition and one consumer carry 30% of the load. Total throughput looks fine on paper and that one partition lags. Test with a realistic key distribution, not random keys.
  • More partitions isn't free. Each adds files, memory and replication work on the brokers, and more partitions per consumer group means longer rebalances. Increasing partitions later also changes which partition a key maps to.

Producer throughput and latency

Producer performance is mostly configuration. The settings to vary in a test:

  • acks: acks=all waits for all in-sync replicas. Safer, slower. It has been the default since Kafka 3.0, along with idempotence. Test with what production uses.
  • linger.ms and batch.size: waiting a few milliseconds to fill bigger batches raises throughput and cuts broker load, at the cost of a little latency.
  • compression.type: lz4 or zstd usually raise throughput by sending fewer bytes, at some CPU cost on producers.
  • Message size: test with the real size distribution. Throughput in MB/s and in messages/s behave very differently as size changes.

Consumer throughput and lag

In real systems the consumer's processing (database writes, HTTP calls) is almost always slower than Kafka itself. So the useful consumer test exercises your real consumer code against its real dependencies, not just Kafka's fetch speed.

# lag per partition for a consumer group: CURRENT-OFFSET, LOG-END-OFFSET, LAG
kafka-consumer-groups.sh --bootstrap-server broker1:9092 --describe --group order-processor

For dashboards, export lag continuously with a lag exporter or your platform's metrics (managed Kafka services publish consumer lag metrics). Watch the trend during the test: lag that rises during the peak and falls back afterwards is acceptable if the maximum lag in time is within your target. Lag that never comes back down means consumers are under capacity.

Also watch for rebalances in consumer logs. A consumer that takes longer than max.poll.interval.ms (default 5 minutes) between polls is removed from the group, which triggers a rebalance, which pauses everyone. Slow processing under load can turn into a rebalance loop.

Kafka's perf-test scripts

Kafka ships with producer and consumer performance tools in its bin/ directory. They measure what the cluster can do with synthetic records, which is the right first test after building or resizing a cluster.

# create a test topic like the production one
kafka-topics.sh --bootstrap-server broker1:9092 --create --topic perf-test \
  --partitions 12 --replication-factor 3

# produce 5 million 1 KB records as fast as possible (--throughput -1 = no limit)
kafka-producer-perf-test.sh --topic perf-test --num-records 5000000 --record-size 1024 \
  --throughput -1 \
  --producer-props bootstrap.servers=broker1:9092 acks=all linger.ms=10 batch.size=65536 compression.type=lz4

# consume them back
kafka-consumer-perf-test.sh --bootstrap-server broker1:9092 --topic perf-test \
  --messages 5000000 --group perf-consumer --timeout 60000

The producer tool prints records/sec, MB/sec, average and max latency and the 50th, 95th, 99th and 99.9th percentile latencies. The consumer tool prints MB/sec and messages/sec, plus rebalance and fetch times.

  • Set --throughput to a target rate (for example 50000) to measure latency at a given load. With -1, latency is measured with the producer's buffer full, which is a saturation figure.
  • Run several producers in parallel from separate machines to find the cluster's limit rather than one client's limit.
  • Versions differ. In Kafka 4.2 some options were renamed: --command-property replaces --producer-props and --num-records replaces the consumer tool's --messages. The old names still work with a deprecation warning. Run each script with --help for your version. On Windows the scripts are .bat files in bin\windows, and some distributions drop the .sh suffix.

xk6-kafka: messaging inside a k6 test

To produce and consume as part of a wider load test, for example HTTP traffic that triggers events plus a direct Kafka load, use xk6-kafka. It is a community k6 extension (not maintained by Grafana), so you build a custom k6 binary with xk6:

# xk6-kafka v2.x targets k6 v2. See the project's README for the exact build line for your version.
go install go.k6.io/xk6/cmd/xk6@latest
CGO_ENABLED=1 xk6 build --with github.com/mostafa/xk6-kafka/v2@latest
./k6 run kafka-test.js

A minimal script with the v2 API:

import { Producer, Consumer } from 'k6/x/kafka';

const brokers = ['broker1:9092'];
const producer = new Producer({ brokers, topic: 'orders' });
const consumer = new Consumer({ brokers, topic: 'orders', groupId: 'k6-check' });

export const options = {
  vus: 20,
  duration: '5m',
  thresholds: { kafka_writer_error_count: ['count == 0'] },
};

export default function () {
  producer.produce({
    messages: [{ key: `customer-${Math.floor(Math.random() * 1000)}`, value: JSON.stringify({ total: 4999 }) }],
  });
}

export function teardown() {
  producer.close();
  consumer.close();
}

Versions before 2.0 used Writer, Reader and Connection, and serialised keys and values through a SchemaRegistry helper. Those names still work in 2.x as deprecated aliases. The extension reports metrics such as kafka_writer_message_count, kafka_writer_error_count, kafka_reader_message_count and kafka_reader_lag. Check the README for the full list and for Avro and JSON Schema support.

For end-to-end latency, put a timestamp in each message (or use the record timestamp) and have the real consumer record "now minus timestamp" as a metric when it finishes processing. That is the number the business cares about, and no load tool can measure it from the outside.

Test scenarios worth running

  1. Peak steady state: produce at peak arrival rate for at least 30 minutes with real consumers. Pass if lag stays bounded and end-to-end latency meets the target.
  2. Burst and drain: produce at 2 to 3 times peak for 10 minutes, then drop to normal. Measure the maximum lag and how long it takes to drain.
  3. Consumer outage and catch-up: stop consumers for 15 minutes while producing, then restart. Catch-up hits downstream databases much harder than normal flow does. That is often where the real bottleneck shows.
  4. Broker failure under load: stop one broker during the peak test. Watch producer errors and latency, leader elections and under-replicated partitions. See chaos and resilience.
  5. Scaling consumers: add consumers during the test and measure the rebalance pause.

The same ideas apply to RabbitMQ, Amazon SQS, Azure Service Bus and Google Pub/Sub. Each has its own limits (queue depth, in-flight message limits, API rate limits) and its own lag metric, but the principle of arrival rate versus consumer capacity doesn't change. See back-pressure for what should happen when consumers can't keep up.
