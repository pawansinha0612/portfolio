Frontend performance testing

The API answers in 120 ms at peak load and the load test passes. Meanwhile a real shopper on a mid-range Android phone waits 4.8 seconds for the product image and taps "Add to cart" twice because nothing happened the first time. Backend load tests measure the server. Users experience the page, and most of a page's load time is spent in the browser.

Core Web Vitals: LCP, INP, CLS

Google's Core Web Vitals are three user-centred metrics. They are assessed at the 75th percentile of page loads, separately for mobile and desktop.

MetricMeasuresGoodPoor
LCP: Largest Contentful PaintWhen the largest image or text block in the viewport rendered. Loading.≤ 2.5 s> 4 s
INP: Interaction to Next PaintDelay from a click, tap or key press to the next frame, across the visit (roughly the worst interaction). Responsiveness.≤ 200 ms> 500 ms
CLS: Cumulative Layout ShiftHow much visible content jumps around unexpectedly. Visual stability.≤ 0.1> 0.25

INP replaced First Input Delay as a Core Web Vital in March 2024. Supporting metrics help diagnose: TTFB (server and network, the part a backend load test does affect), First Contentful Paint, and Total Blocking Time in the lab.

LCP breaks into four parts worth measuring separately: TTFB, resource load delay (time before the LCP image starts downloading), resource load duration and element render delay. A slow LCP with a fast TTFB is a frontend problem, often a late-discovered or oversized hero image.

Lab data vs field data

Lab (synthetic)Field (real users)
SourceA scripted browser on a defined device and network: Lighthouse, WebPageTest, k6 browserReal visits: Chrome UX Report (CrUX), your own RUM
Good forDebugging, comparing builds, CI gates, testing before releaseThe truth about what users get, across devices and networks
Weak atRepresents one device and network. Can't measure real INP (no real interactions).Lagging (CrUX is a rolling 28-day window), noisy, only for pages with enough traffic

Use lab tests to find and fix, field data to confirm. When they disagree, the field is right and the lab profile is wrong: usually your users have slower phones or networks than the lab assumes. PageSpeed Insights shows both for a URL, field data at the top when CrUX has enough samples. For your own field data, the web-vitals JavaScript library reports LCP, INP and CLS from real sessions to any endpoint you choose.

import { onLCP, onINP, onCLS } from 'web-vitals';

function send(metric) {
  navigator.sendBeacon('/rum', JSON.stringify({ name: metric.name, value: metric.value, id: metric.id }));
}
onLCP(send);
onINP(send);
onCLS(send);

Lighthouse

Lighthouse runs in Chrome DevTools, on the command line, and inside PageSpeed Insights. By default the mobile run emulates a mid-range phone on a slow 4G connection using simulated throttling: it loads the page on your real connection and then models how long it would have taken.

npx lighthouse https://www.example.com/ \
  --only-categories=performance \
  --output=json --output=html --output-path=./lh/home \
  --chrome-flags="--headless=new"
  • Run it several times. Scores vary between runs from CPU load, network and server variance. Take the median of 3 to 5 runs before comparing builds.
  • Read the metrics, not the score. The 0 to 100 score is a weighted blend of lab metrics, and the weights change between Lighthouse versions. LCP, TBT and CLS values plus the diagnostics (render-blocking resources, unused JavaScript, image sizes) are what you act on.
  • TBT is the lab stand-in for INP. Total Blocking Time sums main-thread work over 50 ms per task during load. High TBT means long JavaScript tasks that will also delay interactions.
  • Test from a quiet machine. A busy CI runner inflates CPU-bound metrics. Keep the runner type fixed.

WebPageTest

WebPageTest (now run by Catchpoint, with a free tier that needs an account) loads pages in real browsers from many locations and network profiles. Its strengths are the views Lighthouse doesn't give you: the full request waterfall with connection reuse visible, a filmstrip and video of the page rendering, repeat-view (cached) runs, and side-by-side comparison of two tests.

  • Run from a location near your users with a realistic connection profile (for example 4G) and a real mobile device or emulation.
  • Use at least 3 runs and look at the median run.
  • Read the waterfall for the LCP resource: when was it discovered, did it wait for other resources, and was its connection already open?
  • Scripted tests can log in or step through a journey before measuring a page.

k6 browser: frontend under backend load

The most useful frontend test for a performance engineer is often a hybrid: many protocol-level virtual users generate backend load, while a few real browsers measure what a user experiences during that load. k6 does both in one script with the k6/browser module (bundled with k6. Older releases used k6/experimental/browser with a different, synchronous API).

import http from 'k6/http';
import { browser } from 'k6/browser';
import { check } from 'k6';

export const options = {
  scenarios: {
    load: {                      // backend load at a fixed arrival rate
      executor: 'constant-arrival-rate',
      rate: 100, timeUnit: '1s', duration: '5m',
      preAllocatedVUs: 50, maxVUs: 200,
      exec: 'api',
    },
    ui: {                        // two real browsers measuring the page during that load
      executor: 'constant-vus',
      vus: 2, duration: '5m',
      exec: 'page',
      options: { browser: { type: 'chromium' } },
    },
  },
  thresholds: {
    'http_req_duration{scenario:load}': ['p(95)<500'],
    browser_web_vital_lcp: ['p(75)<2500'],
    browser_web_vital_cls: ['p(75)<0.1'],
  },
};

export function api() {
  http.get('https://www.example.com/api/products?page=1', { tags: { name: 'products' } });
}

export async function page() {
  const p = await browser.newPage();
  try {
    await p.goto('https://www.example.com/products');
    await p.locator('h1').waitFor();
    check(await p.locator('h1').textContent(), { 'heading shown': (t) => t.length > 0 });
  } finally {
    await p.close();
  }
}

k6 reports browser_web_vital_lcp, browser_web_vital_cls, browser_web_vital_inp, browser_web_vital_fcp and browser_web_vital_ttfb. Browsers are heavy: each browser VU needs far more CPU and memory than a protocol VU, so keep their count small and watch the load generator. INP is only reported when the script interacts with the page (clicks, typing). Comparing LCP from the browser scenario with and without the backend load tells you how much of the user's wait the backend is responsible for at peak.

Budgets and CI

A performance budget turns the numbers into a gate: LCP under 2.5 s in the lab profile, no more than 300 KB of JavaScript, TBT under 200 ms. Lighthouse CI (npx @lhci/cli autorun) runs Lighthouse several times per build and asserts on budgets. k6 thresholds do the same for browser metrics. Gate on stable lab metrics in CI, then track field data on a dashboard to make sure the lab profile still matches reality. See synthetic monitoring for running the same checks against production on a schedule.

What usually moves the numbers

  • LCP: make the LCP image discoverable in the HTML (not injected by JavaScript), give it fetchpriority="high", don't lazy-load it, serve it at the right size in a modern format, and cut TTFB with caching and a CDN.
  • INP: break up long JavaScript tasks, defer non-critical third-party scripts, and keep event handlers small, moving heavy work after the next paint.
  • CLS: set width and height (or aspect-ratio) on images and embeds, reserve space for ads and banners, and avoid inserting content above what the user is reading.

Network-level causes (handshakes, CDN misses, DNS) are covered in network and CDN bottlenecks.
