Specialist performance testing topics

A standard load test sends HTTP requests and measures responses. Plenty of real performance risk sits elsewhere: in the browser, in a database that only slows down at production data volumes, in a Kafka consumer that falls behind, in a phone on a train, in a dependency that fails halfway through peak. Each guide below covers what to measure, which tools fit and the mistakes that make results misleading.

Browser

Frontend performance

Core Web Vitals, lab vs field data, Lighthouse, WebPageTest and k6 browser tests.

 Data

Database load testing

Data volumes, realistic data, and pgbench, sysbench and HammerDB.

 Messaging

Kafka and messaging

Producer and consumer throughput, lag, partitions, and the perf-test scripts and xk6-kafka.

Mobile app performance

Startup time, frame rate, profilers, network conditioning and mobile traffic patterns on the backend.

 Resilience

Chaos and resilience testing

Fault injection with Toxiproxy, AWS FIS, Chaos Mesh and LitmusChaos, combined with load.

 Cloud

Microservices and cloud

Autoscaling tests, cold starts, rate limits and cost per transaction.

How these fit with a normal load test

Most of these topics add a dimension to a load test rather than replacing it. A chaos experiment is more useful while realistic load runs. A database test is only as good as its data. A frontend measurement needs the backend under load to be honest about peak-time experience. Start from the workload model and the risks that worry you most, then pick the guides that cover them. The bottleneck playbook and monitoring guide apply to all of them.
