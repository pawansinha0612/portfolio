Exercise 1: your first smoke test

You write a 300-user test, press run and go for coffee. Every request failed in the first second because the auth header had a typo, and the next 20 minutes of "results" measure how fast the server says no. A smoke test catches that in ten seconds: one user, a handful of requests, and checks that prove each response is real.

  • 15 minutes
  • 1 virtual user, 5 requests
  • Local QuickPizza, or the public demo for this exercise only

Goal

Run a k6 script end to end, add checks that validate the response body as well as the status, and learn to read the end-of-test summary. Then break the script on purpose and see what k6 does, and does not, do about it.

Setup

Do the one-time setup: install k6 and, ideally, start QuickPizza locally. This is the only exercise where the public demo at quickpizza.grafana.com is fine, because it sends five requests in about seven seconds. Keep it that way.

The script

Save this as 01-smoke.js in your practice folder:

// Exercise 1: a first smoke test. One virtual user, five iterations.
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';

export const options = {
  vus: 1,
  iterations: 5,
};

const params = {
  headers: {
    'Content-Type': 'application/json',
    // Token of the demo user that QuickPizza creates on start-up
    Authorization: 'token abcdef0123456789',
  },
};

export default function () {
  const restrictions = {
    maxCaloriesPerSlice: 1000,
    mustBeVegetarian: false,
    minNumberOfToppings: 2,
    maxNumberOfToppings: 5,
  };
  const res = http.post(`${BASE_URL}/api/pizza`, JSON.stringify(restrictions), params);

  const ok = check(res, {
    'status is 200': (r) => r.status === 200,
    'has a pizza name': (r) => r.status === 200 && !!r.json('pizza.name'),
    'has ingredients': (r) => r.status === 200 && r.json('pizza.ingredients').length > 0,
  });
  if (ok) console.log(`Got pizza: ${res.json('pizza.name')}`);

  sleep(1);
}

Three things to notice. iterations: 5 with one VU means "run the default function five times, then stop". BASE_URL comes from -e BASE_URL=... so the same script runs anywhere. And each check that reads the body first confirms the status is 200, because calling r.json() on an error page throws an exception and ends the iteration.

Run it

# Against your local QuickPizza (recommended)
k6 run 01-smoke.js

# Or against the public demo, exactly as written: 1 VU, 5 iterations
k6 run -e BASE_URL=https://quickpizza.grafana.com 01-smoke.js

What you should see

Five log lines with pizza names, then a summary shaped like this (numbers are illustrative, from a run against the public demo from Melbourne):

    checks_succeeded...................: 100.00% 15 out of 15
    checks_failed......................: 0.00%   0 out of 15

    ✓ status is 200
    ✓ has a pizza name
    ✓ has ingredients

    HTTP
    http_req_duration..............: avg=283.01ms min=252.72ms med=268.31ms max=356.71ms p(90)=327.34ms p(95)=342.03ms
    http_req_failed................: 0.00%  0 out of 5
    http_reqs......................: 5      0.71/s

    EXECUTION
    iteration_duration.............: avg=1.39s    min=1.25s    med=1.28s    max=1.84s    p(90)=1.64s    p(95)=1.74s
    iterations.....................: 5      0.71/s

Locally, http_req_duration will be lower because there is no internet round trip. Most of what remains is QuickPizza's own work: several internal HTTP calls per pizza, plus a deliberate random pause while it "measures how funny the name is".

Questions

  1. Why is iteration_duration about one second longer than http_req_duration?
  2. The slowest iteration is usually the first one. Run again with --summary-mode=full. Which extra metric explains it, and why isn't that time inside http_req_duration?
  3. Change the token in the script to wrongtoken000000 and run again (locally). What happens to the checks and to http_req_failed? Then run echo $?. What exit code did k6 return, and why is that a problem in a CI pipeline?
  4. Put the token back. How many checks ran in total, and why is it 15 and not 5?
Answer / what to look for
  1. The sleep(1) at the end of each iteration. An iteration is everything in the default function: the request, the checks and the think time. http_req_duration is only the request.
  2. http_req_blocked, http_req_connecting and, on HTTPS, http_req_tls_handshaking. The first request has to open a TCP connection (and do a TLS handshake on the public demo), later ones reuse it through keep-alive. k6 defines http_req_duration as sending + waiting + receiving, so connection setup is reported separately. That is useful: a slow handshake and a slow server are different problems.
  3. Every check fails and http_req_failed is 100%, because a 401 is outside k6's default "expected" statuses (200–399). But the exit code is 0. Checks record results, they don't fail the run. A CI job would go green on a test where nothing worked. Thresholds fix that, which is the next exercise.
  4. Three checks per iteration times five iterations. checks_total counts each check evaluation, not each request.
