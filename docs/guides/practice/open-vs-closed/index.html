Exercise 4: open vs closed workload model

Production slows down at 9 am. Your load test of "10 users" slows down too, and quietly sends a third of the traffic it sent yesterday. Real customers don't wait politely for the previous customer's page to load before they arrive. Your test did, so it went easy on the server exactly when it should have pushed.

  • 30 minutes
  • 4 runs of 1 minute
  • Run locally only

Goal

See the difference between a closed model (a fixed number of VUs, each waiting for its response before sending the next request) and an open model (new requests arrive at a fixed rate whatever the server does). Then slow the server down and watch how differently they react.

Setup

Start QuickPizza normally for the first two runs:

docker run --rm --name quickpizza -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

The script

Save as 04-open-vs-closed.js. One file, two scenarios, chosen with -e MODEL=...:

// Exercise 4: the same journey under a closed model (fixed users) and an open model (fixed arrival rate).
// Run locally only:  k6 run -e MODEL=closed 04-open-vs-closed.js   then   -e MODEL=open
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';
const MODEL = __ENV.MODEL || 'closed';

const scenarios = {
  // Closed: 10 users, each waits for its response, thinks 1s, then sends the next request.
  closed: { executor: 'constant-vus', vus: 10, duration: '1m' },
  // Open: 8 new iterations start every second, however slow the server gets.
  open: {
    executor: 'constant-arrival-rate',
    rate: 8,
    timeUnit: '1s',
    duration: '1m',
    preAllocatedVUs: 10,
    maxVUs: 50,
  },
};

if (!scenarios[MODEL]) throw new Error(`MODEL must be closed or open, got ${MODEL}`);

export const options = {
  scenarios: { [MODEL]: scenarios[MODEL] },
  summaryTrendStats: ['avg', 'med', 'p(95)', 'p(99)', 'max'],
};

const params = {
  headers: { 'Content-Type': 'application/json', Authorization: 'token abcdef0123456789' },
  tags: { name: 'pizza' },
};

export default function () {
  const res = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), params);
  check(res, { 'status is 200': (r) => r.status === 200 });
  // Think time belongs to the closed model. In the open model the arrival rate already sets the pace.
  if (MODEL === 'closed') sleep(1);
}

Both scenarios start at the same load: 10 VUs with 1 s of think time send a bit under 10 requests per second, and the open scenario asks for 8 per second.

Run it

# Healthy server
k6 run -e MODEL=closed 04-open-vs-closed.js
k6 run -e MODEL=open 04-open-vs-closed.js

Now make every pizza request 2 seconds slower. Stop the container (Ctrl+C) and start it with a delay:

docker run --rm --name quickpizza -p 3333:3333 \
  -e QUICKPIZZA_DELAY_RECOMMENDATIONS_API_PIZZA_POST=2s \
  ghcr.io/grafana/quickpizza-local:latest
# Slow server
k6 run -e MODEL=closed 04-open-vs-closed.js
k6 run -e MODEL=open 04-open-vs-closed.js

Write down http_reqs (count and rate), p95, and the vus line from all four runs.

What you should see

Illustrative numbers. The pattern is what matters:

RunRequests/sp95VUs
Closed, healthy≈ 9.5≈ 0.1 s10
Open, healthy≈ 8≈ 0.1 sa few busy at a time
Closed, slow≈ 3.3≈ 2.1 s10
Open, slow≈ 8≈ 2.1 sclimbs to about 17

In the slow open run you may also see a few dropped_iterations near the start, while k6 creates the extra VUs it suddenly needs.

Questions

  1. Both slow runs report the same p95. So what did the closed model get wrong?
  2. Use Little's Law to predict the closed model's request rate on the slow server, and the number of VUs the open model needs. Do your predictions match?
  3. Set maxVUs: 12 in the open scenario and repeat the slow open run. What happens, and which metric tells you?
  4. When is a closed model the right choice?
Answer / what to look for
  1. The load. On the slow server the closed test sent about a third of the requests, because each VU spent 2 seconds waiting instead of sending. A test that is meant to say "can we handle 8 requests per second?" answered a different question: "can we handle 3?". In a real system, lower load also means less queueing, so a closed test can understate latency once the server is near saturation. This back-off is closely related to coordinated omission.
  2. Closed: 10 VUs ÷ (2.1 s response + 1 s think) ≈ 3.2 requests/s. Open: concurrency = 8 requests/s × 2.1 s ≈ 17 VUs busy at once. Little's Law predicts both.
  3. k6 can't start iterations without a free VU, so it skips them and counts them in dropped_iterations, and you get a warning about insufficient VUs. The achieved rate falls below 8 per second. Any test with dropped iterations did not deliver the load you designed, so check that line on every open-model run.
  4. When the real users really are a fixed population that waits: a batch job with N workers, a connection pool, a call centre with 50 agents. For public web traffic, where arrivals don't depend on how fast you are, use an arrival-rate executor.
