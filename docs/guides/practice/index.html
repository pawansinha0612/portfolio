Performance testing practice: 10 hands-on exercises

You can explain p95, the hockey stick and the open workload model. Then an interviewer asks, "Tell me about a bottleneck you found," and you realise you have never watched latency bend on a server you started yourself. These exercises fix that. You run every test, on a small app on your own machine, and finish by finding a slow dependency that someone hid from you.

Tick exercises as you finish them.

Your progress is saved in this browser only. Nothing is sent anywhere.

Rules of the playground

Only put load on systems you own or have written permission to test. A load test against someone else's site looks exactly like a denial-of-service attack. It can breach their terms of service and computer misuse laws, and it can hurt real users. These exercises never need it.

  • Every load exercise runs locally, against a QuickPizza container on your own machine. Each page says so at the top.
  • The public demo at quickpizza.grafana.com is run by Grafana for small k6 demos. Only Exercise 1 may use it, and only as written: 1 virtual user, 5 requests. Don't raise the numbers.
  • Don't use test.k6.io. It is deprecated. Its pages now live inside QuickPizza.
  • Don't swap in a "demo" site you found online. If you didn't start it and nobody invited you, it is not a practice target.

One-time setup (10 minutes)

You need three things: k6, Docker and a folder to keep your scripts in.

1. Install k6

# macOS
brew install k6
# Windows
winget install k6 --source winget
# Linux: see https://grafana.com/docs/k6/latest/set-up/install-k6/
k6 version

The scripts were checked with k6 v1.0. Anything newer should work.

2. Start QuickPizza locally

QuickPizza is Grafana's open-source demo app for k6 workshops. It generates pizza recommendations through a small set of internal services (catalog, copy, recommendations) that call each other over HTTP, which is exactly what makes it useful for finding bottlenecks. Install Docker, then:

docker run --rm --name quickpizza -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

Leave that terminal open. In a second terminal, check it answers:

curl -s -X POST http://localhost:3333/api/pizza \
  -H 'Content-Type: application/json' \
  -H 'Authorization: token abcdef0123456789' \
  -d '{}'

You should get JSON with a pizza object. abcdef0123456789 is the token of a demo user QuickPizza creates on start-up. Stop the container with Ctrl+C. It keeps everything in memory, so every restart is a clean slate.

3. Make a practice folder

mkdir perf-practice && cd perf-practice

Save each exercise's script here with the file name shown on its page.

The fault switches you will use

QuickPizza can slow itself down or fail on purpose. Delays are environment variables on the container (Go durations such as 300ms or 2s). Errors on the ingredients lookup are request headers.

SwitchEffectUsed in
QUICKPIZZA_DELAY_RECOMMENDATIONS_API_PIZZA_POSTAdds a delay to every POST /api/pizza4, 7
QUICKPIZZA_DELAY_COPY_API_NAMES, …_ADJECTIVES, …_QUOTESSlows one endpoint of the internal copy service7, 8, 9
QUICKPIZZA_FAIL_RATE_RECOMMENDATIONS_API_PIZZA_POSTFails that percentage (0–100) of pizza requests with a 503Try it yourself
Headers x-error-get-ingredients + x-error-get-ingredients-percentageMakes the internal ingredients lookup fail for that request, some percentage of the time2, 7
Headers x-delay-get-ingredients + …-percentageDelays the internal ingredients lookupTry it yourself

Pass an environment variable with -e, for example docker run --rm --name quickpizza -p 3333:3333 -e QUICKPIZZA_DELAY_COPY_API_NAMES=300ms ghcr.io/grafana/quickpizza-local:latest. These come from QuickPizza's source and can change between versions. If one seems to do nothing, check the repository.

Numbers on these pages are illustrative. Your laptop, Docker settings and QuickPizza version all change them. What should match is the shape: which number moves, in which direction, and roughly by how much.

The exercises

Do them in order. Each one is 15 to 40 minutes and ends with questions and a hidden answer.

Foundations

  • 1. Your first smoke test15 min

    One user, five requests, checks that prove the response is real. Why 100% failures can still exit with code 0.

  • 2. Thresholds that fail the run20 min

    Pass/fail on p95 and error rate, exit code 99, and stopping early with abortOnFail. Inject errors and watch it fail.

  • 3. Ramp up and read the summary20 min

    Stages, percentiles vs the average, and checking the summary with Little's Law.

Realistic load

  • 4. Open vs closed workload model30 min

    Slow the server down and watch a fixed-user test quietly send less traffic, while an arrival-rate test keeps the pressure on.

  • 5. Test data and correlation30 min

    Users from a CSV file, one login per virtual user, and values captured from one response to use in the next.

  • 6. Find the knee40 min

    Step the arrival rate up on a CPU-limited container until latency bends. Your first capacity number.

Diagnosis

  • 7. Find the hidden slow dependency30 min

    A shell one-liner hides a delay in one internal service. Find it with tags, then confirm it with the server's own metrics.

  • 8. Watch it live in Grafana40 min

    Stream k6 metrics into Prometheus and Grafana with the free monitoring kit, and scrape QuickPizza's server-side metrics next to them.

  • 9. Compare two runs25 min

    Measure run-to-run noise first, then ship a "release" with a small regression and prove it is real.

  • 10. The same test in JMeterOptional · 30 min

    The pizza journey as a JMeter plan with an assertion and an extractor, run from the command line, and compared with k6.

Questions people ask

Can I do this without Docker?

Exercise 1 works against the public demo. For the rest you need your own QuickPizza. Without Docker you can build it from source (it is a Go app, see the repository's README), but Docker is far less effort.

Why does my laptop matter? Isn't the server the thing under test?

Here k6 and QuickPizza share one machine, so they compete for CPU. That is fine for learning, and Exercise 6 limits the container's CPU so the server saturates long before k6 does. In real work the load generator runs on separate machines and you watch its CPU too. A busy load generator makes the server look slower than it is.

I have done these. What next?

Write up Exercise 7 as if it were a real finding, using the results report template: the symptom, the evidence, the cause and the fix. Then work through finding bottlenecks and the rest of the learning path.
