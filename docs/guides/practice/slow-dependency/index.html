Exercise 7: find the hidden slow dependency

"Pizza is slow." That is the whole bug report. The pizza endpoint calls a catalog service and a copy service, several times each, and any of them could be the problem, or none of them. Guessing gets you a week of tuning the wrong thing. This exercise hides a delay somewhere in QuickPizza without telling you where, and you find it with evidence.

  • 30 minutes
  • 3 virtual users, 45 seconds
  • Run locally only

Goal

Break a slow user journey down into its parts with request tags, find the slow part, confirm it from the server side using QuickPizza's own Prometheus metrics, and then see how a small dependency failure rate turns into a large user-facing one.

Setup: hide the fault

This picks one of three delay switches at random and starts QuickPizza with it, without printing which. Don't peek.

SLOW=$(printf '%s\n' QUICKPIZZA_DELAY_COPY_API_NAMES QUICKPIZZA_DELAY_COPY_API_ADJECTIVES \
  QUICKPIZZA_DELAY_RECOMMENDATIONS_API_PIZZA_POST |
  awk 'BEGIN { srand() } { a[NR] = $0 } END { print a[int(rand() * NR) + 1] }')
docker run --rm --name quickpizza -p 3333:3333 -e "$SLOW=300ms" ghcr.io/grafana/quickpizza-local:latest

Better still, ask a friend to pick one and start the container for you.

The script

Save as 07-slow-dependency.js. Each iteration runs the user journey (create a pizza), then probes each dependency directly, one request each, every request tagged with a name:

// Exercise 7: the user journey plus a probe of each dependency, tagged by name,
// so you can see which part is slow. Run locally only.
// Optional fault injection on the journey: -e FAIL_PCT=10
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';
const FAIL_PCT = __ENV.FAIL_PCT || '';
const AUTH = { 'Content-Type': 'application/json', Authorization: 'token abcdef0123456789' };

const probes = ['names', 'adjectives', 'quotes', 'doughs', 'tools', 'ingredients'];
const paths = {
  names: '/api/names',
  adjectives: '/api/adjectives',
  quotes: '/api/quotes',
  doughs: '/api/doughs',
  tools: '/api/tools',
  ingredients: '/api/ingredients/tomato',
};

// k6 only prints per-tag numbers for metrics that have a threshold, so give each tag a loose one.
const thresholds = { 'http_req_duration{name:pizza}': ['p(95)<5000'] };
for (const p of probes) thresholds[`http_req_duration{name:${p}}`] = ['p(95)<5000'];

export const options = {
  vus: 3,
  duration: __ENV.DURATION || '45s',
  thresholds,
  summaryTrendStats: ['avg', 'med', 'p(95)', 'max'],
};

export default function () {
  const journeyHeaders = { ...AUTH };
  if (FAIL_PCT) {
    journeyHeaders['x-error-get-ingredients'] = 'practice-fault';
    journeyHeaders['x-error-get-ingredients-percentage'] = String(FAIL_PCT);
  }
  const res = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), {
    headers: journeyHeaders,
    tags: { name: 'pizza' },
  });
  check(res, { 'pizza status is 200': (r) => r.status === 200 });

  // Probe every dependency directly, one request each
  const batch = probes.map((p) => ['GET', `${BASE_URL}${paths[p]}`, null, { headers: AUTH, tags: { name: p } }]);
  http.batch(batch);

  sleep(1);
}

The loose thresholds are a k6 trick: k6 prints numbers for a tagged sub-metric only when a threshold refers to it. p(95)<5000 will never fail here. It is there to make the per-name rows appear.

Run it

k6 run 07-slow-dependency.js

Then ask the server. QuickPizza exposes Prometheus metrics at /metrics, including a request duration histogram labelled by route. This prints the average time per route since the container started:

curl -s http://localhost:3333/metrics | awk '
  /^quickpizza_server_http_request_duration_seconds_sum\{/   { k = $1; sub(/^[^{]*/, "", k); s[k] = $2 }
  /^quickpizza_server_http_request_duration_seconds_count\{/ { k = $1; sub(/^[^{]*/, "", k); c[k] = $2 }
  END { for (k in s) if (c[k] > 0) printf "%8.1f ms  %s\n", 1000 * s[k] / c[k], k }' | sort -rn

When you have an answer, check it:

docker inspect quickpizza --format '{{range .Config.Env}}{{println .}}{{end}}' | grep DELAY

What you should see

In the THRESHOLDS block, one row per name. One of the three patterns below, with illustrative numbers:

pizza p95names p95adjectives p95Everything else
≈ 400 ms≈ 330 ms≈ 30 ms≈ 30 ms
≈ 400 ms≈ 30 ms≈ 330 ms≈ 30 ms
≈ 400 ms≈ 30 ms≈ 30 ms≈ 30 ms

The server-side averages should tell the same story, with route patterns such as path="/api/names" and path="/api/ingredients/{type}". They include the calls QuickPizza makes to itself while building each pizza, not only your probes. Label names can change between QuickPizza versions, so if the awk prints nothing, look at the raw /metrics output.

Questions

  1. Which switch was it? Write the evidence in two sentences, as you would in a defect.
  2. In the third pattern, no dependency is slow, yet pizza is. What does that tell you, and what would you look at next on a real system?
  3. The direct probes and the server metrics are two kinds of evidence. Why is it worth having both?
  4. Restart QuickPizza without a delay and run k6 run -e FAIL_PCT=10 07-slow-dependency.js. Compare the pizza check's pass rate with http_req_failed. Why is the overall error rate so misleading here?
Answer / what to look for
  1. The slow probe names it. For example: "POST /api/pizza p95 rose from about 100 ms to about 400 ms. GET /api/adjectives on its own has p95 of about 330 ms against about 30 ms for every other dependency, and the server's own metrics show the same 300 ms extra on /api/adjectives, so the copy service's adjectives endpoint is the cause."
  2. The time is spent inside the pizza handler itself (here, the …_API_PIZZA_POST delay). On a real system, the next step is inside the service: a profiler, traces with spans around the handler's own work, thread dumps, or logs with timings. "Not a dependency" is a useful result, because it tells you where not to look.
  3. Direct probes show how a dependency performs on its own. Server metrics show how it performs for the real callers, under the real mix. They can differ: a dependency can be fast when called alone and slow when the main service calls it, because of connection pool limits, retries or timeouts on the caller's side. When both agree, you have a strong case.
  4. Roughly a third of pizzas fail (the fan-out from Exercise 2: four ingredient lookups, each failing 10% of the time). But http_req_failed shows only a few percent, because the six probes per iteration all succeed and dilute it. The probe requests outnumber the pizza requests six to one. Always look at errors per request name. A global error-rate threshold can pass while the one journey customers care about fails a third of the time.
