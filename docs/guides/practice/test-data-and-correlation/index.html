Exercise 5: test data and correlation

Your test logs in 500 virtual users as the same account, gets the same cached page 500 times and reports a beautiful p95. Production has 500 different customers, each with their own session, their own data and their own cache misses. A test only resembles real traffic once each virtual user is someone, and carries what the server gave it from one step to the next.

  • 30 minutes
  • 5 virtual users, 30 seconds
  • Run locally only

Goal

Read users from a CSV file, give each VU its own user, log in once per VU and reuse the token, and use a value from one response (the new pizza's id) in the next request. That last part is correlation: capturing dynamic values instead of hard-coding them.

Setup

docker run --rm --name quickpizza -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

Save this as users.csv next to the script. These are throwaway practice accounts: the script registers them on your local QuickPizza in setup().

The script

Save as 05-login-correlation.js:

// Exercise 5: test data from a CSV file, a login per virtual user, and correlation
// (the token and the pizza id come from earlier responses). Run locally only.
import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';
const JSON_HEADERS = { 'Content-Type': 'application/json' };

// Read users.csv once and share it between VUs (columns: username,password)
const users = new SharedArray('users', function () {
  const lines = open('./users.csv').trim().split(/\r?\n/).slice(1);
  return lines.map((line) => {
    const [username, password] = line.split(',');
    return { username, password };
  });
});

export const options = {
  vus: 5,
  duration: '30s',
  thresholds: {
    checks: ['rate>0.99'],
    http_req_failed: ['rate<0.01'],
  },
};

// Practice data only: a fresh QuickPizza container has no practice users, so register them.
// 201 = created, 400 = already exists from an earlier run. Both are fine here.
export function setup() {
  for (const u of users) {
    http.post(`${BASE_URL}/api/users`, JSON.stringify(u), {
      headers: JSON_HEADERS,
      tags: { name: 'setup-register' },
      responseCallback: http.expectedStatuses(201, 400),
    });
  }
}

// Module scope is per VU in k6, so each VU keeps its own token.
let token = '';

export default function () {
  // VU 1 uses row 1, VU 2 uses row 2, and so on (wrapping round if there are more VUs than rows)
  const user = users[(exec.vu.idInTest - 1) % users.length];

  if (!token) {
    const login = http.post(`${BASE_URL}/api/users/token/login`, JSON.stringify(user), {
      headers: JSON_HEADERS,
      tags: { name: 'login' },
    });
    const ok = check(login, {
      'login status is 200': (r) => r.status === 200,
      'login returned a token': (r) => r.status === 200 && typeof r.json('token') === 'string',
    });
    if (!ok) {
      sleep(1);
      return;
    }
    token = login.json('token'); // correlation 1: capture the token
  }

  const auth = { ...JSON_HEADERS, Authorization: `token ${token}` };

  const pizza = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), {
    headers: auth,
    tags: { name: 'pizza' },
  });
  if (!check(pizza, { 'pizza status is 200': (r) => r.status === 200 })) {
    sleep(1);
    return;
  }
  const pizzaId = pizza.json('pizza.id'); // correlation 2: capture the new pizza's id

  const rating = http.post(`${BASE_URL}/api/ratings`, JSON.stringify({ pizza_id: pizzaId, stars: 5 }), {
    headers: auth,
    tags: { name: 'rate' },
  });
  check(rating, { 'rating status is 201': (r) => r.status === 201 });

  sleep(1);
}

Three k6 details carry this script. SharedArray parses the file once and shares one read-only copy between VUs, instead of one copy per VU. Code at the top level of the file runs once per VU, so let token is a separate variable in every VU. And setup() runs once before any VU starts. Its responseCallback marks 400 as expected, so a second run (when the users already exist) doesn't count as errors.

Run it

k6 run 05-login-correlation.js

What you should see

    ✓ login status is 200
    ✓ login returned a token
    ✓ pizza status is 200
    ✓ rating status is 201

Both thresholds pass. Count the requests: 5 registrations in setup, 5 logins (one per VU, not one per iteration), and then pairs of pizza and rating requests. The exact count depends on how fast your machine is.

Questions

  1. Run the test with --http-debug=full for a few seconds (stop with Ctrl+C). Find the login response and the token in it. Now copy that token into the script as a fixed string, remove the login, restart QuickPizza and run again. What happens, and why?
  2. Change vus: 5 to vus: 8. Which users do VUs 6, 7 and 8 get? When would that be a problem in a real system?
  3. The script logs in once per VU. When would you log in on every iteration instead?
  4. Replace the captured pizzaId with a fixed 1. Does the rating request still succeed? What does that tell you about checking only status codes?
Answer / what to look for
  1. Every pizza and rating request fails with 401. Each new QuickPizza container starts with an empty in-memory database, so the practice users are created again with new random tokens. A recorded token is stale the moment the session behind it ends. That is the whole case for correlation: tokens, session ids, CSRF values and new record ids must come from the response, every run.
  2. VU 6 gets row 1 again, VU 7 row 2, VU 8 row 3, because of the modulo. Two VUs then share one account. In real systems that can mean one login invalidating the other's session, lock contention on the same records, or artificially warm caches. Have at least as many test users as VUs, or design the sharing on purpose.
  3. When the thing you are testing is the login itself (an identity provider, a session store), or when real users mostly arrive, log in, do one thing and leave. Logging in every iteration when real users stay logged in for an hour overloads the auth service and under-loads everything else.
  4. It succeeds, because QuickPizza ships with a seeded pizza whose id is 1. Every VU now writes ratings against one row. Real traffic never does that, and in a real database a hot row like this can create lock contention that exists only in your test. The checks stay green throughout. Status checks can't catch a correlation mistake that still produces valid requests. Reviewing the requests with --http-debug=full, and checking that captured values actually change between iterations, can.
