Exercise 6: find the knee

At 80 requests per second, p95 is 115 ms. At 100 it is 180 ms. At 130 it is over half a second, and at 160 the server can't keep up at all. Nothing broke and no errors appeared. You just walked past the knee of the curve. Every system has one, and knowing where yours is turns "it seemed fine" into a capacity number.

  • 40 minutes
  • Several 40-second steps
  • Run locally only, CPU-limited container

Goal

Run the same open-model test at increasing arrival rates, plot p95 against throughput, find where latency bends upward, and prove which resource ran out. This is the hockey stick from queueing theory, measured on a real server.

Setup

Limit QuickPizza to one CPU core. Without a limit, a Go app on a modern laptop can outrun the k6 process on the same machine, and you would find the knee of your load generator instead of the server.

docker run --rm --name quickpizza --cpus=1 -p 3333:3333 ghcr.io/grafana/quickpizza-local:latest

Close other heavy apps. You also need jq for the step script (brew install jq on macOS). On Windows, use WSL or Git Bash.

The scripts

Save as 06-knee.js. It runs one step: a fixed arrival rate for 40 seconds.

// Exercise 6: one step of a step-load test at a fixed arrival rate. Run locally only.
//   k6 run -e RATE=50 --summary-export=knee-50.json 06-knee.js
import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.BASE_URL || 'http://localhost:3333';
const RATE = Number(__ENV.RATE || 20);

export const options = {
  scenarios: {
    step: {
      executor: 'constant-arrival-rate',
      rate: RATE,
      timeUnit: '1s',
      duration: __ENV.DURATION || '40s',
      preAllocatedVUs: 20,
      maxVUs: 400,
    },
  },
  summaryTrendStats: ['avg', 'med', 'p(90)', 'p(95)', 'p(99)', 'max'],
};

const params = {
  headers: { 'Content-Type': 'application/json', Authorization: 'token abcdef0123456789' },
  tags: { name: 'pizza' },
};

export default function () {
  const res = http.post(`${BASE_URL}/api/pizza`, JSON.stringify({ maxNumberOfToppings: 5 }), params);
  check(res, { 'status is 200': (r) => r.status === 200 });
}

Save as knee.sh and make it executable (chmod +x knee.sh). It runs one step per rate and prints a line for each:

#!/usr/bin/env bash
# Runs 06-knee.js once per rate and prints one line per step. Needs k6 and jq.
set -u
RATES="${RATES:-10 20 40 60 80 100 130 160 200}"
printf '%-8s %-10s %-9s %-9s %-9s %s\n' rate achieved med_ms p95_ms p99_ms dropped
for r in $RATES; do
  k6 run -q -e RATE="$r" --summary-export="knee-$r.json" 06-knee.js > /dev/null 2>&1
  jq -r --arg r "$r" '[$r,
      (.metrics.http_reqs.rate | floor),
      (.metrics.http_req_duration.med | floor),
      (.metrics.http_req_duration["p(95)"] | floor),
      (.metrics.http_req_duration["p(99)"] | floor),
      (.metrics.dropped_iterations.count // 0)] | @tsv' "knee-$r.json" |
    awk -F'\t' '{ printf "%-8s %-10s %-9s %-9s %-9s %s\n", $1, $2, $3, $4, $5, $6 }'
done

Separate short runs are simpler to read than one long ramp: each step gets its own clean summary, and you can rerun a single step to check it.

Run it

./knee.sh

While a high step is running, look at the container in another terminal:

docker stats quickpizza --no-stream

If p95 hasn't bent by the last step, add higher rates (RATES="200 260 320" ./knee.sh) or restart the container with --cpus=0.5. Don't go past the point where k6 itself is using most of your CPU.

What you should see

A table shaped like this. The numbers are illustrative and depend heavily on your machine:

rate     achieved   med_ms    p95_ms    p99_ms    dropped
10       9          45        90        110       0
20       19         46        92        115       0
40       39         48        95        120       0
60       59         50        102       130       0
80       79         55        115       160       0
100      99         70        180       260       0
130      124        240       610       900       3
160      131        900       1700      2100      410

Three things happen together near the end. p95 climbs steeply, the achieved rate stops following the requested rate, and dropped appears because k6 runs out of VUs to start new iterations. docker stats shows the container's CPU close to 100% (one full core).

Questions

  1. Where is the knee in your table? Define it in a sentence you could put in a report.
  2. Why does latency rise before throughput stops growing?
  3. Use Little's Law on the last step: how many requests were in flight at once? Compare with the earlier steps.
  4. What evidence says the bottleneck is the server's CPU, and not k6, the network or a lock?
  5. If this were production, what request rate would you tell the team the service can handle?
Answer / what to look for
  1. The knee is the last rate before p95 starts rising much faster than load. In the example, p95 moves by 25 ms between 10 and 80 requests/s, then more than triples between 100 and 130. A report-ready version: "Up to 100 requests/s, p95 stays under 200 ms. Above that, p95 rises sharply and throughput tops out at about 130 requests/s, limited by CPU."
  2. Queueing. As the CPU gets busier, the chance that a new request arrives while the CPU is busy goes up, so requests wait. Waiting time grows roughly with utilisation ÷ (1 − utilisation): at 50% busy that factor is 1, at 80% it is 4, at 90% it is 9. Throughput still rises until utilisation hits 100%, but every request pays more in waiting along the way.
  3. In flight = throughput × time in the system. At 131 requests/s and about 1 s per request, that is roughly 130 requests in flight. At 40 requests/s and 0.05 s it was 2. Those requests are queueing inside the server.
  4. The container's CPU sits at its 1-core limit while the host still has spare CPU, there are no errors, and latency grows smoothly with load as queueing theory predicts. To rule out k6, check k6's own CPU in top or Activity Monitor and confirm it isn't saturated. To rule out the CPU limit as the only cause, raise --cpus to 2 and repeat: the knee should move to a higher rate. A lock or a pool limit would plateau with the CPU not busy.
  5. Not 130. Plan to run well below the knee, often at around 70% of it, so bursts and slow dependencies don't push you over. Here that is about 70 requests/s per core, with the condition stated: this hardware, this data volume, this mix of requests.
