1Executive summary

GO, after two fixes

Both must-fix issues, plus two smaller changes, were made by Northwind's developers in Week 2 and retested. The site now handles 2× the forecast Black Friday peak with all journeys inside their targets and an error rate of 0.04%.

97 req/sForecast peak (email-blast minute)
200 req/sProven in the retest (2.06× forecast)
1.4× → 2.4×Breaking point, before → after fixes
56 orders/minCheckout rate held at 2×, no failed orders

Three things the business needs to know

  1. Checkout would have failed at 1.4× the forecast. The checkout held a database connection open while waiting for the payment provider, so the connections ran out and orders failed (6.2% errors). Fixed: the order is saved before the payment call, and the pool was resized. Checkout now holds 2× with no errors.
  2. Search was slow even at normal peak. Filtering by size and colour took 1.9 s (p95) because a database index was missing. Fixed: 390 ms at forecast peak, 420 ms at 2×.
  3. A slow payment provider could slow the whole site. 30-second timeouts with 3 retries tied up the API, so browsing slowed too. Now the timeout is 10 s with one retry and a circuit breaker, and a slow provider only affects the payment step.

Also in place for the event: pre-scaling to 10 API containers from 6 pm on each peak day, because autoscaling was too slow for the email blast (finding 4), and a release freeze from 20 November. Remaining risks are listed in section 8.

3Workload model

The forecast comes from last year's analytics and this year's campaign plan, not a guess.

Last Black Friday, busiest hour 600 orders × growth since last year (+20%) × 1.20 × campaign uplift (bigger email list, first paid social campaign) × 1.17 = forecast busiest hour ≈ 840 orders ÷ conversion rate (analytics: 3%) = 28,000 shopper sessions in that hour ÷ 60 ≈ 467 sessions per minute (hour average) × email-blast burst (8 pm send, last year's busiest minute was 2× the hour) = 933 sessions per minute at peak

Shopper behaviour comes from last year's funnel: most visitors browse, few buy. Each journey makes a set number of requests to the site (pages and API calls that reach the servers; cached images and scripts are not counted).

Targets: forecast peak = 97 requests per second and 28 orders a minute. Headroom test = 2× forecast, about 194 requests per second (the retest ran slightly above, at 200). Testing at 2× covers a forecast that's wrong, a second email send, or a competitor's site going down.

How many virtual users that takes, with Little's Law (users = arrival rate × time each session lasts). Each request takes about 0.5 s and shoppers pause about 8 s between pages:

Browse 18.7 sessions/s × (5 × 8.5 s = 42.5 s) ≈ 793 users Search 7.8 sessions/s × (7 × 8.5 s = 59.5 s) ≈ 462 users Cart 3.7 sessions/s × (9 × 8.5 s = 76.5 s) ≈ 286 users Checkout 0.9 sessions/s × (14 × 8.5 s = 119 s) ≈ 111 users Total at 2× forecast ≈ 1,650 concurrent shoppers

The tests use an arrival rate (new shoppers per minute), not a fixed pool of users. Real shoppers keep arriving when the site slows down, so this is the honest way to test a sale.

7Bottlenecks and fixes

Ranked by risk to Black Friday sales. Each one was traced to a cause during the test runs, not guessed afterwards.

1. Checkout runs out of database connections at 1.4× Must fix Fixed and retested

What
From 140 req/s, 6.2% of checkout requests failed with "timed out waiting for a database connection".
Evidence
Connection pool wait time rose from 2 ms to 4.8 s; all 60 connections (10 per container × 6) were busy; database CPU was only 41%, so the database itself had room.
Cause
Checkout opened a database transaction, then called the payment provider inside it. Each order held a connection for the whole payment call (1.2 s at p95), so the pool emptied as orders rose.
Fix
Save the order as "pending" and commit, call the payment provider with no connection held, then update the order. Pool raised from 10 to 20 per container. At the 12-container maximum that's 240 connections, inside the database's limit of 300 with room for admin and background jobs.
Retest
At 2× forecast: pool wait p95 3 ms, at most 148 of 240 connections in use, no checkout errors. Breaking point moved from 1.4× to about 2.4×.

2. Search with filters is slow at normal peak Must fix Fixed and retested

What
Search p95 was 1.9 s at forecast peak against a 1 s target, and 3.4 s at p99.
Evidence
The database's slowest-queries view showed the size and colour filter query at 620 ms on average, 41% of all database time. Its query plan was a full scan of the 180,000-row variants table.
Cause
No index covering category, stock status and size, the three columns the filter uses together.
Fix
One composite index, added in a quiet window without locking the table. Query time 620 ms → 18 ms.
Retest
Search p95 390 ms at forecast, 420 ms at 2×. Database CPU at forecast peak dropped from 41% to 24%.

3. A slow payment provider can slow the whole site Should fix Fixed and retested

What
With 5 s of extra delay added to the payment stub, browse and search p95 rose to over 6 s, not just payment.
Evidence
API containers filled up with waiting payment calls; request queues grew on every endpoint.
Cause
Payment calls used a 30 s timeout with 3 automatic retries, so one slow minute at the provider tied up the API for much longer.
Fix
10 s timeout, one retry using the provider's idempotency key (so a customer is never charged twice), and a circuit breaker that pauses payment calls for 30 s if more than 20% fail. The shopper sees "Payment is busy, please try again in a moment" and keeps their cart.
Retest
Same 5 s delay: only the payment step slowed; browse and search stayed under 500 ms p95.

4. Autoscaling is too slow for the email blast Should fix Fixed and retested

What
In the spike test, 3.1% of requests failed for about 3 minutes.
Evidence
Containers went from 6 to 10, but scaling started only after CPU had been over 80% for 2 minutes, and new containers took about 2 minutes to start and pass health checks.
Cause
Reactive scaling can't keep up with a jump from 20% to 200% in one minute.
Fix
Scheduled pre-scale to 10 containers from 6 pm on each peak day (the email goes at 8 pm), and scale on requests per container instead of CPU.
Retest
Same spike: 0.06% errors; checkout p95 peaked at 1,350 ms in the first minute, then settled under 1 s.

8Recommendations and day-of-event runbook

Before the event

  1. Release freeze from 20 November until the Tuesday after Cyber Monday. Any change after the retest invalidates part of this result.
  2. Keep the pre-scale schedule for Black Friday, the Saturday and Cyber Monday (10 containers from 6 pm, back to normal after midnight).
  3. Agree a stagger with marketing: send the email in two halves, 15 minutes apart. It halves the spike for free.
  4. Check the CDN hit ratio stays above 90% for product and category pages after the sale prices go in (a price change can clear the cache).
  5. Tell the payment provider your expected peak (about 56 orders a minute at 2×) and ask about their rate limits.

Day-of checklist

  • 6 pm: pre-scale has run (10 containers), dashboard open, everyone on the call
  • Who to call is agreed: on-call developer, hosting support, payment provider support line, and the performance engineer watching the dashboard
  • Last known good release is tagged, and rolling back has been practised once in staging
  • Feature flags ready to switch off under load, in this order: product recommendations, live reviews widget, "recently viewed"
  • 8 pm email send confirmed with marketing (two halves, 15 minutes apart)
  • First 30 minutes after the send: check every metric above every 5 minutes
  • Next morning: short review of what happened against this report, kept for next year's test

Risks and limits of this test

  • Staging matched production size, but real shoppers on mobile networks will see slower pages than the test machines did.
  • The payment provider and the CDN were not load tested (they're run by third parties). The circuit breaker limits the damage if the provider slows down.
  • No queue or waiting room is set up. Above about 2.4× the site will slow down for everyone. If marketing expects more than 2× (for example a TV mention), set one up and test it.
  • The forecast relies on a 3% conversion rate. If last year's analytics under-counted sessions, peak traffic could be higher, which is why the test went to 2×.

9Appendix: k6 scenario and thresholds

The full scripts, test data generator and raw results are handed over in Northwind's repository, so the test can be run again before every peak. This is the load model:

import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE = __ENV.BASE_URL;                 // staging URL
const PEAK = Number(__ENV.PEAK || 2);         // 1 = forecast, 2 = headroom test

// New shopper sessions per minute at the forecast peak (section 3),
// and the virtual users needed at 2× (Little's Law).
export const options = {
  scenarios: {
    browse:   journey('browse',   560, 800),
    search:   journey('search',   233, 470),
    cart:     journey('cart',     112, 290),
    checkout: journey('checkout',  28, 120),
  },
  thresholds: {
    http_req_failed: ['rate<0.005'],
    'http_req_duration{scenario:browse}':   ['p(95)<800'],
    'http_req_duration{scenario:search}':   ['p(95)<1000'],
    'http_req_duration{scenario:cart}':     ['p(95)<800'],
    'http_req_duration{scenario:checkout}': ['p(95)<1500'],
  },
};

function journey(fn, perMinute, vus) {
  return {
    executor: 'ramping-arrival-rate',   // shoppers keep arriving when the site slows
    exec: fn,
    timeUnit: '1m',
    startRate: 0,
    preAllocatedVUs: vus,
    maxVUs: Math.ceil(vus * 1.5),
    stages: [
      { duration: '5m',  target: perMinute * PEAK },  // ramp up
      { duration: '45m', target: perMinute * PEAK },  // hold the peak
      { duration: '2m',  target: 0 },
    ],
  };
}

export function browse() {
  const pages = ['/', '/c/tents', '/p/alpine-2-tent', '/p/trail-pack-40', '/p/merino-tee'];
  for (const path of pages) {
    const res = http.get(`${BASE}${path}`, { tags: { name: path.split('/')[1] || 'home' } });
    check(res, { 'status is 200': (r) => r.status === 200 });
    sleep(8);                                   // think time between pages
  }
}

// search(), cart() and checkout() follow the same pattern, with test
// accounts, product IDs from a CSV and test cards for the payment stub.
export function search() { /* ... */ }
export function cart() { /* ... */ }
export function checkout() { /* ... */ }

Runs with k6 run -e BASE_URL=https://staging.example -e PEAK=2 peak.js. A failed threshold makes k6 exit with an error, so the same script can gate future releases in CI.
