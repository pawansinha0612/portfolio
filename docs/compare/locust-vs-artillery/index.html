Locust vs Artillery

Two light, free tools that suit developers. Locust tests are Python classes and you can steer a run from a web UI. Artillery tests are YAML with JavaScript hooks, built around arrival rates. Your team's language usually decides it.

Facts checked November 2026. Written by Pawan Sinha, who has used JMeter, LoadRunner, k6 and Gatling on banking, payments and lottery projects.

The short answer

Which one should you pick?

Pick Locust if…

  • Your team writes Python, or the system has a Python client library you want to reuse.
  • You want to change the number of users during a run from a web UI.
  • You need to test an unusual protocol and are happy to write a small Python client.
  • Your users behave like a fixed population (staff on an internal system), so a closed model fits.

Pick Artillery if…

  • Your team writes JavaScript or TypeScript and uses npm.
  • Most tests are simple flows that read well as YAML.
  • You want arrival-rate (open) load, which matches public web traffic, as the default.
  • You run on AWS and want the tool to spread a big test over Lambda or Fargate.

Same test, two tools

A 50-user load test in each

The same simple test in both: load the home page, check for a 200 response, ramp up to 50 users over a minute, then hold for three minutes with one second of think time.

Locust (Python)

from locust import HttpUser, task, constant

class Visitor(HttpUser):
    host = "https://test.example.com"
    wait_time = constant(1)  # think time

    @task
    def home(self):
        with self.client.get("/", catch_response=True) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")

# Ramp to 50 users (1 new user a second), run for 4 minutes, no web UI:
#   locust -f locustfile.py --headless -u 50 -r 1 -t 4m

The ramp is set on the command line here. For staged ramps written in code, subclass LoadTestShape. Failing the run on a response-time goal takes a few lines of Python in an event hook.

Artillery (YAML)

config:
  target: "https://test.example.com"
  phases:
    - name: Ramp up
      duration: 60
      arrivalRate: 1
      rampTo: 50     # new visitors per second
    - name: Hold
      duration: 180
      arrivalRate: 50
  plugins:
    expect: {}
    ensure: {}
  ensure:
    thresholds:
      - http.response_time.p95: 500  # fail the run if p95 > 500 ms

scenarios:
  - name: Home page
    flow:
      - get:
          url: "/"
          expect:
            - statusCode: 200
      - think: 1     # think time, in seconds

Run it with artillery run test.yml. Artillery uses an open model: arrivalRate is new virtual users per second, and each one runs the flow once and leaves. A visit here lasts about a second, so 50 arrivals a second keeps roughly 50 users busy (Little's Law). A failed ensure check gives a non-zero exit code, so CI fails too.

Switching

Moving between Locust and Artillery

  1. Translate the load model, not just the requests. Locust users are a closed population. Artillery phases are arrival rates. Use Little's Law: arrivals per second × seconds per visit ≈ concurrent users.
  2. A Locust @task maps to an Artillery scenario. Task weights map to scenario weight. wait_time maps to think.
  3. Python helper code becomes JavaScript processor functions.
  4. Compare one run in each tool at the same load before you switch.

FAQ

Common questions

Is Locust or Artillery easier?

Whichever matches your language. Python teams usually find Locust easier. JavaScript teams usually find Artillery easier, and simple flows in YAML need very little code at all.

Are both free?

Yes. Locust is MIT and Artillery is MPL-2.0. Artillery Cloud, a hosted dashboard, is a separate product. Check its current pricing.

Which handles more load per machine?

Both are interpreted, so neither is the most efficient per request. Locust needs one worker process per CPU core. Artillery can push the load out to AWS. Watch the load generator's CPU whichever you use.
