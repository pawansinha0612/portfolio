Performance testing glossary

The words that come up in load tests, capacity plans and incident reviews, each explained in plain English with a worked example, how to measure it and the mistakes people make.

A

  • ApdexApdex is a score from 0 to 1 that rates user satisfaction with response times, counting requests as satisfied (at or under a target T), tolerating (up to 4T) or frustrated (over 4T).Metrics and SLOs
  • APM (application performance monitoring)APM is tooling that measures how an application performs from the inside, recording response times, errors, throughput and traces for each transaction, often down to individual database queries and external calls.Observability
  • Arrival rateArrival rate is the number of new requests or user journeys that start per unit of time, such as 50 checkouts a second, regardless of how long each one takes to finish.Test design
  • AutoscalingAutoscaling automatically adds or removes servers, containers or pods based on measures such as CPU use, request rate or queue length, so capacity follows demand.System behaviour

B

  • Back-pressureBack-pressure is a way for a busy component to tell the components sending it work to slow down, such as by rejecting requests, limiting a queue or blocking the sender, instead of accepting more than it can process.System behaviour
  • BaselineA performance baseline is a recorded set of results from a known version under a known load, used as the reference point that later tests are compared against.Test design
  • BenchmarkA benchmark is a standard, repeatable test that measures the performance of a system, component or configuration so it can be compared fairly with alternatives.Test design
  • BottleneckA bottleneck is the single resource or component that limits a system's throughput, so improving anything else makes little difference until it is fixed.System behaviour
  • Breakpoint testingBreakpoint testing increases load steadily until the system can no longer meet its targets, to find the maximum throughput it can sustain.Test design
  • Burn rateBurn rate is how fast a service is using its error budget compared with the steady rate that would use it up exactly at the end of the SLO window, so a burn rate of 1 is on track and 10 is ten times too fast.Metrics and SLOs

C

  • Cache stampedeA cache stampede happens when a popular cached item expires and many requests miss the cache at the same moment, all asking the database or backend to rebuild the same value at once.System behaviour
  • Capacity testingCapacity testing finds how many users or transactions a system can serve while still meeting its targets, so you can plan infrastructure for future growth or a known event.Test design
  • CDN hit ratioCDN hit ratio is the share of requests a content delivery network answers from its own cache instead of passing them to your origin servers.System behaviour
  • Chaos engineeringChaos engineering is the practice of deliberately injecting failures, such as killing servers, adding network delay or cutting off a dependency, in controlled experiments to check that a system keeps working.Test design
  • Checks and assertionsChecks and assertions verify that each response in a load test is correct, for example the status is 200 and the body contains the order number, instead of only measuring how fast it came back.Test design
  • Circuit breakerA circuit breaker stops calls to a failing dependency after errors or timeouts pass a limit, fails fast for a set time, then lets a few trial calls through to see whether the dependency has recovered.System behaviour
  • CLS (Cumulative Layout Shift)CLS is a Core Web Vital that measures how much visible content unexpectedly moves while a page is in use, with a score of 0.1 or less at the 75th percentile counted as good.Metrics and SLOs
  • Connection poolA connection pool is a set of open, reusable connections to a database or other service that an application shares between requests, instead of opening a new connection each time.System behaviour
  • Coordinated omissionCoordinated omission is a measurement error where a load tool waits for slow responses before sending the next request, so it sends fewer requests during a stall and under-reports how slow the system really was.Metrics and SLOs
  • Core Web VitalsCore Web Vitals are Google's three key measures of real-world page experience: LCP for loading, INP for responsiveness and CLS for visual stability, each judged at the 75th percentile of visits.Metrics and SLOs
  • CorrelationCorrelation is capturing a dynamic value from one server response, such as a session ID, CSRF token or order number, and sending it in later requests so the script behaves like a real session.Test design

D

  • Database deadlockA database deadlock happens when two or more transactions each hold a lock the other needs, so neither can continue, and the database has to cancel one of them to break the cycle.System behaviour
  • Distributed tracingDistributed tracing follows a single request as it passes through multiple services, recording how long each step (a span) takes so you can see where the time went.Observability

E

  • Error budgetAn error budget is the amount of unreliability an SLO allows over its window, equal to 100% minus the SLO target, such as 0.1% of requests or about 43 minutes a month for 99.9%.Metrics and SLOs
  • Error rateError rate is the share of requests or transactions that fail, such as returning an HTTP 5xx status, timing out or returning the wrong content, out of all requests in a time window.Metrics and SLOs

F

  • Fan-out amplificationFan-out amplification is the effect where a request that calls many backend services in parallel is only as fast as the slowest of them, so rare slow responses become common for the overall request.Metrics and SLOs
  • Flame graphA flame graph is a picture of profiling data where each box is a function, stacked by who called whom, and the width of each box shows how much of the sampled time was spent in that function and the functions it called.Observability

G

  • Garbage collection pauseA garbage collection pause is a period when a managed runtime such as the JVM, .NET or Go stops or slows application threads to reclaim unused memory, adding delay to the requests in progress.System behaviour

H

  • HeadroomHeadroom is the spare capacity between expected peak load and the most a system can handle while still meeting its targets, often expressed as a percentage or multiple of the peak.System behaviour
  • Horizontal vs vertical scalingHorizontal scaling adds more machines or instances to share the load, while vertical scaling makes one machine bigger with more CPU, memory or faster storage.System behaviour
  • HTTP 429 Too Many RequestsHTTP 429 Too Many Requests is the status code a server returns when a client has sent more requests than its rate limit allows, often with a Retry-After header saying how long to wait.System behaviour

I

  • INP (Interaction to Next Paint)INP is a Core Web Vital that measures how quickly a page responds visually to clicks, taps and key presses across the whole visit, with 200 milliseconds or less at the 75th percentile counted as good.Metrics and SLOs
  • Inter-token latency (TPOT)Inter-token latency, also called TPOT (time per output token), is the average time between tokens after the first one while a language model streams its answer.Metrics and SLOs

L

  • Latency vs response timeResponse time is the full time a user waits for a request, from sending it to receiving the full answer, while latency usually means the delay before the response starts, such as network travel or time spent waiting in a queue.Metrics and SLOs
  • LCP (Largest Contentful Paint)LCP is a Core Web Vital that measures how long it takes for the largest image or block of text in the viewport to appear, with 2.5 seconds or less at the 75th percentile counted as good.Metrics and SLOs
  • Little's LawLittle's Law says that the average number of items in a stable system equals their average arrival rate multiplied by the average time each one spends in the system, written L = λ × W.Metrics and SLOs
  • Load testingLoad testing checks how a system behaves under the traffic you expect at peak, to prove it meets its response time and error targets before real users arrive.Test design
  • Lock contentionLock contention happens when many threads or transactions wait for the same lock, such as a database row, a table or a synchronised block in code, so they queue instead of working in parallel.System behaviour

M

  • Memory leakA memory leak is when an application keeps holding memory it no longer needs, so memory use grows over time until the application slows down from constant garbage collection or runs out and crashes.System behaviour

N

  • N+1 queryThe N+1 query problem is when code runs one query to fetch a list and then one more query for each item in it, so showing 50 items takes 51 database round trips instead of one or two.System behaviour

O

  • ObservabilityObservability is how well you can understand what is happening inside a system from what it outputs, usually its metrics, logs and traces, including problems nobody predicted in advance.Observability
  • Open vs closed workload modelA closed workload model has a fixed number of users who each wait for a response before the next request, while an open model sends new requests at a set rate whether earlier ones have finished or not.Test design

P

  • PacingPacing controls how often each virtual user starts a new iteration, so each user runs at a fixed rate whatever the response time, for example one iteration every 30 seconds.Test design
  • ParameterisationParameterisation replaces fixed values in a load test script, such as usernames, search terms and product IDs, with values drawn from a data file or generated at run time, so each virtual user acts like a different person.Test design
  • Percentiles (p95, p99)A percentile is the value below which a given share of measurements fall, so p95 is the response time that 95% of requests were faster than and 5% were slower than.Metrics and SLOs
  • Performance budgetA performance budget is an agreed limit on a measure such as page weight, number of requests, LCP or API response time that a team commits not to exceed when adding features.Test design
  • Prompt cachingPrompt caching is a feature of many LLM providers and model servers that reuses work already done for the start of a prompt that repeats, such as a long system prompt, so repeated input tokens cost less and the first token arrives sooner.System behaviour

R

  • Ramp-upRamp-up is the period at the start of a load test where load increases gradually from zero to the target level instead of arriving all at once.Test design
  • Rate limitingRate limiting caps how many requests a client, user or key can make in a period of time, such as 100 requests a minute, and rejects or delays anything above the cap.System behaviour
  • RED methodThe RED method is a way to monitor request-driven services by tracking three things for each one: Rate (requests per second), Errors (failed requests) and Duration (how long requests take, as a distribution).Observability
  • Retry stormA retry storm happens when many clients or layers retry failed requests at the same time, multiplying the load on a service that is already struggling and stopping it from recovering.System behaviour
  • RUM (real user monitoring)Real user monitoring collects performance data from actual visitors' browsers or apps, such as page load times and Core Web Vitals, so you see what people on real devices and networks experience.Observability

S

  • SaturationSaturation is the point where a resource has more work than it can handle, so extra work has to wait in a queue, which shows up as rising response times while throughput stops increasing.System behaviour
  • Scalability testingScalability testing measures how throughput and response time change as you add resources such as pods, servers or database replicas, to show whether the system actually scales.Test design
  • Shift-left performance testingShift-left performance testing means testing performance early and often, in development and in the CI pipeline, instead of only in a big load test just before go-live.Test design
  • SLA (service level agreement)An SLA is a contract with customers that promises a level of service, such as 99.9% monthly availability, and sets out what happens, usually service credits or refunds, if it is missed.Metrics and SLOs
  • SLI (service level indicator)An SLI is a measured number that shows how well a service is doing for its users, usually a ratio of good events to total events, such as the share of requests served successfully in under 300 ms.Metrics and SLOs
  • SLO (service level objective)An SLO is a target for an SLI over a time window, such as "99.9% of checkout requests succeed in under 800 ms over 30 days", that a team agrees to meet.Metrics and SLOs
  • Smoke testingA performance smoke test runs a tiny load, often one or two virtual users for a minute, to prove the script, the environment and the monitoring work before a real test starts.Test design
  • Soak testingSoak testing runs a realistic load for many hours to find problems that only appear over time, such as memory leaks, connection leaks, growing queues and full disks.Test design
  • Spike testingSpike testing hits a system with a sudden, sharp jump in traffic to see whether it survives the burst and how quickly it scales and recovers.Test design
  • Steady stateSteady state is the part of a load test where the load is held constant and the system's response times, throughput and resource use have settled, which is the window you report on.Test design
  • Stress testingStress testing pushes a system beyond its expected peak to find where it breaks, how it fails and whether it recovers once the load drops.Test design
  • Synthetic monitoringSynthetic monitoring runs scripted checks against a site or API on a schedule from known locations, such as loading the home page or completing a test login every 5 minutes, to catch problems before users report them.Observability

T

  • Tail latencyTail latency is the response time of the slowest requests, usually measured at p99, p99.9 or the maximum, which is often far slower than the median.Metrics and SLOs
  • Think timeThink time is the pause a load test script inserts between steps to copy the time a real person spends reading, typing or deciding before their next action.Test design
  • Thread poolA thread pool is a fixed set of worker threads that an application server uses to handle requests or tasks, where new work waits in a queue when every thread is busy.System behaviour
  • ThresholdsThresholds are pass or fail rules in a load test, such as "p95 under 500 ms" or "error rate under 1%", that the tool checks automatically so the result is a clear yes or no.Test design
  • ThroughputThroughput is the amount of work a system completes per unit of time, such as requests per second, orders per minute or messages per second.Metrics and SLOs
  • Thundering herdA thundering herd is a burst of requests from many clients that all wake up or retry at the same moment, such as after an outage ends, a cache is cleared or a scheduled job fires on the hour.System behaviour
  • Tokens per secondTokens per second is how fast a language model produces output, measured either for one request while it streams or as total output tokens across all requests on a server or account.Metrics and SLOs
  • TPM and RPM limitsTPM (tokens per minute) and RPM (requests per minute) are the rate limits AI providers put on an API key, project or deployment, and going over either one gets requests rejected with a 429 error.System behaviour
  • TPS and RPSTPS (transactions per second) and RPS (requests per second) are rates of throughput, where a request is one HTTP call and a transaction is a business action that may need several requests.Metrics and SLOs
  • TTFB (time to first byte)TTFB is the time from a browser or client starting a request until the first byte of the response arrives, covering redirects, DNS, connection set-up, TLS and the server's time to start replying.Metrics and SLOs
  • TTFT (time to first token)TTFT (time to first token) is the time from sending a prompt to a language model until the first word or token of the answer arrives.Metrics and SLOs

U

  • USE methodThe USE method, from Brendan Gregg, is a checklist for finding resource bottlenecks by checking Utilisation, Saturation and Errors for every resource, such as CPU, memory, disk, network and connection pools.Observability
  • Utilisation lawThe utilisation law says that a resource's utilisation equals its throughput multiplied by the service time each request needs from it, written U = X × S.System behaviour

V

  • Virtual userA virtual user is one simulated client in a load test that runs a script in a loop, sending requests the way a real user or device would.Test design
  • Volume testingVolume testing checks how a system performs when it holds or processes a large amount of data, such as a full-size database, a big batch file or a long order history.Test design

W

  • Warm-upWarm-up is a short period of light load before measurement starts, so that caches fill, code is compiled and connection pools open, as they would be in a running production system.Test design
  • Workload modelA workload model describes what a realistic load looks like: which user journeys run, in what proportions, at what rates, with what think times and data, usually taken from production logs or analytics.Test design
